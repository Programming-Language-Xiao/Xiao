## 三、必须先冻结的 5 条

### 3.1 两条待定项（**已定，本批开局清账**）

| 待定项 | 出处 | **冻结为** |
| --- | --- | --- |
| 自动登记的包发生**根名称冲突**时如何消歧 | `00-decisions:676` | **报错，要求显式 `import`** |
| 延迟加载**首次失败后的缓存与重试** | `00-decisions:682` | **不缓存失败，每次引用都重试** |

**理由**：

- **根名冲突报错**：与 `12-tests:864` 的「**不依赖包扫描顺序选择胜者**」直接一致。
  扫描顺序本质是文件系统顺序，拿它当语义**不可重现**；且本仓一贯「不猜」——
  冲突时宁可不登记该根名，让用户写 `import` 明确指定；
- **失败不缓存**：REPL 是**交互式**的——用户可能刚在外部修了包或改了环境，
  缓存失败会让会话变成死局；且 `12-tests:865` 要求「失败后会话仍可继续使用」。
  **代价是重复失败会重复付出加载开销**，这是可接受的。

`12-tests` 当前已写成「由 I4 冻结为」，本批将 `00-decisions` 的待定项移入已冻结段，
同时把首次失败不缓存、再次引用重试的结果写进退出条件，保持两处一致。

**⚠️ 处理方式照 I1b/I2 的先例**：结论写进 `00-decisions` 的「终端交互式解释器」**已冻结段**，
**并把两条从待定段删除**。

### 3.2 接口形状：**查询不执行，加载在 `run` 内部**

`11b:71` 与 `12-tests:863` 划的边界是：

- **启动、提示符渲染、名称枚举、只读接口查询——都不执行包模块**；
- **只有首次真正引用包内容时**才调用运行时加载接口。

**冻结为两个动作，不是一个**：

1. **环境包视图查询**（新请求）：给定环境，返回**可解析的包根名称**
   与**可选的无副作用接口元数据**（导出名与签名）。**纯读取，绝不求值**；
2. **运行时加载**：**不是新请求，而是 `run` 内部的行为**——
   源码首次引用某包内容时，由 VM 侧加载并初始化该模块。
   **不得**让 CLI 先调一个"加载"请求再调 `run`（那会把加载时机暴露给 CLI，
   与「首次真正引用时才加载」的语义不符，也无法保证"至多初始化一次"）。

**⚠️ 这条是本批的核心设计判断**：**加载的触发点在 VM 内部，不在协议层**。
协议层只提供**元数据查询**这一个新读取入口。

**⚠️ "同一具体模块在至多初始化一次"落在哪一侧**：`11b:71` 说的是
「一个 REPL **运行实例**」——那**必须由承载模块状态的 VM 会话保证**（§3.5），
**不能靠 CLI 在协议层记缓存**（CLI 记的缓存跨不过进程，也管不到初始化语义）。

### 3.3 命名：**不要复用已有的 `package` 能力**

协议里**已经有**一个叫 `package` 的能力，**它是包管理的**：
`PackageRequest.operation` 是 `"sync" | "install" | "lock" | "update" | "add" | "remove"`
（`messages.ts:154`），Rust 侧对应 `service.rs:314` 的 `package_request_response`，
处理的是 `config.xiao`、锁文件、本地/远程安装。

**⚠️ 它与本批的「环境包视图」语义完全不同**，只是名字相近。

**冻结**：

- **新请求必须用可区分的名字**（如 `repl_packages` / `package_view` 一类），
  **不得**扩展现有 `PackageRequest` 的 `operation` 枚举来塞进去；
- **能力协商同理**：`hello` 的 `capabilities` 里已有的 `"package"` 表示**包管理能力**，
  **新能力要用新字符串**，否则旧客户端会把「支持包管理」误读成「支持 REPL 包视图」；
- **⚠️ 这条要写进协议 UseDoc**，因为两个 `package` 并存是后期最容易混淆的地方。

### 3.4 能力协商与协议版本

- **新能力走既有的 `hello` 协商**（`message.rs:252` 的 `capabilities`），
  **不新开握手**；
- **旧核心不报该能力时**，CLI 侧**降级为"无包视图"**——
  `11b:71` 已明确「该能力依赖第 11A 阶段的环境包视图，**不阻塞无第三方包的 REPL 核心闭环**」；
- **⚠️ 协议版本号是否要升**由现有约定决定（`request.rs` 里有 `protocol_version`）。
  **若升版本，`validate.rs` 的拒绝规则与 `tests/spec/11x0-protocol/` 的向量要同步**；
- **⚠️ 不得**让新字段成为必填而打断旧客户端——照 `peak_live_bytes` 的先例
  （`protocol.md:66`：「客户端不得因缺失该字段而崩溃」）。

### 3.5 **待查明**：模块状态与 run 的会话语义

**⚠️ 这是本批唯一一个"先查清再动手"的前置，不要跳过。**

R6 第 5 条要求「**复用第 05 阶段的模块状态**，保证同一具体模块在一个 REPL
运行实例中至多初始化一次」，但实测（§现状盘点）**在 `xiao-driver` 侧看不到
会话结构或模块缓存**：`run.rs` 的入口是 `pub fn run(request: &DriverRequest) -> DriverOutcome`，
**看不出 `run` 之间是否共享 VM 或模块状态**。

**本批必须先回答**：

1. **同一个核心进程内连续两次 `run`，模块状态是否保持？** 如果不保持，
   「至多初始化一次」就**没有落脚点**；
2. **如果不保持**，是**在本批补**（让 `run` 复用会话级 VM 与模块表），
   还是**登记为 I4b 的前置**？——**判断依据是它属于协议层还是会话层**：
   若只是"同一进程内复用 VM"，属本批；若需要"CLI 保持一个长驻进程"，
   **进程生命周期归 I4b**（§2.3），本批只保证**同一进程内**的语义正确；
3. **接口元数据查询**要复用 05 阶段的哪一层（模块图？导出表？），
   **不要另建一套符号表**——那是本仓头号病史。

**⚠️ 查清后要把结论写进文档**，无论结论是"本批能做"还是"归 I4b"。
**不要让"至多初始化一次"在没有落脚点的情况下被写成已完成。**

**调查结论**：`xiao-driver::run` 每次构建新的 `FrontendVmDriver`，
`xiao-vm::run_request` 每次创建新的 `Vm`；`serve` 将运行请求派给独立工作线程。
即使连续向同一个核心进程发送两次 `run`，也不会共享 VM、模块表或已初始化状态。
更早的 05-B 模块层只保留静态 `ProjectModuleResult`（模块图、符号接口和初始化顺序），
不是运行时缓存；I4a 调查时 09 字节码的 `Import` 尚不会生成执行指令。
因此“同一进程内两次独立 run 至多初始化一次”目前**不成立**，不能用协议级缓存冒充。
建立长驻 VM 和跨请求状态是 I4b 的会话前置；单次 VM 内的加载与去重由 I4a2 实现，
接口查询应复用 05-B 的 `ModuleRecord.symbols` 而非另外构建符号表。

**I4a 阶段落地进度**：已实现独立 `repl_packages` 能力、环境隔离、冲突诊断、只读
`ModuleRecord.symbols` 与类型签名查询，并验证不会执行顶层抛错探针；已同步 TS 协议类型、
旧核心空视图降级、双语向量与 UseDoc。当时的视图响应不足以证明运行时加载；
**后续 I4a2** 已补静态命名空间、导入执行和 VM 按需加载，并用独立探针验证首次引用、
失败重试与单次运行初始化一次。跨请求 VM 状态仍归 I4b；全仓测试尚有独立的配置
快照基线失败，I4a/I4a2 的 `module-registry` 条目暂保持 `draft`。

## 九、验收

1. **环境视图**：按激活状态只返回全局或该虚拟环境的包根名，**两个视图不交叉泄漏**（`:863`）。
2. **不执行**：启动、枚举、元数据查询、只读接口查询**都不执行包初始化代码**——
   **有副作用探针**（`12-tests:784` 的既有做法）证据（`:864`）。
3. **首次引用才加载**：未引用时无加载；引用后才加载（`:864`）。
4. **至多初始化一次**：同一进程内重复引用只初始化一次；
   **若 §3.5 判定归 I4b，则本批明确记录该结论与理由**，不得写成已验证（`:871`）。
5. **失败重试**：首次加载失败**不缓存**，再次引用会重试；失败诊断含**包名、来源环境、底层原因**（`:871`、`:865`）。
6. **根名冲突**：冲突时**报错并要求显式 `import`**，**不依赖扫描顺序**（`:865`、§3.1）。
7. **兼容**：旧核心不报新能力时 CLI 降级为无包视图，不崩（§3.4）。
8. **协议向量与 UseDoc 同步**，且**两个 `package` 的区别写清楚了**（§3.3）。
9. **门禁全绿**，含 `cargo test`。
