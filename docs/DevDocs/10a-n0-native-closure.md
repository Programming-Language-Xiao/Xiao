## 一、四条已定决策（2026-09-21）

### 1.1 决策一：**手写 LLVM IR 文本 + 外部 `clang`/`llc`**

不引入 `inkwell` / `llvm-sys`，不要求安装 LLVM 开发库。后端生成 `.ll` 文本，
由外部工具链编译成目标文件并链接。

**选它的理由（按强度排序）**：

1. **零重量级依赖**：Windows 与 Docker 都只需要工具链可执行文件。`inkwell` 要求
   安装 LLVM 开发库，并把 LLVM 版本变成编译期硬绑定——在本仓「Windows 原生为主 +
   容器做 Linux 验证」的双环境下，那是每台机器都要复现一次的麻烦。
2. **与本仓既有传统一致**：`xiao-bytecode/src/encode/codec.rs` 就是手写的字节级编解码器，
   它经过了 09R 全程的验证并被冻结。手写文本生成在这套工程文化里不是异类。
3. **可测试性更好**：IR 文本可直接 diff、可落快照、可进区分度验证；`llvm-as` 能独立
   验证语法，不必先跑通整条后端。

**必须承接的代价**：文本拼接容易构造出**语法合法但语义错误**的 IR。防守是两条腿——
`llvm-as` 的语法验证，加上第三节的**字节码差分**（同一 IR 两种执行，结果必须一致）。
**字节码差分是这条决策的安全网，不是可选项。**

### 1.2 决策二：**四批交付**

| 批次 | 范围 | 依据 |
| --- | --- | --- |
| **N0-A** | 纯静态标量闭环：标量类型映射、控制流、函数调用、溢出检查、入口。**零 Runtime 依赖** | `10:78`「纯静态标量程序**不会**因为动态运行时能力而完整装载 Runtime」 |
| **N0-B** | Runtime ABI：动态值、引用计数、`Weak`、容器、表、释放计划 | `10:47-49` 的二级任务 2、3 |
| **N0-C** | 错误路径与源码映射：统一错误路径、`try`/`catch`/`finally`、诊断事件、**字节码差分** | `10:60`、`10:71`、`12-tests:687` |
| **N0-D** | 产物验证与裁剪：三目标固定宽度、Runtime 裁剪验证、调试构建标志 | `10:54-57`、`10:78-80` |

**A 的边界不是随手切的**：`10:78` 把「纯静态标量程序不装载完整 Runtime」写成验收标准，
说明"零 Runtime 依赖的程序"是这套设计里一个**天然存在的档位**，而不是人为缩小范围。

### 1.3 决策三：**新增 `xiao-runtime-abi` crate**

`10:15` 要求「原生程序所链接的 Xiao Runtime 组件也以 Rust 实现，**并通过稳定 ABI 供 LLVM
生成代码调用**」，而 `10:63` 又禁止「把 Rust 内部类型布局直接暴露为 Xiao 语言契约」。

**两条合起来只有一个解**：必须有一层**独立于 `xiao-runtime` 的 C ABI**。

- **落点**：新 crate `xiao-runtime-abi`；
- **位置**：依赖图中在 `xiao-runtime` **之上**、`xiao-codegen-llvm` 与字节码路径之**下**
  （字节码路径将来也需要同一套 ABI，所以它不能属于 `xiao-codegen-llvm`）；
- **理由**：ABI 的版本与兼容规则要有**单一位置**。塞进 `xiao-runtime` 会让"实现"与
  "对外契约"同 crate，`10:63` 那条约束更难守。

**开工前先核对 `00a-project-layout.md:44-63` 的依赖图**，确认新 crate 的落点不引入环，
并同步登记（`docs/module-registry.json`）。

### 1.4 决策四：**诊断窗口归 X0**

N0 只交付**事件接口与启动入口**；诊断进程、管道协议、GUI 子系统交互归 X0
（`12-tests:700` 的 X0 退出条件第 8 条才验收窗口）。

与 B0 的口径一致——B0 也只交了事件接收器，窗口留给 X0。

## 三、N0-A：纯静态标量闭环

### 3.1 范围

**交付**：

1. **LLVM 类型映射**（`10:47` 的一半）：`int`/`float` 固定 64 位、`sint`/`sfloat` 固定
   32 位（`10:27`）、`bool`、函数签名与返回值；
2. **控制流降低**：分支、循环、函数调用与返回，映射为 LLVM 基本块（`10:49`）；
3. **溢出检查**（`10:31`）：每个可能溢出的算术操作使用带检查的实现，
   LLVM 的 `llvm.*.with.overflow` 内在函数是现成手段；
4. **入口**：脚本模式与 `[main]` 工程模式，与 B0 保持**同一口径**（见 §3.4）；
5. **IR 文本生成 + 外部工具链驱动**：生成 `.ll`、调 `llvm-as` / `clang` 验证并编译链接；
6. **内部构建驱动器**（`12-tests:683`）——不是 CLI。

**不交付**：动态值、引用计数、`Weak`、容器、表、释放计划、错误路径、诊断事件。
这些分别属于 N0-B 与 N0-C。

### 3.2 溢出失败边：**本批必须明确裁定的第一处**

`10:31` 要求「溢出时**进入统一语言错误路径**」，但**统一错误路径属于 N0-C**。
这是一个真实的跨批依赖，不能含糊过去。

三条路，选一条并在本批交接记录里写明依据：

- **A**：N0-A 的溢出走**最小失败边**（例如 `llvm.trap` 或返回约定的非零），
  并记为具名债项，出口批次 N0-C。**要说清这个最小边与最终错误路径的差异**；
- **B**：把统一错误路径的最小内核提前到 N0-A，代价是 A 的范围变大、不再"零 Runtime 依赖"；
- **C**：证明 N0-A 可以在**不含溢出场景**的测试集下交付，并写明"这会让 `10:31` 在 A
  阶段无法验收"。

**不允许**：让目标平台静默回绕（`10:31` 明文禁止），或把溢出检查整条推给后续批次而不记账。

### 3.3 `str` 归 A 还是 B：**必须裁定的第二处**

`str` 在 `RuntimeValue` 里是标量（与 `Int`/`Float`/`Bool` 并列），但它是**变长**的，
需要分配与生命周期管理。而"零 Runtime 依赖"是 A 的定义。

**给出明确结论**：`str` 在 N0-A 是
（a）只支持字面量常量并放进只读区（`10:41` 的常量嵌入），还是
（b）完全推迟到 N0-B？

**判据要写出来**，并且要与 `10:78`「纯静态标量程序不会因为动态运行时能力而完整装载
Runtime」保持一致——若支持 `str` 字面量会导致链接 Runtime，那 A 就不再是零依赖。

### 3.4 入口口径：与 B0 保持一致

B0 已冻结：脚本模式与 `[main]` 工程模式**共用同一个入口**，降低器固定入口函数 0
（`09-B0-B` 的 `script_and_project_share_entry_zero`）。

**N0-A 不得发明第二条入口路径。** 两种模式在原生侧的差别应当只在**诊断跨度**
（`IrEntryMode::Project { span }`），与 B0-D 的处理一致。

### 3.5 输出：需要一个最小可观察面

一个"能跑通"的程序至少要能被观察到输出。**不要**为此引入完整的 builtin 体系
（那是 20 阶段的事）。

建议：定义**一个最小的输出 ABI 入口**（写 stdout），并把"它是否属于 `xiao-runtime-abi`
的一部分、还是 20 阶段 builtin 的先行者"写清楚。**不要在 N0-A 里发明 builtin 分派机制。**

## 四、与 B0 冻结结果的关系

N0 与 B0 **共享前端产物**，但**不共享执行机制**：

| 项 | B0（字节码） | N0（原生） |
| --- | --- | --- |
| 输入 | 类型化 IR | **同一份**类型化 IR |
| 中间层 | TAC + 研究编码（已冻结） | LLVM IR（本阶段新造） |
| 冻结项 | `FORMAT_VERSION = 3`、opcode `0..40` | **无关**——N0 不碰它们 |

**所以**：

- **不得**为了 N0 去改字节码的编码、opcode 或 TAC 模型；
- **不得**让 N0 成为"第二份前端"——`10:11`「原生后端消费前端已经确定的模块图，
  **不重新扫描目录猜测依赖**」，`10:9`「不依赖运行时 JIT」；
- **要共享**的是语义：溢出、布尔奇偶加减、求值顺序、释放顺序、容器顺序、错误身份
  （`00-decisions.md:370` 已冻结「优化只能改变性能，不能另造一套语言语义」，N0 同理）。

**单模块**：沿用 B0 的口径（09-B0 决策三）。多模块归 D/E。

## 五、最可能翻车的地方

1. **把 Rust 内部布局当 ABI**（`10:63` 明文禁止）。LLVM 生成代码与 Rust Runtime 的边界
   只能用 C ABI 与不透明句柄，**不得**假设 `RuntimeValue` 的 `enum` 布局。
2. **依赖 LLVM 开发库**（违反决策一）。一旦引入 `llvm-sys`，Windows 开发环境与 Docker
   都要跟着改，而且可复现性会被编译期绑定污染。
3. **工具链版本没有登记位置**（§2.1）。可复现构建是 16 阶段的硬要求，_现在不做，
   将来要在所有产物上重做。
4. **在 N0 做工具链发现或 CLI**（`10:21`、`10:57` 留给 11）。
5. **顺手做优化**（`10:37` 明说归 15 阶段，且「不能反向阻塞 N0」）。
6. **N0-A 里偷偷引入 Runtime**（§3.3）。A 的定义就是零 Runtime 依赖；
   若 `str` 或输出接口导致链接 Runtime，要么改 A 的边界并写明，要么推迟那部分。
7. **发明第二条入口路径**（§3.4）。
8. **忘了 `tests/benchmarks` 独立 crate**——它已经绊倒过一次（B0-B 的 lock 漏提交），
   这是第四次点名。
9. **动了 B0 的冻结项**：`FORMAT_VERSION`、opcode、`tests/spec/` 共享向量、
   `tests/benchmarks/reports/`。N0 **不应**产生这些文件的 diff。

## 六、硬性约束

门禁、区分度验证、工具规定、单一来源原则、解耦约束**全部沿用 09R2D 文档第二章**。

### ★ 两条约束**分别**核对，不要只守一条

`09r2d:417` 有两条并列要求，**它们是独立的**：

1. **提交标题带规范前缀**（`feat:`/`fix:`/`test:`/`docs:`/`chore:`）；
2. **正文说明为什么而不只是做了什么**。

**复发历史**（说明为什么必须分开盯）：

```text
261d88e / 66f0cec / B0-A 两个提交   →  标题缺前缀
B0-B / B0-C / B0-D                  →  两条都守住了 ✓
2a33680（21A 收束）                 →  标题守住了，正文掉了
```

最后那一笔改了**四个既有决策文档**（含 `00-decisions.md`）却**正文 0 行**——
审核者只能读 diff 反推。**改既有决策的措辞，正文必须说明旧措辞错在哪。**

### ★ 改动既有文档的措辞必须记账

N0 会复用 B0 的单模块口径、入口口径与语义契约。若发现 B0 的某处表述与 `10` 阶段文档
冲突，**保留原文 + 加修正批注**（本仓既有做法，见 `09b0c` 的修正批注与 `09b0` §2.1），
不要直接删改——删掉会让"为什么曾经这样想"无从追溯。

### 其他

- 新增的每个 `pub` 项都要有文档注释（公共 API 100%、全仓 ≥90% 是硬门槛）。
- 新 crate `xiao-runtime-abi` 要按 `00a-project-layout.md` 登记：同级 `README.md`、

## 七、验收（N0-A）

沿用 09R2D 的「撤掉实现 → 用例必须失败 → 还原 → 通过」。**关键验收不是「测试通过」**：

1. **端到端**：一份纯静态标量源码经 `FrontendCompiler` → 类型化 IR → **N0-A 后端**
   → 原生可执行文件 → 运行结果与**字节码模式一致**（`12-tests:687` 的第三条，
   A 阶段先覆盖标量部分）。
2. **不依赖完整虚拟机**：检查生成程序不链接 VM（`10:70`、`12-tests:685`）。
3. **零 Runtime 依赖**：纯静态程序的产物**不装载 Runtime**（`10:78`）。
   这条要能被检查，不是靠声称。
4. **溢出行为与字节码一致**，且 §3.2 的裁定已写明。
5. **工具链版本有登记位置**，且写明它如何进入构建指纹（§2.1）。
6. **§3.3 的 `str` 结论已写明**，判据与 `10:78` 一致。
7. **IR 有验证手段**：`llvm-as`（或等价）能验证生成的 `.ll`；且有一条用例证明
   语法错误会被抓出来。
8. **门禁全绿**，**包含** `tests/benchmarks` 独立 crate。
