### 1. 单线程非原子 RC：应该把它当成“设计轴心”，而不是早早妥协成全局原子

#### 1.1 为什么要死保“默认单线程非原子 RC”

在很多系统里都发现：**一旦你把所有 RC 都做成原子（shared_ptr / Arc-only 世界），性能和复杂度会直接爆炸**——不只是慢，还有 CPU cache 抖动、内存顺序、伪共享这一堆坑。

Lean、Rust、C++ 这些系统最后都走向了同一个 pattern：

- **线程内对象**：用非原子 RC（Lean 的 per-thread RC、Rust 的 `Rc`）
- **跨线程共享对象**：才用原子 RC（C++ `shared_ptr`、Rust `Arc`）

Xiao 现在的设计其实已经往这个方向走了一半：

- 计数策略接口是可插拔的（后面可以挂“单线程 RC 实现”和“原子 RC 实现”）。
- 06‑B 明确拒绝跨线程句柄，这等于在语义上规定：**这一版 Runtime 只有线程内堆，没有“共享堆”**。

我觉得对 Xiao 来说，**最有利的就是把这条路走到底**：

> **默认句柄永远都是“单线程非原子、不可跨线程发送”的。
> 想跨线程，就得显式换成另一种 handle/容器类型。**

这样你可以保证：

- 大部分用户代码（特别是单线程 CLI/脚本/任务编排那类）
  → 自动享受“RC 成本低、语义简单”的好处。
- 并发相关的复杂度
  → 被集中在极少数“共享类型 / 并发库”里，而不是到处铺。

#### 1.2 应该怎么做（从 Xiao 规格出发的几条建议）

我站在 Xiao 架构师角度，会这么定规则：

1. **给 Strong/Weak 句柄加一个“线程亲和（affinity）标记”**：
   - 每个 Runtime 实例有一个 `ThreadId` 或 `RuntimeId`；
   - 句柄构造时记录所属 Runtime；
   - 任何把句柄传给另一个 Runtime（=线程）的行为，一律静态/动态拒绝（早期可以直接 panic+错误码）。

2. **在类型系统里补一个类似 Rust `Send` / `Sync` 的 trait 轴，但先只针对“能不能跨 Runtime 发”**：
   - 普通 `T` 默认是 `!SendToOtherRuntime`；
   - 将来如果要提供 `Shared<T>` 之类跨线程容器，才实现 `Send`。
   - `xiao-lifetime` 的逃逸分析里，本来就有“跨线程传递的值”这个标记位（06‑A TODO 里有）。

3. **计数策略抽象保持现在的形式，但明确约束：**
   - “默认 Strong/Weak 用的就是 `SingleThreadCounter` 策略”；
   - 将来如果真要做 `Shared<T>` / `AtomicHandle`，那是用另一个计数策略 + 另一套类型，不要 retro-fit 到全部 heap 上。

这样，**你保住了 Xiao 现在这个“单线程 RC + 精确释放”的最强卖点**，同时又不给未来加原子 RC 封死路。

### 2. 环（强环 + Weak）：Xiao 最聪明的做法其实已经写出来了，但要敢“用力收紧”

#### 2.1 他们现在的做法本质是：**强图必须是 DAG / 森林，环一律 Weak 打断**

文档里写得很清楚：

- 所有权边 `A -> B` 表示 A 先于 B 释放，
  → 先对强边做拓扑排序，**强环在静态阶段拒绝**。
- 为了在数据结构层面形成环（父子、缓存、图）时，
  → “必须把至少一条不拥有对象的边声明为弱引用”。

也就是说，**Xiao 已经把自己从“引用计数如何检测环”这整个坑里跳出来了**：

- 不打算做什么 cycle collector、全堆扫描；
- 而是直接要求：**所有“真拥有关系”（Strong 图）组成 DAG**。

这是一个非常大胆但对 Xiao 来说**极有利**的取舍：

- 优点：
  - 释放顺序可以 100% 静态排好（你看到的拓扑 + 声明逆序）；
  - 运行时不需要做复杂标记/扫描。
- 成本：
  - API 设计必须顺着这个规则来；
  - 用户写“自引用”或“图”类结构，会被迫显式标 `Weak`。

#### 2.2 我觉得对 Xiao 最有利的，是“干脆把这条路走得更极端一点”

##### 建议 1：把“强图是森林”写进语言层级，而不仅是实现细节

现在它是 DevDocs 里的说明，我会建议把核心约束提升为“**语言承诺**”：

- 任何强边都被解释为“所有权”（owner → owned）；
- **所有强边形成的图必须是森林（无环）。**
- 所有“反向”关系（parent ← child）以及“缓存、索引、观察者”等，都需要用 Weak 或借用/视图语义来表达。

这样做的好处是：

- 生命周期分析器和 Runtime 都有一个**永久不变的全局约束**可以依赖；
- 将来做 AIGC/工具时，模型只要知道：“你想指回去，就写 Weak/borrow，不要瞎 strong”。

##### 建议 2：标准库帮用户“预设计好”常见环形结构模式

不然用户会被“哪里该 Weak”搞到崩溃。比如：

- 树结构：
  - 父 → 子：Strong；
  - 子 → 父：Weak；
  - 提供一个 `TreeNode`/`Parented<T>` 之类的标准库类型，直接帮你封装好这对 Strong/Weak。

- 双向链表：
  - `next` 用 Strong，`prev` 用 Weak；
  - 提供一个标准 `DoublyLinkedList<T>`，内部已经布局好 Strong/Weak，不让用户自己拼。

- 观察者/订阅：
  - Subject → Observer：Weak（不希望 Observer“锁死” Subject）；
  - Observer 在表中拿的是 Strong handle，但 Subject 在列表里只放 Weak。

- 图(Graph)：
  - 节点彼此互指几乎都是环；
  - 可以提供一种 `Graph<T>`，内部就约定“节点强引用自身资源，边只持 Weak/ID”。

**核心思想：**

> “让用户思考‘所有权树’而不是‘任意图’，
> 图结构交给标准库和约定俗成的模式。”

##### 建议 3：对“环导致的泄漏”保持 0 容忍，而不是偷偷允许泄漏

既然 Xiao 已经说了“强环在静态阶段拒绝”，那就不要再引入“允许泄漏一部分内存”这种灰色区。

- 编译期：发现强环 → 直接错误（有清晰错误码/诊断）；
- 运行期：凡是 RC 对象（Strong 图）都必须保证**能被完全释放**（除非出现 FatalError 直接崩进 OS）。

如果真的有“一次性 arena”那种“故意不做细粒度销毁”的需求，可以在语言里显式暴露：

- `Arena<T>`：
  - 分配归 Arena 持有；
  - 对象之间可以任意强引用；
  - 但只有整个 Arena 一次性释放（这不算“RC 堆上的环问题”，而是一种批量资源）。

这样你把“可能含环的区域”隔离成一种**显式的作用域/区域**概念，而不是在 RC 堆里搞隐式泄漏。

### 3. 并发模型：在“单线程 RC + 强图是森林”前提下，Xiao 最有利的路线

你只要一搞“多线程共享堆 + 通用 RC”，就会掉进一堆人已经写了几十篇论文的坑里面：

- 原子操作到处是；
- 内存模型要细到“哪条 load / store 是 acquire / release / seq_cst”；
- 弱引用在高并发下实现也挺恶心（微软那篇《Wait-Free Weak Reference Counting》就是专门解决这个）。

以 Xiao 当前阶段来说，我认为**最有利的并发选择**是：

#### 3.1 阶段 1：只支持“单 OS 线程 + 多任务（协程）”，完全不谈多核并行

也就是：

- 一个 Runtime = 一个 OS 线程 + 一堆协程/future；
- 所有 Strong/Weak handle 在这个线程里活动，**不需要任何原子操作**。
- 调度可以是：
  - 最简单的：事件循环 + `async/await`；
  - 或者用 Rust Runtime 做底层 executor，但对 Xiao 来说语义就是：“只有逻辑并发，没有真多核共享堆”。

**好处：**

- 可以先把：
  - RC、Weak、表生命周期、释放顺序、错误展开；
  - 容器/选择器 Runtime；
  - 字节码 VM + LLVM 后端
  这整个大堆东西做扎实，而不用被“跨线程 RC”拖住。

- 对很多真实场景（CLI 工具、任务编排、轻量服务），**单线程 + 异步 I/O 已经够用**，Node / Bun 世界就是这么活下来的。

#### 3.2 阶段 2：如果要上多核，就优先选“任务+消息传递”，而不是“一坨共享堆”

等 Xiao 单线程 Runtime 稳了，再考虑多核时，我会这么选：

**原则：每个 OS 线程 / Runtime 有自己的“RC 堆岛（island）”，岛之间只靠消息/复制沟通。**

具体可以有两层能力：

1. **多 Runtime / 多进程模式（最干净）：**
   - 每个 Xiao 进程就是一个 Runtime；
   - 用操作系统管进程隔离，进程间只用序列化（XAR 包或自定义协议）。
   - 优点：实现简单；
   - 缺点：重量级，但对很多工具链/脚本类场景完全可以接受。

2. **多线程 + Actor / Channel 模式（中等复杂度）：**
   - 每个 OS 线程持有一个 Xiao Runtime（=一个 RC 堆）；
   - 不允许把句柄跨 Runtime 传，只能：
     - 深拷贝消息（值类型、不可变结构）；
     - 或者把一块数据“冻结”（类似 Rust `Arc<[T]>` 那种只读共享）；
   - 需要一个“可跨线程发送的值类型”子集（类似 Rust `Send`），比如：
     - 纯值类型（标量、不可变元组、不可变 array）；
     - 不带 Weak、不含 Runtime 对象头的纯数据结构。

**这样做对 Xiao 的好处：**

- 默认 RC 仍然是单线程非原子，不被污染；
- 并发复杂度主要出现在：
  - “哪些类型可跨线程发送”；
  - “发送时是 copy 还是 freeze”；
  - “executor/调度器接口”；
- 不用面对“多线程下 Weak 升级/降级和对象销毁之间的竞态”这些活埋人的细节。

#### 3.3 真要共享可变对象，再单独提供“重武器”而不是全局启用

如果以后真的有需求：“多个线程需要共享一个可变对象”，那我建议 **不要** 改全局 RC 策略，而是加一个非常“显眼”的类型，例如：

- `SharedCell<T>` / `AtomHandle<T>`：
  - 内部持有的是**原子引用计数的对象头**；
  - 所有操作都需要锁/原子保证；
  - 类型上标 `Send + Sync`。

- 使用门槛尽量高：
  - 必须 `import std.concurrent` 才能拿到；
  - 文档反复强调“这里是性能黑洞”。

这样你既满足“极端高并发场景”的人，又不会让普通用户无意间掉进原子 RC 的坑。

### 4. 综合成一句话：如果是我拍板，我会这么定 Xiao 的路线

把你问的三个点合起来，我会给 Xiao 的建议是：

1. **单线程非原子 RC：**
   - 把它当作**语言默认模型**，永远不变；
   - 所有普通句柄都带“线程亲和”，不得跨线程；
   - 计数策略接口只用来给“少数跨线程共享类型”挂原子实现。

2. **环（Strong 图）：**
   - 明确规定：**强引用关系一定组成森林 / DAG**，静态查到环就报错；
   - 所有“反向指针 / 缓存 / 索引 / 观察者”都通过 Weak 或视图/ID 表达；
   - 标准库提供树、图、双链表、观察者等模式的现成封装，帮用户用好 Weak；
   - 如果需要“允许任意环但一起销毁”，提供 `Arena` 这类显式区域，而不是搞隐式泄漏。

3. **并发模型：**
   - 阶段 1：只搞“单 OS 线程 + 协程”（异步 I/O），把 Runtime / VM / LLVM / 生命周期全部打牢；
   - 阶段 2：上多核时，优先选“多 Runtime / actor / channel / 复制或冻结消息”，避免共享 RC 堆；
   - 只有在确认某些场景必须“跨线程共享可变对象”时，再用显眼的 `Shared/Atom*` 类型，把原子 RC 的坑局部封装，不扩散到语言默认路径。

这套组合的好处是：

- 完全顺着 Xiao 已经写在 06‑A/06‑B 里的决策走，不需要推翻；
- 保住了它最有价值的卖点：**确定性释放 + 统一释放顺序 + 简单 RC 性能**；
- 并发和环这两个传统大坑，都被收缩到“可控子系统”，不至于把整个项目拖偏。
