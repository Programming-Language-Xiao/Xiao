# 20C-语言边界批. 逻辑/身份算子：语义裁定、双路径接通与探测覆盖

> **背景**：[20C-第二批](20c-second-batch-probe.md) 的七项候选里，四条被语言/容器边界挡住；
> §九.2 已按星崽裁定写下「只登记缺口、不在本批推动语言能力补齐」，
> 并指明它们**等待后续语言/容器批次**。本批就是那个批次——**按裁定与库批次分开**，
> 不是把库批次变成语言批次。
>
> 本批的直接触发是 2026-10-13 审核 `44fe103` / `2a690e7` 时实测到的一类构造：
> **前端接受、生产降低器拒绝**，且**全仓库没有任何测试覆盖它**。
>
> **一句话概括**：先裁定 `and`/`or` 的短路与释放语义、以及 `is`/`is not` 的身份语义，
> 再按裁定把四个算子接通到两条路径，最后把「已接受构造不得进入 `unsupported`」做成**执行点**——
> 让下一次同类缺口由门禁发现，而不是靠审核人肉撞出来。
>
> 状态：**规划（2026-10-13）**，未开始实现。§二 的六笔账是本批**先做**的部分；
> §三 的两条语义裁定**没有裁定结果之前不得动手写降低**（[00. 决策基线](00-decisions.md) 的既有纪律）。

VM 侧完整诊断（`--nocapture` 原文；取自 `if c >= "A" and c <= "Z"` 那一形态，
即 §2.4 那个夹具里被遮住的那一行）：

```text
phase: Verification, code: "X09-BYTECODE-001", path: Some("program.unsupported[0]")
message: "生产字节码含未降低构造：operator 尚未降低（74..95）"
class: Fatal, code: "X07-FATAL-002", message_id: "fatal.corrupt_artifact"
```

**三件事必须一起说清，缺一条就会把性质讲错**：

1. **原生侧的拒绝是刻意的镜像，不是漏做**——`xiao-codegen-llvm/src/ir.rs:1071-1078` 有原文注释：
   「09-B0 的生产降低器尚未给逻辑/身份运算分配冻结 TAC 语义；原生侧**必须保持同一接受边界**，
   不能用 eager LLVM 指令悄悄扩大语言子集」。
   **这条镜像纪律在本批不解除**（§4.2）；
2. **但缺口的性质仍是「不变量被实际触发」**：`09b0-bytecode-closure.md:203` 的中心不变量是
   `unsupported` **恒为空**，`:254` 写明「非空 `unsupported` 只代表降低器与生产契约的内部缺口」。
   一段**从前端正常接受、类型层正常通过**的源码能走到它，说明「恒为空」在**实际可达面**上不成立；
3. **诊断措辞本身也不对**：装载失败被包成 `X07-FATAL-002` / `fatal.corrupt_artifact` / 「生产执行前验证失败」——
   **产物没有损坏**，是降低器缺一个算子。`xiao-bytecode/src/verify.rs:156` 的注释把这层语义写对了
   （「表示降低器与生产契约脱节」），但**用户可见的 message_id 把它说成了产物损坏**。

### 1.4 为什么这一条直到审核才被发现

- **全仓库零覆盖**：`grep -rln " and " --include=*.xiao .` 只命中 `tests/fixtures/20c/second-case-conversion.xiao`，
  它是 `44fe103` 自己新增的；而该夹具**在前端就被 `X02-TYPE-006` 拒掉**，从没走到后端——
  **探测夹具自己把后端缺口盖住了**（§2.4）；
- **机制有单测、可达面无单测**：`xiao-bytecode/src/verify.rs:1370-1373` 的
  `production_entry_rejects_unsupported_as_internal_error` **手工塞了一条假的 `unsupported`**
  再断言被拒——它守的是**机制**，不是**可达性**；
- **基准程序按协议避开了它们**：09R3 的基准程序「避开三条拒绝路径」，性能语料里也没有逻辑算子；
- **两条路径都拒绝，所以差分测试也不会红**：`d19a_differential` 比较的是两边是否一致——
  **两边一致地拒绝**在它眼里是「通过」。这不是差分套件的缺陷，是它的判据本来就不是「接受面完整」。

## 二、并进来的六笔账（**先做**）

出处：2026-10-13 审核 `44fe103` + `2a690e7`。**六笔都在 §三 之前完成并回填。**

### 2.1 **P-9：第二批探测表第 1 行要拆成两行**

**事实**：[20C-第二批](20c-second-batch-probe.md) 第 148 行把「字符串比较（`==`/`<`/`>`）」整体判为
`X02-TYPE-005` 拒绝，结论写「现有标量比较类型规则不覆盖 `str` 序关系」。
实测与之冲突（§1.2 表 A）：**非字面量**的 `str` 比较**双路径可用**。

**冻结**：

1. 该行**拆成两行**：
   - **非字面量（参数/局部/循环变量）的 `str` 比较：双路径可用**——不是缺口，
     依据是本批 §1.2 的双路径实跑（VM `success=true`、原生 `status=0`）；
   - **字面量对字面量的 `str` 比较：`X02-TYPE-005`**——这才是真实边界，范围**收窄到常量折叠路径**；
2. §4.1 里「字符串比较登记为语言缺口」这句**同步收窄**：登记对象是**字面量常量折叠**，
   不是「`str` 序关系」；`second-string-comparison.xiao` 的期望码与理由一并跟着改；
3. **不许**把「参数比较可用」写成「比较能力已经够了」——它只说明**序关系的运行时语义在**，
   常量折叠那半仍然是缺口，两件事分开记。

### 2.2 **P-10 的登记：四个算子当前不在任何缺口清单里**

**事实**：全仓库检索 `and` / `or` / `is` / `is not` 的**缺口登记**，只命中
[00-decisions](00-decisions.md) 第 187 行的**语法冻结**（P1 把它们的优先级定了），
以及 `xiao-codegen-llvm/src/ir.rs:1071` 的**代码注释**。
**没有任何缺口清单、遗留表或验收文档登记这四个算子**——
`09b0` 的 `unsupported` 章节讲的是机制，没点名这四个。

**冻结**：

1. 在 [09B0](09b0-bytecode-closure.md) 的 `unsupported` 章节**点名登记**这四个算子，
   写清：**需要什么**（冻结的 TAC 语义）、**当前以什么码被拒**（`X09-BYTECODE-001` / 原生 `CodegenError::Unsupported`）、
   **阻塞哪条接口**（20C 的 `text` 大小写转换、以及一切需要布尔组合的模块）；
2. 登记口径按 [20C](20c-official-xiao-library.md) §3.1 第 4 条：**原生后端拒绝信息原样摘录**，
   不替它换词；
3. **本条只登记，不改语义**——语义裁定在 §三，接通在 §四。

### 2.3 **P-11：第二批第 4 行补上类型层**

**事实**：第 151 行记 `X01-PARSE-007`。它确实是 `text[index + 1]` 的**最先**错误码，
但当场还同时报了 `X04-PARSE-004` / `X04-PARSE-003` / `X04-TYPE-002`；
而 `text[index]` 单跑**只**出 `X03-TYPE-003`（类型层）。

**冻结**：该行补一句「**根边界在类型层 `X03-TYPE-003`**；`X01-PARSE-007` 只是复合表达式里最先翻出来的那个」。
**目的**：不改这条，后来人会照 `X01-PARSE-007` 去改**解析器**，而问题在**类型层**。

### 2.4 **遮蔽：大小写转换有两个独立阻塞项**

**事实**：`tests/fixtures/20c/second-case-conversion.xiao` 同时含
`:4` 的 `if c >= "A" and c <= "Z"` 与 `:5` 的 `str(int(c) + 32)`。
前端在 `:5` 以 `X02-TYPE-006` 拒绝 ⇒ **`:4` 的 `and` 从未被执行**。

**冻结**：

1. `大小写转换` 的缺口登记**必须写两个阻塞项**：`int` → `str` 转换（`X02-TYPE-006`）
   **和** 逻辑算子（`X09-BYTECODE-001` / 原生后端 Unsupported）。
   只写转换，等于说「转换修好就够了」——**是错的**，修好转换后它会立刻撞上 `and`；
2. 这条是 [10Z-驱动](10z-performance-driver.md) §2.7 D7 **遮蔽**形态的又一次出现，
   **在本批按遮蔽记名**，不按「另一处小笔误」记；
3. **推广纪律**（写进 §五）：**一个夹具里只允许有一个「待解释的拒绝」**。
   夹具同时含两个未知边界时，先发生的那层会把后一层盖住——
   本批新增的探测夹具一律遵守，**已有的六条第二批夹具在 §六 复探时一并拆开**。

### 2.5 **对账：把表 B 那行拆开**

### 2.6 **审计侧的自我更正（入档）**

**事实**：审核初稿把 P-10 写成「两个后端都不降低……**接了半截**」，把它当**漏做**。

**冻结**：

## 三、语义裁定（**没有裁定，不得动 §四**）

### 3.1 **`and` / `or`：短路与否、求值顺序、释放顺序**

`xiao-codegen-llvm/src/ir.rs:1071` 的注释把卡点说得很准：「**尚未给逻辑/身份运算分配冻结 TAC 语义**」。
所以这不是「照着别的语言抄一个」就行的——下面三条**必须一起定**，因为它们互相牵制：

| 待定 | 选项 | 牵连 |
| --- | --- | --- |
| **A. 是否短路** | ① 短路（右侧按需求值）／② 不短路（两侧都求值后按布尔合并） | 短路需要**控制流**降低（IR 现无对应节点），不短路只是一条二元指令；但②会让 `b != 0 and 1 / b > 1` 这类写法**语义上不可能安全** |
| **B. 求值顺序** | 固定「先左后右」 | 与既有实参求值顺序的冻结口径对齐（[10W](10w-a2-closeout-and-a3-boundary.md) 已冻结实参顺序为左到右） |
| **C. 释放顺序** | 短路时右侧未求值 ⇒ 右侧的临时值**不存在**、不产生释放计划 | 直接撞 [20C](20c-official-xiao-library.md) §3.4 第 1 条「释放验收比较两边共享的 `IrOwnership.release_plans` 顺序」——**③ 没定，双路径释放对账就无从对起** |

**审核倾向（不是裁定）**：A 取①短路，理由是②会让语言的布尔组合与「错误路径一致」这件事直接冲突；
B 取先左后右；C 按 A① 的自然结果——**右侧未求值即不产生释放计划**，
且这条必须在双路径上**逐字一致**。

### 3.2 **`is` / `is not`：定语义，或从接受面移出**

比 §3.1 更根本：`is`/`is not` 在**类型层**已被接受、返回 `bool`
（`xiao-types/src/checker/constant.rs:190`、`numeric.rs:213` 都有分支），但**没有任何文档冻结它的语义**：
标量比什么？句柄比什么？值语义 + 精确释放的语言里，「身份」是什么？

**三个选项，必须选一个**：

- **甲：定语义并接通**。需要先写清「身份」对**每一类值**的含义（标量、字符串、表、集合、句柄），
  以及它与 `==` 的区别。**代价最大**，但语言面完整；
- **乙：从接受面移出**——在**[类型层]**以稳定诊断拒绝（而不是留到后端报内部错误）。
  好处是**接受边界干净**、`unsupported` 不再被触发；代价是**要提升/核对**已有冻结面，
  且 P1 语法仍认这两个 token（语法与语义的差要写明）；
- **丙：保留现状（后端拒绝）**。**审核明确反对**：这正是「不变量被实际触发」的那条，
  且用户拿到的是 `fatal.corrupt_artifact` 这种**指错方向**的诊断。

**审核倾向**：乙。理由是「可持续、可维护」——**接受面只保留语义已冻结的构造**，
比留一个「能解析、能过类型、到了后端说内部错误」的悬空项强；
且 `is`/`is not` 目前**没有任何库或语料在用**（§1.4 的检索），移出的实际影响面接近零。

### 3.3 **冻结与来源**

1. 上两条的结论**由星崽裁定**；**没有裁定结果之前，§四 一行代码都不写**；
2. 裁定结论要**写明来源**（直接裁定 / 规范证据 / 审核倾向被采纳），
   按 [20C](20c-official-xiao-library.md) §2.4 **G-2** 的教训——「与审核倾向一致」**不等于**已裁定；
3. 裁定结果**回填** [00-decisions](00-decisions.md) 与 [02-类型系统](02-type-system.md) 对应章节。

## 四、双路径接通（裁定之后）

### 4.1 **字节码侧**

**冻结**：

1. §3.1 若判**短路**，需要先定**用什么承载**——是新增 TAC 控制流形态，
   还是复用既有的条件跳转（`xiao-codegen-llvm/src/ir.rs` 附近的 `emit_conditional` 结构在原生侧已有同型做法）。
   **选哪个要写进实施记录并说明理由**；**不许**用「先按不短路接上，以后再改」——那会让 §3.1 的裁定作废；
2. 兜底路径 `xiao-bytecode/src/lower/expr.rs:449` **保持存在**（它是最后一道防线），
   但本批之后**这四个算子不得再落到它**；若新增算子又落到它，§五 的守卫必须红；
3. 落地时**同步** `arith_op` / `compare_op` / `set_op` 几张映射表旁边**不留半截分支**——
   §2.6 的教训：注释与实现不一致比缺失更难查。

### 4.2 **原生侧：镜像纪律不解除**

`xiao-codegen-llvm/src/ir.rs:1071-1078` 那段**镜像拒绝的语义本身是对的**，
本批**不删掉它**，而是**把它要镜像的那个缺口补上**：

1. 字节码侧接通后，原生侧**同批**实现同一语义；**不许**一侧先落地、另一侧留拒绝——
   那会让「两边接受边界一致」这条既有性质在本批**中途**被破坏；
2. 若裁定为 §3.2 乙（从接受面移出），则镜像拒绝**上移**到前端/类型层，
   原生侧那段 `matches!` 分支**随之消失并有用例证明它已消失**（不许留成死代码）；
3. 原生侧的拒绝信息（`原生后端不支持 动态二元运算 {op}`）**保留给真正未降低的构造**，
   不因为本批而改口径。

### 4.3 **验收：四个算子的接受边界表**

实施完成后，§五 的守卫会产出一张**逐算子 × 双路径**的表，逐行给出
「成功（输出）/ 在前端哪一层以什么码拒绝 / 在后端以什么信息拒绝」。
**这张表是本批 §四 的验收物**，进实施记录，并回填 [20C](20c-official-xiao-library.md) §3.3。

## 五、覆盖执行点（**本批的中心**）

### 5.1 **为什么这里是重点**

这条洞是**人肉撞出来的**：机制有单测、可达面没有；差分套件判的是「两边一致」而不是「接受面完整」；
基准语料按协议绕开；唯一的夹具被前端错误遮住。
按 D7「**证据必须有执行点**」——**没有执行点的结论，等于没结**。
本批若只接通四个算子而不立守卫，下一条同类缺口还会以同样方式躺到某次审核才被发现。

### 5.2 **判据：从枚举派生，不手写清单**

**冻结**：

1. **清单来源必须是编译器强制的**：写一条测试，对 `BinaryOperator` / `UnaryOperator`
   （`xiao-syntax/src/ast.rs:110-175`）做 **没有 `_` 兜底分支**的 `match`，
   每个变体映射到一段最小源码 + 期望。**新增一个算子变体 ⇒ 测试编译不过**，
   强制作者回来补——这是「**能用 glob 就别枚举**」在 Rust 侧的等价做法
   （本仓库已因手写枚举漏项吃过两次亏：F-3、G-1）；
2. **两个方向都要断言**，缺一不可：
   - **接受面**：每个「已接受」的构造，**不许**产出 `X09-BYTECODE-001` /
     原生 `CodegenError::Unsupported` / `X07-FATAL-002`。**这一条是本批要立的守卫**；
   - **拒绝面**：被判为「从接受面移出」的构造（若 §3.2 取乙），
     必须在**指名的层**以**稳定错误码**拒绝，且**不许**落到后端——
     「拒绝得早」本身也要有断言；
3. **产物名要按安全字符映射**：守卫按算子拼写生成原生产物名时，
   `*` / `<` / `>` / `/` / `%` / `=` **在 Windows 文件名里非法**，链接器会以
   `clang 失败（状态 1104 / 1107）` 报出来——**看起来像后端缺口，其实是文件名**。
   审核本轮就踩过一次（`int-cmp-<`、`int-arith-*` 等六条假失败），
   换成安全字符后全部转绿。**这条必须写在守卫的实现里**，否则下一个人会把假失败当缺口登记；
4. **双路径都要跑**：VM 半边进 `workspace-default-tests`；
   原生半边按 [20C-入口](20c-entry-and-skeleton.md) §2.1 的 **P-3 glob 口径**
   进两处原生作业——**新加的 ignored 用例不需要再对账枚举，但必须确认它真的被跑到**。

### 5.3 **先红后绿，且 main 不许红**

**冻结**（照 [20C](20c-official-xiao-library.md) §2.4 末三条纪律）：

1. 守卫**在接通之前必然红**（四个算子当前就是失败的）——**这正好是一次免费的正例**；
2. 做法：**一次性分支**从 `origin/main` 起，提交 A = 只加守卫（**预期红**），
   提交 B = 接通（**预期转绿**）；做完删分支，`main` 不变红；
3. **两次推送都只许碰守卫所在的那条路径**；推送前**必须核对分支相对 `origin/main` 的整体改动**——
   第七轮审核就是栽在「只看改了哪个文件、没看分支整体」上；
4. 红/绿**运行号**回填本文与 [09B0](09b0-bytecode-closure.md)；
5. **不得**用「本机跑过」代替运行号（本仓库的既有纪律，`20C` §2.2 第 5 条）。

### 5.4 **诊断措辞同期修正**

`fatal.corrupt_artifact` / 「生产执行前验证失败」对这条路径是**指错方向**的（§1.3 第 3 条）。

**冻结**：`X09-BYTECODE-001`（非空 `unsupported`）与 `X09-BYTECODE-002`（结构/引用/ABI）
在**用户可见层**要能分开表达；
若判为基线变更（`message_id` 改动），按 [20C](20c-official-xiao-library.md) §2.4 的既定口径
**单独登记、不许悄悄替换**。**本条可与 §四 分开落地**，但**不许留在「以后再说」**——
它是 §五 守卫出现后，用户第一个会看到的东西。

## 六、被挡住候选的复探（接通之后）

§四 落地后，**重跑第二批被挡住的候选**，逐条给出「现在能不能写」：

| 候选 | 本批接通后的预期 | 依据 |
| --- | --- | --- |
| 大小写转换 | **仍被挡**：还缺 `int` → `str`（`X02-TYPE-006`） | §2.4 |

| 切分 | **仍被挡**：还缺容器参数类型 | 第二批 §3.3 第 7 行 |

**冻结**：

1. 复探**必须真跑、双路径、成表**，口径与 [20C-第二批](20c-second-batch-probe.md) §3.2 逐字相同；
2. **一个夹具只允许一个待解释的拒绝**（§2.4 第 3 条）——复探时把现有夹具按此拆开；
3. 复探结果**决定下一批是库批次还是下一个语言批次**；
   **本批不预先承诺**「接通四个算子后库就能继续」——上表四行里**没有一行会因此解封**，
   这一点必须写在实施记录里，防止后来人以为本批解封了库。

## 九、验收

1. **六笔账**：P-9 已拆行、P-10 已点名登记、P-11 已补层级、遮蔽已记名且夹具已拆、
   表 B 已拆分、审核侧更正已入档；
2. **裁定**：§3.1 与 §3.2 各自有**写明来源**的结论；**没有**「与审核倾向一致」冒充裁定；
3. **接通**：四个算子在**两条路径**上语义一致，或按裁定在**指名的层**稳定拒绝；
   **不许**一侧接通、另一侧仍拒绝；
4. **执行点**：守卫测试的清单**由编译器强制**（新增算子变体会让测试编译不过）；
   接受面与拒绝面**两个方向**都有断言；原生半边**确认被跑到**；
5. **先红后绿**：一次性分支的**红运行号**与**绿运行号**都有；**main 未变红**；
   两次推送**只碰守卫所在路径**，且**核过分支整体改动**；
6. **复探**：四条候选逐条给出「现在能不能写」，成表；**明确写出本批未解封任何一条**；
7. **诊断**：`unsupported` 的用户可见表达与结构错误**能分开**；基线变更已单独登记；
8. **诚实**：表 B 五项原样保留；首批仍 `draft`；
9. **通用**：`cargo test --workspace`、clippy、fmt、`bun test`、`bun run check`、`bunx tsc --noEmit` 全绿；
   提交标题带类型前缀、正文非空。

## 十、裁定结果与后续输入

1. **§3.1 A**：`and`/`or` 是否**短路**？求值顺序是否固定为先左后右？
2. **§3.1 C**：短路时右侧未求值，**不产生释放计划**——是否照此冻结？
3. **§3.2**：`is`/`is not` 取**甲（定语义并接通）/ 乙（从接受面移出）/ 丙（保留现状）**哪一个？
   审核倾向**乙**，理由：接受面只保留语义已冻结的构造，且当前零使用。
4. **§五 的守卫归属**：它守的是「09B0 的中心不变量」，落在 `xiao-driver` 测试下。
   是否同意把它**同时**声明为 09B0 的出口条件（即：不变量从「机制上会拒绝」升级为「可达面上不触发」）？
5. **本批与 20D 的顺序**：本批是 20C 的语言前置；做完之后是回到库批次，
   还是先推 20D（平台资源）？审核倾向**回到库批次**——四条候选里最接近解封的是
   `int` → `str`（大小写转换与数字格式化共用），那是下一个语言批次，不是 20D。
