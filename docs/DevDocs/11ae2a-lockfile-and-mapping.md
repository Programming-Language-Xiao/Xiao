## 三、必须先冻结的 6 条（**否则实现会先于设计**）

### 3.1 锁文件名称与格式（已冻结：`xiao.lock.json`，JSON）

- **名称**：`xiao.lock.json`，位于**项目根**（与 `config.xiao` 同级）；
- **格式**：JSON，顶层 `lock_version: u32` 起始为 `1`；
- **为什么不用 TOML**（这个选择被明确权衡过）：`Cargo.lock` 用 TOML 是因为
  `Cargo.toml` 就是 TOML（同源），`uv.lock` 同理；而 **`config.xiao` 不是 TOML**，
  用 TOML 不带来本仓的格式统一，只多一种格式。此外 Rust 侧 `toml` 零先例（要新引 crate），
  CLI 侧内置 `JSON.parse` 零成本。
- **为什么锁文件可见且应被提交**：`:283` 要求写入「**可 diff、可审计**」；
  `:300-301` 刚强调过「配置里的间接引用不得是唯一记录，否则用户 review 时看不出实际优先级」。
  **不要把它藏进 `.xiao/` 或 `.venv/`。**

⚠️ **`lock_version` 的兼容策略要一并冻结**（与 E1 的 `EnvironmentMetadata` 同构）：
读到高于自身的版本必须**稳定诊断拒绝**，不猜测字段。

### 3.2 锁文件的内容契约：**解析键与内容摘要是两个东西**

`00-decisions:296` 已冻结这条区分，**锁文件两者都要记**：

- **逻辑包身份**：规范化包名 + 版本 + 源身份（**求解的解析键**）；
- **内容摘要**：SHA-256（**内容对象同一性**）。

「字节相同只说明是同一个内容对象，**不代表相同的包名、版本或依赖语义**」
（`:296` 原文）——所以**摘要不能替代逻辑身份**，锁文件里两者并存。

**⚠️ 本地路径依赖带来的一个必须写明的性质**：本地源的 `source_id` 是
`local:<规范化路径>`（D1 的 `model.rs:213` 已实现 `local_source_id`），
**这意味着锁文件会含绝对路径**。

- 这与 E0 冻结的「*指纹*不含绝对路径」（`11ae0` §3）**不矛盾**：
  指纹用于判断"输入变没变"，路径变化不该让指纹变；而锁文件的源身份是**来源审计**，
  路径就是来源本身。
- **但必须在文档里写明**：**含绝对路径的锁文件不可跨机器直接复用**。
  这是本地路径依赖的固有性质，不是缺陷；远程源（E3）才不会这样。

### 3.3 「锁文件是最新的」判据（**E2A 的核心算法**）

`sync` 只在「需要重新求解」时自动写锁文件（`:283`），所以**必须先有"是否需要重解"的判据**。
E2A 要把这个判据做成公共 API（E2B 只是调用它）。

至少要覆盖：

| 变化 | 锁文件是否过期 | 依据 |
| --- | --- | --- |
| `config.xiao` 的依赖声明变了 | **是** | 锁文件记录完整依赖图 |
| 本地包的**内容**变了（摘要变） | **是** | `11a:111`：源目录变化产生新摘要 |
| 本地包的**路径**变了（source_id 变） | **是** | `:289` 源身份进锁文件 |
| 包版本字段变了 | **是** | 解析键含版本 |
| 环境变量 / 绝对路径前缀变了 | **否** | 指纹口径（E0），路径不参与 |

**⚠️ 这块必须复用 E1 的摘要与 E0 的指纹口径，不得另写一套**（§六.1）。

### 3.4 `sync` 的目标环境选择（已冻结：激活优先 → `.venv` → 创建）

`00-decisions:624` 曾把「多个项目环境并存时 `sync` 如何选择目标」列为待定。**本批冻结为**：

1. **有激活环境** → 同步到该环境；
2. 无激活环境但 `.venv` 存在 → 同步 `.venv`；
3. 都没有 → 按 `00-decisions:278` 的规则（向上发现 `config.xiao` 所在项目根，
   找不到回退当前目录）**创建 `.venv` 再同步**。

**⚠️ 前置检查**：E0 的 Shell 钩子目前只设了提示符前缀，**是否设了一个可读的"当前激活环境"变量
尚未核实**。E2A **不实现**这条链路（属 E2B 的接线），但**冻结这条规则本身**，
并要在交接时明确：**若 E0 的钩子没有环境变量，E2B 必须先补它**，否则第 1 条无从判断。

### 3.5 环境映射的原子更新（**跨平台坑，E2A 最可能翻车处**）

现状：`environment.rs:511` 是**裸 `fs::write`**——写一半崩溃会留下损坏的元数据。
E1 的 `cache.rs:229` 已有**临时文件 + `fs::rename`** 的正确先例，**照它写**。

**⚠️ 但有一个 Windows 特有的坑，必须冻结处理**：

- Unix 的 `rename(2)` 在目标存在时**原子覆盖**；
- **Windows 的 `fs::rename` 在目标存在时会失败**（`ERROR_ALREADY_EXISTS`），
  不是覆盖。

所以「写到临时文件再 rename 覆盖」这个模式**在 Windows 上不成立**。
可选口径（**选一个并写明**）：

- **(a)** 目标存在时先删再 rename——**不是原子的**，但窗口极小；
- **(b)** 用平台 API 的原子替换（Windows 的 `ReplaceFileW` / `MoveFileEx` 带
  `MOVEFILE_REPLACE_EXISTING`），Unix 继续 `rename`；
- **(c)** 元数据写入**不用覆盖**：先写临时文件，再 rename 到**唯一新名字**，
  最后用一个稳定的指针文件原子切换（间接层）。

**推荐 (b)**：语义最正确、对调用方零额外复杂度；代价是要写一小段条件编译。
**若选 (a)，必须在本批文档里写明"原子性在 Windows 上弱化"**——
不能默默把"原子更新"当成三平台等价（这正是 E1 只读权限没写明差额的同类问题，见 §十一）。

### 3.6 配置与锁文件不一致的诊断编号

现有：`X05-PACKAGE-001..005`（包粒度）、`X05-ENV-001..004`（环境粒度）、
`X05-CACHE-001..004`（缓存粒度）。

锁文件是**第四种粒度**，建议新开 **`X05-LOCK-*`**，并在文档里写明理由。
**不要塞进 `X05-PACKAGE-*`**——包身份冲突与锁文件过期不是一回事。

## 六、硬约束

### 6.1 单一来源

- **不重新扫描 `config.xiao`**（`05d:103`）——消费 `ConfigDocument`；
- **不重建包图**——D1 的 `PackageGraph` 是唯一包图；
- **不重写摘要**——E1 的规范化与 SHA-256 是唯一实现；
- **不另造指纹口径**——E0 的 `stable_hash` 指纹与 E1 的 SHA-256 内容摘要**各司其职**，
  锁文件按 §3.2 两者都要，**但都不许自己再实现一遍**。

### 6.2 确定性

锁文件的**依赖顺序、字段顺序必须确定**：用 `BTreeMap`，**不用 `HashMap` 迭代顺序**
（D1/E1 已建立这个工程习惯）。同一输入两次生成，**锁文件字节一致**。

### 6.3 不执行包代码

`00-decisions:292`：不执行包代码。锁文件生成只做**静态解析 + 摘要**。

### 6.4 不引入版本求解

`11a:484`：**版本求解属 E3D**。E2A 的锁文件**只覆盖本地路径依赖**
（E1 已限定），版本约束字段**保留但不需要求解**（`00-decisions:285` 的"字段保留"口径同理）。

### 6.5 门禁相关

- `A0-SIZE-001`：单文件 2500 物理行；
- doc-coverage：每个新增 `pub` 项都要有文档注释。

## 八、最可能翻车的地方

1. **Windows 上 `fs::rename` 不覆盖**（§3.5）——「临时文件 + rename」这个在 Unix 上正确的模式，
   在 Windows 上会静默失败或报错，而**本机就是 Windows，CI 也跑 Windows**，
   但只在"目标已存在"这条路径上暴露（首次创建成功、二次更新失败）。
2. **把内容摘要当逻辑包身份**（§3.2）——`00-decisions:296` 明确区分过，
   混用会让"同名不同源"或"同源不同版本"静默合并。
3. **锁文件藏进 `.xiao/` / `.venv/`**（§3.1）——`build`/`run` 会把它当环境产物，
   且 `:300-301` 的 review 要求落空。
4. **为"是否过期"另写一套摘要或指纹**（§6.1）——本仓头号病史。
5. **以为 E2A 该有命令**（§三.7 同源问题）——`sync`/`install` 是 E2B。
6. **在锁文件里做版本求解**（§6.4）——属 E3D。
7. **spec 夹具按 E1 的薄标准做**（§5.3）——D1 才是先例。
8. **原子性只在一平台验证**就宣称三平台等价（§3.5）。

1. **条件 1**：锁文件生成 → 内容含**完整依赖图**（不只是直接依赖）、
   每个条目的**源身份 + 摘要 + 版本**三者齐备；
   **同一输入两次生成字节一致**；`lock_version` 高于自身时稳定拒绝。
2. **条件 2**：**写入中断不留下损坏元数据**——用"先写临时文件再中断"或
   等价方式构造；**二次写入必须成功**（这条专门抓 §八.1 的 Windows 覆盖坑）。
3. **条件 3**：改 `config.xiao` / 改本地包内容 / 改包路径**三种变化各产生独立诊断**；
   未变时必须**不报**（正反例都要）。
4. **复用**：同一图两次生成锁文件 → **第二次不重写**（复用而非重建）。
5. **`XIAO_HOME` 与临时目录隔离**：测试注入临时目录，**不碰真实 `~/.xiao`**。
6. **规格夹具**：`valid.json` + `errors.json` 双份，且 `include_str!` 真实加载（§5.3）。
7. **门禁全绿**：`bun test`、`bun run check`、`check:lock`、`bunx tsc`，
   以及 **`cargo clippy --workspace --all-targets -- -D warnings`**（§十一.1）。

## 十、不负责与不要重复做的事

- **不做 `sync` / `install` / `i` / `add` / `remove` / `lock` / `update`**——E2B 与 E3D。
- **不碰 CLI**（E2A 与 D1/E1 同形）——`cli/ts/src/packages/` 保持为空。
- **不做版本求解与版本约束算法**——E3D（`11a:484`）。
- **不做远程源、联邦索引、离线模式**——E3。
- **不填 `lockfile_summary`**——那是 E0 留给**环境元数据**的字段；
  本批产出的是**独立的锁文件**，不要把两者合并。
- **不做预编译变体维度**——`00-decisions:285`：字段保留、首版为空，依赖 14 阶段。

## 十一、上一批（E1）的欠账与三处修复（**一并纳入本批**）

审核 E1 的三笔提交（`1b6ec61`、`6662fac`、`d3d9398`）后确认 E1 出口条件已满足，
但留下三处偏差。**用户已指示一并纳入 E2A。**

### 11.1 clippy 不在门禁 —— **最该修的一条**

**实测**：`package.json` 的 `bun run check` = `repo-check all` + `check:lock`，**不含 clippy**。
而 `.github/workflows/platform-reproduction.yml:51` **装了 `clippy` 组件却没有执行它的步骤**
（整个 workflow 里 `clippy` 只出现这一次）。

**后果已经发生**：`xiao-config/src/validation.rs` 里一段 collapsible-if 违规是
**`e6c686b`（D1）** 引入的，**积到 `d3d9398`（E1 收口）才被清掉**——
两批之间的所有 clippy 违规都不会被自动拦住。

**修复（二选一或都做）**：

- **本地**：在 `package.json` 加 `"check:clippy": "cargo clippy --manifest-path core/rust/Cargo.toml --workspace --all-targets -- -D warnings"`，
  并**决定是否并入 `check`**（并入会变慢，但不再靠自觉）；
- **CI**：在 `platform-reproduction.yml` 里**加一个 clippy 步骤**——**只需一个平台跑**，
  不必四平台重复。组件已经装好了，加步骤即可。

**⚠️ 无论选哪种，都要在 `00a` 或交接文档里写明"clippy 属于门禁还是提交前手跑清单"**，
消除"验收条款要求它、门禁不跑它"的落差。

### 11.2 `tests/spec/11a-cache/` 比 D1 薄太多

D1 的 `valid.json` 29 行**含真实 `files` 与 `expect`**、`errors.json` 36 行；
E1 只有 `valid.json` **9 行、仅 3 个 case 名字**，**没有 `errors.json`**——
而 E1 新增了 4 个诊断码。README 自陈「快照只提供阶段标识与场景名称」。

**这形式上过了 `11x0spec` 的「有执行入口」判据**（`cache_spec_snapshot_is_executed`
用 `include_str!`），**但实质与 D1 建立的先例不匹配**。

**修复**：E2A 的 `tests/spec/11a-lockfile/` **按 D1 的标准做**（§5.3）；
并**评估是否回填 E1 的 `errors.json`**（若回填，走 E2A 的一个独立提交）。

### 11.3 收口提交的标题与内容不符

`d3d9398` 标题是 `docs(11a): close E1 handoff`，却改了
`core/rust/crates/xiao-config/src/validation.rs` 47 行 Rust 源码
（改法是 `if A { if B {…} }` → `if A && B {…}`，**已逐行核对确认等价**）。

按本仓"标题带规范前缀"的纪律，**文档提交里混源码改动**会让回看历史时漏掉它。
**修复**：E2A 的每个提交**标题与内容一致**；跨类型的顺带修正**单独一笔**。

### 11.4 附带：E1 未写明的只读强度差额

`11ae1` §3.6 要求「若三平台无法做到同等强度，**要在文档里写明差额**」。
实测 E1 代码**确实分了平台**（Windows `set_readonly(true)` / Unix `0o555`·`0o444`），
但**文档没写这个差额**。不影响 E1 条件 3 的满足（条件 3 管**读**的路径，不是写保护强度），
但没做就是没做——**E2A 收尾时补上，或明确标注为接受的不一致**。
