# 10G. N0-C-2 错误边界与字节码差分

> **10 阶段 N0-C 的第二批。** 第 2–4 步（统一错误路径降低、`try`/`catch`/`finally` 展开、
> 源码映射）已由 `31fb944` + `91a3392` 交付，并经 `10F` 专项复核。

>
> **一句话概括本批**：把错误路径**两头封死**（平台异常进不来、可恢复错误出不去），
> 并让**字节码与原生在同一份 IR 上逐项对齐**——输出、错误、释放记录**三样**。
>
> **第 6 步（诊断事件与 `-debug` 独立诊断进程）与第 8 步（UseDocs）归 N0-C-3**——
> 那一块（启动入口、GUI 抑制、独立进程）自成一体，混进来会让批次过大。

## 二、必须先冻结的 6 条

### 3.1 ⚠️ **正向边界当前已经成立——别去"修"一个不是问题的东西**

`10E §3.1` 冻结的是**双向**边界。开工前先看清哪一半真的缺：

| 方向 | 要求 | 现状 |
| --- | --- | --- |
| **正向**：平台异常不得伪装成可恢复 Xiao 错误 | 段错误/栈溢出/非法指令**不得**被 `catch` 接住 | ✅ **已经成立**——当前**根本没有信号处理器**，段错误直接由 OS 终止进程，没有任何 `catch` 能接到它 |
| **反向**：可恢复错误不得因走原生路径变成进程终止 | `try`/`catch` 能接的错误**必须**能接住 | ❓ **缺测试**——16 形态验证的是**能被 `llvm-as` 解析**，不是**运行期真的接住了** |
| **报告**：不可恢复失败要有**可诊断的报告** | `10E §3.1`：「进程终止 **+ 可诊断的报告**」 | ❌ **缺**——这正是本批要补的那一半 |

**冻结**：

- **不要**给"防止平台异常被捕获"再写一层防护——**它已经成立了**，再加一层只是复杂度；
- **要补的是"报告"**：捕获信号/未处理异常后，输出一份**与字节码可比**的机器摘要再终止；
- **反向边界必须有运行期测试**：构造一个 `try`/`catch` 能接住、且**原生路径必须接住**的用例，
  断言**进程没有终止**、**错误被 `catch` 消费**。**这一条目前完全空白。**

### 3.2 平台异常报告：三平台都要，且**必须 async-signal-safe**

**已定**：三平台（Windows / Linux / macOS）都做捕获 + 结构化报告。

**冻结**：

- **Unix**：`sigaction` 处理 `SIGSEGV` / `SIGBUS` / `SIGFPE` / `SIGILL` / `SIGABRT`；
  **栈溢出必须在备用信号栈（`sigaltstack`）上处理**——否则处理器自己也会因爆栈而失败；
- **Windows**：`SetUnhandledExceptionFilter` 或向量化异常处理（VEH）；
- **⚠️ 信号处理器里只能调用 async-signal-safe 函数**——
  只能 `write(2)` 直接写**预先格式化好的**缓冲区；
  **不得** `malloc`、`printf`、取锁、分配 `String`、走本地化目录查找。
  **这条是本批最容易翻车的地方**（见 §八 第 2 条）；
- **报告格式与字节码可比**：字段沿用 `10E §3.2` 的机器字段（`code`/`message_id`/位置/退出码），
  **不得另起一套字段名**；
- **⚠️ 报告里的语言**：信号处理器内**不能**查目录（非 async-signal-safe）。
  所以**要么用不依赖语言的机器摘要，要么在启动时预渲染好几条固定文案**——
  **具体形态属 N0-C-3 的 `-debug` 语言策略，但本批要保证接口留得下**。

### 3.3 语言上下文：**接上，不复制**（照 10E §3.3）

`10:61`：原生后端「从 CLI 接收不可变语言上下文和消息目录接口」，**不复制翻译逻辑**。

**冻结**：

- **原生产物接收 11C-0 的不可变语言上下文**，渲染仍走 **11C-1 的那一份渲染器**；
- **⚠️ 原生侧不得再实现一套目录查找或插值**——本仓头号病史；
  现有的 `xiao_runtime_error_report`（`abi.rs`）自己拼了一份
  `class=… code=… span=…` 的格式串直接写 stderr，**这是第二套渲染，应当收敛到统一渲染器**；
- **机器的部分不受语言影响**：`code`/`message_id`/参数/位置/退出码
  **跨语言、跨后端完全一致**——**这正是差分能成立的前提**。

### 3.4 差分的释放记录：**在 `xiao-runtime` 做一层，两侧共享**

**本批技术上最关键的一条。**

事实：**`xiao-vm` 依赖 `xiao-runtime`**（见 `xiao-vm/Cargo.toml`），
所以**字节码路径与原生路径跑的是同一套 Runtime 内存模型**。

**冻结**：

- **释放事件钩子加在 `xiao-runtime` 的 memory 层一次**，VM 与原生路径共享；
- **⚠️ 绝不允许两侧各写一套释放记录，再互相对照**——
  那样的"一致"是自己跟自己比，**什么也证明不了**，而且正是单一来源的死法；
- **⚠️ 现成的 `xiao-runtime/src/testing/mod.rs` 的 `ReleaseEvent` 不能直接用**：
  它是 **06-B 规格测试驱动器**，注释明写「**驱动器不属于用户程序 API，也不接入 VM**」，
  记录的是**静态释放计划**而不是**运行期实际发生的释放**。
  本批需要的是**运行期**事件流——**别把两者混为一谈**；
- **钩子要有开关**：默认关闭（正常执行不该为此付出开销），只在差分/诊断时启用；
- **事件内容至少要能抓到"时机错位"**：对象身份、释放动作种类、**序号**。
  §3.2 点名要防的是「GC 或析构时机不同而错位」——**只记次数抓不到它**。

### 3.5 差分要**逐项对照**，不是"两边都成功"

**现状**：`xiao-driver/tests/n0_a_native_driver.rs:126` 的
`optional_frontend_artifact_differential_round_trip` **名叫差分，实为冒烟**：

- 用例是 `[main]\nvalue = 1 + 2\n`——**纯静态标量、没有错误路径**；
- 断言只有 `execution.outcome.result.is_success()` 与 `run.status == Some(0)`；
- **输出内容、错误字段、释放记录，一样都没对照。**

**冻结**：

- **对照三样：输出、错误、释放记录**（`12-tests:687`、`10E §3.2`）——**缺一不可**；
- **"错误一致"指**：`code`、`message_id`、参数、**源码位置**、**退出码**逐项一致；
  **不是**"都报错了就算一致"；
- **用例要覆盖错误路径**：至少要有一条 `raise` → `catch` 接住的用例，
  和一条未匹配、传播到程序边界的用例；
- **⚠️ 两侧必须消费同一份 IR**（现有测试已有 `assert_eq!(native.frontend.ir, artifact.ir)`，
  这个断言**要保留**）——否则比的不是同一件东西。

### 3.6 与 N0-C-3 / N0-D 的边界

**冻结**：

- **本批不做**：诊断事件落地、`-debug` 构建标志、独立诊断进程启动入口、UseDocs 收尾；
- **⚠️ 但接口要留得下**：§3.2 的报告格式与语言策略、§3.3 的语言上下文传入点，
  **都会影响 N0-C-3 的形态**，**不能做成只有本批能用的临时形态**；
- **不做 N0-D**：三目标固定宽度、Runtime 裁剪验证、调试构建标志的产物级验证。

## 八、最可能翻车的地方

1. **给"平台异常不被捕获"白加一层防护**（§3.1）——那一半已经成立，纯属浪费且增加复杂度。
2. **信号处理器里调用非 async-signal-safe 函数**（§3.2）——在崩溃处理中再崩一次，
   **表现为"什么都没输出"**，极难定位。**只能预先格式化 + `write`。**
3. **栈溢出没用 `sigaltstack`**（§3.2）——处理器自己爆栈，**报告永远出不来**。
4. **两侧各写一套释放记录再对照**（§3.4）——自己跟自己比，**什么也证明不了**。
5. **把 `testing/mod.rs` 的静态 `ReleaseEvent` 当运行期事件流**（§3.4）——名字一样，语义完全不同。
6. **释放记录只记次数/总量**（§3.4）——抓不到 §3.2 点名要防的"时机错位"。
7. **差分做成"两边都退出码 0"**（§3.5）——现有测试就是这么写的，**别照抄它**。
8. **差分用例不含错误路径**（§3.5）——那是本批最该覆盖的场景。
9. **原生侧再实现一套消息渲染**（§3.3）——本仓头号病史，现有 `xiao_runtime_error_report` 就是例子。
10. **新增依赖只提交一个 lock 文件**（§六 第 9 条）——`31fb944` 的翻车方式。
11. **只跑部分 crate 就说门禁全绿**（§六 第 9 条）。
12. **忘了 `stackrestore` 的栈用量实测**（§一 债项表）——`10F §七` 自述未做，**本批顺手补**。

## 九、验收

1. **错误边界双向**（§3.1）：
   - **正向**：平台异常（段错误/栈溢出/非法指令）**不被** `catch` 捕获，
     表现为不可恢复失败，**且输出可诊断的报告**；三平台各验一条；
   - **反向**：可恢复的 Xiao 错误走原生路径**不终止进程**，**被 `catch` 消费**——
     **运行期测试**，不是解析器测试。
2. **字节码差分**（§3.5，**验收主体**）：同一份 IR 经字节码与原生两条路径，
   **输出、错误、释放记录三样逐项一致**——错误要逐项对
   `code`/`message_id`/参数/位置/退出码。
3. **释放记录对照有效**：钩子在 `xiao-runtime` **一处**实现、两侧共享；
   事件含对象身份与**序号**（能抓时机错位）。
4. **语言上下文**（§3.3）：原生产物按有效语言呈现人类可读文本；
   **机器字段跨语言、跨后端一致**；**没有第二份渲染实现**。
5. **`stackrestore` 栈用量实测**：循环内 `try/finally` 迭代多次的原生程序，栈不增长。
6. **不回归**：N0-A/N0-B、09-B0、11C 系列保持绿；**`cargo test --workspace`** 全绿。
7. **门禁全绿**：`bun run check`（**含 `check:lock`**）、clippy、TS 类型检查、`cli/ts` 测试；
   新增环境门控测试**已登记进 `10D §2` 清单**。

## 十、不负责与不要重复做的事

- **不做 N0-C-3**：诊断事件、`-debug` 构建标志、独立诊断进程启动入口、UseDocs 收尾——§3.6。
- **不做 N0-D**（三目标固定宽度、Runtime 裁剪验证、调试构建标志的产物级验证）。
- **不做用户可见 `xiao build`**——11 / X0。
- **不重开** `10F §七` 冻结的展开契约（标签所有权与终结状态分离）。
- **不重开** N0-A 的档位边界与 N0-B 的 ABI 选型。
- **不重开** `07B` 的展开顺序——本批是实现它。
- **不改** 11C 已交付的语言上下文模型、目录与渲染器——本批只接。
- **不给"平台异常不被捕获"加新防护**——它已经成立。
