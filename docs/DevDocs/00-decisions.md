# 00. 决策基线

> 本文记录 Xiao 当前已经确认的设计方向。它是后续词法、编译器和运行时实现的约束源。

## 一级工程目标：确定语言边界

### 20F 显式容器类型参数（2026-10-19）

顶层函数允许 `def name<T, U>(...)`，类型参数可用于 `set<T>` 参数和返回注解。函数绑定
保留类型参数名称，调用点按独立实例检查；生成期擦除为 `IrType::Variable` 的动态边界，
不做单态化。函数体内把类型参数与具体类型合并报 `X04-TYPE-008`。首版官方模块仅有
`stdlib.set.size` 与 `stdlib.set.is_empty`，集合增删、泛型表和约束语法留待后续批次。

### 20G 集合可变入口与迭代快照（2026-10-19）

`stdlib.set.add`/`remove` 使用共享集合句柄，新增元素保持首次出现顺序；`remove` 找不到
元素时抛出 `Error(code = "SET_ELEMENT_MISSING")`。`contains`、`union`、`intersection` 和
`difference` 是自由函数包装，集合在 `for` 开始时复制快照，循环体内增删不影响当前轮次。

### 20H 集合方法式 API（2026-10-19）

集合方法 `size`、`is_empty`、`add`、`remove`、`contains`、`union`、`intersection`、
`difference` 与 `stdlib.set` 的同名自由函数保持一一对应；方法调用只接受静态 `set<T>`，
接收者先求值一次，链式调用继续沿用自由函数的顺序、别名和错误语义。动态接收者、方法值、
静态集合未知方法分别固定为 `X03-TYPE-024`、`X03-TYPE-025`、`X03-TYPE-026`。方法使用会
把 `stdlib.set` 纳入静态链接计划；`.xiaoc` 仍由宿主标准库 loader 按需提供模块，不把标准库
对象写入产物。

### 20I 非字面量下标、数组注解与文本切分（2026-10-20）

所有有序容器支持单个精确表达式下标；字符串按 Unicode 码点读取且下标非负，数组、元组和字典列复用同一运行时索引路径，字典表在 20I 暂保留名称键语义。函数参数/返回支持一层 `[T]` 数组注解；新增 `array_push<T>` 原地追加并保持别名可见。`text.find` 未找到返回 `-1`，`slice` 使用左闭右开区间，`split` 保留首、中、尾空段；越界和空分隔符分别固定为 `TEXT_SLICE_OUT_OF_RANGE` 与 `TEXT_SPLIT_EMPTY_SEPARATOR`。20I 不做字典表动态键、负/字节索引、范围表达式端点和嵌套数组注解；字典动态键由 20J 单独裁定。

### 20J 字典动态键与 20I 收口（2026-10-20）

字典表与字典列支持单个动态键读取；静态键优先，无同名键时按变量/表达式类型分派，字典列整数仍表示位置。动态缺失键统一为 `X06-RUNTIME-015`，动态位置越界与表达式下标统一为 `X06-RUNTIME-017`，异构字典值读取结果为 `dynamic`。`array_push` 或将数组传给函数后擦除固定长度，避免把可变共享数组误判为静态定长；不做字典注解、动态写入和字典增删方法。

### 20K 字典写入、查询接口与开放注解（2026-10-20）

动态选择器赋值只更新已有键或位置：字典缺失键固定为 `X06-RUNTIME-015`，字典列/数组动态位置越界固定为 `X06-RUNTIME-017`，不允许 upsert。函数参数和返回值使用 `dict<str, T>` 表示开放键集，固定形状字典按共同值类型兼容；局部变量声明、嵌套字典注解和方法式字典 API 留待后续。官方 `stdlib.dict` 以自由函数提供 `get`、`set`、`remove`、`contains`、`keys`、`values`，键和值枚举返回新数组，删除缺失键保持 015。

### 20L 字典方法式 API 与 20K 收口（2026-10-20）

字典表与字典列支持 `get`、`set`、`remove`、`contains`、`keys`、`values`、`size`、`is_empty` 八个直接方法；方法只接受静态字典接收者，按字符串键复用 `stdlib.dict` 自由函数，方法值、动态接收者、未知方法分别固定为 `X03-TYPE-028/027/029`。数组变更摘要采用用户函数调用图传递闭包，修改后未知长度数组的字面量越界统一为 `X06-RUNTIME-017`；`run.sh` 只有两条已知 REPL 失败可在隔离重试通过时放行，普通 Bun 失败保持红灯。

### 目标与非目标

Xiao 的目标是让同一份源码同时拥有两种执行路径：

1. 开发阶段通过字节码运行，获得接近脚本语言的快速反馈。
2. 发布阶段通过 LLVM 生成跨平台原生二进制，程序不依赖 Xiao 虚拟机。

Xiao 不是“所有代码都自动变成零开销 C”的承诺。动态值、堆对象、字符串、异构容器和并发任务可能需要 Xiao Runtime；未使用的运行时能力应在链接或优化阶段被移除。

### 设计取舍

- 优先保证两种模式的语义一致，再追求解释器速度或生成代码速度。
- 语法默认简洁，但需要有明确的静态边界；动态能力必须可定位、可诊断。
- 资源释放选择确定性方案，不接受不可预测的全堆暂停。

## 一级工程目标：冻结基础语义

### 变量与类型

- `a = 1` 会推断出整数类型，之后不能直接赋值字符串。
- 普通变量默认可变，可以继续接受与已锁定类型兼容的赋值，例如 `a += 1`。
- 可以用 `int a = 1` 显式声明静态类型；初始化值和后续赋值都必须兼容该类型。
- 普通变量首次绑定后类型锁定；换成不兼容类型必须经过明确的释放或动态边界语法。
- 语言支持静态值和少量动态值。动态值可以使用统一的运行时值表示，但不能让所有普通变量退化成动态类型。
- `const` 表示编译期常量。编译器可以内联常量，是否占用存储由实现决定，不把“绝对零内存”作为语义保证。

### 动态能力

`@f` 和动态变量方向保留，但最终的动态声明关键字仍待定。当前约束如下：

- `@f` 不能作为普通静态变量的日常改类型语法。
- 动态重绑定只能发生在显式动态变量或动态容器中。
- 静态代码使用动态值时必须经过类型检查、装箱或显式转换。

### 数值

| 类型 | 默认位宽 | 语义 |
| --- | ---: | --- |
| `int` | 64 位 | 默认整数类型 |
| `float` | 64 位 | 默认浮点类型 |
| `sint` | 32 位 | 短整数类型 |
| `sfloat` | 32 位 | 短浮点类型 |
| `lint` | 不限 | 超大整数类型 |
| `lfloat` | 不限 | 超高精度浮点类型 |

所有平台必须提供一致的数值语义。整数、浮点和高精度类型发生溢出时直接报告错误，不静默回绕。浮点舍入、无穷大和非数的细节在类型阶段补充。

字符串类型的正式关键字为 `str`，不再保留 `string` 作为候选关键字或同义关键字。

### 显式布尔转换

- 显式转换表达式统一按“源值 `as` 目标类型”书写，例如 `raw as bool` 和 `flag as str`。
- `bool(value)` 与 `value as bool` 同时存在，并使用同一套转换成功条件和错误语义；不能只因采用构造式写法，就自行推导 Python 式的隐式真值规则。
- 当前已经冻结的字符串转布尔规则只接受 `"true"`、`"True"`、`"false"` 和 `"False"`。其他字符串必须报告转换错误。
- 布尔值转为 `str` 时固定产生小写的 `"true"` 或 `"false"`。
- 显式转换产生新值，不会原地改变源变量已经锁定的静态类型槽。

### 布尔加减

- `bool` 不是整数的子类型，不参与普通数值隐式转换。
- 只允许布尔值位于左侧、整数位于右侧的 `+`、`-`、`+=` 和 `-=` 运算；这里的整数包括 `sint`、`int` 和 `lint`。
- 右侧整数为偶数时结果保持不变，为奇数时结果翻转。加法与减法在这个规则下结果相同，负整数仍按奇偶性判断。
- 运算结果仍为 `bool`。`整数 + bool`、`整数 - bool`、`bool + bool`、`bool - bool` 以及布尔值与浮点数的加减均为类型错误。

### 容器与路径

异构数组可以保存以下值：整数、浮点、字符串、布尔值、数组、元组、集合、字典表和字典列。数组的局部类型约束使用斜杠路径，例如：

```xiao
int list[3/2]
```

所有容器数字索引统一从 `0` 开始。这表示 `list` 中索引为 `3` 的元素（第 4 个位置）是内嵌数组，并且该内嵌数组中索引为 `2` 的元素（第 3 个位置）必须是 `int`。

所有有序且可索引的容器采用统一选择语法。选择条件必须放在同一对方括号中，避免与逗号表达式及比较表达式冲突：

```xiao
values[0, 1]
values[0~2, 5~6]
values[<2]
values[<=2]
values[>0]
values[>=0]
```

- 选择范围 `start~end` 包含两端。数组、元组、`str` 和字典列支持普通索引、多选、范围、步长与随机选择；无序字典表只支持精确键和嵌套路径选择，集合完全不可索引。单个精确索引返回该位置的值，多选、范围和随机选择返回保留来源容器类型及嵌套形状的投影结果，没有元素时返回对应类型的空容器。字典列出现重复直接键时，结果按选择顺序表示为元组。

步长写在被选容器与选择器之间，例如 `values{x}[=]`。步长必须是非零整数字面量或整形变量；正数向前，负数反向，零直接报错。`values[?x]` 表示无放回随机抽取，`values[!?x]` 表示放回随机抽取；抽取数量必须是非负整数字面量或整形变量。无放回抽取数量大于可选元素数时报错，放回抽取允许数量大于元素数，但不能从空容器中抽取正数个元素。

集合采用与 Python `set` 相同的基础语义：元素唯一、没有顺序、不能通过数字或键名索引。非空集合使用花括号直接列出值，`set()` 表示空集合；空花括号 `{}` 保留给空字典表。

```xiao
values = {1, "x", true}
empty_values = set()
empty_table = {}
```

集合默认允许异构值，也可以显式指定统一的元素类型。所有集合元素都必须可哈希：元素的哈希值在其位于集合期间必须稳定，并且相等的值必须具有相同哈希。数组、字典表、字典列和普通集合等可变容器不可哈希，因此不能作为集合元素。当前实现将元组统一视为不可哈希；元组递归哈希证明留给后续阶段。

动态值插入集合时必须在运行时验证实际值是否可哈希；静态类型已经证明不可哈希时直接产生编译错误。集合不通过后台扫描追踪元素变化。

集合运算沿用 Python 的集合代数，但并集运算符改为 `+`：

| 运算 | Xiao 写法 |
| --- | --- |
| 并集 | `left + right` |
| 原地并集 | `left += right` |
| 交集 | `left & right` |
| 差集 | `left - right` |
| 对称差 | `left ^ right` |
| 子集/真子集 | `left <= right` / `left < right` |
| 超集/真超集 | `left >= right` / `left > right` |
| 成员判断 | `value in set_value` / `value not in set_value` |

`|` 和 `|=` 不承担集合并集语义。

#### C2-A 首批实现边界（已完成静态阶段）

C2-A 采用严格渐进路线：集合仍然是无序容器，源码中元素的书写顺序只用于
诊断和稳定测试输入，不能被类型层、后端或用户程序观察为集合顺序。显式元素
类型是对集合成员类型的约束，不是位置或索引声明；例如 `int ids = {1, 2, 3}`
表示 `ids` 的每个成员都必须是 `int`。

首批静态闭环允许 `int`、`sint`、`lint`、`float`、`sfloat`、`lfloat`、`str`、
`bool` 和 `none` 作为元素类型。`bool` 是独立类型，绝不与整数或浮点类型合并。
当时未显式声明的集合要求推断为单一元素类型；这一限制由 C2-B 明确扩展，不能
回写为当前规范。

C2-A 负责静态集合类型、静态重复元素、可哈希性、`in`/`not in` 成员判断和
不可索引诊断；集合代数、运行时集合对象、增删操作和 `frozenset` 仍不在其范围内。

#### C2-B 异构集合静态闭环（已完成静态阶段）

C2-B 保留 C2-A 的无序、唯一、可哈希和不可索引语义，并冻结以下扩展：

1. 未显式声明的非空集合默认推导静态成员类型并集，例如
   `{1, "x", true}` 的类型为 `set<bool | int | str>`。并集显示顺序只为稳定的
   类型摘要和诊断服务，不是集合的迭代顺序。
2. 变量根可以使用 `set<T>` 或 `set<T | U>` 显式声明成员类型，例如
   `set<int | str> values = {1, "x"}`。当前类型项只允许标量和 `none`；重复项
   在类型层去重。显式声明即使初始化器只含一个成员类型，也保留完整的声明并集。
3. 旧式 `int values = {...}` 等标量前缀继续表示同构容器约束，不能因为默认异构
   规则而接受不兼容的字符串或布尔成员。`set<T>` 只能约束变量根，不能写成
   `set<T> values[path]`；`const set<T>` 暂不开放。
4. 集合相等性和哈希身份按静态类型隔离：`true` 与 `1`、`1` 与 `1.0`、不同
   整数宽度都不是同一个静态元素。只有静态类型相同且常量值相等时才报告重复。
5. 动态元素保留已知静态成员并集，并设置动态尾标；插入或成员查询的实际值必须
   在 Runtime 再验证可哈希性和成员类型。类型层只登记 `SetHashability` 或
   `SetMembership` 检查，不能把动态边界伪装成静态证明。
6. `set()` 在无上下文时仍是未知元素类型；位于 `set<T>` 初始化器位置时由声明
   上下文具体化。`{}` 永远是空字典表，集合仍完全不可索引。

C2-B 本身只实现上述语法、静态类型和旁路 Runtime 检查标记；09R2F1 的研究 VM
已消费其中的可哈希检查并创建集合对象，但 C2-B 仍不负责增删、元组递归哈希或
`frozenset`。集合代数、比较和成员判断的执行契约由 09R2F1 独立冻结。

#### C2-C 集合运算静态闭环（已冻结，已完成静态阶段）

C2-C 只在类型层闭合集合运算，不提前创建 Runtime 集合对象。两侧为集合时，`+` 是
并集，`&` 是交集，`-` 是差集，`^` 是对称差；`|` 和 `|=` 仍只用于类型注解，不能
表示集合并集。`&` 优先于 `^`，两者都低于比较和算术。`+=`、`-=`、`&=`、`^=` 按
左值当前锁定类型检查，不自动拓宽。

结果成员类型规则已经确定：`+`/`^` 取已知成员并集，`-` 保留左侧已知成员，`&`
取静态成员交集。静态证明没有共同成员的交集使用内部 `SetType::Empty`（文本显示为
`set<never>`），与 `set()` 的 `Unknown` 状态严格区分；未知或动态边界保留已知成员并
设置动态尾标。集合比较 `==`、`!=`、`<`、`<=`、`>`、`>=` 一律返回 `bool`，允许
异构集合比较，动态情况登记 `SetComparison`。集合代数动态情况登记 `SetOperation`，
原地写回还登记 `SetMembership`。

C2-C 的稳定操作数诊断为 `X03-TYPE-021`（集合运算）和 `X03-TYPE-022`（集合比较），
参数包含 `operator`、`left_type`、`right_type`。09R2F1 已让研究 VM、IR 和字节码
消费集合代数、比较和成员判断的动态标记；正式生产 Runtime、LLVM 和集合增删仍属于
后续阶段。

### P1 表达式与选择器语法（已冻结）

P1 使用 Pratt 解析器建立可递归的表达式 AST，但只负责语法结构，不执行
代码、不做类型检查或容器边界检查。优先级从高到低为：调用/成员/选择器
后缀、幂运算（一律右结合）、一元运算、乘除整除取模、加减、比较与
`in`/`not in`/`is`/`is not`、`not`、`and`、`or`；赋值由语句层处理。

**逻辑与身份算子的语义裁定（星崽直接裁定，2026-10-14）** —— 上面那条冻结的是**语法**，
下面是**语义**，两者必须分开读（裁定落点见 [20C-语言边界](20c-language-boundary-and-operators.md) §三）：

- **`and` / `or`：短路**（右侧按需求值）；**求值顺序固定先左后右**；
  **右侧未求值 ⇒ 该次求值不产生释放计划**，这条在双路径上必须**逐字一致**。
  它们是本语言**接受面**里的构造，两条路径都要降低——不是「暂不支持」；
- **`is` / `is not`：从接受面移出**。语义（标量比什么、句柄比什么）从未冻结，
  两者当前**全仓库零使用**，因此取「类型层以稳定码 `X02-TYPE-005` 拒绝」，
  而不是留一个「能解析、能过类型、到后端报内部错误」的悬空项。
  **注意这与上面的语法冻结不冲突**：`is` / `is not` 的 **token 与优先级仍在**，
  **不许**从词法/解析里删掉；**语法认、类型层拒**，这个差是裁定的一部分。

调用允许空参数列表和尾逗号。`new Type(args...)` 形成独立构造调用节点。
`as` 在 P1 只接受 `int`、`sint`、`lint`、`float`、`sfloat`、`lfloat`、
`str`、`bool` 八种标量目标；数组、元组、集合、字典表和字典列的转换
使用构造调用，具体转换矩阵由 C0/S0 冻结。

选择器的所有项目必须位于同一对 `[]` 中，精确项、闭区间、单边范围、
全选和随机项可以混用。路径段是数字索引、普通名称或反引号名称，`/`
只在选择器路径中表示嵌套。数字索引支持 Python 风格负索引；`str` 的
索引单位固定为 Unicode 码点。重复精确项和重叠范围按书写顺序保留，
步长对每个选择项独立应用；随机抽取先按书写顺序展开选择项再抽取。
步长和随机数量允许任意表达式。

P1 允许选择器出现在赋值左侧并保存为语法节点；多选/范围写入的广播、
长度匹配、边界错误和失败回滚不在 P1 执行。普通名称的简单 `=` 继续
使用 P0 `Statement::Assignment` 形状，复合赋值或其他目标使用扩展赋值节点，
以保持既有调用方兼容。

### 标识符与表容器

- 常规变量名使用 ASCII 标识符规则。
- 反引号可以包裹任意 UTF-8 变量名，定义和引用必须保持同样的反引号形式：

```xiao
`新变量1` = 1
print(`新变量1`)
```

- 字典表使用花括号包裹，条目写作 `键 = 值`，键值无顺序要求，按键访问。
- 字典列使用尖括号包裹，键值顺序固定，支持数字索引和数字加键名索引。

#### 表与生命周期静态边界（05-C 已冻结）

- `[Table]` 是单例表，`[[Table]]` 是可实例化表；表头必须顶层顶格，表体缩进一级，方法体
  继续缩进。表体只允许字段赋值/声明、`const` 字段和 `def` 方法。
- 字段与方法共享成员符号表；以下划线开头的成员默认私有，其余默认公开。表不能作为集合
  元素或索引对象；成员访问和可见性由独立类型检查模块完成，禁止在模块解析器中复制。
- 表字段初始化器必须是静态纯表达式（字面量、已知常量、纯运算或纯容器）；`input`、`print`、
  普通函数、`new`、动态成员和选择器不允许在字段初始化阶段执行。
- `new` 只接受 `[[Table]]`；无 `init` 时只能无参，有 `init` 时按去掉 `self` 后的参数匹配。
  方法首参数必须是普通 `self`，`drop` 只能有 `self`，`init`/`drop` 返回类型必须是 `none`。
- 05-C 只产出 AST、`TableType`、`TableSignature` 和结构化诊断，不执行 `init`/`drop`，不创建
  实例，不实现 RAII、逃逸分析或引用计数；这些能力留给 06/R0。

#### 生命周期静态闭环（06-A 已冻结）

- 生命周期分析独立放在 `xiao-lifetime`，消费 `Program` 与 `TypeCheckResult`，不修改类型结果，
  也不让类型层反向依赖生命周期层。
- 默认所有权关系为强拥有；局部绑定、返回值、闭包捕获和更长生命周期容器存储都进入同一
  静态模型。跨线程传递保留 `CrossThread` 事实类别，待并发表面语法冻结后由后续阶段生产。
- `A -> B` 固定表示 A 必须先于 B 释放。释放计划先按强边拓扑排序，同一拓扑层按声明序号
  逆序、再按稳定值身份逆序；弱边不参与强图。强环静态拒绝，不能宣称引用计数会自动回收。
- 每个作用域和每类退出边（正常、返回、循环控制、错误、构造失败、动态检查失败、致命退出）
  都有独立计划；一条路径中同一值最多释放一次，已经转移到外层/调用方的值不在当前动作中。
- 动态或缺失类型采用保守 `HeapStrong`，同时生成 Runtime 检查；首期不创建堆对象、不执行
  引用计数、`Weak::upgrade`、`drop` 或异常语法。稳定诊断使用 `X06-LIFETIME-*` 编号、
  `message_id`、结构化参数和源码区间，展示文案由后续国际化层替换。

### 模块、包与依赖

- 除项目根的特殊配置文件 `config.xiao` 外，每个普通 `.xiao` 源文件形成一个模块。源文件是模块的规范来源，不要求维护 C/C++ 风格的独立声明头文件。
- 源码文件使用 Python 风格的绝对 `import` 表达实际模块依赖，不能把每一条文件间导入边都移到项目配置中。已冻结的完整语法、AST 和诊断见 [05A](05a-import-syntax.md)。
- 项目根直接作为源码根；子目录自动形成纯目录命名空间，不需要 `__init__.py`。根 `config.xiao` 不作为模块，嵌套目录中的 `config.xiao` 标记后续包边界并停止当前项目扫描该子树；点目录排除，符号链接不跟随，`target`/`node_modules` 当前不特殊排除。
- 目录命名空间本身不执行初始化代码；只有具体 `.xiao` 模块可以包含模块初始化行为。普通文件/目录段必须是大小写精确的 ASCII 标识符且不能是 Xiao 保留字；文件/命名空间同名和 ASCII 大小写折叠冲突直接报错。
- `import a.b` 默认绑定根名称 `a`，`import a.b as c` 绑定完整目标 `c`；`from a.b import name [as alias]` 支持多个选择项。导入可出现在顶层、函数、分支和循环体；块内绑定不泄漏，顶层选择导入可以再导出。
- 相对导入、通配导入、动态字符串导入、括号续行和跨逻辑行导入不支持。模块/命名空间限定符不是一等运行时值，不能单独读取、赋值或放入容器。
- 目录命名空间限定到具体文件时记录延迟使用边；直接导入边按依赖优先形成初始化计划。循环依赖立即报错并且初始化计划为空；Runtime 只在执行到导入语句时初始化目标，同一具体模块至多一次。
- 包内符号默认不向包外公开，公共模块与公共符号由项目根目录的 `config.xiao` 集中列出；配置读取、外部包和锁文件仍由 05-D/11A 实现，不能由本地 resolver 提前解释。
- 外部 Xiao 包必须提供以 `.xiao` 源文件和声明式包元数据组成的规范源码产物。发布者可以同时提供匹配特定 Xiao/Runtime ABI、目标平台和构建条件的预编译 `.xiaoc` 模块作为可选加速产物；预编译产物不能取代源码级模块契约，找不到兼容变体时必须能够回到源码构建。

### 虚拟环境与包管理

- 虚拟环境创建器、同步器和包管理器统一集成在 `xiao` 命令中，不要求安装第二套管理程序。
- `xiao venv` 创建并激活逻辑名称为 `venv`、目录为 `.venv` 的默认环境；`xiao venv dev` 等带名称形式使用同一个名称作为逻辑名称和目录名，例如 `dev` 对应目录 `dev`。
- `xiao sync` 在没有目标环境时先创建环境，再按项目配置安装依赖并激活；已有环境时补齐缺失依赖后激活。
- `xiao install [路径]` 与缩写 `xiao i [路径]` 直接安装指定 `config.xiao` 声明的依赖，不等同于 `sync`。路径可以是项目目录或配置文件；省略时在终端当前目录查找 `config.xiao`。
- `install`/`i` 不创建或激活环境：已经激活环境时安装到该环境，未激活时安装到全局环境。
- 自动激活通过一次性初始化的 Shell 钩子修改父终端状态。激活后在原提示符前增加绿色的 `$环境名$` 前缀，两个 `$` 与环境名均为绿色；原提示符的路径、符号和其余配色保持不变。
- `xiao run`、`xiao build` 和 `xiao test` 仍必须能直接定位项目环境，不把用户手工执行激活命令作为运行前提。
- 项目环境不重复保存每一份依赖源码，而是引用全局的内容寻址缓存。相同依赖内容只需保存一次，不同项目的锁定结果仍彼此隔离。
- 全局环境只是未激活时 `install`/`i` 的依赖选择与映射，不是另一份包源码仓库；项目环境和全局环境都引用同一不可变内容缓存。
- 全局包缓存保存经过完整性校验的不可变内容；构建产物缓存与源码包缓存分离，并按工具链、目标平台和构建条件隔离。
- `config.xiao` 复用 Xiao 的词法器和语法基础，但只允许不可执行的声明式子集。读取依赖配置不得执行函数、控制流、模块导入或项目代码。
- 05-D 已冻结独立 `ConfigDocument` 配置模型：`[project]`（非空 `name`/`version`）和
  `[exports]`（公开名称到项目根相对 `.xiao` 路径）是首版专属语义；字符串、数值、布尔值、
  递归数组和字典表是首版静态值范围。`[CLI]`、`[language]`、`[debug]`、`[VM]`、依赖、
  工具链和构建表只作为保留静态节点，具体字段语义由后续阶段冻结。配置未知顶层表、严格
  字段、重复键/表头和所有可执行构造必须以 `X05-CONFIG-*` 诊断拒绝；源码 `.xiao` 的
  `[main]` 不属于配置解析。
- 11A-E0 已冻结环境激活基础协议：初始化命令是 `xiao shell-init <shell>`，只输出由用户显式求值的一次性幂等钩子且不自动修改 profile；取消激活命令是 `xiao deactivate`，钩子保存原提示符并在重复激活、切换或取消时先移除旧前缀再恢复原值。Bash 和兼容 PowerShell 5.1 的 PowerShell 是 E0 基础样本；`cmd.exe` 走不支持钩子的降级路径，不修改注册表，也不宣称已自动激活。非 TTY、`NO_COLOR` 或 `--color=never` 只输出纯文本 `$环境名$ ` 前缀，完整 Shell 矩阵与 profile 安装留给 E3D。
- 11A-E0 已冻结环境目录基准：`venv`/`sync` 从向上发现的 `config.xiao` 所在项目根创建目录，找不到配置时回退当前目录；无参数环境为逻辑名 `venv`、目录 `.venv`，显式名称同时作为逻辑名和目录名。
- 11A-E0 的配置指纹消费已经规范化的 `ConfigDocument`，采用版本化、带长度边界的类型化规范编码，不采用 RFC 8785/JCS；源码区间和绝对路径不得进入配置指纹。RFC 8785/JCS 仍保留给后续包源索引场景。
- 11A-E1 已冻结全局环境与全局内容缓存的实际位置：统一使用 `XIAO_HOME`；未设置或为空时回退到用户主目录下的 `.xiao`，相对路径拒绝，不可写时报告稳定诊断且不静默改用其他位置。源码包对象位于 `cache/objects/source/sha256/<前两位>/<digest>/`，全局环境位于 `envs/<name>/`；`.xiaoc` 等其他对象保留独立命名空间。
- 依赖锁文件提供完整依赖图，项目环境由配置与锁文件物化且必须可删除重建。常规命令不能悄悄升级锁定版本。
- `xiao sync` 的语义**对标 `uv sync`**：以锁文件为准把环境同步到目标状态，**默认移除环境中不属于依赖集的多余包**；反向开关保留多余包。缺少目标环境时先创建再同步。
- 锁文件在 `sync` 需要重新求解时**自动创建或更新**。这是上一条「不能悄悄升级」的**受控例外**：写入必须落进锁文件、可 diff、可审计，不允许只改环境不改锁文件。
- 11A-E2A 将项目根锁文件冻结为与 `config.xiao` 同级的 `xiao.lock.json`：`lock_version: 1` 的 JSON 保存根配置 E0 指纹、完整依赖图、每个包的源身份/版本/源码 SHA-256 摘要及直接依赖边；未来版本稳定拒绝。本地 `path:` 源身份含绝对路径，锁文件不能跨机器直接复用。锁文件与其同目录暂存文件是生成产物，不参与 E1 源码摘要。
- 11A-E2A 冻结 `sync` 的环境选择顺序为已激活环境 → 已有 `.venv` → 按项目根发现规则创建 `.venv`；E2B 接线必须把激活环境路径暴露给子进程，不能只读提示符名称。
- `sync` 必须提供两个**禁止写入锁文件**的模式：`--locked` 要求锁文件已是最新，若需要变动则**以非零退出码失败并指出原因**；`--frozen` 只使用现有锁文件，缺失或不一致直接失败。CI 与可复现构建必须使用其中之一，否则每次同步都可能悄悄改写锁定版本。
- 锁文件的**预编译变体与目标条件维度暂缓**：字段保留但首版允许为空，按单目标与源码产物物化。该维度依赖第 14 阶段的 `.xiaoc` 真正存在，现在冻结会定错；届时再定表达方式与切换平台时的补装/重建语义。
- Xiao 的用户级依赖模型采用语言包与项目环境语义，不采用操作系统级全局包数据库；本地体验以锁文件优先、并行元数据查询/下载和全局内容缓存实现接近 `uv` 的快速同步。
- 包源采用类似 apt 的可配置多源模型，不要求所有依赖集中在同一服务器。一个项目可以配置多个相互独立的官方、社区、企业、局域网或本地包源；符合 Xiao 包源规范的静态站点或 GitHub 仓库也可以成为包源。
- 所有包源通过统一的声明式源协议向解析器提供规范化包名、版本、依赖、源码产物、可选预编译变体、目标/Runtime 条件和完整性信息。包源可以使用不同传输适配器，但不能迫使依赖解析器为每种来源建立不同语义。
- 锁文件必须记录每个依赖实际选中的源身份、不可变版本或提交引用及内容摘要。多个源出现同名包时，依赖显式指定的源优先；未指定源时按 `config.xiao` 中源的书写顺序逐源尝试。不得把不同源的候选放在一起比较版本号后选择“最高版本”；在既定源优先级、约束和锁定信息仍无法得到唯一结果时，必须直接报歧义错误，不能依赖网络返回顺序或遍历偶然顺序。
- 用户首次配置源路径，或修改源地址、源身份和源顺序后，包管理器必须使旧联邦视图失效，并尝试读取每个已配置源的最新可用索引快照；各快照的包元数据随后合并为一份本地联邦源索引。未改变源配置且锁文件/快照缓存仍有效时可以走离线快速路径。这里的“最新”指每个源的最新快照（完整清单或同一快照的一致分片集合），不是只保留每个包的最高版本；为支持版本约束回溯，索引保留源提供的全部可用版本元数据，包正文仍按需下载。联邦索引必须保留源身份、配置序号、快照标识/摘要和候选来源，不能因合并而抹掉来源审计信息。**源列表的内容变化同样属于配置变化**：配置指纹必须同时保存**整个列表的摘要**与**按最终优先级排列的规范化源序列**——只存 `source_id` 集合会丢掉顺序、重复项与导入来源，而上游增删源若不进指纹，就会静默复用旧联邦索引，绕过失效规则。
- 源不可达时，若有效锁文件和完整缓存足以复现结果，可以离线继续；若某个可能影响选择的源没有可用快照，不能把它静默当作空源、改写源顺序或转而选用后续源，必须给出源不可达或结果不确定的明确诊断。
- 首个远程包管理闭环禁止包提供或执行任意安装前、安装后脚本。依赖元数据解析和环境安装均不得执行包代码；以后需要原生扩展时，只能进入另行冻结的声明式、隔离构建流程。
- 包源有**三个必须分开的概念**，不得合并成一个 `name`：**稳定的 `source_id`**（`kind + ":" + 规范化 location`，如 `git-index:github.com/example/xiao-packages`；协议与 host 小写、去默认端口、去路径尾部斜杠与 `.git` 后缀）、**配置内用于引用的 `alias`**、**纯展示用的显示名**。**依赖只能引用 `alias` 或明确的 `source_id`；显示名不参与身份，也不能被依赖引用**。`alias` 冲突默认报错，只有用户显式改名或建立映射时才接受。分开的理由：改显示名不得让联邦索引缓存失效，而依赖绑定又必须有一个稳定、可校验的引用名。
- 包源索引以**规范化静态 JSON 为唯一权威**，对外展示与人工 review 一律以它为准。可选的 Protobuf 视图只是**派生的加速层**，必须在自身携带所依据的 JSON 摘要；客户端读到先校验摘要，**不匹配、缺失或过期时一律回退 JSON**。不得把加速层当作第二真相源，也不得在它不可用时视为空索引。加速层由**源侧**在包列表更新后重新生成，客户端不参与生成。
- 源协议版本采用与仓内 AST 适配器协议相同的姿态：**客户端遇到不认识的协议版本必须拒绝该源并给出明确诊断，不得尽力而为地解析或静默降级**。静默降级会把「源格式变了」伪装成「包不存在」，而这类错误在依赖求解里极难定位。
- 依赖求解的**解析键是「规范化包名 + 版本 + 源身份」**——求解阶段不得下载正文，因此不能用内容摘要当键。**内容的同一性由摘要（SHA-256）判定**，但那是**内容对象同一性**——字节相同只说明是同一个内容对象，**不代表相同的包名、版本或依赖语义**。它支持跨源缓存去重，**不替代锁文件里的逻辑包身份**；摘要不同则在锁文件中分别保留来源与审计信息。
- 包源索引的 JSON 规范化**采用 RFC 8785（JCS）**，不自造规则：UTF-8 编码、拒绝重复键与非 I-JSON 数值、超出安全整数范围的值以字符串表达，摘要一律对**规范化后的字节**计算，规范化在**源侧生成时**完成。没有这条，「派生层携带所依据的 JSON 摘要」就是未定义的——改缩进、换键序、`1.0` 写成 `1` 都会让字节变化而摘要对不上。**RFC 是规范依赖，不要求运行时依赖外部服务或库**；Rust 与 TypeScript 两侧必须共用同一组规范化测试向量——N 个实现各写一套规范化正是本仓登记在案的头号病史。
- **包源列表是与包源索引不同的一类产物**：前者描述「有哪些源」，后者描述「有哪些包」。两者不得共用 schema，也不得互相嵌套。
- 导入源列表的**最终顺序是一个确定算法，不是一条原则**：**先全部直接声明的源（按书写顺序），再各导入列表的源（列表本身按配置中的书写顺序，列表内部按该清单的顺序）**。只写「导入的源不得压过显式源」不够——它与「按 `config.xiao` 书写顺序」在导入项写在显式项之前时会给出**不同结果**，必须由这条算法裁决。清单内与跨清单的 `alias` 冲突必须显式解决，不得静默覆盖。
- **展开结果写入一份可提交、可 diff 的源清单**：配置保留导入引用**及其摘要**，清单记录完整展开结果——每个源的来源、`alias`、最终顺序与冲突处理。配置里的间接引用不得是唯一记录，否则用户 review 自己的项目时看不出**实际优先级**。
- E3A 冻结源声明语法：`[sources]` 下每个具名条目为直接源 `{kind, location, alias?, display?, protocol?}`（条目名为默认 alias）或导入列表 `{list, digest}`；直接源优先于所有导入源。源列表是独立于包索引的 JSON 清单，索引使用 `snapshot.json` 与 `index/<package>.json` 分片。源身份保留传输协议以免 HTTP/HTTPS 意外合并；只规范协议与主机大小写、默认端口、尾斜杠和 `.git` 后缀。E3A 只提供静态解析和本地目录适配器，不实现远程获取或配置注释写回。
- **清单本身必须可被摘要钉住**，上游增删源不得悄悄生效；源列表的更新走**显式命令**，不得由普通 `sync` 静默完成。

## 一级工程目标：确定执行与内存模型

### 06-B Runtime 对象边界（已冻结）

- Runtime 对象头保持私有不透明布局，至少记录类型标签、布局摘要、强/弱计数、释放钩子和销毁状态；公开层只允许安全句柄查询、克隆、降级和升级，不暴露裸指针。
- 引用计数策略通过可插拔接口隔离；06-B 首版只实现单线程非原子计数，Strong/Weak 句柄拒绝跨线程传递。最后一个强句柄归零时立即执行载荷释放钩子并移除隐式弱引用，最后一个弱句柄归零才释放对象头。
- `[Table]` 单例与 `[[Table]]` 实例必须消费 05-C 已验证的 `TableSignature`，运行时不重新推断成员类型、可见性或生命周期契约。表状态固定经过 `Allocated -> FieldsInitializing -> InitCompleted -> Usable -> Dropping -> Released`；`init` 失败回滚，`drop` 只执行一次。进入 `Dropping` 后，`drop` 钩子仍可只读观察已存活字段，但不能写字段或改变签名。
- 错误展开顺序固定为 `finally -> drop -> catch/继续传播`。主错误、原因链和结构化字段必须保留；清理错误追加到 `suppressed`，不能覆盖主错误。Runtime 错误码保持稳定，展示文案由后续国际化层渲染。
- 06-B 只实现标量、`str`、表和释放计划驱动器；数组、元组、集合、字典、选择器、VM、LLVM、并发和调试窗口均为后续阶段，禁止把占位表示写成完整能力。

## 一级工程目标：确定优化与产物方向

### 已确认的产物目标

- Xiao 需要同时覆盖编译路径和解释路径的优化能力；首组对外优化级别采用 C 风格的 `-O0`、`-O1`、`-O2`、`-O3`。`xiao run`、REPL、普通 `xiao build` 和 `xiao build -xar` 在没有任何显式配置时都采用内建默认 `-O0`。
- Xiao 字节码的公开文件扩展名为 `.xiaoc`。它承担“优化后字节码”产物的定位，类似旧版 Python `.pyo` 的用途，但不兼容 Python 字节码格式；每个 `.xiaoc` 文件对应一个模块。
- 字节码执行路径默认生成、验证并缓存 `.xiaoc`。普通源码模块进入全局内容寻址缓存；依赖可变会话状态的 REPL 片段只进入会话缓存，只有形成独立完整模块后才能提升到全局缓存。普通原生 `xiao build` 仍默认 `-O0`，但不为 LLVM 不消费的模块强制额外生成 `.xiaoc`。
- `.xiaoc` 采用 Xiao 自有的确定性分段二进制格式：保留“固定文件头 + 分区目录 + 可跳过的可选分区”架构，正文按类型分区，不直接序列化宿主语言内存结构，也不把整个文件编码成 Protobuf。固定指版本内的字段职责和边界契约，不承诺 48 字节文件头或 40 字节目录项；具体字段宽度、顺序和扩展编码待字节码指令集稳定后冻结。`.xiaoc` 内部不压缩；压缩由 `.xar` 容器负责。
- 不含 FFI、目标 CPU 指令或平台资源的 `.xiaoc` 默认标记为平台无关；一旦使用平台能力，模块和包含它的 `.xar` 都必须显式记录目标约束，不能假装跨平台。
- 字节码可以进一步打包为 ZIP/ZIP64 兼容的 `.xar` 归档；目标体验类似 `.jar`，用户能够双击归档并由已安装的 `xiao` 启动运行。归档包含项目使用的外部/第三方依赖，但不包含由 Xiao Runtime 随工具链提供的官方依赖（例如标准库）；没有安装 `xiao` 或没有建立文件关联时，双击不能运行。
- 字节码对象采用内容寻址：对最终规范化 `.xiaoc` 的完整文件字节计算 `SHA-256`，使用完整的 64 字符小写十六进制摘要作为文件名主体。摘要不写入自身被散列的文件；缓存文件名或 `.xar` 索引提供期望摘要。
- 二进制索引首版采用 Protobuf（Protocol Buffers）。每个 `.xar` 固定只有一个归档索引 `META-INF/xiao/index.pb`；本机全局内容缓存另有一个逻辑缓存索引，首版不增加项目级 Protobuf 索引。Schema、版本和确定性序列化规则由 Xiao Runtime/工具链提供。
- `.xar` 不要求脱离 `xiao` 环境自解释或独立运行。通用 ZIP 工具可以读取物理成员，但归档入口、依赖、模块身份和 Xiao Protobuf 字段含义由 `xiao`/Xiao Runtime 的内置 Schema 与加载器解释；归档不重复携带 Protobuf descriptor，也不自包含 Xiao Runtime。
- `xiao build -xar "<源路径>" [-O0|-O1|-O2|-O3]` 是打包字节码归档的正式命令；源路径可以是 `config.xiao`、包含 `[main]` 的 `.xiao` 文件，或任意可独立打包的 `.xiao` 脚本。优化参数可以省略，此时按配置或内建 `-O0` 处理。`xiao -xar "<归档路径>"` 是运行 `.xar` 的正式入口。

文档中的 `-O<级别>` 是占位写法，实际参数为 `-O0`、`-O1`、`-O2` 或 `-O3`；用户示例中的 `-Ox` 表示将 `x` 替换为其中一个数字，不是固定的字面参数。

`-O0` 表示不运行可选的语义优化 Pass，不表示跳过类型检查、生命周期分析、字节码降低、规范化、格式验证或安全校验。显式命令行或 `config.xiao` 可以覆盖内建默认值；两者同时存在时的最终优先级仍需在 CLI 阶段冻结。

标准 `.xar` 只打包显式声明的应用资源。每个 `.xiaoc` 默认保留生成错误回溯所需的紧凑源码位置映射，但不嵌入源码正文或完整调试符号；后两者只能通过以后冻结的显式调试打包选项加入独立内容寻址对象。归档内所有模块与资源都使用固定的摘要路径，由唯一的 Protobuf 索引恢复逻辑模块名和资源路径。

### 不可突破的工程边界

优化只能改变性能、体积、启动时间或编译时间，不能另造一套语言语义。字节码与 LLVM 必须共享第 08 阶段的类型化 IR 和语义约束；溢出错误、布尔奇偶加减、求值顺序、动态检查、随机选择、容器顺序、模块加载、引用计数、`drop` 和错误诊断都不能因优化被静默删除或非法重排。

优化后的 `.xiaoc`、内容寻址对象和 `.xar` 均须先完成格式、版本、依赖/Runtime 条件和完整性验证，再交给虚拟机运行。若未来增加 JIT 或运行时指令特化，其可变缓存不能原地改写不可变的公开 `.xiaoc` 文件。

JIT、PGO、LTO、跨模块特化、数字签名和自包含 Runtime 不作为一次会话或首个可运行闭环的隐式前置；它们必须各自拥有独立的设计、实现、测试和发布门槛。

优化、字节码产物、内容寻址索引和 `.xar` 归档的实施顺序与 SOP 见 [13. 优化契约与统一管线](13-optimization-contract.md) 至 [19. 优化、兼容性与发布验收](19-optimization-release.md)。这些后置阶段不阻塞第 09、10 阶段的未优化最小闭环。

### 绝对无追踪式 GC

Xiao 不使用追踪式垃圾回收。内存方案由以下部分组成：

- 作用域退出时确定性执行资源释放。
- 发生逃逸的值自动从栈提升到堆。
- 逃逸堆对象使用引用计数管理。
- 可能形成环的边使用 `Weak` 弱引用；强拥有图必须保持无环，静态发现强环时拒绝。当前规则是 DAG，不额外收紧为森林；共享拥有关系仍然允许。Xiao 源码中的 Weak 构造语法仍未开放。

### 并发安全边界

- 数据竞争不属于合法且可依赖的程序行为。
- 编译器能够证明存在数据竞争时必须拒绝编译。
- 竞争只能在运行时确定时，运行时必须报告明确错误，不能静默继续。
- 线程、任务池、`async`/`await` 或 Actor 等具体并发模型尚未确定。

### RC、强环与并发后置边界（21A）

- 06-B 当前的普通 `StrongHandle`/`WeakHandle` 是单线程、非原子句柄；`Rc` 标记只负责让宿主 Rust 类型不自动实现 `Send`/`Sync`，不代表已经存在 Runtime ID 或语言级线程亲和协议。默认路径保持非原子 RC，但不把“永远不变”写成未来 ABI 承诺。
- `xiao-lifetime` 的 `CrossThread` 是挂在具体 `ValueId` 上的生命周期事实，不是类型能力。并发表面冻结前不得通过名称启发式产生；未来的可发送/可共享能力必须由独立的类型或 IR 契约表达。
- 当前 `RefCountStrategy` 只提供 checked 算术，不能直接承载原子计数存储、弱升级竞态、载荷同步或对象头回收。未来共享句柄必须经过独立的对象头/句柄设计，不得仅增加策略枚举值或改造所有普通句柄。
- `Arena` 不豁免 RC 强环。若以后需要区域分配，必须以独立区域/存储模型表达区域内引用，不能让 `StrongHandle` 在区域内形成可泄漏的强环。
- 07-D 只研究候选并发执行机制；完整并发实现必须在 B0 字节码和 N0 原生闭环之后建立新的独立阶段。`async`、`await`、Actor、发送/冻结/共享 API 在该阶段之前都不是正式语言契约。

### 07-D 研究深度记录（2026-10-21）

07-D 当前的成本矩阵、边界候选和取消清理方案属于桌面定性研究与伪代码比较，不是已经
测量的性能、内存或调度成本，也不构成执行模型、对象头、Runtime ABI 或标准库接口裁定。
若后续要据此冻结模型，必须先在独立原型中定义测量方法、运行环境、重复次数、错误/清理
观测字段和可复现实验结果；在此之前不登记新阶段代号，不把候选名称写入语言契约。

### 07-D 并发模型裁定（2026-10-22）

星崽已对 07-D.1 的八项入口问题作出选择。这些选择是研究/原型输入，不是语言语法或
公开 API：

1. **执行机制**：采用 **OS 线程/任务池**方向；首个动作是**最小 OS 线程原型**，不直接
   承诺完整任务池。
2. **`Send`/`Sync`**：采用**候选 A（递归能力推导）**；普通句柄、可变容器和动态值按
   递归规则拒绝或要求显式边界。
3. **`CrossThread`**：**拆分为任务边界与线程边界**两个生命周期事实；IR、诊断和
   lowering 必须分别记录。
4. **值传递**：**深拷贝先行**；版本化序列化后置，冻结共享继续研究。跨线程默认边界值
   仍以深拷贝为准。
5. **取消与清理**：采用 07-D §10.4 的顺序：标记取消 → 停止接纳 → 关闭或 drain 边界
   队列 → 等待已运行任务到达安全点 → 执行 finally/drop → 释放边界值 → 汇总主错误与
   suppressed 错误。
6. **原子共享句柄**：**首阶段实现**，范围是**只读共享 + 共享可变**。共享可变只能通过
   显式的共享句柄进入，不能把普通 `StrongHandle`/`WeakHandle` 隐式跨线程；对象头、
   锁、取消、清理顺序和跨平台 ABI 必须在同一轮原型中一起验证。此项细化了上一问
   “共享可变暂缓”的范围：默认值传递仍是深拷贝，共享可变只走显式共享句柄。
7. **官方库结构**：模型冻结后再评估；首阶段不承诺链表、树、观察者或图。
8. **研究深度**：先做**最小 OS 线程原型**再决定；原型必须覆盖线程入口、深拷贝、
   拆分后的 `CrossThread` 事实、只读和共享可变原子句柄、取消/清理和错误汇总，并记录
   可复现的测量结果。

### 错误模型与诊断

- 首版采用“结构化可恢复错误 + 致命 `panic`”的混合模型。可恢复运行时错误使用统一 `XiaoError`，由 `try`、`catch`、`finally` 和 `raise` 传播与处理；虚拟机不变量损坏、损坏字节码、无法安全建立错误对象的内存耗尽和硬件异常进入致命终止路径，普通 `catch` 不得伪装恢复。
- 07-A 将统一错误核心放在 `xiao-diagnostics`。`xiao-runtime` 只能通过别名/重导出兼容旧调用点，不得长期维护独立 `RuntimeError` 结构；既有 `X06-RUNTIME-*` 错误码保持不变，不做统一重编号。致命故障使用独立 `FatalError` 和 `X07-FATAL-*` 编号空间，普通可恢复错误处理器不能捕获恢复。
- 07-A 的统一帧模型固定包含模块、函数、源文件、`SourceSpan`、用户/Runtime 帧标记，并预留字节码偏移、原生地址和内联深度；字节码与 LLVM 后端以后只填充同一模型。
- 07-A 报告器只提供语言无关的 `ReportRecord`、默认文本渲染和可替换 `MessageRenderer` 接口，不直接依赖 `xiao-i18n`，也不冻结 JSON 或其他序列化字节格式；11C 再接入实际语言目录。
- 错误对象至少保留稳定 `code`、错误类型、消息、源码位置、原因链、结构化上下文和可关联的调用栈；程序不能依赖错误文本进行判断。所有错误退出路径都必须执行确定性 `drop`，清理错误作为附加错误保留，不能覆盖主错误。
- `Result` 风格返回值和简化传播语法属于后续类型系统/泛型阶段，不阻塞首个可运行闭环。
- 显式 `-debug` 是强制的运行时诊断激活位。对 `xiao run`、源码快捷运行和 `xiao -xar` 等直接运行入口，程序开始执行用户代码前必须打开独立诊断窗口；`xiao build -debug` 与 `xiao build -xar ... -debug` 必须把该激活位、源码映射、诊断元数据和运行时钩子能力固化到产物，产物以后启动时无需再次传参也必须打开窗口。没有 `-debug` 的普通运行或发布构建不得因为 `[debug]` 配置而自动打开窗口。
- 诊断窗口由独立诊断进程承载，目标程序通过本地匿名管道或本地套接字发送结构化事件。调试版原生程序必须内嵌或随产物携带能启动该进程的组件，不得依赖 `xiao` 启动器；即使普通模式使用 GUI 子系统并声明不打开终端窗口，调试激活位也必须打开独立诊断窗口。诊断报告必须脱敏，不能改变程序标准输出、错误传播或退出语义。
- 诊断窗口状态栏的“报错数量”统计本次运行产生的全部结构化运行时错误事件，不因日志等级、是否捕获或是否展示而过滤；编译期诊断不计入。日志聚焦规则默认把匹配事件从总日志分流到指定文件，需要同时写入总日志时必须显式使用 `mirror`。

### 运行时配置

配置文件表达的是运行时配置，不是“原生程序必须运行在虚拟机里”。原规划中的 `gc_verbose` 名称与无 GC 目标冲突，后续应改成引用计数或内存释放诊断名称。`config.xiao` 的 `[debug]` 表负责保存诊断默认值，包括终端日志等级、文件日志等级、日志目标、堆栈详细程度和模块/源码文件聚焦规则；它只能控制已经激活的诊断会话如何筛选和落盘，不能替代 `-debug` 激活窗口，也不能关闭调试产物的强制窗口。具体字段白名单由 CLI 阶段冻结。

### 国际化与语言包

- `config.xiao` 支持 `[language]` 表；首版规范字段为 `locale`，用于切换 Xiao 工具链和运行时系统文案的呈现语言。项目级配置和全局 `config.xiao` 都可以声明该表。
- 首版内置简体中文 `zh-CN` 和英语 `en-US`；输入别名 `zh`、`en` 规范化为对应标签。项目语言优先于全局语言，二者都未设置时使用内置 `zh-CN`。

### CLI 技术栈

- `xiao` CLI 的命令解析、配置调度、环境管理、终端渲染和交互式解释器前端统一使用 TypeScript 编写。
- TypeScript 层只负责命令、配置、终端交互和进程/库边界，不实现第二套 Xiao 词法、类型、字节码或运行时语义。
- `xiao build` 生成的原生程序不能因为 CLI 使用 TypeScript 而依赖 Node.js 或完整 Xiao 工具链。
- CLI 面向 Windows、Linux 和 macOS 发布独立可执行程序，最终用户不需要另外安装 Node.js；具体嵌入或打包工具属于实现选择。
- `xiao config [--global] <key.path> <value>` 是结构化配置修改入口；首个已冻结字段 `CLI.git.summary` 只接受布尔值，项目级与全局写法分别用于当前项目和全局配置。

### 核心实现语言与性能目标

- 字节码解释器（虚拟机）及其执行所需的 Xiao Runtime 核心统一使用 Rust 编写。执行栈、值表示、容器运行库、引用计数/`drop`、错误传播、诊断事件和模块加载等执行语义只能有这一份 Rust 实现；不能在 TypeScript、Python 或其他语言中再维护一个语义相近的解释器。
- 交互式解释器的终端输入、编辑状态和提示符仍属于 TypeScript CLI；用户代码的词法、类型检查、字节码执行和 Runtime 行为必须通过稳定的 Rust 核心接口完成。CLI 与 Rust 核心之间的进程协议或库 ABI 在对应阶段单独冻结，不能把任一方的内部对象当成跨层契约。
- 本决策明确冻结的是“字节码执行核心使用 Rust”。编译器前端、共享优化器和 LLVM 原生后端是否也统一使用 Rust，暂不由这一条自动推定；它们必须继续遵守类型化 IR 和后端接口，具体实现语言在各自阶段确认。
- “Xiao 程序性能至少达到 Java 以上”是发布性能目标，不是 Rust 选型本身能够自动保证的语言语义。性能声明必须建立在固定硬件、操作系统、输入规模、线程数、热身/重复策略、Java 基线版本和 Xiao 优化配置上的可复现实验；启动时间、吞吐/延迟、峰值内存和产物体积分别记录，不能用单一数字替代。
- 已确认性能目标只以 `xiao build` 的 LLVM 原生模式为标准；默认 `-O0` 不是性能发布基线，具体发布优化配置由第 19 阶段冻结。`xiao run`/REPL 的 Rust 字节码 VM 仍需测量启动、吞吐和内存，但其结果不直接作为“达到 Java”发布门槛。若未来要对解释路径设硬门槛，必须另立分层编译/JIT 阶段。

### 原生平台适配顺序

- 目标平台的正式适配顺序冻结为 **Windows → Linux → macOS**。每个平台完成后必须保留前一平台的语义、ABI、产物和 CLI 回归矩阵；后续平台不能通过修改公共 IR 或 Runtime 语义来“迁就”平台差异。

- 平台相关实现只能放在平台适配层，语言核心、类型化 IR、字节码格式和错误码保持跨平台不变。平台顺序是实施顺序，不限制从早期开始编写平台无关代码或准备 CI。

### 终端交互式解释器

- 无参数运行 `xiao` 进入单行交互模式，回车立即提交当前输入。
- `xiao --inLF` 直接进入多行编辑模式；`xiao --inLF "<file.xiao>"` 在多行模式中打开现有 Xiao 源文件供编辑和运行。
- 当前环境中的所有已安装包都对会话可用。启动时只把包根名称登记为可直接引用的延迟命名空间，不要求用户逐个书写 `import`，也不执行模块初始化或载入完整包内容；首次真正引用包中内容时才加载对应模块。
- 自动登记的包根名称发生冲突时不按扫描顺序选取胜者：报错并要求显式 `import` 指明来源。
- 延迟加载失败不进入模块成功缓存；下次引用重新尝试，成功加载的同一具体模块在同一个 VM 运行实例中至多初始化一次。
- 包视图和接口元数据查询只能读取，不能执行包代码；运行时加载由 VM 首次引用触发，不由 CLI 在 `run` 前预加载。

- 多行模式支持保留换行与缩进的大段粘贴。逻辑行使用五字符宽、右对齐的行号和 `|`，终端软换行只显示空白行号区及 `|`，不会创建新的逻辑行。
- `!inLF!` 在会话中进入多行模式；`!outLF!` 或 `Shift + Enter` 进入运行确认阶段。按 Enter 执行当前缓冲区；按 Esc 取消运行并无损返回编辑界面。

I1b 确认态只接受 Enter 执行与 Esc/Ctrl+C 取消，不修改源码；执行结束或中断后保留缓冲区，
光标回到执行前位置，覆盖模式与程序内剪贴板保持不变。执行输出采用追加式终端输出，
输出段不清屏，结束后重新绘制编辑区。运行内存摘要表示本次执行中 Xiao Runtime
管理对象的峰值存活字节，不等同于进程 RSS。
I1b 按现有长度前缀进程协议完成运行、输出和取消；执行期临时退出 raw mode 以恢复
终端 SIGINT。`xiao-core` 的 stdin 仍专用于协议帧，语言级 `input()`/交互输入需要后续
独立的 VM I/O 通道，不在 I1b 把原始输入字节混进协议流。

## 一级工程目标：建立实现顺序

### 必须先完成的基础

1. 先按 [00A. 工程框架与目录布局](00a-project-layout.md) 建立代码目录、依赖方向、README 和文档覆盖率门槛。
2. 再建立编译器工程骨架、源码游标和位置模型。
3. 再完成只包含标识符、整数、`=`、换行和文件结束的最小 Token 流。
4. 分批补全 UTF-8、字符串、运算符、注释、缩进和表头词法。
5. Token 流稳定后才实现最小语法树，不把解析器塞进 Token 最小里程碑。
6. 名称解析和静态标量类型稳定后，再逐步实现函数及基础容器。
7. 集合、复杂运行时、字节码和 LLVM 都属于更后的独立子里程碑。

### 01 阶段词法与源码位置冻结项

- 源文件必须先通过 UTF-8 校验；非法字节以 `X01-SOURCE-001` 拒绝，不用替换字符继续扫描。
- 源码位置同时保留原始 UTF-8 字节偏移与一基行列号；列号按 Unicode 标量值计数，LF 和 CRLF
  都只产生一个逻辑换行，CRLF 的区间仍覆盖两个原始字节。
- 普通标识符采用 `[A-Za-z_][A-Za-z0-9_]*`；反引号允许任意 UTF-8 名称，包裹关键字时按名称处理，
  且定义和引用必须保持反引号形式一致。
- 每个 Tab 在编译和解释时统一展开为四个空格；空格与 Tab 混用只要展开后的缩进层级一致就允许。
- 语句只由换行结束，首版不支持显式分号；文件末尾没有真实换行时不补逻辑换行。
- L0 最小 Token 只包含标识符、十进制整数、`=`、换行、EOF 和 Invalid；整数允许前导零，正负号
  在后续运算符词法中作为独立 Token。
- L0 非法字符以 `X01-LEX-001` 记录并继续扫描；Token、诊断和后续 AST 统一使用 `SourceSpan`。
- 空值关键字冻结为 `none`，但在 L1 基础词法扩展时加入，不阻塞 F0/L0。
- L1 的字符串字面量同时支持单引号和双引号；原始引号保留在 Token 文本中，基本反斜杠转义
  （反斜杠、引号、换行、回车、制表、空字符及常见控制转义）在词法层验证。未闭合字符串使用
  `X01-LEX-002`，不支持的转义使用 `X01-LEX-003`，错误后继续扫描。
- L1 的十进制浮点支持带小数点的形式（包括 `.5` 和 `1.`）及带可选正负号的 `e/E` 指数；
  指数至少需要一位十进制数字，结构不完整使用 `X01-LEX-004`。数值位宽、精度和溢出留给第 02 阶段。
- `true`、`false` 和 `none` 分别产生布尔/空值字面量 Token；控制流、导入、转换和已确认的标量
  类型名称产生 `Keyword(KeywordKind)`。保留字区分大小写，`True` 等大写拼写仍是普通名称。
- L1 的基础运算符与分隔符采用最长匹配：`//=`、`**=`、`!?`、`!=`、`<=` 和 `>=` 各自产生
  一个 Token；`/` 暂不在词法层区分除法与嵌套路径，`+` 也不在词法层特殊解释为集合并集。
- L2 反引号名称产生独立的 `BacktickIdentifier` Token，内容允许任意合法 UTF-8 和空格，不能
  跨物理换行；仅允许 `\\`` 与 `\\\\` 转义，未闭合和非法转义分别使用 `X01-LEX-005` 与
  `X01-LEX-008`。
- 普通 `#` 注释跳过到当前物理换行，不产生 Token；`###` 到下一个 `###` 是一个完整的
  `DocComment` Token，同一行形式也有效。文档注释内部的换行属于该 Token，不额外产生内部
  `Newline`；未闭合使用 `X01-LEX-006`。
- L2 保留每个物理 `LF`/`CRLF` 的 `Newline` Token。行首 Tab 展开为四个逻辑空格，代码层级固定
  为四空格倍数；真实代码行根据缩进栈产生 `Indent`/`Dedent`，空行、注释行和分隔符内部不改变
  缩进栈。非法宽度使用 `X01-LEX-007` 并向下归入最近已知层级，EOF 先发剩余 `Dedent` 再发 `Eof`。
- 圆括号、方括号和花括号的开闭顺序由词法器记录，以控制分隔符内部缩进；不匹配关闭符使用
  `X01-LEX-009`，EOF 未闭合起点使用 `X01-LEX-010`。这些诊断不替代后续语法分析。

### 01/P0 严格最小 AST 与解析器冻结项

- P0 的程序根节点由多条按源码顺序排列的顶层语句组成；每个 AST 节点和诊断都复用原始
  UTF-8 字节偏移的 `SourceSpan`。程序区间覆盖完整源码，语句区间不包含结尾换行。
- P0 只接受整数、浮点、字符串、布尔值、`none` 五类字面量，以及普通 ASCII 名称和
  反引号 UTF-8 名称。独立字面量或名称可以成为表达式语句。
- 简单赋值的左侧必须是一个普通/反引号名称，右侧必须是一个字面量或名称；`+`、`-`、
  调用、索引、类型声明、`as`、`const`、容器、控制流和模块语法不在 P0 内。
- P0 不把字面量解码为 Rust 数值/字符串，也不执行名称转义；原始文本通过节点区间从
  `SourceFile` 读取。反引号名称的 `span` 包含首尾反引号。
- 连续文档注释和空行挂接到相邻后续成功语句；文件末尾孤立文档注释保留在程序根节点。
  普通 `#` 注释继续由词法层丢弃。
- 解析错误固定使用 `X01-PARSE-001` 至 `X01-PARSE-005`；错误恢复同步到 `Newline`、
  `Dedent` 或 `Eof` 后继续。`Indent` 在 P0 报告不支持代码块并跳过对应缩进区域，避免
  把未实现代码块误解释为顶层语句。词法 `Invalid` 不重复生成解析错误。
- `Parser::new` 先运行完整 L2 词法器，`Parser::parse` 返回程序根节点和合并诊断；即使有
  可恢复错误也尽量返回部分 AST。P0 API、快照和交接边界见 [01D](01d-p0-parser-implementation.md)。

### 后置能力

并发、JIT、包管理、FFI、完整调试器和高级泛型不能阻塞最小双模式闭环，应在核心语义稳定后加入。

## 已冻结补充

### 架构耦合硬约束

Xiao 全仓库禁止高度耦合。模块必须沿既定依赖方向通信，不得循环依赖、跨层访问私有
状态或在多个层复制同一语义。`xiao-syntax`、`xiao-types`、Runtime、后端和 CLI
必须通过最小、稳定、可测试的接口连接；实现文件应按单一职责拆分，中心门面只做
装配与重导出。新增模块必须在同一提交提供 README、允许/禁止依赖说明和架构检查用例。

该约束与单文件 2500 物理行上限都优先于短期代码复用便利。跨层依赖若确需例外，仍必须
先在本文件记录边界、理由、替代方案和移除计划，未记录的跨层依赖一律视为错误。

单文件行数若因硬耦合确实不能拆分，必须在源文件同目录提供
`<文件名>的硬耦合需要的说明.md`，并分别以“边界”“理由”“替代方案”“移除计划”四个
非空章节说明为什么不能拆、为什么不选替代方案、已经考虑的拆法以及何时移除豁免。只有
四段齐全时 `A0-SIZE-001` 才降为仍然可见的 `warning`；缺段、空文件或没有说明都保持
`error`。研究编码器的 `encode.rs` 与语法解析器的 `parser.rs` 已通过拆分解除尺寸门禁；
未来再次超标的文件仍必须优先拆分，不能用旁置说明掩盖可移除的耦合。

### A0 工程清单与质量工具

- TypeScript workspace 已冻结为 Bun：仓库根 `package.json` 显式登记 `cli/ts`、`tools/repo-check`、`tools/doc-coverage`，锁文件统一为 `bun.lock`，不采用不可审计的 glob，也不提交 npm/pnpm/Yarn 的第二套锁文件。
- 文档覆盖率已冻结为原生 AST 适配器：Rust 使用独立 `xiao-doc-coverage-rust` crate 的 `syn` AST，TypeScript 使用 Compiler API，由 TypeScript/Bun 统一 CLI 汇总；不以正则或统一 tree-sitter 作为 A0 回退。
- A0 的政策清单为 `tools/repo-check/repository.manifest.json`，模块代码/测试/UseDocs 关系为 `docs/module-registry.json`；两者与 Cargo/Bun manifest 三方交叉校验，检查器只读且不自动修复。

### C1 有序容器选择器冻结项

- 字典列键在一个容器内必须唯一；数字索引、键名索引或范围产生同一直接键的重复选择时，结果改用按选择顺序排列的元组，不能伪造重复键的字典列。
- 选择器测试和后端通过 `RandomSource` 注入随机源；`random.seed(value)` 接受非负整数语义值，静态值记录为 `RandomSeedPlan`，动态值登记 Runtime 检查。随机状态不在类型阶段推进。
- 选择器左值采用标量广播：标量复制到全部目标，右侧容器不逐项配对；随机目标、复合赋值和复杂根表达式拒绝。Runtime 必须先验证全部目标，失败时整次回滚。
- C1 范围端点按有序容器的深度优先路径排序，负索引按 Python 规则规范化，步长对每个选择项独立应用；范围不能穿过无序字典表。

### 04 函数与控制流静态闭环冻结项

- 函数定义关键字固定为 `def`；函数头不使用冒号，函数体完全由缩进界定。
- 参数支持普通位置/关键字、`/` 位置专用、默认值、裸 `*` 后关键字专用、`*args` 和
  `**kwargs`；参数和调用参数的展开只在 AST/类型阶段记录形状，实际展开留给 Runtime。
- 类型检查先预登记函数签名，再检查函数体，因此同文件递归和前向调用有效；无注解参数通过
  函数体、返回语句和调用点统一，整份程序收尾时仍无法推断才报错。
- 没有显式 `return` 值的函数统一返回 `none`；同一函数的所有返回路径必须统一类型。
- `if`、`elif`、`else` 和 `while` 条件只接受 `bool`，不把整数、字符串或容器隐式转换为真值。
  `for in` 接受已知数组、元组、集合、字典表、字典列或动态值；动态边界登记 Runtime 检查。
- `break`/`continue` 只能出现在最近循环内；函数边界重置循环深度，不能从嵌套函数控制外层循环。
- 无 `[main]` 时记录脚本入口；独立 `[main]` 表头记录工程入口。入口元数据不在本阶段生成启动函数，
  初始化和跨文件顺序留给模块/IR 阶段。
- 04 阶段只交付静态 AST、类型结果和 Runtime 检查计划，不实现执行 Runtime、字节码、LLVM、逃逸分析、
  闭包对象或生命周期释放。解析/类型诊断的 `code`、`message_id`、结构化参数和源码区间稳定，中文译文
  只是可替换预览。
- 04 阶段代码必须按解析、函数签名、控制检查和门面装配职责拆分，禁止把所有逻辑重新集中到单一检查器文件；
  后续消费者只能通过公开 AST、签名和检查计划接口连接。

### 05-A/B 本地模块静态闭环冻结项

- `xiao-syntax` 只负责 `ImportPath`、导入项、别名、`Statement::Import` 和可恢复诊断；
  `xiao-modules` 负责项目文件发现、命名空间、绑定、再导出和依赖图。两层不能互相访问私有状态。
- 模块路径段只允许 ASCII 标识符且大小写精确匹配；选择名称和别名可使用反引号 UTF-8 名称。
  相对、通配、动态字符串、括号续行和跨逻辑行导入均拒绝。
- 顶层导入可以进入模块接口并再导出，块内导入只在自身词法作用域有效；共享根命名空间的无别名
  导入可以合并，其他同名绑定报告冲突。
- 目录是纯命名空间，不初始化；导入/限定使用产生的图边和文件模块初始化顺序稳定可复现。循环
  依赖是错误，初始化顺序必须为空，不能交给 Runtime 或后端部分执行。
- 05-A 解析错误编号为 `X05-PARSE-001` 至 `X05-PARSE-004`，05-B 模块错误编号为
  `X05-MODULE-001` 至 `X05-MODULE-008`；所有诊断都保留 `code`、`message_id`、结构化参数
  和源码/模块上下文，展示译文可由后续国际化层替换。
- 05-A/B 已有 `d0_imports.rs`、`d0_modules.rs` 和 `tests/spec/06-modules` 规格；代码目录
  README、分层 UseDocs 和模块登记必须与实现同一提交。

## 待定决策

### 需要语言设计确认

- 动态变量的声明形式。
- 类型前缀同时用于标量槽和容器元素约束时，非字面量初始化及无初始化声明采用什么无歧义规则。

## 已冻结补充：E3B 工具链内部并发（11A-CONC）

- **判据**：改变某个并发机制若不会改变任何 Xiao 程序的语义，它属于工具链内部并发；否则属于语言级并发。E3B 的并行读源和跨进程缓存协调属于前者，不受 07-D 的语言级并发后置条件阻塞；本节不决定 Xiao 程序采用线程、任务池、`async`/`await` 还是 Actor。
- E3B 新增的并行读取使用 `std::thread::scope`；不新增并发 crate，不在工具链内部引入 `async`/`await`。此约束不追溯修改 `xiao-driver` 已有的 `std::thread`/`Arc` 用法。
- 并发上限必须是有依据的具名常量（建议 8），不得随源数量增长；超过上限分批读取，工作线程和在途读取在任一时刻均不得超过上限。合并前按 `config_order` 重排结果，不能用完成顺序决定候选优先级。
- 单源不可达、摘要不匹配或协议版本不受支持记录为该源状态，不妨碍其他源；缓存根不可写、锁无法获取或磁盘耗尽等本地基础设施失败则中止。当前阶段不额外引入取消协议；需要中止时先等待本批工作线程结束。
- 跨进程缓存锁沿用 `create_new` 的排他创建模式，按缓存条目而非缓存根加锁；陈旧锁回收必须有明确的判定规则，不能只凭等待超时，也不能依赖 Windows 能删除其他进程仍打开的锁文件。原子提交复用已有同目录暂存与 `atomic_write_file`，不引入文件锁 crate。实现与区分度测试归 E3B；完整依据见 [11A-CONC](11a-concurrency-model.md) §一。

## 已冻结补充：E3B 快速解析与缓存

- **四类缓存分离**：包元数据按 JCS 摘要放在 `cache/objects/metadata/sha256/`，正文复用 `cache/objects/source/sha256/`；快照以源身份的 SHA-256 分目录存历次不可变版本，用 `current.json` 原子替换当前指向；联邦视图以配置指纹及有序源序列摘要的 SHA-256 分层保存 `index.json` 并独立原子替换，旧单文件只读兼容。不得混用构建产物的 `objects/xiaoc/` 命名空间。
- **快速路径**：锁文件结构及配置指纹一致、锁文件钉住的快照身份与可能影响优先级的当前源快照及元数据相符、所有锁定正文对象存在且通过完整性校验，三者同时成立才能离线复用；未钉住源快照的旧锁仍能读取但不能命中对应包源的快速路径。显式来源按依赖逐项判定；任一不满足则重新读取或明确报不确定，不能跳过更靠前的源。
- **失效与状态**：不用时间 TTL 决定过期，配置/锁文件/内容完整性改变才触发重新解析。`fresh` 表示本次读取成功，`cached` 表示复用已验证旧快照（报告摘要与读取时间），`unavailable` 表示源不可达且无可用旧快照；无法判定优先级时不得将其当作空源。
- **中断与断点**：本地源只验证失败不留下半成品缓存和重试可恢复；部分读取能力由适配器声明，不支持时整体重取，真实 HTTP Range 断点恢复留 E3C 验证。
- **诊断与锁**：延续 `X05-SOURCE-*`；`008` 是缓存/锁基础设施故障，`009` 是缓存对象损坏，`010` 是快照归属错误，均不降级为源不可用。跨进程条目锁以 `create_new` 获取；确认 PID 已退出且记录时间合理后回收，未写完的无效锁超过 60 秒才回收；仍存活或无法确认的 PID 不回收，等待最多 30 秒后返回基础设施错误。进程竞争和退出锁回收由 E3B 测试验证；实际远程传输的断点续传仍待 E3C 验证。

## 已冻结补充：11A-E3D 版本约束

- **版本**：发布版本必须符合 SemVer 2.0.0 的 `major.minor.patch[-prerelease][+build]`；三段无前导零的非负整数、合法的非空 ASCII 标识符，数字预发布标识符也不得有前导零。按 SemVer 比较数字/字符串预发布标识符，构建元数据不参与优先级。非法版本或约束直接诊断，不能按字符串排序或当作未匹配。
- **语法**：`1.2.3` 精确匹配；`^1.2.3` 到下一非零位的上界（`^0.2.3 <0.3.0`、`^0.0.3 <0.0.4`），`~1.2.3 <1.3.0`；比较符 `>`、`>=`、`<`、`<=`、`=` 可以用逗号合取。`1` 等同 `1.*` 即 `[1.0.0, 2.0.0)`，`1.2` 等同 `1.2.*` 即 `[1.2.0, 1.3.0)`，**不按 `^` 展开**；通配符仅允许末尾缺失位。比较符作用于部分版本时，`>=1.2` 从 `1.2.0` 起、`<2` 截止 `2.0.0`、`>1.2` 从 `1.3.0` 起、`<=1.2` 截止 `1.3.0`（开区间）。不支持 `||`、连字符范围及随意空格分隔的隐式合取。
- **预发布**：默认排除；只有同一条合取中存在与候选相同 `major.minor.patch` 的预发布比较基准，才可参与所有比较符的匹配。构建元数据不改变精确匹配的优先级；相同优先级的多个不同正文候选不得任意挑选。
- **选择**：显式源优先，否则逐源按配置顺序尝试，不跨源比较版本；同一源先筛约束、目标与撤回状态，再按 SemVer 优先级从高到低作确定性回溯。若相同最高优先级在约束及锁定条件下仍不唯一，报歧义；约束冲突报失败，不回退成任选候选。普通命令优先验证/复用锁定版本，只有显式 `update` 或输入变化需要重解时才选择新版。约束解析、求解和写回统一调用一份解释实现。锁文件已记录选中版本及源身份，本批不改变 `lock_version: 1`；远程签名方案仍待单独冻结。
