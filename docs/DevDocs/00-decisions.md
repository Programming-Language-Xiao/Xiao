# 00. 决策基线

> 本文记录 Xiao 当前已经确认的设计方向。它是后续词法、编译器和运行时实现的约束源。

## 一级工程目标：确定语言边界

### 目标与非目标

Xiao 的目标是让同一份源码同时拥有两种执行路径：

1. 开发阶段通过字节码运行，获得接近脚本语言的快速反馈。
2. 发布阶段通过 LLVM 生成跨平台原生二进制，程序不依赖 Xiao 虚拟机。

Xiao 不是“所有代码都自动变成零开销 C”的承诺。动态值、堆对象、字符串、异构容器和并发任务可能需要 Xiao Runtime；未使用的运行时能力应在链接或优化阶段被移除。

### 设计取舍

- 优先保证两种模式的语义一致，再追求解释器速度或生成代码速度。
- 语法默认简洁，但需要有明确的静态边界；动态能力必须可定位、可诊断。
- 资源释放选择确定性方案，不接受不可预测的全堆暂停。

## 一级工程目标：冻结基础语义

### 变量与类型

- `a = 1` 会推断出整数类型，之后不能直接赋值字符串。
- 普通变量默认可变，可以继续接受与已锁定类型兼容的赋值，例如 `a += 1`。
- 可以用 `int a = 1` 显式声明静态类型；初始化值和后续赋值都必须兼容该类型。
- 普通变量首次绑定后类型锁定；换成不兼容类型必须经过明确的释放或动态边界语法。
- 语言支持静态值和少量动态值。动态值可以使用统一的运行时值表示，但不能让所有普通变量退化成动态类型。
- `const` 表示编译期常量。编译器可以内联常量，是否占用存储由实现决定，不把“绝对零内存”作为语义保证。

### 动态能力

`@f` 和动态变量方向保留，但最终的动态声明关键字仍待定。当前约束如下：

- `@f` 不能作为普通静态变量的日常改类型语法。
- 动态重绑定只能发生在显式动态变量或动态容器中。
- 静态代码使用动态值时必须经过类型检查、装箱或显式转换。

### 数值

| 类型 | 默认位宽 | 语义 |
| --- | ---: | --- |
| `int` | 64 位 | 默认整数类型 |
| `float` | 64 位 | 默认浮点类型 |
| `sint` | 32 位 | 短整数类型 |
| `sfloat` | 32 位 | 短浮点类型 |
| `lint` | 不限 | 超大整数类型 |
| `lfloat` | 不限 | 超高精度浮点类型 |

所有平台必须提供一致的数值语义。整数、浮点和高精度类型发生溢出时直接报告错误，不静默回绕。浮点舍入、无穷大和非数的细节在类型阶段补充。

### 布尔加减

- `bool` 不是整数的子类型，不参与普通数值隐式转换。
- 只允许布尔值位于左侧、整数位于右侧的 `+`、`-`、`+=` 和 `-=` 运算；这里的整数包括 `sint`、`int` 和 `lint`。
- 右侧整数为偶数时结果保持不变，为奇数时结果翻转。加法与减法在这个规则下结果相同，负整数仍按奇偶性判断。
- 运算结果仍为 `bool`。`整数 + bool`、`整数 - bool`、`bool + bool`、`bool - bool` 以及布尔值与浮点数的加减均为类型错误。

### 容器与路径

异构数组可以保存以下值：整数、浮点、字符串、布尔值、数组、元组、集合、字典表和字典列。数组的局部类型约束使用斜杠路径，例如：

```xiao
int list[3/2]
```

所有容器数字索引统一从 `0` 开始。这表示 `list` 中索引为 `3` 的元素（第 4 个位置）是内嵌数组，并且该内嵌数组中索引为 `2` 的元素（第 3 个位置）必须是 `int`。

集合采用与 Python `set` 相同的基础语义：元素唯一、没有顺序、不能通过数字或键名索引。非空集合使用花括号直接列出值，`set()` 表示空集合；空花括号 `{}` 保留给空字典表。

```xiao
values = {1, "x", true}
empty_values = set()
empty_table = {}
```

集合默认允许异构值，也可以显式指定统一的元素类型。所有集合元素都必须可哈希：元素的哈希值在其位于集合期间必须稳定，并且相等的值必须具有相同哈希。数组、字典表、字典列和普通集合等可变容器不可哈希，因此不能作为集合元素。元组只有在其全部元素都可哈希时才可哈希。

动态值插入集合时必须在运行时验证实际值是否可哈希；静态类型已经证明不可哈希时直接产生编译错误。集合不通过后台扫描追踪元素变化。

集合运算沿用 Python 的集合代数，但并集运算符改为 `+`：

| 运算 | Xiao 写法 |
| --- | --- |
| 并集 | `left + right` |
| 原地并集 | `left += right` |
| 交集 | `left & right` |
| 差集 | `left - right` |
| 对称差 | `left ^ right` |
| 子集/真子集 | `left <= right` / `left < right` |
| 超集/真超集 | `left >= right` / `left > right` |
| 成员判断 | `value in set_value` / `value not in set_value` |

`|` 和 `|=` 不承担集合并集语义。

### 标识符与表容器

- 常规变量名使用 ASCII 标识符规则。
- 反引号可以包裹任意 UTF-8 变量名，定义和引用必须保持同样的反引号形式：

```xiao
`新变量1` = 1
print(`新变量1`)
```

- 字典表使用花括号包裹，条目写作 `键 = 值`，键值无顺序要求，按键访问。
- 字典列使用尖括号包裹，键值顺序固定，支持数字索引和数字加键名索引。

### 模块、包与依赖

- 除项目根的特殊配置文件 `config.xiao` 外，每个普通 `.xiao` 源文件形成一个模块。源文件是模块的规范来源，不要求维护 C/C++ 风格的独立声明头文件。
- 源码文件使用 Python 风格的 `import` 表达实际模块依赖，不能把每一条文件间导入边都移到项目配置中。
- 源码根下的目录自动形成命名空间，不需要 `__init__.py` 或其他目录标记文件。
- 目录命名空间本身不执行初始化代码；只有具体 `.xiao` 模块可以包含模块初始化行为。
- 包内符号默认不向包外公开，公共模块与公共符号由项目根目录的 `config.xiao` 集中列出。
- `config.xiao` 集中声明项目身份、源码根、入口、直接外部依赖、包外导出、约束和运行时默认值；其中依赖部分只记录直接依赖，不要求用户手写完整传递依赖树。
- 依赖解析器根据各包的直接依赖生成依赖锁文件。锁文件记录实际解析出的完整依赖图，用于可复现运行与构建，不由用户日常手工维护。
- 外部 Xiao 包同样以 `.xiao` 源文件为规范输入。编译器可以生成私有缓存或预编译产物，但它们不能取代源码级模块契约。

计划中的源码写法与 Python 相近，准确语法仍需在模块阶段完成规格测试：

```xiao
import net.http
import net.http as http
from app.models import User
```

### 虚拟环境与包管理

- 虚拟环境创建器、同步器和包管理器统一集成在 `xiao` 命令中，不要求安装第二套管理程序。
- `xiao venv` 创建并激活逻辑名称为 `venv`、目录为 `.venv` 的默认环境；`xiao venv dev` 等带名称形式使用同一个名称作为逻辑名称和目录名，例如 `dev` 对应目录 `dev`。
- `xiao sync` 在没有目标环境时先创建环境，再按项目配置安装依赖并激活；已有环境时补齐缺失依赖后激活。
- `xiao install [路径]` 与缩写 `xiao i [路径]` 直接安装指定 `config.xiao` 声明的依赖，不等同于 `sync`。路径可以是项目目录或配置文件；省略时在终端当前目录查找 `config.xiao`。
- `install`/`i` 不创建或激活环境：已经激活环境时安装到该环境，未激活时安装到全局环境。
- 自动激活通过一次性初始化的 Shell 钩子修改父终端状态。激活后在原提示符前增加绿色的 `$环境名$` 前缀，两个 `$` 与环境名均为绿色；原提示符的路径、符号和其余配色保持不变。
- `xiao run`、`xiao build` 和 `xiao test` 仍必须能直接定位项目环境，不把用户手工执行激活命令作为运行前提。
- 项目环境不重复保存每一份依赖源码，而是引用全局的内容寻址缓存。相同依赖内容只需保存一次，不同项目的锁定结果仍彼此隔离。
- 全局环境只是未激活时 `install`/`i` 的依赖选择与映射，不是另一份包源码仓库；项目环境和全局环境都引用同一不可变内容缓存。
- 全局包缓存保存经过完整性校验的不可变内容；构建产物缓存与源码包缓存分离，并按工具链、目标平台和构建条件隔离。
- `config.xiao` 复用 Xiao 的词法器和语法基础，但只允许不可执行的声明式子集。读取依赖配置不得执行函数、控制流、模块导入或项目代码。
- 依赖锁文件提供完整依赖图，项目环境由配置与锁文件物化且必须可删除重建。常规命令不能悄悄升级锁定版本。

## 一级工程目标：确定执行与内存模型

### 双模式执行

统一前端生成类型化中间表示：

```text
源码 -> 词法/语法 -> 名称解析 -> 类型检查 -> 类型化 IR
                                      ├─ 字节码解释器：xiao run
                                      └─ LLVM 后端：xiao build
```

`xiao run` 可以使用字节码虚拟机；`xiao build` 生成的程序不要求安装或携带完整虚拟机，但可以链接按需裁剪的 Xiao Runtime。

### 绝对无追踪式 GC

Xiao 不使用追踪式垃圾回收。内存方案由以下部分组成：

- 作用域退出时确定性执行资源释放。
- 发生逃逸的值自动从栈提升到堆。
- 逃逸堆对象使用引用计数管理。
- 可能形成环的边使用 `Weak` 弱引用；强引用环的处理策略仍需细化。

### 并发安全边界

- 数据竞争不属于合法且可依赖的程序行为。
- 编译器能够证明存在数据竞争时必须拒绝编译。
- 竞争只能在运行时确定时，运行时必须报告明确错误，不能静默继续。
- 线程、任务池、`async`/`await` 或 Actor 等具体并发模型尚未确定。

### 运行时配置

配置文件表达的是运行时配置，不是“原生程序必须运行在虚拟机里”。原规划中的 `gc_verbose` 名称与无 GC 目标冲突，后续应改成引用计数或内存释放诊断名称。

## 一级工程目标：建立实现顺序

### 必须先完成的基础

1. 先建立编译器工程骨架、源码游标和位置模型。
2. 再完成只包含标识符、整数、`=`、换行和文件结束的最小 Token 流。
3. 分批补全 UTF-8、字符串、运算符、注释、缩进和表头词法。
4. Token 流稳定后才实现最小语法树，不把解析器塞进 Token 最小里程碑。
5. 名称解析和静态标量类型稳定后，再逐步实现函数及基础容器。
6. 集合、复杂运行时、字节码和 LLVM 都属于更后的独立子里程碑。

### 后置能力

并发、JIT、包管理、FFI、完整调试器和高级泛型不能阻塞最小双模式闭环，应在核心语义稳定后加入。

## 待定决策

### 需要语言设计确认

- 动态变量的声明形式。
- `bool(value)` 等类型构造写法是否与 `value as bool` 并存，以及字符串类型关键字最终采用 `str` 还是 `string`。
- `free` 是否保留为用户可写语句，以及它与 RAII 的关系。
- 表、模块、配置表的命名空间关系。
- 同一包内部的符号可见性，以及相对导入、通配导入和循环导入规则。
- 依赖锁文件名称、版本约束算法、包来源和完整性格式。
- 多个项目环境并存时 `sync` 如何选择目标，以及是否清除多余依赖或纠正已安装版本。
- `sync` 与 `install`/`i` 对锁文件的读取和更新规则。
- 全局环境与全局内容缓存的实际位置、全局环境参与运行解析的条件。
- Shell 钩子的初始化命令、取消激活命令和不支持钩子时的降级行为。
- 错误是否采用异常、错误值，或两者并存。
- 是否提供不可变集合 `frozenset`；若提供，其构造和字面量语法是什么。
- `bool`、整数和浮点等不同数值类型之间相等时，集合是否视为同一个元素。

### 需要实现验证

- `lint`/`lfloat` 的跨平台表示和算术库。
- 无 GC 条件下的引用环诊断。
- 字节码与 LLVM 后端的释放顺序一致性。
