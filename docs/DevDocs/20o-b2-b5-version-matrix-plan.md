# 20O-B2-B5. ABI 升至 1.19、沿用生成器 21 与版本矩阵实施规划

> **2026-11-13 版本裁定执行：星崽在本会话已批准“B4 升到生成器21，更新规划并调整B5边界”。B4-3改LLVM调用文本，按后端版本规则20→21；ABI仍1.18、接口1。B5只将ABI升1.19并核验既有生成器21的最终拒绝/重生成矩阵，不再次因本批接线递增生成器。下文将21留B5或B4不得升21的旧句均由本裁定替代；签署的冻结正文及历史证据不改写。**

> **B4-0/B4-1、B4-2A/FIX1、B4-2B与B4-3已完成Windows本机内部验收；B4-4/B4-5尚未完成；B5仍未开始，B6、B7与B2-C后置。**
> B5 开工入口必须是 B4-5 内部收口后的固定源码与证据；B4-3前历史版本为ABI1.18/生成器20；B4-3产品接线最终提交为`e0d5993e`，`CODEGEN_VERSION=21`，fixed-final2冷构建、O0/O3矩阵与审计已通过；B4-3退出版本固定为ABI1.18/生成器21、接口1。详情见[B4-3固定证据](assets/20o-b2-b/entry-20261113-b4-3/README.md)。
> B5只将ABI升级到1.19，CODEGEN_VERSION沿用B4-3的21，完成旧/新产物拒绝、缓存重生成和C ABI加法扩展。
> B5 不新增 cmath 数学语义或语言接线；B4 全链路内部验收是开工前置。不升级 registry/教程、不跑旧 721；B2-C 才做最终公共发布。
> **2026-11-15 审核同步：B4-3 已完成生成器 20→21 接线及冷构建验证；旧/新产物接受或拒绝、旧缓存失效及重生成的完整矩阵仍待 B5 实跑，不能继承为 B4-3 已验收结论。**

B5 是 **版本矩阵内部切换批**，不是 B2-C 最终发布。开工前要求 B4-5 已记录内部 `language_available=true`，公开 `stdlib.cmath`/UseDocs/registry 仍 planned。B5 的产物仍只作内部验证；最终三平台公共产物、完整 721 和 registry 升级留 B2-C。

### 1.1 要做

1. ABI 次版本 1.19（编码 `0x0001_0013`）、生成器沿用 B4-3 的 21、标准库接口保持 1，intrinsic 1～48 与 ID 100 墓碑不变；
2. `.xiaoc` 头、`.xar` 索引和指令流记录精确 1.19；
3. 原生元数据记录 ABI 1.19、沿用生成器 21 和标准库身份 1；
4. B1 原始 1.18 `.xiaoc`/`.xar`/原生元数据按 F-6a 在执行前拒绝，原件不改写；
5. 新 1.19 `.xiaoc`/`.xar`/原生元数据被固定身份的旧 1.18 验证器拒绝；
6. 实测两组缓存：ABI保持1.18时生成器20→21的失配，以及生成器保持21时ABI1.18→1.19的失配；分别核对miss原因及重生成，不能用冷构建代替；
7. 保留 B5 入口实际存在的全部 1.18 C 符号/布局/调用约定；本批不得移除、重命名、重编号或改变旧入口语义；如另有新增 C 入口，必须单列符号清单并只做加法；
8. 保存旧/新拒绝、缓存重生成、B1 20 入口回归和版本身份证据；
9. 区分原生元数据接受范围与缓存命中：当前`NativeMetadata::validate`要求ABI、目标、特性及标准库身份匹配，同时接受生成器14～当前上限21。旧20元数据可被当前1.18/21验证器接受；这不等于构建缓存可复用，后者按完整指纹核对。详见B5-2接受/拒绝矩阵和B5-3缓存重生成。

### 1.2 明确不做

- 不手改旧 `.xiaoc`/`.xar` 头或放宽 max 版本；
- 不增加迁移工具或“兼容重放”旧原件；
- 不改变容器格式/索引 schema 版本；
- 不升级 `stdlib.cmath`/registry/教程；
- 不跑旧 721，不关闭 22C/22D、19/11/22；
- 不把 B5 内部 1.19/21 写成 B2-C 最终发布或三平台产品。

## 三、分批执行

### B5-0：版本/产物基线

1. 固定B4-5最终源码、B1原始1.18产物、旧验证器/Runtime、生成器20历史缓存及B4生成器21过渡缓存；
2. 为 F-6a 每个原始产物记录来源、原始字节数和 SHA-256，并记录 `.xiaoc` 头、`.xar` 索引、指令流 runtime ABI、原生元数据中的 ABI/生成器/标准库身份；
3. 分别生成并保存 F-6a 历史 1.18 C 符号/布局清单与 B4-3退出后的内部1.18/21源码快照清单；后者当前已含 `xiao_runtime_lfloat_divide` 和 `xiao_runtime_cmath_*`，不据此改写历史基线；
4. 固定旧 1.18 验证器/Runtime 的源码提交、构建工具链、二进制/静态库 SHA-256；版本字符串不能单独证明旧验证器身份；
5. 分别记录生成器20历史缓存与21过渡缓存的源码、目标、优化计划、ABI 与 Runtime 静态库身份；
6. 保存只读基线清单与原始文件摘要。

退出：两类 1.18 基线、产物/验证器/缓存/C 符号身份可分别复现；旧原件保持未改写。

### B5-1：ABI 1.19（生成器沿用21）

1. `ABI_MINOR_VERSION=19`，由 `encoded_abi_version(1, 19)` 得到 `0x0001_0013`；主版本仍 1；
2. `CODEGEN_VERSION`沿用21；ABI变化本身不导致生成器再次升级；标准库接口保持1；
3. `.xiaoc` 头 runtime ABI min/max 精确 1.19；
4. `.xar` 索引 runtime ABI min/max 精确 1.19；
5. 指令流运行时 ABI 精确 1.19；
6. 原生元数据记录 ABI 1.19、生成器 21、标准库身份 1；
7. 不改变容器 schema/索引结构版本；
8. 保存常量、头/索引/元数据样本。

退出：新产物精确记录 1.19/21；`.xiaoc` 格式、`.xar` 目录/索引 schema 均未变化。

### B5-2：旧/新接受与拒绝矩阵

1. 使用 B5 验证器加载 F-6a 原始 1.18 `.xiaoc`/`.xar`，必须在入口版本检查、任何用户代码/模块初始化/宿主副作用前拒绝；原件 SHA-256 前后不变；
2. 使用 B5 1.19 验证器读取新 `.xiaoc`/`.xar` 并确认接受；再用固定身份的旧 1.18 验证器读取同一产物，必须在执行前拒绝；
3. F-6a 原始 1.18 原生元数据被 B5 验证器按精确 ABI 范围/标准库身份拒绝；
4. B5 验证器接受新 1.19/21 原生元数据；固定身份的旧 1.18 验证器拒绝同一元数据；
5. 每格记录输入 SHA-256、验证器/Runtime SHA-256、退出码、实际拒绝阶段/错误和无执行副作用检查；不能只凭版本字符串或执行到未知原语失败；
6. `.xiaoc` 格式及 `.xar` 目录/索引 schema 维持基线版本；拒绝由冻结的 ABI min/max 与元数据身份规则触发；
7. 不做迁移工具、不手改旧头、不放宽 max；
8. 保存四类旧/新拒绝的原始日志、机器回执和原件只读摘要。

生成器过渡与ABI升级分别取证，以下均为B5待执行格；当前行为依据`native_metadata.rs::NativeMetadata::validate`及`toolchain.rs::fingerprint_with_optimization`核对，不充作实跑通过证据：

| 阶段 | 原件身份 | 验证器身份 | 预期与原因 |
| --- | --- | --- | --- |
| B4生成器过渡 | 原生元数据ABI1.18/生成器20 | ABI1.18/生成器上限21 | 其余要求匹配时接受；生成器接受范围为14～21，不能写成拒绝所有旧20产物 |
| B4生成器过渡 | 原生元数据ABI1.18/生成器21 | 固定旧ABI1.18/生成器上限20 | 其余要求匹配时因21超过理解上限而拒绝 |
| B5 ABI升级 | B1原始ABI1.18原件及B4内部1.18/21原件 | ABI1.19/生成器上限21 | `.xiaoc`、`.xar`、原生元数据均因精确ABI不符而在执行前拒绝；原件不改写 |
| B5 ABI升级 | 新ABI1.19原件，原生生成器21 | 固定B1旧1.18验证器及B4内部1.18/21验证器 | 在执行前拒绝；记录实际版本拒绝阶段，不能仅以生成器号解释全部拒绝 |
| B5同版本 | 新ABI1.19原件，原生生成器21 | ABI1.19/生成器上限21 | 其余要求匹配时接受，并执行代表性语料 |

表中的生成器号对应原生元数据；`.xiaoc`/`.xar`的版本拒绝按各自头、索引与指令流中的ABI字段验证。B4-3没有执行上述过渡矩阵；其冷构建成功不改变旧20元数据当前可被接受这一事实。

退出：生成器过渡接受范围及ABI旧/新`.xiaoc`、`.xar`与原生元数据矩阵全部实际执行；原件未改写，拒绝格均发生在用户代码运行前。

### B5-3：缓存重生成

1. 固定生成器20历史缓存和B4内部1.18/21过渡缓存各一份；分别记录源码提交、目标三元组、工具链、优化计划、ABI及Runtime静态库身份；
2. 在独立任务根实测20→21缓存失配：保持输入源码、目标、优化计划、ABI1.18和Runtime归档一致，只切换固定身份的生成器；即使旧20元数据可通过新验证器，也须按生成器指纹miss并重生成；
3. 另在独立任务根以B4的1.18/21过渡缓存作为探针，升ABI至1.19并沿用生成器21。核对ABI及新Runtime内容引起的miss；逐项保存实际变化，不能把Runtime摘要变化误称为仅生成器变化；
4. 证明旧对象、旧可执行文件和旧 Runtime 未被链接或执行；新产物链接到摘要已记录的 1.19 Runtime；缓存探针在独立 target/cache 根运行，不读写 Cargo 全局缓存；
5. 保存旧 fingerprint、miss 原因、新 fingerprint、新对象及 Runtime SHA-256 和链接/执行日志。

退出：两组旧缓存均未误用；生成器与ABI/Runtime变化导致的miss和重生成证据分别完整。

### B5-4：C ABI 加法扩展

1. 以 F-6a 历史 1.18 C ABI 清单为旧调用方基线，并另存 B4当前1.18/21过渡符号集；
2. B5 保留 F-6a 全部符号、布局和调用约定；当前 B4 内部快照已存在的 33～48 相对 F-6a 基线属于加法扩展，B5 保留其精确符号和签名，不在 B5 重复定义或改变；
3. B5 不新增 intrinsic ID；如需增加冻结集之外的新 C 符号，必须另有明确接口授权并以追加方式登记；
4. 实测旧 1.18 调用方仅使用 F-6a 既有符号时可链接/运行于 1.19 Runtime；使用 33～48 的 1.19 产物仍必须被旧 Runtime 在执行前拒绝；
5. C ABI 向后兼容不放宽 `.xiaoc`/`.xar`/原生元数据的精确版本拒绝；
6. 保存历史/内部/新版本符号表差异、布局断言、旧调用方实测和拒绝矩阵关联证据。

退出：相对F-6a的C ABI扩展清单可解释；历史符号布局未破坏，B5入口的内部1.18/21快照所含33～48未被重复定义。

1. ABI升至1.19后执行`.xiaoc`/`.xar`编码、解码及代表性语料；原生生成器沿用21，容器格式/目录schema与基线一致；
2. 执行B5-2全部生成器接受范围及ABI旧/新产物拒绝矩阵；
3. 原生元数据20/21过渡接受范围及ABI1.18/1.19旧/新拒绝，均按B5-2逐格执行；
4. B5-3的两组缓存失配/重生成均实测，新对象和1.19 Runtime实际链接身份可核对；
5. 从 B1 七库源码在 1.19/21 下重新生成回归产物，运行 20 入口、资源 17、双精确及 B4 cmath 内部语言链路；不得把旧 1.18 的执行成绩当新版本回归；完整 721 留 B2-C；
