# 20D-能力上下文. 能力上下文的载体与校验

> **背景**：[20D-冻结](20d-freeze-resource-contract.md) §2.7（G）已把能力上下文的**形状**定死：
> 驱动器创建、**随一次 Runtime 请求携带**、执行期间不可变、**不作为 Xiao 用户值暴露**；
> `u64` 位集，**位 0–4** 固定为 `filesystem`/`clock`/`process`/`network`/`native_extension`，
> **其余位必须为零**；省略上下文等价于十位全开；位缺失报 `X06-RUNTIME-026`。
> **本批把它实现出来。**
>
> **但**：实施前核了两件事，都与冻结**直接相关**——
> **(a)** 冻结的五个位里**没有 `stdout`/`stdin`**，而现有**唯一的两个外部入口**恰恰是它们（§三.1）；
> **(b)** 方向稿 §5.2 那句「LLVM 仍处接口准备阶段、只能声称字节码侧完成」**已经过期**（§三.2）。
>
> **一句话概括**：先解开这两处，再谈怎么搬。

状态：**规划中（2026-10-17）**，两道裁决待下（§五）。**未改任何代码。**

## 一、为什么是这一批

1. **顺序**：[20D-规划](20d-platform-resources-stage-plan.md) §4.2 的裁定是
   **冻结 → 能力上下文 → 资源承载 → 首批 API，不可倒**。冻结已完成（`02a867a`），本批是第二步；
2. **它是地基**：方向稿 §5.1 要求「**所有外部操作必须通过该上下文进入**」，
   而现在能力只是一个**声明字段 + 两处形状校验**（§3.3）——**没有载体**；
3. **再往后就没机会了**：资源承载一批会新增 `RuntimeValue` 变体，首批 API 一批会新增真正的
   外部操作。**上下文不先就位，那两批都会顺手绕过它**（而且很难事后补）。

## 二、冻结已经定死的（**输入，不许重新论证**）

| 项 | 冻结内容 | 出处 |
| --- | --- | --- |
| 表示 | **`u64` 位集** | [冻结](20d-freeze-resource-contract.md) §2.7 |
| 位数 | **位 0–4**：`filesystem`/`clock`/`process`/`network`/`native_extension`；**其余位必须为零**，由请求校验拒绝 | 同上 |
| 默认 | **省略上下文 = 五个已知位全 1**（首版默认全开） | 同上 |
| 载体归属 | 由**驱动器创建**、**随一次 Runtime 请求携带**、**执行期间不可变** | 同上 |
| 可见性 | **不作为 Xiao 用户值暴露** | 同上 |
| 校验时机 | **Runtime 入口先检查对应位、再触碰宿主** | 同上 |
| 失败身份 | 位缺失 → **`X06-RUNTIME-026`**（`runtime.capability_unavailable`） | 同上 |
| 契约义务 | 每条**外部** intrinsic 必须声明一个**非 `none`** 能力位 | 同上 |

## 三、实施前核出的两处

### 3.1 `stdout` / `stdin` **不在那五个位里**——而它们是今天唯一的外部入口

**实测现状**：

- `Capability` 枚举只有三个变体（`xiao-intrinsics/src/lib.rs:97`）：
  `None` / `Stdout` / `Stdin`；
- 契约表里**非 `none` 的只有两条**：`print` → `stdout`、`input` → `stdin`
  （其余 20 条都是 `none`）；
- 而冻结的位表是 `filesystem`/`clock`/`process`/`network`/`native_extension`
  ——**`stdout`/`stdin` 一个都不在其中**，且**位 5+ 必须为零**。

⇒ **冻结与现状直接冲突**：冻结还要求「每条**外部** intrinsic 必须声明一个非 `none` 能力位」，
可在冻结的位表下，`print`/`input` 声明的能力**没有对应的位**。
**要么加位，要么把它们排除出「外部操作」的定义**——见 §5.1。

**为什么这条不能拖到下一批**：本批需要一条**负面证据**（伪造一个能力不足的上下文，
操作必须被拒且报 `X06-RUNTIME-026`）。**今天能触发外部操作的只有 `print`/`input`**——
不解决它们的归属，**本批就做不出负面证据**，只能靠「写了但没人调用」。

### 3.2 方向稿 §5.2 的限定**已经过期**——原生路径现在确实在调 Runtime ABI

方向稿 §5.2 写着：

> 当前 LLVM 后端仍处于接口准备阶段，在它真正能调用 Runtime ABI 之前，
> **只能声称字节码侧完成**，不能声称 `os` 已实现双后端一致性。

**实测：这句话今天不成立。** 原生路径已经调用 Runtime ABI：

- `xiao-codegen-llvm/src/dynamic/expression.rs:504` 直接发射
  `@xiao_runtime_print_values(ptr …, i64 …)`；
- 该入口在 `xiao-runtime/src/abi_io.rs:37` 真实存在，并有自己的签名。

⇒ **如果照 §5.2 把本批缩到「字节码侧」，原生路径就会绕过能力检查**——
而「所有外部操作必须通过该上下文进入」正是冻结的核心要求。
**本批要显式处理这一点**（§5.2），**不许**引一句已过期的话把半个后端放下。

### 3.3 现状：能力是「声明字段 + 两处形状校验」

- 消费点只有两处（`xiao-vm/src/semantics/exec.rs:1956` 的 `Print`、`:1980` 的 `Input`），
  且它们检查的是「**这条 intrinsic 的 `capability` 必须恰好是 `Stdout`/`Stdin`**」——
  **对声明的形状校验**，不是对**上下文的允许检查**；
- `xiao-runtime` 与 `xiao-driver` 里**没有**任何能力上下文的运行时表示
  （按 `capability` 全仓检索，除契约表生成与上面两处外零命中）。

⇒ 本批要做的是**从「声明校验」走到「执行时允许检查」**。

## 四、本批要做的事（编号；顺序大体可并行，但 4 必须在 3 之后）

1. **`Capability` 与位的映射**：把枚举的每个变体映射到位
   （`stdout`/`stdin` 的归属按 §5.1 的裁定）；
2. **载体**：`DriverRequest`（`xiao-driver/src/run.rs:122`）增加能力位字段；
   `DriverRequest::new` 的默认值对应「省略 = 全开」；
   **不可变**——进入执行后不再改变（用只读参数传下去，不给 `&mut`）；
3. **校验点**：在**外部操作进入**处检查位，缺失报 `X06-RUNTIME-026`；
   现有两条外部入口是 `print`/`input`（VM 侧在 `exec.rs` 的分派前，原生侧在
   `xiao_runtime_print_values`/`xiao_runtime_input` 的 ABI 入口）；
4. **负面证据**：伪造一个**缺位**的上下文，**两条路径都**必须被拒且报 `X06-RUNTIME-026`；
   再做一条**默认全开**的正例，证明行为不变；
5. **能力位的**「其余位必须为零」校验：请求构造时拒绝越界位（位 5 及以上）；
6. **文档**：方向稿 §5.1 回填实现状态；§5.2 那句过期限定要**按实测订正**（§3.2）。

## 五、两道待定裁决

### 5.1 裁决一：`stdout` / `stdin` 怎么进能力模型

| | 做法 | 代价 |
| --- | --- | --- |
| **甲** | **加两个位**：位 5 = `stdout`、位 6 = `stdin`；同时把冻结的「位 0–4 固定、其余位必须为零」改成「位 0–6」 | 要改冻结文本（**已冻的东西**），但模型统一：所有外部 intrinsic 都有位 |
| **乙** | **把 `print`/`input` 排除出「外部操作」**（它们是调试输出，不是宿主资源访问），能力模型只管资源类 | 不改冻结；但「外部操作」出现两种定义，而 `input` **确实**读宿主输入 |
| **丙** | 位表**不动**，但允许 `stdout`/`stdin` 声明的 intrinsic **跳过**位检查 | 最省；但「位缺失报 026」就有两个例外，负面证据只能靠未来的资源 API |

**审核倾向：甲。** 理由：`stdin` 读的是宿主输入、`stdout` 写的是宿主输出，
**它们就是外部操作**；把它们排除会让「所有外部操作必须通过该上下文进入」这句话名不副实。
**代价要说清**：这是**回头改冻结**，要按「裁定后增补」的方式记，并**不许**让读者以为原本就是 0–6。

### 5.2 裁决二：原生侧本批接不接

| | 做法 |
| --- | --- |
| **甲** | **本批两条路径一起接**：VM 分派前 + `xiao_runtime_print_values`/`xiao_runtime_input` 的 ABI 入口 |
| **乙** | **本批只接 VM**，原生侧登记为下一批；**并在文档里写明「原生路径当前绕过能力检查」** |
| **丙** | 本批只接 VM，并**照 §5.2 的旧文**声称「只能声称字节码侧完成」 |

**审核倾向：甲。** 理由：§3.2 已实测原生路径**确实**调用 Runtime ABI，
「接口准备阶段」的说法过期了；在双路径都能调外部入口的情况下只接一半，
等于**给原生路径留一个已知的绕过口**。
**反方**（要一并摆上）：ABI 入口加参数是**破坏性变更**（调用约定、符号签名），
可能牵动既有 native 差分与 `abi_io` 的测试面——**这是甲的主要代价**。

**丙 明确排除**：它等于引用一句已过期的话来给半个后端开脱。

## 六、不许

1. **不许**把能力上下文做成「执行时再读一个全局变量」——冻结要求它**随请求携带、执行期不可变**；
2. **不许**把它做成 Xiao 用户值（冻结：不作为用户值暴露）；
3. **不许**只做「声明校验」的加强（那正是现状）——本批要的是**执行时允许检查**；
4. **不许**用「默认全开」当理由跳过校验点：默认全开只是**默认值**，
   **校验路径必须存在**（否则将来受限模式没有拦截点——方向稿 §5.1 的原话）；
5. **不许**在没跑出**负面证据**的情况下声称完成：伪造缺位上下文必须被拒，
   **两条路径都要**（按 §5.2 的裁定）；
6. **不许**顺手接资源 intrinsic——那是「20D-资源承载」与「20D-首批 API」的事。

## 八、验收

1. **载体存在且不可变**：能力位随请求进入执行，执行期没有任何可变入口；
2. **校验点存在**：外部入口**先**查位、**再**触碰宿主；缺位报 `X06-RUNTIME-026`；
3. **负面证据**：伪造缺位上下文 → 被拒且报 `X06-RUNTIME-026`，
   **两条路径都验**（按 §5.2 裁定）；**默认全开**的正例行为不变；
4. **越界位拒绝**：位 5 及以上（若取 5.1 甲则为位 7 及以上）在请求构造时被拒；
5. **诚实**：方向稿 §5.2 那句过期限定**必须按实测订正**，
   **不许**继续用它给半个后端开脱；若 §5.2 取乙，**必须写明「原生路径当前绕过」**；
6. **通用**：`cargo test --workspace`、clippy、fmt、`bun test`、`bun run check`、`bunx tsc --noEmit` 全绿；
   提交标题带类型前缀、正文非空；凡改动 `README.md` 的 20D 行或本文，逐行跑一次粗体配对检查。
