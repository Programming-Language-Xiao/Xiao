# 11. CLI、项目配置与平台

> 本阶段把开发者使用的核心命令、项目/运行时配置和平台适配整理为稳定工具链，并为第 11A 阶段的环境与包管理命令预留入口。运行时配置不暗示原生程序必须运行在虚拟机中。

## 一级工程目标：冻结命令行界面

### 核心命令

规划中的核心命令为：

```text
xiao run <file.xiao>
xiao build -o <output> <file.xiao>
xiao test <project>
```

直接写 `xiao <file.xiao>` 是 `xiao run` 的脚本快捷方式。参数顺序、短参数和子命令错误提示需要在 CLI 实现时固定并写入帮助文本。

### 配置覆盖

命令行可以覆盖项目配置，但覆盖只影响当前进程或当前构建，不修改源文件。原规划中的 `xiao -VM config_path.xiao test.xiao` 先作为候选形式，最终选项名待 CLI 阶段确认。

## 一级工程目标：设计项目配置文件

### 规范文件名

项目根目录统一使用全小写 `config.xiao`。这是跨平台规范名称，文档、CLI 和错误消息不能交替使用 `Config.xiao`。配置采用 Xiao/TOML 风格的顶层表和顶格键值。

### 配置职责

`config.xiao` 集中保存以下项目级信息：

- 项目身份、版本、源码根和入口。
- 项目直接使用的外部包及版本/来源约束。
- 允许其他包导入的公共模块和公共符号。
- 平台、功能、权限或依赖使用约束。
- 原生构建需要固化的运行时默认值。

它不保存每个源码文件实际写了哪些 `import`，也不要求用户手写所有传递依赖。下面仅是候选分表，表名和字段还需要单独冻结：

```xiao
[Project]
name = "app"
version = "0.1.0"
source = "src"
entry = "main"

[Dependencies]
http = { version = "^1.4" }
utils = { path = "../utils" }

[Exports]
modules = ["api", "models.user"]

[Constraints]
deny_imports = ["internal.debug"]
```

### 依赖锁文件

第 11A 阶段的依赖解析器根据每个包的直接依赖生成完整依赖图，并写入工具维护的依赖锁文件。接入后，运行、测试和构建必须复用同一锁定结果。本阶段只保留结构化配置和 CLI 扩展接口，不以生成锁文件为退出条件。锁文件的正式名称、序列化格式、校验算法和库/应用提交策略仍待定。

### 声明式解析边界

依赖关系必须在项目源码编译前读取。`config.xiao` 确定复用 Xiao 的词法器和语法基础，但只接受不可执行的声明式子集，禁止函数、控制流、导入、运行时变量和其他需要执行项目代码的构造。

配置允许哪些字面量和静态组合仍需形成白名单；平台条件和可选功能必须使用声明字段表达，不能通过在配置中执行 `if` 实现。

## 一级工程目标：预留环境与包管理入口

### 无需激活的项目环境

虚拟环境管理确定直接属于 `xiao` CLI，并在第 11A 阶段实现。完成后，`run`、`build` 和 `test` 默认能够自行定位项目环境，不以 Shell 已执行激活脚本为前提；激活命令仅作为可选便利功能。

### 全局缓存与项目隔离

第 11A 阶段实现的项目环境引用全局内容寻址的不可变包缓存，相同内容不在每个项目重复保存。环境状态必须绑定配置、锁文件、工具链和目标条件；源码缓存与目标文件缓存分开管理。这些能力不作为第 11 阶段核心 CLI 的退出条件。

完整架构、阶段和验收规则见 [11a-environments-and-packages.md](11a-environments-and-packages.md)。

## 一级工程目标：设计运行时配置

### 运行时表头

现有示例使用 `[VM]` 表头；它表达的是运行时配置，是否改名为更准确的 `[Runtime]` 在本阶段冻结。

### 配置项

候选配置项包括：

- `max_memory`：堆内存上限。
- `initial_memory`：初始申请内存。
- `call_stack_depth`：调用栈深度上限。
- `refcount_trace`：引用计数增减诊断。
- `memory_verbose`：分配、释放和内存错误诊断（替代无 GC 语义的 `gc_verbose`）。
- `jit_threshold`：未来实现 JIT 时的热点阈值；没有 JIT 时不得影响语义。
- `inject_env`：注入进程环境的键值列表。

配置值必须经过类型检查和范围检查；未知键可以在严格模式下报错，在兼容模式下给出警告。

### 原生构建固化

`xiao build` 可以把经过验证的运行时配置嵌入产物，让双击运行时拥有确定的默认行为。命令行覆盖是否允许覆盖已固化配置，需要在构建发布阶段明确。

## 一级工程目标：完成跨平台层

### 路径与进程

文件路径、环境变量、进程退出码、动态库后缀和终端编码通过平台适配层提供，语言核心不直接拼接平台字符串。

### 目标工具链

编译器需要读取目标三元组，选择对应 LLVM 目标、链接器、调试格式和 Runtime 实现。没有目标平台工具链时，错误应说明缺少的组件和安装方向。

## 二级实现任务

### CLI 实现

1. 实现命令解析、帮助、版本和错误退出码。
2. 实现 `run`、`build`、`test` 的参数校验。
3. 为后续环境创建、锁定、同步、依赖增删和显式升级命令预留一致的子命令扩展接口。
4. 实现配置读取、命令行覆盖和配置诊断。
5. 输出可脚本消费的机器可读错误模式。

### 项目与依赖配置

1. 只识别规范名称 `config.xiao`，并在能够检测时诊断非规范大小写。
2. 分别解析项目元数据、直接依赖、包外导出、约束和运行时配置。
3. 向第 11A 阶段提供结构化的直接依赖配置，不把传递依赖反写成用户配置。
4. 让 `run`、`test` 和 `build` 使用同一项目根、源码根和当前可用模块图。

### 平台实现

1. 封装路径、环境、时间和进程 API。
2. 为 Windows、Linux、macOS 建立最小构建矩阵。
3. 验证固定宽度数值和高精度库的二进制可移植性。
4. 验证原生程序的 Runtime 链接和发布目录结构。

## 验收标准

### CLI 验收

- 新用户可以仅凭 `xiao --help` 运行脚本、构建程序和执行测试。
- 配置错误在执行前报告，并指出文件、表和键。
- `run` 与 `build` 对同一配置的语义一致。
- 项目配置始终以全小写 `config.xiao` 识别。
- `run`、`build` 和 `test` 对同一项目使用相同的项目根、源码根和配置解析结果。
- 环境与包管理未实现时，核心 CLI 不伪造锁定结果，并能通过预留接口在第 11A 阶段扩展。

### 平台验收

- 三个目标平台都能完成最小项目的运行和构建。
- 生成的原生程序不依赖完整虚拟机。
