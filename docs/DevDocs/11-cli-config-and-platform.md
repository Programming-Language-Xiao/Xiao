# 11. CLI、项目配置与平台

> 本阶段把开发者使用的核心命令、项目/运行时配置和平台适配整理为稳定工具链，并为第 11A 阶段的环境与包管理命令、第 11B 阶段的终端交互式解释器及第 11C 阶段的国际化层提供公共入口。运行时配置不暗示原生程序必须运行在虚拟机中。

## 一级工程目标：冻结命令行界面

### 实现语言

`xiao` CLI 固定使用 TypeScript 编写。命令解析、配置调度、环境与包管理入口、Shell 集成、提示符渲染和交互式解释器前端都属于这个 TypeScript 层；字节码解释器和执行时 Xiao Runtime 固定由 Rust 实现。两层通过稳定的进程协议或库 ABI 接入，不能把 CLI 内部对象当成语言语义契约。

TypeScript CLI 不得复制 Rust VM 的词法、类型、索引、算术、生命周期、错误传播或字节码执行逻辑。CLI 只负责把命令行/配置归一化为后端请求、启动和监督 Rust 核心、渲染结构化结果；具体协议字段和 ABI 版本在第 09 阶段接口稳定后冻结。

CLI 的发布形态已经冻结：TypeScript 源码必须针对各目标平台打包为独立可执行程序，最终用户无需另行安装 Node.js。具体打包工具可以在实现阶段选择，但不能改变命令行为；`xiao build` 产生的原生程序同样不能因此依赖 Node.js。

### 核心命令

规划中的核心命令为：

```text
xiao
xiao --inLF
xiao --inLF "<file.xiao>"
xiao run <file.xiao> [-debug]
xiao build -o <output> <file.xiao> [-debug]
xiao build -xar "<config.xiao|main.xiao|任意.xiao>" [-O0|-O1|-O2|-O3] [-debug]
xiao -xar "<file.xar>" [-debug]
xiao test <project>
xiao config [--global] <key.path> <value>
```

无参数 `xiao` 打开交互式解释器，`--inLF` 直接进入多行模式，并可加载一个现有 `.xiao` 文件用于编辑和运行。直接写 `xiao <file.xiao>` 仍是 `xiao run` 的脚本快捷方式，不进入编辑器。`xiao config` 修改结构化配置，不能把点分路径当作普通文本搜索替换。交互细则见 [11b-interactive-repl.md](11b-interactive-repl.md)。其他参数顺序、短参数和子命令错误提示需要在 CLI 实现时固定并写入帮助文本。

`xiao build -xar "<源路径>" [-O0|-O1|-O2|-O3]` 与 `xiao -xar "<归档路径>"` 是已经确定的后置命令入口；方括号表示优化参数可省略，不是需要输入的字符。其实现不进入本阶段核心 CLI 的退出条件。参数校验、归档路由和文件关联的 SOP 见 [18. 优化与产物 CLI 接入](18-optimization-cli.md)；在该阶段完成前，CLI 不能自行发明其他临时优化级别或归档语义。

所有支持优化级别的执行与构建命令在命令行和配置均未指定时统一使用 `-O0`。字节码执行路径默认生成并缓存经过验证的 `.xiaoc`，但缓存写入由后端产物层负责，TypeScript CLI 不自行序列化字节码；普通原生 `build` 不为 LLVM 不使用的模块额外生成 `.xiaoc`。

### 运行时调试开关

`-debug` 是强制的运行时诊断开关，适用于 `run`、脚本快捷运行和 `.xar` 启动。只要直接运行入口收到该参数，执行用户代码前就必须启动独立诊断进程和诊断终端窗口，并显示内部日志、错误、模块/函数节点、生命周期钩子和固定指标栏。对 `build` 和 `build -xar`，该参数还必须把调试激活位、源码映射、诊断元数据和运行时钩子能力写入产物；调试产物以后直接启动时自动打开窗口，无需再次传参。`-debug` 不等同于完整交互式调试器，也不能改变程序标准输出、错误传播或退出语义。

命令行的具体参数顺序和短选项在 CLI 阶段冻结，但所有入口必须把 `-debug` 归一化为同一个后端诊断配置。`config.xiao` 的 `[debug]` 只提供已经激活会话的默认等级、日志目标、堆栈详细程度和模块/源码文件聚焦规则；它不能替代 `-debug` 打开窗口，也不能关闭调试产物的强制窗口。错误、日志和指标的详细契约见 [07. 错误模型与并发安全边界](07-concurrency-and-errors.md)。

### 配置修改命令

配置修改命令的正式形态为：

```text
xiao config [--global] <key.path> <value>
```

- 不带 `--global` 时，目标是当前项目的 `config.xiao`。
- 带 `--global` 时，目标是 Xiao 的全局 `config.xiao`；全局文件的跨平台规范位置仍待确定。
- `key.path` 是配置模式中的点分字段路径，不是 Xiao 源码表达式。
- `value` 必须按目标字段的配置类型解析并校验，不能一律写成字符串。
- 写入必须通过配置语法树或等价的结构化文档模型完成，并采用不会遗留半文件的原子替换流程；不得使用正则表达式直接改源码。

当前已经冻结的首个配置路径是 `CLI.git.summary`，只接受布尔值 `true` 或 `false`：

```text
xiao config CLI.git.summary true
xiao config --global CLI.git.summary false
```

项目级命令应产生与下列配置结构等价的结果；格式化器可以保留原文件中合法的等价结构、注释和无关字段：

```xiao
[CLI]
git = { summary = true }
```

语言配置使用同一个结构化入口：

```text
xiao config language.locale en-US
xiao config --global language.locale zh-CN
```

这两个命令分别修改当前项目和全局 `config.xiao` 的 `[language].locale`；语言标签和别名在写入前完成校验与规范化，具体消息目录由第 11C 阶段提供。

一般项目配置与全局配置同时定义同一字段时的优先级、从子目录定位项目根的规则，以及目标配置文件不存在时能否自动创建，尚待确认；`[language].locale` 的专用优先级已经由第 11C 阶段冻结。

### `[language]` 系统提示语言

`config.xiao` 中的 `[language]` 表用于选择 Xiao 自身的系统文案语言，而不是切换源码关键字或翻译用户程序输出。首版规范结构为：

```xiao
[language]
locale = "zh-CN" # 可选 "en-US"；"zh"/"en" 是别名
```

项目 `config.xiao` 的设置覆盖全局 `config.xiao`，两者都没有设置时使用内置 `zh-CN`。有效语言上下文在 CLI 启动时解析一次，并传递给编译器、Runtime、包管理器、REPL、日志和诊断窗口；项目值非法时直接报告配置错误，不静默回退到全局值。详细的消息目录、回退和语言包插件契约见 [11c-localization.md](11c-localization.md)。

### 配置覆盖

命令行可以覆盖项目配置，但覆盖只影响当前进程或当前构建，不修改源文件。原规划中的 `xiao -VM config_path.xiao test.xiao` 先作为候选形式，最终选项名待 CLI 阶段确认。

## 一级工程目标：设计项目配置文件

### 规范文件名

项目根目录统一使用全小写 `config.xiao`。这是跨平台规范名称，文档、CLI 和错误消息不能交替使用 `Config.xiao`。配置采用 Xiao/TOML 风格的顶层表和顶格键值。

### 配置职责

`config.xiao` 集中保存以下项目级信息：

- 项目身份、版本、源码根和入口。
- 项目直接使用的外部包及版本/来源约束。
- 多个相互独立的包源及其传输/信任约束；包源可以是注册表、静态目录、本地目录或符合规范的 GitHub 仓库。
- 允许其他包导入的公共模块和公共符号。
- 平台、功能、权限或依赖使用约束。
- 原生构建需要固化的运行时默认值。
- 系统提示、错误说明、日志和调试窗口使用的 `[language]` 语言设置。
- CLI 的项目级行为，例如是否显示 Git 摘要。

它不保存每个源码文件实际写了哪些 `import`，也不要求用户手写所有传递依赖。下面的 `[Project]`、`[Dependencies]`、`[Exports]` 和 `[Constraints]` 仍是候选分表；`CLI.git.summary` 和 `[language].locale` 的字段语义已经冻结：

```xiao
[Project]
name = "app"
version = "0.1.0"
source = "src"
entry = "main"

[Dependencies]
http = { version = "^1.4" }
utils = { path = "../utils" }

[Exports]
modules = ["api", "models.user"]

[Constraints]
deny_imports = ["internal.debug"]

[language]
locale = "zh-CN"

[CLI]
git = { summary = true }
```

### 依赖锁文件

第 11A 阶段的依赖解析器根据每个包的直接依赖生成完整依赖图，并写入工具维护的依赖锁文件。接入后，运行、测试和构建必须复用同一锁定结果。本阶段只保留结构化配置和 CLI 扩展接口，不以生成锁文件为退出条件。锁文件的正式名称、序列化格式、校验算法和库/应用提交策略仍待定。

### 声明式解析边界

依赖关系必须在项目源码编译前读取。`config.xiao` 确定复用 Xiao 的词法器和语法基础，但只接受不可执行的声明式子集，禁止函数、控制流、导入、运行时变量和其他需要执行项目代码的构造。

配置允许哪些字面量和静态组合仍需形成白名单；平台条件和可选功能必须使用声明字段表达，不能通过在配置中执行 `if` 实现。

## 一级工程目标：预留环境与包管理入口

### 自动激活的项目环境

虚拟环境管理确定直接属于 `xiao` CLI，并在第 11A 阶段实现。`xiao venv` 创建后自动激活，`xiao sync` 创建或补齐环境后自动激活；二者通过预先初始化的 Shell 钩子修改当前终端，并为原提示符添加绿色 `$环境名$` 前缀。

`run`、`build` 和 `test` 仍默认自行定位项目环境，不以用户手工激活为前提。激活状态还用于决定 `install`/`i` 安装到当前虚拟环境还是全局环境。

### 全局缓存与项目隔离

第 11A 阶段实现的项目环境引用全局内容寻址的不可变包缓存，相同内容不在每个项目重复保存。环境状态必须绑定配置、锁文件、工具链和目标条件；源码缓存与目标文件缓存分开管理。这些能力不作为第 11 阶段核心 CLI 的退出条件。

完整架构、阶段和验收规则见 [11a-environments-and-packages.md](11a-environments-and-packages.md)。

语言配置、错误消息目录和可扩展语言包见 [11c-localization.md](11c-localization.md)。

## 一级工程目标：设计运行时配置

### 运行时表头

现有示例使用 `[VM]` 表头；它表达的是运行时配置，是否改名为更准确的 `[Runtime]` 在本阶段冻结。

### 配置项

候选配置项包括：

- `max_memory`：堆内存上限。
- `initial_memory`：初始申请内存。
- `call_stack_depth`：调用栈深度上限。
- `refcount_trace`：引用计数增减诊断。
- `memory_verbose`：分配、释放和内存错误诊断（替代无 GC 语义的 `gc_verbose`）。
- `jit_threshold`：未来实现 JIT 时的热点阈值；没有 JIT 时不得影响语义。
- `inject_env`：注入进程环境的键值列表。

配置值必须经过类型检查和范围检查；未知键可以在严格模式下报错，在兼容模式下给出警告。

### `[debug]` 诊断配置

`[debug]` 是与 `[VM]`/`[Runtime]` 并列的运行时诊断表。其最小语义包括：终端日志等级、文件日志等级、日志目录或文件、堆栈详细程度，以及按模块名或源码文件匹配的聚焦输出规则。聚焦规则默认把命中事件从总日志分流到指定文件；只有显式 `mirror` 才同时写入总日志。具体字段名称、默认目录和日志轮转在 CLI 阶段冻结。

示意结构：

```xiao
[debug]
terminal_level = "info"
file_level = "debug"
log_dir = "logs"
stacktrace = "full"
focus = [
    { module = "app.net", output = "logs/net.log", level = "trace", mirror = false }
]
```

### 原生构建固化

`xiao build` 可以把经过验证的运行时配置嵌入产物，让双击运行时拥有确定的默认行为。使用 `-debug` 构建时，调试激活位也必须嵌入产物，保证脱离 `xiao` 启动器直接启动仍打开独立诊断窗口；普通构建不得携带该强制激活位。命令行覆盖是否允许覆盖已固化的非激活配置，需要在构建发布阶段明确。

## 一级工程目标：完成跨平台层

### 路径与进程

文件路径、环境变量、进程退出码、动态库后缀和终端编码通过平台适配层提供，语言核心不直接拼接平台字符串。本阶段实现第 09、10 阶段抽象接口的主机接线与工具链发现，不回头改变已经冻结的运行参数对象或目标描述。

### 目标工具链

编译器需要读取目标三元组，选择对应 LLVM 目标、链接器、调试格式和 Runtime 实现。没有目标平台工具链时，错误应说明缺少的组件和安装方向。

## 二级实现任务

### CLI 实现

1. 建立 TypeScript 工程、静态检查、测试和跨平台命令入口。
2. 实现命令解析、帮助、版本和错误退出码，并区分无参数 REPL、`--inLF` 编辑入口与源码运行快捷方式。
3. 实现 `run`、`build`、`test` 和 `config` 的参数校验。
4. 让 `config` 按字段模式解析点分路径和值，并以结构化、原子写入方式修改项目或全局配置。
5. 为后续 `venv`、`sync`、`install`/`i`、依赖编辑和显式升级命令预留一致的子命令扩展接口。
6. 实现配置读取、命令行覆盖和配置诊断。
7. 输出可脚本消费的机器可读错误模式。
8. 通过稳定的进程或库接口调用编译器/执行核心（其中字节码 VM 与执行 Runtime 为 Rust 实现），不在 TypeScript CLI 中复制词法、类型或运行时语义；接口版本失配时给出明确诊断。
9. 为 Windows、Linux 和 macOS 生成独立 CLI 可执行程序，并在未安装 Node.js 的干净环境中验证启动。
10. 将 `-debug` 和 `[debug]` 归一化为后端诊断配置，不能在 CLI 中另造一套日志或堆栈语义；对调试构建写入不可绕过的诊断激活位，并传递独立窗口进程所需的启动信息。
11. 将 `[language].locale` 解析为不可变语言上下文并传递给所有系统提示边界；不在 CLI 中复制消息目录或错误格式化逻辑。
12. 在三个目标平台验证 TypeScript CLI 能启动、定位 Rust 核心并转发结构化 stdout/stderr、退出码、取消和诊断事件；不得通过解析本地化文本判断后端结果。

### 项目与依赖配置

1. 只识别规范名称 `config.xiao`，并在能够检测时诊断非规范大小写。
2. 分别解析项目元数据、直接依赖、包外导出、约束、CLI 设置和运行时配置。
3. 向第 11A 阶段提供结构化的直接依赖配置，不把传递依赖反写成用户配置。
4. 让 `run`、`test` 和 `build` 使用同一项目根、源码根和当前可用模块图。

### 国际化配置接线

1. 读取项目和全局 `[language]` 表，校验 `locale` 的规范标签/别名和项目优先级。
2. 向第 11C 阶段提供统一的语言上下文、配置来源和回退原因，不让各子命令自行选择语言。
3. 验证配置错误、帮助、包管理提示和调试入口都通过稳定消息身份渲染；机器可读错误不依赖译文。

### 平台实现

1. 封装路径、环境、时间和进程 API。
2. 为 Windows、Linux、macOS 建立最小构建矩阵。
3. 验证固定宽度数值和高精度库的二进制可移植性。
4. 验证原生程序的 Runtime 链接和发布目录结构。
5. 为第 17、18 阶段预留 `.xar` 文件关联的安装、检查和移除接口，但不把双击关联计入本阶段核心退出条件。

## 验收标准

### CLI 验收

- CLI 源码、测试和构建配置均以 TypeScript 为准，不出现另一套并行命令实现。
- 各目标平台的 CLI 以独立可执行程序交付，用户机器未安装 Node.js 时仍能显示帮助、进入 REPL 并调用已经安装的 Xiao 工具链组件。
- 新用户可以仅凭 `xiao --help` 运行脚本、构建程序和执行测试。
- 配置错误在执行前报告，并指出文件、表和键。
- `xiao config CLI.git.summary true` 把布尔值写入项目配置；加入 `--global` 后写入全局配置，非法布尔文本在写入前报错。
- 配置修改不会破坏无关表、键或注释，写入中断不会留下半个 `config.xiao`。
- `run` 与 `build` 对同一配置的语义一致。
- `run`、`.xar` 启动和 `build -debug` 对同一诊断配置使用一致的错误码、源码位置和日志等级；任何带 `-debug` 的直接运行以及调试产物启动都打开独立诊断窗口。调试版原生产物不依赖 `xiao` 启动器；`.xar` 仍由 `xiao -xar` 按 Runtime 前提启动，但窗口由独立诊断进程负责。普通 GUI 子系统设置不能抑制该窗口；无法创建窗口时必须报告明确的诊断启动失败，不能静默降级为普通运行。
- 项目 `[language].locale` 覆盖全局同名设置；缺少两者时使用内置 `zh-CN`，`zh`/`en` 别名能规范化为 `zh-CN`/`en-US`。
- 配置语言只改变系统提示和人类可读诊断，不改变源码、稳定错误码、退出码、机器可读输出或用户程序标准输出；非法语言值在执行前报告。
- 项目配置始终以全小写 `config.xiao` 识别。
- `run`、`build` 和 `test` 对同一项目使用相同的项目根、源码根和配置解析结果。
- 环境与包管理未实现时，核心 CLI 不伪造锁定结果，并能通过预留接口在第 11A 阶段加入自动激活及安装目标选择。

### 平台验收
