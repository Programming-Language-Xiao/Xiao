## 一、先澄清一处措辞：窗口是**新开的终端**，不是 GUI 窗口

`07:183` 写的是「诊断进程和诊断**终端**窗口」，而 `:195` 又提到「**无图形环境**下的失败
呈现」，`:197` 说窗口进程负责「滚动区域、固定状态栏、颜色和筛选」。三处措辞看起来不指向
同一个答案。

**已确认（2026-09-22）**：**就是新开一个终端窗口，不是 GUI 窗口。**

这条澄清一次解掉三处表面矛盾：

| 表面矛盾 | 澄清后的读法 |
| --- | --- |
| `00a:16`「不负责……**选择具体 GUI 框架**」 | **不受影响**——本批不选 GUI 框架，因为它不做 GUI |
| `:195`「无图形环境下的失败呈现」 | 指**找不到可用终端**时的行为（§5.2） |
| `:197`「滚动区域、状态栏、颜色、筛选」 | 是**终端里的 TUI**，不是窗口系统的控件 |

**所以**：本批的技术栈是「**平台终端 + TUI + 进程间管道**」，**不是** Tauri / egui /
WebView 一类。**不要因为看到"窗口"两个字就去引入 GUI 框架。**

## 二、范围与退出条件映射

X0 第 8 条是本批的唯一权威范围，逐句拆开：

| 第 8 条的要求 | 本批的落点 |
| --- | --- |
| `-debug` 能从 CLI 传递到运行/构建后端 | CLI → 协议 → `xiao-core` 的**激活位字段** |

| 无法创建窗口时必须报告明确失败，**不能静默降级** | §5.2 的失败路径 |

## 三、必须先裁定的三件事

### 3.1 诊断进程装在哪（**最重的一处**）

`07:197` 要求「**独立的诊断窗口进程**」，`07:217` 又要求「调试版原生程序**必须内嵌或随
产物携带启动该诊断进程所需的组件**，**不依赖外部 `xiao` 启动器**」。

**这一条把 TypeScript 排除了**：如果渲染器是 TS，`xiao build -debug` 的产物就得依赖
bun/node，直接违反 `:217`。

**候选**：

- **A. `xiao-core` 的一个模式**（例如 `xiao-core --diagnostics <endpoint>`）
  —— 复用现有二进制，零额外产物；
- **B. 独立的 Rust 二进制**（`xiao-diagnostics`）
  —— 职责更清晰，但 `xiao build` 的产物要**多带一个文件**；
- **C. CLI 侧**——**不可行**（见上）。

**选哪个都要回答**：调试版产物**怎么拿到**这个组件？（`07:217` 明说"内嵌**或**随产物
携带"，两条路都要说明可行性。）

### 3.2 平台终端启动

"新开一个终端"在三平台**没有统一做法**，而这是本批最容易低估工作量的一处：

| 平台 | 候选 | 难处 |
| --- | --- | --- |
| Windows | `cmd /c start`、`wt.exe`、`powershell Start-Process` | 需要区分有/无 Windows Terminal |
| Linux | `x-terminal-emulator`、`gnome-terminal`、`konsole`、`xterm` | **没有统一标准**，发行版差异大 |
| macOS | `open -a Terminal`、`osascript` | 相对统一 |

**必须给出**：

1. **查找顺序**（本批定死并写进文档）；
2. **每一条的失败行为**；
3. **全部失败时**的行为——`07:195` 说「不得静默降级为普通无窗口运行，**必须报告诊断
   启动失败**」，所以那是**明确失败**，不是"继续跑但没窗口"。

**与本仓既有经验的联系**：X0-C 刚做完「核心发现」——**同一类问题**（按顺序找可执行文件、
候选带来源、失败时列出尝试过什么）。**复用那个形状**，包括诊断的稳定 `code` 与候选列表。

### 3.3 匿名管道还是本地套接字

`07:197` 原文给了两个选项：「通过本地**匿名管道或本地套接字**发送」。

**要选一个并说明依据**。可考虑的点：

- **Windows 的匿名管道**与 **Unix domain socket** 的继承/命名语义差异；
- 调试版**原生产物**（不是 `xiao run`）启动诊断进程时，谁创建端点、谁继承句柄；
- `:197` 还要求「**通信中断时 Runtime 应继续运行**并把事件写入已配置的文件目标」——
  这一条对两种方案的压力不同。

### 3.4 窗口必须在**用户代码之前**就绪

`:183` 明说「必须在**执行用户代码前**启动独立的诊断进程和诊断终端窗口」。

**这意味着**：调试路径不能"先把程序跑起来、边跑边开窗"——窗口没起来之前，用户的程序
**不能开始执行**。要在验收里体现（§7 第 1 条）。

## 四、激活位与"不依赖 `xiao` 启动器"

### 4.1 激活位是**产物的一部分**

`07:217`：

> `xiao build -debug` 和 `xiao build -xar ... -debug` 必须把**诊断激活位、源码映射、
> 诊断元数据和运行时钩子能力**写入产物，产物启动时**自动**打开窗口，无需再次传参。

**所以**：激活位不是命令行开关的转发，而是**产物里的持久数据**。
`xiao build` 本身的工具链发现和协议路由归 X0-E（§4.2），但**激活位的格式与读取路径**
归本批；X0-E 负责把激活位和诊断组件写入最终原生产物。

**同时**：`:217` 要求「普通发布构建**不携带**该激活位，也**不得因 `[debug]` 配置自行
打开窗口**」——所以"有没有激活位"是**唯一**的判据，配置不能替代它。

### 4.2 `xiao build` 与本批的交接

`xiao build` 与主机工具链发现已经归 **X0-E** 落地。本批提供**激活位的形状**与**诊断进程的
启动路径**；X0-E 在调试构建中把 `xiao-diagnostics` 复制到可执行文件目录，并把最终组件
组件文件名交给 native startup shim；shim 运行时按自身可执行文件目录解析相邻路径。组件缺失、
复制失败或 shim 无法启动时均返回稳定诊断，不执行用户代码。

**不要**在本批重复实现工具链发现或改变 `build` 参数语义；构建参数、目标探测和配置固化
以 [11X0-E](11x0e-build-and-toolchain.md) 为准。

## 五、失败路径与不得静默降级

### 5.1 通信中断 ≠ 程序出错

`07:195`：

> 诊断窗口关闭、通信中断或日志目标写入失败**不能改变程序语义**。

**所以**：窗口崩了、被用户关了、管道断了——用户的程序**继续跑**，退出码**不变**。
这条要有断言（§7 第 4 条）。

### 5.2 开不出窗口 = **明确失败**

`:195` 末句：

> 在 `-debug` 启动阶段**无法创建强制诊断窗口**时，**不得静默降级**为普通无窗口运行，
> 必须**报告诊断启动失败**。

**这与 §5.1 不矛盾**，两者是**不同阶段**：

| 阶段 | 行为 |
| --- | --- |
| **启动阶段**开不出窗口 | **明确失败**（诊断启动失败），不跑用户代码 |
| **运行阶段**窗口没了 | **继续运行**，语义与退出码不变 |

**这个区分很容易写反**——把启动失败当成"继续跑"，或把运行中窗口关闭当成"程序失败"。
验收里要有**两条**独立用例。

## 八、验收

沿用 09R2D 的「撤掉实现 → 用例必须失败 → 还原 → 通过」。**关键验收不是「测试通过」**：

1. **窗口先于用户代码**：用一个会立即写标准输出的程序，断言诊断窗口就绪**早于**
   第一行用户输出（§3.4）；
2. **标准输出不被污染**：同一程序在 `-debug` 与非 `-debug` 下，**用户可见输出与退出码
   完全一致**（第 8 条的明写要求）；
3. **启动失败是明确失败**：在**没有可用终端**的环境下跑 `-debug`，得到的是**诊断启动
   失败**，**不是**"程序跑了但没窗口"（§5.2）；
4. **运行中断不影响语义**：运行中强制关闭窗口，程序**继续跑完**且退出码不变（§5.1）；
5. **激活位是持久数据**：`-debug` 构建的产物在**不带任何参数**直接启动时也开窗；
   普通构建**不带**激活位、**也不因配置**开窗（§4.1）；
6. **不依赖 `xiao` 启动器**：把调试产物**单独**放到一个没有 `xiao` 的目录里启动，
   窗口仍能打开（`:217`）；
7. **平台记录**：逐项说明每个环境用的是什么终端、跑了什么、**与 Windows 的差异**；
   macOS 仍记待复现；
8. **门禁全绿**，含 `check:lock`、`bunx tsc`，且跳过数可见。

## 十、实现记录（2026-09-23）

本批已按上面的约束落地。诊断渲染器选择独立 Rust `xiao-diagnostics` 二进制，原因是
调试原生产物不能要求用户安装 Bun/Node.js；它作为 `xiao` 分发目录中的相邻文件携带，
并由 `XIAO_DIAGNOSTICS_PATH` 或同目录发现。渲染器只消费诊断消息，不拥有 Xiao 前端、
Runtime 或用户代码入口。

Runtime 与窗口之间选择本机回环 TCP 套接字。我们评估过 UDS/AF_UNIX：Windows 10 1803+ 已
支持 AF_UNIX，但旧 Windows、命名空间生命周期和跨平台权限语义仍需额外适配；匿名管道的
句柄继承也会让脱离启动器的原生程序分出两套代码路径。回环 TCP 由 Runtime 在三平台统一
创建，随机端口加一次性令牌限制错误进程接入；**监听端口本身不是权限边界**，令牌只是纵深
防御。每条消息使用八字节大端长度前缀，帧上限为 4 MiB，握手顺序为 `hello`、`ready`、事件、
`final`、`close`。窗口进程没有反向请求消息类型。

`xiao-driver` 在 `FrontendVmDriver` 之前启动会话，因此窗口就绪是用户代码执行的前置条件。
终端候选顺序和来源固定，所有候选失败返回 `X11-DIAGNOSTIC-START-001`，并在 `details`
中列出命令、来源和失败原因。运行阶段写端断开、窗口关闭或文件目标失败只移除对应输出
目标；VM 继续运行，协议结果仍从原 `DriverOutcome` 派生，标准输出和退出码不经过诊断进程。

事件生产仍来自既有 `VmEventSink`。Runtime 把事件补齐单调时间、模块、源码、节点/函数、
错误编号字段和结构化负载；终端等级、总文件等级和聚焦文件规则独立过滤。聚焦命中事件
默认从总 JSONL 分流，只有显式 `mirror = true` 才镜像；错误计数在过滤前累加。状态栏刷新
只写终端，结束时才写入一次最终指标快照。

`xiao build` 协议响应在 `optimization.debug = true` 时写入旁置
`<executable>.xiao-debug.json` 激活位，并在响应中返回 `diagnostic_activation`；普通构建
会删除同名激活位。激活位格式和读写 API 位于 `xiao-diagnostics::window`，包含格式版本、
源码映射声明、元数据版本和钩子能力。X0-E 负责把该文件和诊断二进制放入最终原生产物
目录；启动桥只嵌入组件基名，并在运行时按自身可执行文件目录解析，因此三件文件可整体搬迁。
该行为已在 Windows 原生真实构建中验证；Linux 原生、WSL 和 macOS 仍待复现。

X0-E 的 Windows 原生启动桥使用 `CreateProcessW(CREATE_NEW_CONSOLE)`，不再让诊断进程继承
主程序控制台。桥接层传入一次性 `--ready-file`，诊断进程刷新首屏后写入标记，原生入口等到
标记出现才执行用户代码；创建失败、提前退出或五秒超时均返回
`X11-DIAGNOSTIC-START-001`。实测调试产物的主标准输出和标准错误均为空，缺失组件时在用户
入口前以 70 退出。

测试证据包括：共享 `debug-run-request.json` 的 Rust/TypeScript 双向帧回环、终端候选顺序、
激活位持久化/普通构建缺失、CLI `-debug` 结构化传递、诊断帧上限和真实运行驱动器回归。
真实终端测试使用 `#[ignore]` 显式门控；默认测试输出会显示 ignored 数量，不用条件 `return`
静默跳过。当前只宣称 Windows 原生端到端口径；Linux Docker 仅作构建/功能证据，Linux
原生、WSL 和 macOS 仍列入待复现清单。
