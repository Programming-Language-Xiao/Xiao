# 11A-E1. 本地依赖与共享缓存

> **这是 11A 的第三批。** 退出条件四条（`12-tests-and-milestones.md:742-750`）：
> ① 本地路径依赖可以进入经过校验的全局内容寻址缓存；② 两个项目环境可以复用相同包内容，
> 同时保持各自的依赖映射；③ Windows、Linux、macOS 通过只读逻辑映射读取同一缓存内容，

> 缓存内容使用前经过摘要验证，损坏条目不会进入构建。
>

## 三、必须先冻结的 7 条（**否则实现会先于设计**）

### 3.1 缓存根目录与全局环境的**实际位置**（已冻结：统一 `~/.xiao/`）

`00-decisions:625` 把**两条**一起列为待定——「全局环境与全局内容缓存的实际位置」。
**一起冻结，因为它们同根。**

```text
~/.xiao/                                   ← 用户域根，XIAO_HOME 可覆盖
  cache/
    objects/
      source/sha256/<前两位>/<digest>/     ← 源码包对象（本批）
      tmp/                                 ← 写入暂存，同文件系统内，保证 rename 原子
  envs/                                    ← 全局安装环境（E1 建映射，E2 建命令）
    <name>/.xiao-environment.json
```

**为什么选统一 `~/.xiao/` 而不是平台约定位置（`%LOCALAPPDATA%` / `~/Library/Caches` /
`$XDG_CACHE_HOME`）**：E1 条件 3 要求三平台读同一缓存内容。三条平台路径规则意味着
**三份文档、三份测试、三套形态**，而收益只是"更符合习惯"。统一根让
「三平台行为一致」变成**一条可断言的规则**，测试注入 `XIAO_HOME` 即可完全隔离。

**⚠️ 与 16 的对齐（否则会把两类对象混成一个命名空间）**：

- 本批源码包 → `objects/source/sha256/<前两位>/<digest>/`（**目录**，内含规范化文件树）；
- 16 的 `.xiaoc` → `objects/xiaoc/sha256/<前两位>/<digest>.xiaoc`（**单文件**）。

`16:3` 与 `11a:125` 都要求「构建产物、源码包和依赖锁文件必须保持**不同的命名空间与生命周期**」。
**把源码包放进 `objects/xiaoc/` 是硬性违规。**

**要一并冻结的还有 `XIAO_HOME` 的边界行为**（否则三平台各写一套）：

- 未设置 / 空串 → 回退到用户主目录下的 `.xiao`；
- 相对路径 → **报诊断，不接受**（相对路径在不同 CWD 下指向不同缓存，等于静默损坏）；
- 不可写 → 稳定诊断，不静默降级到别处。

### 3.2 摘要算法：**SHA-256，不是 `stable_hash`**

`00-decisions:295` 已经冻结：「**内容的同一性由摘要（SHA-256）判定**」。
所以算法没有选择余地，**但实现方式要定**。

**结论：引入 `sha2` crate（RustCrypto）。**

理由：本批要的是**密码学摘要**，用来满足条件 4「损坏条目不会进入构建」——
自造 SHA-256 是"自造规范化规则"的同类风险，而 `16:360` 已把 SHA-256 冻结为
`.xiaoc` 的内容寻址算法，将来 16 阶段要么复用本批实现、要么再引一次依赖。
**一份实现，两处消费。**

⚠️ **`xiao-package` 目前的外部依赖只有 `serde` + `serde_json`**，核心 crate 其余全是
零外部依赖（已核实）。加 `sha2` 是第二个外部依赖，**要在提交正文里说明理由**，
不能顺手加。

⚠️ **`stable_hash` 是 FNV-1a，绝不可用于完整性校验。** 它就在同一个 crate 里被
`environment.rs:12` import 着，**顺手拿它当内容摘要是最容易犯的错**——
FNV-1a 无抗碰撞性，改一个字节可能只改摘要几位且可被构造，条件 4 会变成纸面条款。
**指纹（`stable_hash`）与内容摘要（SHA-256）是两个不同强度的东西，不许互相替代。**

### 3.3 「规范化包内容」的定义（**E1 条件 1 的核心，也是单一来源病史的高发区**）

`11a:107` 说「以**规范化包内容**的加密摘要作为缓存身份」，但**规范化规则本身没冻结**。

必须冻结的最小集（不冻结则摘要不稳定，跨平台复用直接失败）：

| 维度 | 冻结口径 | 不冻结的后果 |
| --- | --- | --- |
| 路径分隔符 | 规范化输入一律 `/` | Windows 与 Linux 对同一包算出不同摘要 |
| 文件排序 | 按**路径字节序**（`BTreeMap` 序），不依赖 `read_dir` 顺序 | 同机两次运行摘要都可能不同 |
| 权限位 | **不参与**摘要 | Windows 无 Unix 权限位，跨平台必然不一致 |
| 换行符 | **不做 CRLF/LF 转换**，按字节摘要 | Git autocrlf 会静默改摘要 |
| 空目录 | **参与**（记一条空条目），或在文档里显式排除 | 两者都可，**但必须写死一个** |
| 符号链接 | **不跟随**，遇到即报诊断 | 跟随会让摘要依赖包外内容，且可能成环 |
| 绝对路径 | **不参与**（同 E0 的 `11ae0` 冻结口径） | 同一包在不同机器上摘要不同 |

**⚠️ 一条现实警告**：本仓自身的 Git 配置开启了换行符转换
（`git add` 会报 `LF will be replaced by CRLF`）。这意味着**同一个包在开了 autocrlf 的
机器和没开的机器上，磁盘字节可能不同**，于是摘要不同、缓存无法跨机器复用。

这不违反上述冻结规则——**摘要本来就该反映真实字节**。但**必须在文档里写明**：
跨机器内容复用的前提是**包内容字节稳定**，由 Git 克隆/检出配置引入的转换
**不在本批处理范围**，也不能靠"摘要时归一化换行"来掩盖（那会让摘要不再代表实际内容，
反而破坏条件 4 的完整性校验）。

**⚠️ 与 E0 配置指纹的关系（必须写清楚，否则会有人去"统一"它们）**：

- E0 的配置指纹输入是 `ConfigDocument::canonical_fingerprint_input()`
  —— **类型化的、带长度边界的规范编码**（`environment.rs:196`）；
- E1 的包内容摘要输入是**字节级目录树**；
- **两者共用的是"确定性"这个要求，不共用编码规则**，也**不共用哈希函数**
  （一个 FNV-1a、一个 SHA-256）。
- **不要为"统一"去改 E0 已冻结的编码**——那是已验证契约。

### 3.4 「只读逻辑映射」的物理形态（**`11a:109` 已排除三种最直觉的做法**）

`11a:109` 原文：「项目环境只保存指向缓存条目的**逻辑映射**，工具链根据映射**直接读取**
全局缓存，**不把缓存内容以符号链接、硬链接或副本暴露到项目环境**。」

**所以"逻辑映射"= 一份映射数据 + 一个读取器，不是任何文件系统级别的链接。**
这一条**同时解决了条件 3 的跨平台难题**——没有链接，就没有 Windows 缺 symlink 权限的问题。

要冻结的三件事：

1. **映射存在哪**：扩展 `.xiao-environment.json`（`environment.rs:20` 的
   `ENVIRONMENT_METADATA_FILE`），还是新增独立文件？
   **⚠️ 这触发 §3.5 的版本升级问题。**
2. **映射的键值形状**：键是 `PackageIdentity`（D1 的 `model.rs:78`），
   值是 `{ digest, object_kind }`。**键不能退化成包名**——`00-decisions:295` 明写
   「摘要**不替代锁文件里的逻辑包身份**」，反过来也一样。
3. **读取器是谁**：`xiao-package` 提供解析映射并定位对象的公共 API；
   **E1 不接 CLI**（§3.7），读取器的消费者是 E2 的 `sync` 与 11B。

### 3.5 `EnvironmentMetadata` 从 v1 升到 v2（**不能原地改契约**）

E0 冻结了 `ENVIRONMENT_METADATA_VERSION: u32 = 1`（`environment.rs:22`），
结构体字段见 `:86-106`。E1 要往里加依赖映射，**这是对已验证契约的结构性变更**。

**冻结口径**：**升版本到 2**，且读取侧必须：

- 读到 v1 → 按"无依赖映射的空环境"处理，**不报错**（E0 建的环境要能用）；
- 读到高于自身的版本 → 稳定诊断拒绝，**不猜测字段**；
- **同一个字段不写两遍**（不新增一个 v2 专用文件把 `environment` 指纹再存一份）。

⚠️ `:102` 的 `lockfile_summary: Option<String>` 是 E0 为 E2 预留的，
**E1 不要填它**——E1 不产锁文件（§十）。

### 3.6 缓存条目的只读与损坏隔离

`11a:109`：「缓存条目创建完成后**必须设为只读**，并在使用前验证内容摘要；
校验失败时**隔离损坏条目**，不能继续构建。」要冻结：

- **只读的跨平台口径**：Unix 用 `0o555`/`0o444`；Windows 用文件只读属性
  （**注意 Windows 的只读属性对目录基本无效，对文件才生效**）。
  若三平台无法做到同等强度，**要在文档里写明差额，而不是假装一致**。
- **隔离到哪**：不原地删除、不原地覆盖（`11a:111` 明禁"原地改写旧缓存条目"）。
  建议移到 `objects/source/sha256/<前两位>/<digest>.corrupt` 并报诊断。
- **诊断编号**：见 §四末尾。

### 3.7 E1 无命令入口（已冻结：核心 API + 测试驱动，**不碰 CLI**）

`sync`/`install`/`i` 都是 E2 的（`11a:438-445`），E1 自己没有用户入口。
**已冻结为**：`xiao-package` 提供物化 API，由 **Rust 集成测试**驱动真实闭环
（建两个项目 + 各自环境 + 一个全局环境，验证指向同一 object）。
**CLI 一行不改。**

这与 D1 同构——D1 也是核心逻辑批次、零 CLI 改动。

**⚠️ 由此产生一条必须写明的限制**：E1 交付后，**用户仍然无法通过 `xiao` 命令触发物化**。
这不是缺陷，是边界；但**必须在 `11a` 的 E1 章节里补一句**，否则下一个接手者
会以为 E1 漏了命令。

### 3.8 本地路径依赖的「不可变快照」语义

`11a:111`：「本地路径依赖导入缓存时必须形成经过校验的**不可变快照**；源目录后续发生变化
会产生**新的内容摘要**，**不能原地改写旧缓存条目**。」

要冻结的关键一条：**快照 = 把规范化后的包内容复制进缓存条目目录**（内容寻址天然去重），
**不是**记录一个指向源目录的引用。
即：**源目录之后被改/被删，缓存条目不受影响**——这正是条件 4「损坏条目不会进入构建」的另一半。

## 六、硬约束

### 6.1 单一来源

- **不重复扫描 `config.xiao`**：`05d:103` 明令 11/11A 直接消费 `ConfigDocument`；
- **不重建包图**：D1 的 `PackageGraph` 是唯一包图；
- **规范化规则只有一份**：写入侧算摘要、读取侧校验摘要，**必须调同一个函数**。
  两边各写一套正是本仓登记在案的头号病史。

### 6.2 确定性

缓存内容与映射的**遍历顺序必须确定**：用 `BTreeMap`，**不用 `HashMap` 的迭代顺序**
（D1/E0 已建立这个工程习惯）。映射写进 JSON 时字段顺序要稳定，
否则同一个环境两次物化产生不同文件内容。

### 6.3 不执行包代码

`00-decisions:288`：元数据解析与安装都**不得执行包代码**。
本批读包内容是为了**摘要与复制**，不解析、不执行其中的 `.xiao`。

### 6.4 门禁相关

- `A0-SIZE-001`：单文件 2500 物理行。`cache.rs` 若接近上限要拆。
- `A0-DOCS-001`：新增页面要登记，链接层级要对（**这个我上次栽过**）。
- doc-coverage：每个新增 `pub` 项都要有文档注释，门槛见 `00a:185`。

## 九、验收

沿用 D1/E0 的「**撤掉实现 → 用例必须失败 → 还原 → 通过**」。**关键验收不是"测试通过"**：

1. **条件 1**：本地路径包进入 `objects/source/sha256/…`；
   **同一内容放在两个不同路径 → 同一个 object，磁盘上只有一份**；
   **源目录之后被修改 → 产生新摘要，旧条目内容不变**（§3.8）。
2. **条件 2**：两个项目各自的环境映射指向**同一 object**，且两个映射**互不污染**
   （改一个不影响另一个）。
3. **条件 3**：**缓存的读取路径里不出现任何 `symlink`/`hard_link`/`copy`**
   —— 建议写成一条**区分度用例**：在只读权限下读取仍成功，
   且项目环境目录里**不存在**指向缓存的文件系统链接。
   三平台一致性靠**同一份测试**在 CI 四平台跑（沿用 X0 的平台复现工作流）。
4. **条件 4**：**手工篡改一个缓存条目的字节 → 必须报诊断且不进入构建**；
   损坏条目被隔离而非原地覆盖；全局环境与项目环境引用同一 object。
5. **契约兼容**：**手写一份 v1 元数据 → v2 读取器必须能读**（不能假设全是 v2）。
6. **`XIAO_HOME` 注入隔离**：测试全程注入临时 `XIAO_HOME`，
   **不碰真实 `~/.xiao`**；相对路径与空串的行为有正反例。
7. **确定性**：同一输入两次物化，**缓存条目路径与映射 JSON 字节一致**。
8. **门禁全绿**：`cargo test --workspace`、`cargo clippy --workspace --all-targets -- -D warnings`、
   `cargo fmt --all -- --check`、`bun test`、`bun run check`、`check:lock`、`bunx tsc`。

**顺带清上一批的欠账**（见 §十一），不必单开批次。
