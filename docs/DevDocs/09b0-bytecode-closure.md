## 一、冻结七项是本阶段的**输入契约**

09R3 `:637-638` 冻结的七项在 B0 及其后不得再改。B0 不是"重新决定"，而是"落实"：

| # | 冻结项 | B0 的落实方式 |
| --- | --- | --- |
| 1 | **最终字节码机型 = 栈式** | 生产运行入口只暴露栈式；见 §2.2 |
| 2 | **寄存器类别与分配策略** | `CategoryMap` 与线性扫描规则原样转正；生产验证器须校验类别映射与活跃区间一致 |
| 3 | **函数调用 ABI** | `CallSigTable` / `ParamKind` / `TAC_BYTECODE_ABI_VERSION` 原样转正；见 §4.1 |
| 4 | **异常与清理转移 ABI** | handler 表、`finally` 子程序、释放序列的转移语义原样转正 |
| 5 | **指令编码与版本字段** | `FORMAT_VERSION = 3`、opcode `0..40`、两种操作数宽度；**只能追加不得重排** |
| 6 | **源码映射格式** | `PcMap` / `span_at_pc` 的查询语义原样转正 |
| 7 | **性能阈值与基准协议** | 不重跑、不改口径；`tests/benchmarks/` 原样保留 |

### 1.1 冻结不等于公开：R1-AB 继续有效

09R `:422`（R1-AB）定的是：**研究编码不是公开文件格式**，不得使用 `.xiaoc` 扩展名落盘、
不得借研究编码提前冒充公开格式。**办理迁移不等于解除这条**——

- 生产 `xiao-bytecode` 的 `MAGIC` 仍是研究魔数 `X9RD`，**不得改成 `XIAOC`**；
- B0 不改 `14-bytecode-optimization.md:39` 冻结的文件头魔数（`58 49 41 4F 43 0D 0A 1A`）；
- 正式分段容器、分区目录与加载器仍归第 14 阶段。

**换句话说**：B0 转正的是**指令层与执行层**，不是**文件层**。这两件事在 09 文档 `:64` 里
已经分开写死：「本阶段先完成内存字节码和虚拟机最小闭环，第 14 阶段再实现正式 `.xiaoc` 格式」。

## 二、总体方案：迁移转正（四条已定决策）

### 2.1 决策一：迁移转正 + `research` 兼容重导出

**已定（2026-09-20）**：研究模块的实质内容迁到 crate 根的生产路径，`research` 目录保留为
**重导出别名层**。

依据是 `xiao-bytecode/src/research/mod.rs` 自己的措辞：「试验性指令、寄存器类别和调用签名
**在 09R3 冻结前**不得被 `xiao-driver`、CLI 或任何生产路径依赖」——**冻结后这扇门就开了**。

选它而不是「目录改名」或「另写一份」，理由是后两者各自的代价：

- **另写一份**会让 opcode 表、语义核、编码器各出现两位主人。这正是本仓 09R2D `:174`
  登记的「同一条规则在两层各写一份，然后漂移」——**A 类缺陷，已犯 7 次，是头号病**。
- **目录改名**要同步触碰 79 条共享向量所在的测试、6 个 `r2_*.rs`、`tests/benchmarks/`
  与两处模块登记，把一次纯移动变成大面积改动，审核时**无法用 `git diff --stat` 一眼判定
  "没有语义变更"**。

别名层带来一个必须记账的债项：**移除计划**。触发条件是「**`tests/benchmarks/src/main.rs`
与 6 个 `r2_*.rs` 都改到生产路径之后**」；届时再删别名层。

> **2026-09-21 修正**：本条原先写的是「B0-C 交付且生产驱动器成为唯一消费方」，那是错的——
> 别名层的消费方是**测试与基准工具**，不是生产驱动器（驱动器从一开始就会用生产路径）。
> B0-C 交付后别名层照样有人用，按错误条件判断会误删。详见
> [09-B0-C](09b0c-frontend-to-vm-driver.md) 第七节。

### 2.2 决策二：`machine/` 整体转正，生产入口只暴露栈式

**已定（2026-09-20）**：`carrier.rs` 与 `machine/{stack,register,hybrid}.rs` 一并迁入生产层。

理由有两条，第二条是决定性的：

1. `semantics/` 的核心是 `impl<C: Carrier>`。把 `Carrier` trait 留在研究层、语义核放进生产层，
   会制造一条**人为的层级缝**（生产依赖研究），方向恰好是 09R2D `:426` 明令禁止的反向。
2. 09R3 冻结的是「**选栈式**」，不是「**删掉另外两个**」。Linux/macOS 仍在**待复现清单**上
   （09R3 `:131`），三载体齐全是复现该清单的前提。删掉它们等于作废一项已交付资产。

**但"代码归属转正"不等于"产品地位转正"。** 生产 API 面必须让栈式成为唯一入口：

- `xiao_vm::run(program, options) -> RunOutcome` 走栈式，**这是生产契约**；
- `xiao_vm::machine::{RegisterCarrier, HybridCarrier}` 公开可达（基准与复现需要），
  但**不是生产 ABI**，其文档注释必须明说这一点；
- 生产驱动器（B0-C）**不得**提供机型选择参数。09 文档 `:45` 要求「平台差异只能位于适配层，
  不能改变字节码结果」，同理，机型也不该成为运行期可调项。

### 2.3 决策三：B0 的范围是**单模块**

**已定（2026-09-20）**：B0 只跑单文件脚本与单模块 `[main]`。

依据：`FrontendArtifact.ir` 的类型就是**单个** `IrProgram`（`xiao-driver/src/frontend.rs:174`），
`ExternalModuleGraph` 只携带外部包名列表，不含模块内容。这与 09 文档 `:64`「每个 `.xiaoc`
只表示一个模块」和 14 文档 `:11`「不得把跨模块依赖偷偷塞进单个模块文件」都一致。

多模块工程图、依赖解析与锁文件归 D/E 阶段。**不要为"看起来完整"而擅自扩大范围**——
那会把一个可验收的执行闭环变成半个包管理器。

### 2.4 决策四：三批交付，一批一交接

**已定（2026-09-20）**：按权威定义 (`09r:642-649`) 的 `B0-A → B0-B → B0-C` 顺序推进，
**每批独立可验收、可审核、可回滚**。前一批的门禁与区分度证据是后一批的入场条件。

| 批次 | 内容 | 对应权威定义 |

### 3.1 迁移的具体形状

**`xiao-bytecode`**

| 从 | 到 |
| --- | --- |
| `src/research/{tac,cfg,liveness,sig,verify}.rs` | `src/` 同名 |
| `src/research/lower/` | `src/lower/` |
| `src/research/encode/` | `src/encode/` |
| `src/research/mod.rs` | 改为**重导出层**，保持 `research::X` 全部路径可用 |

**`xiao-vm`**

| 从 | 到 |
| --- | --- |
| `src/research/{carrier,frame,ops,sink,run}.rs` | `src/` 同名 |
| `src/research/semantics/` | `src/semantics/` |
| `src/research/machine/` | `src/machine/` |
| `src/research/mod.rs` | 改为**重导出层** |

**重导出层必须覆盖所有既有公开路径**，包括 `research::encode::{...}`、
`research::machine::stack::StackCarrier` 这类嵌套路径。`tests/benchmarks/src/main.rs:15-17`
同时用了 `xiao_bytecode::research::{FORMAT_VERSION, OPCODE_MAX, encode, lower_program}`
和 `xiao_driver::{FrontendCompiler, FrontendRequest}`——它是**别名层完整性的现成回归夹具**，
迁移后**必须原样能编译通过**，一个字符都不改。

模块级文档注释要同步改口径：「研究原型，冻结前不得依赖」→「**生产接口**；沿革见 09R2D，
冻结依据见 09R3」。**不要**把 09R 的历史抹掉——它是这套设计的依据。

### 3.2 迁移提交必须是**纯移动**

本批的第一个提交只做移动与路径改写，**不得夹带任何语义变更**。判定方式是审核者能用

```text
git show --stat <sha>        # 只有重命名
git show -M --stat <sha>     # 重命名检测下增删行数应为 0
```

一眼确认。**任何行为改动都另开提交**——把"移动"与"改动"混在一笔里，正是 09R2H 那条
★ 约束要防的形态：审核者只能读 diff 反推意图，而他**没有义务**替你还原。

### 3.3 中心不变量：生产路径上 `TacProgram.unsupported` 恒为空

**这是 B0-A 最重要的一条，也是它真正的实质工作量。**

现状（已实测）：

- 降低器有一张覆盖 **14 个 RuntimeCheckKind** 的白名单（`src/lower/mod.rs`）。不在其中的
  构造仍会走 `record_unsupported`，但生产验证入口会把它作为内部一致性错误拦截；合法前端
  产物不会留下该向量。
- `encode/validate.rs:40` 对非空 `TacProgram.unsupported` **直接拒绝编码**；
- 于是「前端接受了的合法程序」在**编码期**才失败，且拿到的是 `EncodeError::Unsupported`
  ——一条**没有源码位置、没有稳定诊断码**的路径。

这在研究期是**正确的保守设计**（宁可拒绝也不静默算错），但生产上不成立：09 文档 `:120`
要求「为每个可观察执行结果保留稳定的结构化表示」，`:106` 要求错误上下文必须含稳定的
`code`、`message_id` 和结构化参数。

**B0-A 的裁定**：

1. **保留字段与编码布局**（`Vec<String>`、`count + string`），**不改结构**。改字段类型会动
   程序级布局，等于在已冻结的编码上开新口子——正是 09R3 `:84` 禁止的重新冻结。
   这一点没有商量余地。
2. **生产路径必须使该向量为空**，并且这是一条**可断言的不变量**，不是一个约定：
   B0-A 要提供一个验证入口（挂在 `verify` 或新增并列入口），在驱动器消费前断言
   `unsupported.is_empty()`，非空即报**内部一致性错误**。
3. **`record_unsupported` 的每一处调用点都要复核**，逐个回答：它守的是"已知未实现的
   语言语义"（→ 应该在更早的层被拒绝），还是"不应发生的内部错误"（→ 应该是断言的失败边）。
   `lower/mod.rs:332`（`运行时检查未消费：{kind}`）尤其可疑：它意味着**某个 span 上的检查
   被发射了但没人消费**，那是接线缺口，不该以"记账后拒绝编码"收场。

### 3.4 `string_boolean`：本批**唯一**需要裁定的语义缺口

实测确认：`RuntimeCheckKind` 共 14 个变体，B0-A 已把此前唯一缺口
`string_boolean` 接入降低白名单；`xiao-ir/src/lower.rs` 的穷尽性测试继续钉住字符串桥接。

它的触发是**字符串转布尔**（`x as bool` / `bool(x)`，`ConversionKind::StrToBool`）。
此前含该构造的程序无法通过研究编码器；B0-A 后检查会进入 TAC，编码与验证均可通过，
基准程序仍按 09R3 既定协议避开三条拒绝路径。

**B0-A 的结论是接通**，理由按强度排序：

1. **它是中心不变量的唯一破坏者**（§3.3）。不变量是"**恒为空**"——只要有一条能触发，
   B0 就得永远带着 `unsupported` 的处理路径，B0-B/B0-C 都要为一条**理论上不该发生**的
   路径写代码。接通它，这条路径就真的死了。
2. **类型层语义已经通过前置里程碑**。`ConversionKind::StrToBool` 与 `RuntimeCheckKind::StringBoolean`
   都是 02/03 阶段已冻结的成果；B0 退出条件第 3 条要求「只纳入**已经通过前置里程碑**的语义」
   ——这不构成新增语言语义，是**补接通**。
3. 工作量可控：白名单加一项，`check_value` 复用 `RuntimeValue::convert_to(ScalarType::Bool)`
   的唯一规则，并使用既有 `TYPE_MISMATCH_CODE`。降低测试确认检查位于 `Cast` 前，三载体
   回归覆盖四种合法拼写和非法拼写。

因此不需要降级 §3.3 的不变量；非空 `unsupported` 只代表降低器与生产契约的内部缺口，
由 `verify_production` 以 `X09-BYTECODE-001` 拒绝。

> 无论走哪条路，**绝不能用 `record_unsupported` 给它（或任何东西）记账**——一记就把
> 编码体积指标整条堵死，而且要到验收才流血。这条 09R2F1 已写过一次，这里再写一次。

### 3.5 验证器加固

`09r:645` 要求「建立指令边界、寄存器类别、跳转目标、调用帧和释放计划验证」。研究的
`verify.rs`（三地址自校验与释放序列对账）与 `encode/validate.rs`（编码输入不变量）已覆盖
大部分，但它们是**研究级**的。逐项核对并补齐：

| 项 | 现状 | B0-A 要做的 |
| --- | --- | --- |
| 指令边界 | `decode_op` + 引用验证 | 核对未知 opcode、越界引用、定宽溢出在**生产入口**同样拒绝 |
| 寄存器类别 | `CategoryMap` 有，但 09R2D `:149` 记过「没有任何生产代码消费 `TacProgram.categories`」 | 让类别映射与活跃区间**互相校验**，不再是只写不读的字段 |
| 跳转目标 | `cfg::jump_targets` 有，但 09R2D `:426` 的架构测试只保证依赖方向 | 校验目标块存在且在函数内；新增 `TacOp` 时 `jump_targets` **编译器不强制**（09R2D 8 处清单第 7 处） |
| 调用帧 | `CallSigTable` 有 | 校验实参个数/类别与签名一致、`CallSub`/`RetFromSub` 配对 |
| 释放计划 | `reconcile_release_plans`（`X08-IR-003`）有 | 确认它在生产路径上**真的被调用**，而不是只有测试在调 |

**注意**：`TacProgram.categories` 那条是本批最可能"看起来已经有、实际没人用"的一项。
09R2D 已经因为同款问题被记过一次（09R2G 漏改三处文档）。**判据不是"字段存在"，
而是"有没有一条断言会在它错的时候失败"。**

B0-A 的落点如下：生产 `verify_program` 对每个函数使用局部 `TacFunction::categories`，
将指令使用/定义和活跃区间逐一登记；程序级 `TacProgram::categories` 只保留兼容观察用途。
`verify_production` / `verify_for_execution` 在编码器或执行器消费前返回结构化错误，

## 四、B0-B 方向：生产 VM 执行闭环（仅定方向）

`09r:646-647` 的范围是「接入 `xiao-runtime`、统一错误、表生命周期、容器和选择器；
保持调试事件接收器，但不实现诊断窗口」。研究 VM **已经**接了前四项，所以 B0-B 的实质
新增是**把研究期的临时契约换成生产契约**：

### 4.1 生产入口 ABI —— 本批的核心新增

研究 VM 的入口**明确声明自己不是生产 ABI**（`xiao-vm/src/research/run.rs`）：

- `RunOutcome.value`：「为了让 09R 研究测试观察语义结果而暴露的调试字段，**不是生产执行
  接口的稳定承诺**」；
- `run_with_values`：「只供研究 VM 的动态边界向量注入入口形参；实参按入口函数的形参声明
  顺序绑定，**不承诺生产 VM 的脚本调用 ABI**」。

B0-B 要定义的是 09 文档 `:163` 要求的**两种模式**：

| 模式 | 入口语义 | 依据 |
| --- | --- | --- |
| **脚本模式** | 直接执行顶层语句；无 `[main]` 时的快速启动路径 | 09 文档 `:127`、`:163` |
| **`[main]` 工程模式** | 按 `[main]` 的签名绑定参数并调用 | 09 文档 `:163`、04 阶段的入口元数据 |

两种模式的参数绑定、返回值与退出码必须**各有唯一来源**，不得各写一份。
04 阶段已产出「脚本/工程入口元数据」，**先查它能不能直接消费**，不要重新推断。

### 4.2 其余四项

- **结构化结果**：`RunResult { Success, Error(XiaoError), Fatal(FatalError) }` 的分工是好的
  （`Fatal` 不是"更严重的错误"，它不可被 `catch` 恢复、不执行释放计划），**沿用**；
  B0-B 要补的是**退出码**与**结构化诊断**，且不得让消费方解析人类可读文本（09 文档 `:120`）。
- **栈回溯与源码位置**：`PcMap::span_at_pc` 已有，接上统一 `StackFrame` 与 `ReportRecord`
  （07-A 交付）。
- **`VmEventSink`**：`sink.rs` 的 `RecordingSink` 是研究实现。B0-B 要把它变成**生产事件
  接口**（09R `:611` 要求至少记录模块、函数、作用域、释放、错误、堆栈和运行指标）。
- **不实现诊断窗口**：`-debug` 的**窗口进程启动**归 X0（12-tests `:700` X0 退出条件第 8 条
  才要求窗口）。B0 只交付**事件发送接口**。这条是有意为之的边界，不要顺手补。
