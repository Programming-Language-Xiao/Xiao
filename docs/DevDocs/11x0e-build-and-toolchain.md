## 二、三块工作

### 2.1 主机工具链发现（**本批的核心**）

`10:57`：「通过受控目标描述和测试适配器验证三个目标……**主机工具链自动发现留到第 11 阶段**。」
`10:21` 也把主机路径、进程与工具链发现划给本阶段。

**要发现的**（`10A` §2.1 已定 N0 用调用方注入，现在要补上"怎么找到"）：

| 工具 | 用途 | 备注 |
| --- | --- | --- |
| `clang` | 编译 LLVM IR、链接 | N0-A 实测用的就是它 |
| `llvm-as` | 验证 IR 语法 | `10A` §1.1 的"语法验证"那条腿 |
| `llc` | 可选，按需 | |
| `rustc` | 查 `--print native-static-libs`（10C 的教训） | **版本要进构建指纹** |

**必须复用 X0-C 的形状**（`11X0-C` §2.2）：候选按顺序、**候选带来源**、
失败时**列出尝试过什么**而不是一句"找不到工具链"。

**两个必须回答的问题**：

1. **版本匹配怎么判**？`llvm-toolchain.toml` 登记了 `minimum_major = 18`——
   找到的 clang 低于这个数怎么办？（拒绝？警告？）
2. **找不到的自然后果**：`xiao build` 报**稳定诊断**并**不产出半成品**，
   而不是"构建失败"这种不可编程的文本。

**落地口径**：`clang` 是必需工具，`llvm-as`、`llc` 和 `rustc` 按需记录；候选来源固定为
`override`、`adjacent`、`path`、`development`。显式 `XIAO_CLANG`、`XIAO_RUNTIME_LIBRARY`
或 `XIAO_DIAGNOSTICS_PATH` 指向无效文件时立即返回 `X11-CLI-TOOLCHAIN-OVERRIDE-001`，
不静默回退。clang 主版本低于 `minimum_major` 返回
`X11-CLI-TOOLCHAIN-VERSION-001`。发现成功后还用目标三元组做一次真实 C 编译/链接探测；
MSVC 目标若实际只有 GNU ABI 或 SDK/linker 不可用，在产出前返回
`X11-CLI-TOOLCHAIN-TARGET-001`/`X11-CLI-TOOLCHAIN-LINK-001`。

### 2.2 `xiao build` 命令路由

后端已经做完了（N0-A/B），本批只接路由：

- CLI 的 `build` 子命令 → 协议 `build` 消息 → `xiao-core` → `FrontendNativeDriver`；
- **产物位置**：默认输出到哪、`-o` 怎么解析，本批定死；
- **优化级别**：`10:37` 说普通原生构建默认 `-O0`，且**第 15 阶段才有优化**——
  本批只接 `-O0`，**不要顺手做优化级别解析**（那是 15/18）。

**落地口径**：输入必须是 `.xiao`；未给 `-o` 时写入 `build/<源码基名>[.exe]`，
`--emit-llvm` 可额外写出 LLVM 文本；`-O1` 至 `-O3` 和其他优化值稳定拒绝。

### 2.3 原生启动 shim（X0-D 留的）

X0-D 的落地记录写明：

> X0-E 继续负责尚未冻结的**原生启动 shim**。

`07:217` 要求「调试版原生程序**必须内嵌或随产物携带启动该诊断进程所需的组件**，
不依赖外部 `xiao` 启动器」。

X0-D 交付了**诊断组件**（`xiao-diagnostics` 二进制）与**激活位**（旁置 `.xiao-debug.json`），
但"**产物怎么启动它**"没冻结。本批要定：

- 产物在启动时**怎么找到** `xiao-diagnostics`（同目录？随产物携带？）；
- **在什么时机**启动（必须在用户代码之前，`07:183`）；
- **找不到时**的行为（`07:195`：明确失败，**不得静默降级**——与 X0-D §5.2 同一条规则）。

**落地口径**：调试构建把 `xiao-diagnostics` 复制到原生可执行文件所在目录，并把启动 shim
链接进 `main`；shim 在用户入口前启动 `--standalone --parent-pid --ready-file`。Windows 路径
使用 `CreateProcessW(CREATE_NEW_CONSOLE)` 创建独立控制台，只有诊断进程刷新首屏并写入就绪
标记后才放行用户入口；子进程提前退出或五秒内未就绪都返回
`X11-DIAGNOSTIC-START-001` 对应的非零结果。普通构建不写激活位，也不复制强制开窗组件。

**这条与 §2.1 是同一个问题的两个面**：一个是找**构建**工具链，一个是找**运行时**组件。

## 三、运行时配置固化（`11:212-220`）

`11:212`：

> `xiao build` 可以把经过验证的运行时配置**嵌入产物**，让双击运行时拥有**确定的默认行为**。

`11:220` 自带一个**待定决策**：

> 命令行覆盖是否允许覆盖已固化的非激活配置，**需要在构建发布阶段明确**。

**本批要处理**：

1. **嵌入哪些配置**？`11:177` 的运行时表头与 `:191` 的 `[debug]` 诊断配置是候选；
2. **激活位与普通配置的关系**：`-debug` 的激活位**必须**嵌入（`:212` 末句、`07:217`），
   而普通配置的嵌入规则**不同**——`07:217` 明说普通构建**不得**因 `[debug]` 配置自行开窗；
3. **`:220` 那个待定决策**：给出结论并写进 `11-cli-config-and-platform.md`。
   **不要**留给"构建发布阶段"——本批就是那个阶段的前半。

**本批结论**：经过 `parse_config_text` 校验的配置写入
`<executable>.xiao-runtime.json`，摘要格式版本为 `1`，并声明 `cli_overrides = true`。
命令行覆盖只在当前进程/当前构建生效，允许覆盖普通 Runtime 和日志字段，不回写
`config.xiao`；`-debug` 是唯一的激活位，普通 `[debug]` 配置不能自行开窗，命令行也不能
关闭调试产物的强制开窗。激活位与运行时配置分开写入，避免普通构建因残留 `[debug]` 表格而
改变启动语义。

### 5.1 X0-D 的回环通信缺一段理由

X0-D 选了**本机回环 TCP** 作为 Runtime 与诊断进程之间的通道，理由是「Windows 匿名管道
句柄继承和 Unix 管道/套接字语义不一致，而回环端点可由 Runtime 在三平台统一创建」。

**但 `07:197` 的原文是「本地匿名管道或本地套接字」**，而"本地套接字"在中文语境里通常指
Unix domain socket。Windows 10 1803+ 也支持 AF_UNIX，所以"三平台统一"对 UDS 同样成立。

**本批要做的**：在 `11x0d` 的落地记录里**补一句 UDS 的对比**——说明是评估过才选 TCP，
而不是没想到。TCP 回环是**监听端口**而非文件系统对象，本机任何进程都能尝试连接
（一次性令牌缓解了这一点，但那是纵深防御而非权限控制）。

**这不影响 X0-D 的验收**，是记录完整性问题。

**结论**：已在 `11x0d` §十补记 UDS 评估。AF_UNIX 在 Windows 10 1803+ 可用，确实能统一
三平台，但 UDS 的地址生命周期、抽象命名空间和旧 Windows 部署差异仍需额外适配；本批保留
随机端口 TCP，并用一次性令牌和本机绑定降低误连风险。TCP 监听端口不是权限边界，这一点已
写入风险记录。

**结论**：本批不把取消检查分支塞入冻结后的 VM 热循环。`B0-C-CANCEL-001` 转交新批次
**09-B0-E「VM 中途取消检查点」**；该批的出口条件是可注入取消源、指令循环检查频率、
清理/退出码回归和关闭检查点后的性能对照。09R3 的固定基准不采取消路径，因此本批数字
不受影响；在 09-B0-E 完成前只能宣称阶段边界取消。

## 十、落地记录（2026-09-23）

本批已完成从真实 Xiao 源码到原生可执行文件的完整路由：TypeScript CLI 读取 `.xiao` 和
项目 `config.xiao`，按固定顺序发现工具链，发送版本协商后的 `build` 消息，Rust 核心再经
`FrontendNativeDriver`、N0 LLVM 后端和外部 clang 生成产物。协议新增字段均带默认值，旧的
`run`/`hello` 形状保持兼容。

工具链发现的机器诊断保留每一次候选的路径、来源、状态、版本和失败原因。Windows 原生实测
使用 Visual Studio 开发环境中的 MSVC 目标 clang，真实构建了
`tests/benchmarks/programs/deep-expression-arithmetic.xiao`，产物脱离 `xiao` 直接运行并返回
零退出码；当前机器默认 PATH 的 MSYS2 GNU clang 会在发现阶段被目标/链接探测拒绝，不再等到
后端返回不可编程的链接文本。

调试构建把 `xiao-diagnostics` 复制到产物目录。Windows 启动 shim 使用
`CreateProcessW(CREATE_NEW_CONSOLE)` 拉起相邻组件，并以
`--standalone --parent-pid --ready-file` 完成就绪握手；只有新控制台刷新首屏后才进入用户代码。
shim 只把诊断组件的文件名编入原生代码，运行时按自身可执行文件目录解析相邻路径；因此将
可执行文件、激活位和诊断组件整体搬到另一目录仍然有效，不会携带构建机绝对路径。
组件复制失败、创建进程失败、子进程提前退出和就绪超时都保留稳定诊断。`config.xiao` 只接受
配置 crate 的静态树，非法文本不会生成可执行文件；合法配置旁置摘要声明允许普通字段覆盖，
但激活位仍由 `-debug` 独占。

验证记录：TypeScript 类型检查、CLI 定向测试、Rust `xiao-driver`/`xiao-codegen-llvm`/
`xiao-diagnostics` 定向测试、真实 Windows 原生 build/run/debug 回环均通过。调试产物直接运行
返回零，主标准输出和标准错误均为空；把诊断组件覆盖为不存在的路径时，产物在用户入口前以
70 退出并报告 `X11-DIAGNOSTIC-START-001`。工具链真实 smoke 测试默认以显式跳过计数呈现，
只有设置 `XIAO_TOOLCHAIN_SMOKE=1` 才会运行。Linux 原生、WSL 和 macOS 未在本批运行，仍按
§5.5 待复现。
