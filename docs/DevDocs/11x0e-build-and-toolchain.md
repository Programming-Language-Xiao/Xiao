## 二、三块工作

### 2.1 主机工具链发现（**本批的核心**）

`10:57`：「通过受控目标描述和测试适配器验证三个目标……**主机工具链自动发现留到第 11 阶段**。」
`10:21` 也把主机路径、进程与工具链发现划给本阶段。

**要发现的**（`10A` §2.1 已定 N0 用调用方注入，现在要补上"怎么找到"）：

| 工具 | 用途 | 备注 |
| --- | --- | --- |
| `clang` | 编译 LLVM IR、链接 | N0-A 实测用的就是它 |
| `llvm-as` | 验证 IR 语法 | `10A` §1.1 的"语法验证"那条腿 |
| `llc` | 可选，按需 | |
| `rustc` | 查 `--print native-static-libs`（10C 的教训） | **版本要进构建指纹** |

**必须复用 X0-C 的形状**（`11X0-C` §2.2）：候选按顺序、**候选带来源**、
失败时**列出尝试过什么**而不是一句"找不到工具链"。

**两个必须回答的问题**：

1. **版本匹配怎么判**？`llvm-toolchain.toml` 登记了 `minimum_major = 18`——
   找到的 clang 低于这个数怎么办？（拒绝？警告？）
2. **找不到的自然后果**：`xiao build` 报**稳定诊断**并**不产出半成品**，
   而不是"构建失败"这种不可编程的文本。

### 2.2 `xiao build` 命令路由

后端已经做完了（N0-A/B），本批只接路由：

- CLI 的 `build` 子命令 → 协议 `build` 消息 → `xiao-core` → `FrontendNativeDriver`；
- **产物位置**：默认输出到哪、`-o` 怎么解析，本批定死；
- **优化级别**：`10:37` 说普通原生构建默认 `-O0`，且**第 15 阶段才有优化**——
  本批只接 `-O0`，**不要顺手做优化级别解析**（那是 15/18）。

### 2.3 原生启动 shim（X0-D 留的）

X0-D 的落地记录写明：

> X0-E 继续负责尚未冻结的**原生启动 shim**。

`07:217` 要求「调试版原生程序**必须内嵌或随产物携带启动该诊断进程所需的组件**，
不依赖外部 `xiao` 启动器」。

X0-D 交付了**诊断组件**（`xiao-diagnostics` 二进制）与**激活位**（旁置 `.xiao-debug.json`），
但"**产物怎么启动它**"没冻结。本批要定：

- 产物在启动时**怎么找到** `xiao-diagnostics`（同目录？随产物携带？）；
- **在什么时机**启动（必须在用户代码之前，`07:183`）；
- **找不到时**的行为（`07:195`：明确失败，**不得静默降级**——与 X0-D §5.2 同一条规则）。

**这条与 §2.1 是同一个问题的两个面**：一个是找**构建**工具链，一个是找**运行时**组件。

## 五、需要完善的方面（**跨批次带过来的，一并记账**）

这一节是历次审核中确认的、**尚未关闭**的事项。本批能关的关掉，关不掉的**明确转交**。

### 5.1 X0-D 的回环通信缺一段理由

X0-D 选了**本机回环 TCP** 作为 Runtime 与诊断进程之间的通道，理由是「Windows 匿名管道
句柄继承和 Unix 管道/套接字语义不一致，而回环端点可由 Runtime 在三平台统一创建」。

**但 `07:197` 的原文是「本地匿名管道或本地套接字」**，而"本地套接字"在中文语境里通常指
Unix domain socket。Windows 10 1803+ 也支持 AF_UNIX，所以"三平台统一"对 UDS 同样成立。

**本批要做的**：在 `11x0d` 的落地记录里**补一句 UDS 的对比**——说明是评估过才选 TCP，
而不是没想到。TCP 回环是**监听端口**而非文件系统对象，本机任何进程都能尝试连接
（一次性令牌缓解了这一点，但那是纵深防御而非权限控制）。

**这不影响 X0-D 的验收**，是记录完整性问题。

### 5.2 `B0-C-CANCEL-001`：VM 中途取消检查点

`09-B0-C` 记的债：驱动器只做**阶段边界采样**，**VM 指令循环的中途检查点**留给 `11/X0`。
现在正是 X0。

**本批要做的**：要么接通最小检查点（并说明它对 09R3 冻结的性能口径意味着什么），
要么**再次明确转交**并给出新的出口批次。**不允许**继续挂着不表态。

### 5.3 `xiao test` 的语义

X0-B 把它裁定为「**已登记未实现**」并要求「后续批次冻结项目测试文件发现、执行顺序和
结果协议」。

**本批要做的**：给出**归属批次**。如果本批不做，就在 `11-cli-config-and-platform.md` 里
写明它由哪一批关闭——否则 X0 退出条件第 1 条会一直留一个不明状态的项。

### 5.4 别名层的移除计划

`09-B0` §2.1 的债：`research::` 别名层的移除条件是「**`tests/benchmarks/src/main.rs`
与 6 个 `r2_*.rs` 都改到生产路径之后**」。

**本批要做的**：确认这个条件**现在是否满足**（X0-A/B/C/D 都没动那些文件，
所以大概率**没满足**）。若不满足，写明"仍不满足，原因是基准与共享向量仍用旧路径"，
**不要**在没有依据的情况下删掉别名层。

### 5.5 平台待复现清单

历次累积，**当前仍开放**：

| 平台 | 状态 |
| --- | --- |
| Windows 原生 | ✅ 主验收环境 |
| Linux（Docker） | ✅ 构建/功能证据（不是原生验收） |
| **Linux 原生** | ❌ 待复现 |
| **WSL** | ❌ 待复现（11X0-C 记录：Ubuntu/Arch 发行版**没有本批固定工具链**） |
| **macOS** | ❌ **无环境**，不得宣称已验证 |

**本批新增的 `xiao build` 会让这份清单变长**（工具链发现在每个平台都要各验一次）。
**逐项更新，不要沿用旧表述。**

## 八、验收

沿用 09R2D 的「撤掉实现 → 用例必须失败 → 还原 → 通过」。**关键验收不是「测试通过」**：

1. **`xiao build` 端到端**：真实源码 → CLI → 协议 → 原生产物 → **产物能独立运行**；
2. **工具链发现**：候选按顺序、带来源、失败时列出尝试过什么（复用 X0-C 的形状）；
3. **版本门槛**：低于 `llvm-toolchain.toml` 的 `minimum_major` 时**拒绝**并有稳定诊断；
4. **原生启动 shim**：`-debug` 产物在**没有 `xiao`** 的目录里启动时仍能拉起诊断窗口，
   找不到组件时是**明确失败**（§2.3）；
5. **配置固化**：`:220` 的待定决策**有结论**并写进 `11-cli-config-and-platform.md`；
6. **§5 的五个事项逐条有结论**——**关掉或明确转交**，不允许继续挂着；
7. **平台记录逐项更新**（§5.5），macOS 不得宣称已验证；
8. **门禁全绿**，含 `check:lock`、`bunx tsc`，且跳过数可见。
