# 20D-冻结. 平台资源的前置冻结

> **背景**：[20D-规划](20d-platform-resources-stage-plan.md) §三/§6.2 实测：**20D 的前置不满足**——
> 方向稿 [20](20-builtins-and-standard-library.md) §八 把与资源句柄直接相关的第 **3/5/6** 条
> 列为「仍待冻结」，而 §4.1 末句要求「显式关闭 API、关闭后别名的错误身份、
> 每种资源的复制/继承语义」**在第一个资源 intrinsic 实现前冻结**。
>
> **所以本批是 20D 的第一步，而且只做决定、不写代码。**
> 依据是 [20D-规划](20d-platform-resources-stage-plan.md) §4.2 的裁定（星崽 2026-10-17）：
> **冻结 → 能力上下文 → 资源承载 → 首批 API，顺序不可倒**。
>
> **一句话概括**：把「资源长什么样、怎么关、怎么传、缺能力报什么」**先定死**，
> 再让任何人去写第一个资源 intrinsic。

状态：**规划完成（2026-10-17）**：§六 四道**全部裁定**（1–3 取甲、第 4 条取甲）。
**但第 4 条的裁定把本批的执行顺序绑住了**：跨模块形式不能拍脑袋定，
必须**先读 `xiao-runtime-abi` 的现状**（§6.1）。**本批预期不改任何 Rust 代码。**

## 一、为什么必须是第一批

1. **API 的签名与错误身份由冻结决定**：文件/目录/进程的每条 intrinsic 都要写
   「参数是什么、返回什么、失败报什么码」——**这三样现在都没有**；
2. **承载必须先于第一个资源 intrinsic**（方向稿 §4.1 末句、§4.3）；
3. **能力上下文是地基**：方向稿 §5.1 要求「**所有外部操作必须通过该上下文进入**」，
   而它**现在不存在**（[20D-规划](20d-platform-resources-stage-plan.md) §3.2 实测）。
   上下文的**形状**是契约，属本批；它的**实现**属下一批；
4. **反过来做会付两次**：先写 API 再补契约，等于把每条签名、每个错误码、每条边界重来一遍。

## 二、要冻的六件事

每件都写清三行：**现状（实测）**、**要决定什么**、**落在哪**。

### 2.1 A：首批**资源种类**清单

- **现状**：方向稿 §4.1 只给了「例如 `file`、`directory`、`process`」；
  `RuntimeValue` 里**没有**资源变体。
- **要决定**：首批做哪几种、每种的语言可见种类名是什么、**不做**哪些。
- **已裁定（星崽，2026-10-17）：乙——只 `file` + `directory`**。
  **`process` 明确不在首批**，它平台差异最大（启动、退出码、子进程清理），
  等前两种把 Contracts 走通再单独立项。
- **落点**：方向稿 §四 补「首批资源种类」小节 + `02-type-system.md` 的类型表。

### 2.2 B：**显式关闭**语义与关闭后别名

- **现状**：方向稿 §4.1 给了最低契约的两条（「显式关闭与最后一个强引用释放必须**幂等**，
  重复关闭不能导致二次释放」「已关闭或已失效的别名访问**必须返回稳定的运行时错误**」），
  但**没定**关闭的**写法**，也没定那个「稳定错误」**是哪个码**。
- **要决定**：
  1. 关闭的**语言形式**（方法？`close(h)`？还是别的）；
  2. 关闭后访问别名的**错误身份**——**新码**还是复用既有的
     `X06-RUNTIME-012`（`runtime.invalid_value`，`xiao-diagnostics/src/lib.rs:41`）；
  3. 关闭**再关闭**是否静默成功（幂等）还是报错——**方向稿说的是幂等，要写成可测的**。
- **第 2 项已裁定（星崽，2026-10-17）：甲——新开一个稳定码**，
  即 **`X06-RUNTIME-025`**（分配见 §6.2）。理由：`X06-RUNTIME-012` 的语义是
  「**值**不满足操作要求」，而「句柄**已关闭**」是**生命周期**的错——
  混用会让用户分不清「你传错了东西」和「你提前关了它」。
- **落点**：方向稿 §4.1 + 诊断表。

### 2.3 C：**复制/继承**与**跨调用边界**

- **现状**：方向稿 §4.1 只写「克隆句柄的语义是**共享同一逻辑资源**，
  不是隐式复制操作系统资源」；「每种资源的复制/继承语义」明确留给冻结。
- **要决定**：
  1. 传参/返回/赋给新变量时是**共享**还是**复制**（按 §4.1 应为共享，但要写明可测的判据）；
  2. 句柄**能否进容器**（方向稿 §4.2 说**不能作集合元素或字典键**，
     但没说能否放进数组/元组——**这是两个不同的问题，别混**）；
  3. 句柄能否进**常量池 / 字节码常量 / `.xiaoc` / `.xar`**——§4.1 最后一条给了否定，
     要写成**可执行的拒绝**而不是「文档说不许」。
- **落点**：方向稿 §4.1/§4.2 + `03-collections.md` 的容器边界。

### 2.4 D：句柄的**跨模块 ABI**（方向稿 §八 第 3 条）

- **现状**：未冻。方向稿 §5.2 还有一句限定：「当前 LLVM 后端仍处于接口准备阶段，
  在它真正能调用 Runtime ABI 之前，**只能声称字节码侧完成**」。
- **要决定**：句柄以什么形式过模块边界（§4.1 要求「**不能把宿主裸指针暴露给 Xiao 或跨 ABI 传递**」，
  那跨模块传的到底是什么）；错误返回布局；与既有 `xiao-runtime-abi` 的关系。
- **落点**：方向稿 §八 第 3 条转为已冻 + `xiao-runtime-abi` 的 README。
- **注意**：**这条不许在没看 `xiao-runtime-abi` 现状的情况下定**——它是本批唯一
  需要先读大量既有 ABI 代码的一条。

### 2.5 E：首批 `os` API 与**平台能力清单**（方向稿 §八 第 6 条前半）

- **现状**：未冻。方向稿 §5.2 定了**平台顺序**（Windows → Linux → macOS）
  与「没有某平台能力时报告稳定的『能力不可用/目标不支持』错误，**不静默改走另一种语义**」。
- **要决定**：首批 API 逐条（名、签名、错误身份）、**每条能力在三平台的可用性**。
- **落点**：新建 `os` 的规格段落（方向稿 §五 之下）。

### 2.6 F：**缺失能力**的稳定错误码（方向稿 §八 第 6 条后半）

- **现状**：错误码族见 §三.2；**没有**「能力不可用/目标不支持」这个身份。
- **要决定**：它是**运行时**码（`X06-RUNTIME-025`）还是**编译期**码，
  以及**目标不支持**与**上下文不允许**要不要**分开两个码**。
  （方向稿 §5.1 说首版默认全开、未来才有受限模式——所以「上下文不允许」
  首版**可能不可达**；**不可达的码要不要现在就占位，是一个决定**。）
- **已裁定（星崽，2026-10-17）：甲——运行时新码 + 同时占位一个编译期码**。
  分配：**能力不可用 = `X06-RUNTIME-026`**；**目标不支持 = 编译期码**，
  但**它的家族待定**（编译期族里没有现成的「平台/目标」位置），候选与倾向见 §6.2。
- **落点**：诊断表（`xiao-diagnostics/src/lib.rs` 与 i18n 表）。

### 2.7 G：**能力上下文的形状**（契约部分）

- **现状**：`Capability` 只有 `None`/`Stdout`/`Stdin` 三个变体
  （`xiao-intrinsics/src/lib.rs:97`），契约表实际取值 20 `none` + 1 `stdout` + 1 `stdin`；
  消费点只有 `xiao-vm/src/semantics/exec.rs:1956`/`:1980` 两处**形状校验**；
  `xiao-runtime`/`xiao-driver` 里**没有运行时载体**。
- **要决定**：上下文**长什么样**（有哪些能力位、默认全开怎么表达、请求怎么携带它）、
  **谁创建**、以及「所有外部操作必须通过它」在契约层怎么表达（是不是每条外部 intrinsic
  都必须声明非 `none` 的能力）。
- **落点**：方向稿 §5.1 + `xiao-intrinsics` 的 `Capability` 设计。
- **本条只定形状，不实现**；实现是 **20D-能力上下文** 那一批。

## 三、已核的事实（本批不许重新论证，直接引用）

### 3.1 `is_hashable` 是**排除式**匹配——新变体会被误判为可哈希

`xiao-runtime/src/containers/mod.rs:36-48`：

```rust
pub fn is_hashable(value: &RuntimeValue) -> bool {
    !matches!(
        value,
        RuntimeValue::Table(_) | RuntimeValue::TableDropView(_)
            | RuntimeValue::Array(_) | RuntimeValue::Tuple(_)
            | RuntimeValue::DictTable(_) | RuntimeValue::DictColumn(_)
            | RuntimeValue::Set(_) | RuntimeValue::Error(_)
    )
}
```

⇒ **加一个 `ExternalResource` 变体，它会通过 `!matches!` 被判为可哈希**——
方向稿 §4.2 的警告**属实，且这是本批要写进「20D-资源承载」的硬要求**：
改成**正向允许标量/`none`**，或至少加**专门的拒绝分支**。
**本条在本批只冻结要求，不改代码。**

### 3.2 错误码空位

| `X06-RUNTIME-*` | `001`–`024` | **`025`** |
| `X07-FATAL-*` | `001`–`006` | `007` |
| `X09-BYTECODE-*` | `001`/`002`/`003` | `004` |

## 四、20D 的阶段出口条件（本批一并写，免得重演 20C）

[20C](20c-official-xiao-library.md) 走到第九批才补上出口条件（§七）。
**20D 不许重演**：本批要给出 20D 的出口条件**提案**，并在 20D-首批 API 落地后**逐条对账**。

提案（每条都要能回答「满足了吗」）：

1. **交付物**：方向稿 §七 给 20D 那一行的每一项——**文件/目录/进程首批 API**、
   **能力上下文**、**三平台差分**；
2. **契约先于实现**：六件事**全部冻结**，且每条决定都能在文档里被指到（不是「讨论过」）；
3. **能力路径存在**：外部操作**确实**通过上下文进入——**要有负例**
   （伪造一个能力不足的上下文，操作必须被拒且报稳定码）；
4. **三平台差分**：同一源码、同一上下文在三平台结果一致，
   **能力不可用处报稳定码而不是静默改道**；
5. **容器与产物边界**：资源**不进**集合/字典键/常量池/`.xiaoc`/`.xar`，
   且**有可执行的拒绝**（不是文档声明）；`type_name` 不落 `dynamic` 兜底文本；
6. **移除验证**：删掉表项／VM 绑定／ABI 包装任一环节，专门用例必须失败。

3. **不许**把 D（跨模块 ABI）在没读 `xiao-runtime-abi` 现状的情况下定——

4. **不许**顺手实现 §2.2/§2.6 里定下的任何一条——**定与做分开**，
   这是 [20D-规划](20d-platform-resources-stage-plan.md) §4.2 裁定「顺序不可倒」的直接含义；
5. **不许**把「首版能力默认全开」写成「所以能力模型可以先不做」——
   方向稿 §5.1 明写「这不是放弃能力模型」。

### 6.1 第 4 条的连带：本批**多了一件必须先做的侦察**，且**顺序被它绑住**

**裁定取甲**（能跨模块）——这与审核倾向（乙：首版收窄）**不一致**，
按 **G-2** 以**直接裁定**记，本文不以倾向改写。

**它带来的后果要写清**：跨模块形式**不能拍脑袋定**（§2.4 已经把这句写在前面）。
所以**本批的执行顺序被它绑住了**：

1. **先读 `xiao-runtime-abi` 的现状**——至少要知道：
   现行的**调用约定**、**错误返回布局**、以及**既有值（标量、容器、表值）现在怎么过模块边界**；
2. **再定**句柄的跨模块形式（它必须与第 1 步读到的形式**相容**，不是新造一套）；
3. **然后**才冻其余五件（它们在语义上不依赖 ABI，但 API 签名依赖）。

**两件要说清**：

- 这与 §五 第 1 条「不许写任何 Rust 实现」**不冲突**——**读代码不是实现**；
- 但**它是本批工作量最大的一条**，而且它是**甲 选项的代价**：
  乙（首版不许跨模块）本来可以整条绕开。**代价是裁定本身带来的，如实记下**。

### 6.2 第 1–3 条的连带：码的分配与**一处仍未定的家族**

三条裁定要落到**具体的码**，且其中一条要求「占位一个编译期码」——
而**编译期族里没有现成的「平台/目标」位置**（族号按阶段编：`X01` 词法/解析、
`X02`–`X04` 类型、`X05` 模块/配置、`X06` 运行期、`X07` Fatal、`X09` 字节码、
`X11` 协议、`X17` 归档）。

**本文件分配如下**：

| 决定 | 码 | 说明 |
| --- | --- | --- |
| 关闭后访问别名 | **`X06-RUNTIME-025`** | 运行时新码；与 `X06-RUNTIME-012`（「值不满足操作要求」）**分开**，因为这是**生命周期**的错 |
| 能力不可用（上下文不允许） | **`X06-RUNTIME-026`** | 运行时新码 |
| **目标不支持**（编译期） | **`X20-TARGET-001`** | 新建族，见下 |

**家族已裁定（星崽，2026-10-17）：甲——新建 `X20-TARGET` 族。**
理由：族号跟阶段走是本仓库的既有惯例（`X01` 词法/解析、`X02`–`X04` 类型、
`X05` 模块/配置、`X06` 运行期、`X07` Fatal、`X09` 字节码、`X11` 协议、`X17` 归档），
而 **20 阶段正是平台资源**；新建族比借用语义不同的族更不容易被误读。

**这个族名要同步到两处**（否则又是一个「两处各写一份」）：
`xiao-diagnostics/src/lib.rs` 的常量与 **i18n 的 `message_id` 表**
（`xiao-i18n/src/lib.rs`，实测该表有 **297** 条条目；
注意**不是** `language_pack.rs`——那是语言包清单与校验，零条消息 id）。
