# 11A-CONC. 并发模型：工具链内部并发与语言级并发的边界

> **为什么单开这一件。** E3B 任务 2 要求「多源索引快照的**有界并行**读取」、任务 4 要求
> 「**进程协调**」，而 `00-decisions:399` 明写「线程、任务池、`async`/`await` 或 Actor 等
> 具体并发模型**尚未确定**」；`README:35` 又写着「未决决策**不得通过临时实现偷偷冻结**」。
> 直接写并行实现就是干这件事。
>
> **⚠️ 核心结论先说**：`00-decisions:399` 那条说的是**语言级并发**，而 E3B 要的是
> **工具链内部并发**。**两者不是一回事，本文件把边界划清，并只冻结后者。**
>
> - **§一**：工具链内部并发——**冻结**，E3B 可直接依据。
> - **§二**：语言级并发边界——**仅划界与登记，不冻结任何东西**，归 `07-D`。

## 一、工具链内部并发（**本文件冻结这一部分**）

### 1.1 先划清：什么算"内部"，什么算"语言级"

**判据（本文件冻结的定义）**：

> 若某个并发机制的改变**不会让任何 Xiao 程序的语义发生变化**，
> 它就是**工具链内部并发**；否则是**语言级并发**。

按这个判据：

| | 工具链内部并发 | 语言级并发 |
| --- | --- | --- |
| 例子 | 并行读多个包源、并行校验缓存条目、跨进程锁缓存 | 线程/任务池/`async`/`await`/Actor **作为语言特性** |
| 影响 | 只影响 `xiao` 命令的**耗时** | 影响 Xiao **程序的执行语义** |
| 归属 | **本文件（11A-CONC）** | `07-D`（`07:252-262`），且受 `07:39` 阻塞 |
| 冻结状态 | **本文件冻结** | **未冻结，本文件不碰** |

**`00-decisions:399` 那一条为什么是语言级**：它上面两条是「数据竞争不属于合法且可依赖的
程序行为」「编译器能够证明存在数据竞争时**必须拒绝编译**」——这些是对 **Xiao 程序**的约束。
同一节 `:401-404` 又逐条约束了 06-B 的句柄、`CrossThread` 事实和 `RefCountStrategy`，
全部是**运行时值模型**。**那一节整体是语言语义，不是工具链实现。**

**先例（这不是新开的口子）**：

- `core/rust/crates/xiao-driver/src/diagnostics.rs:13` 已经 `use std::thread;`；
- 更硬的是 **`xiao-driver/src/protocol_architecture_tests.rs:116` 断言
  `service.rs` 必须包含 `std::thread` 和 `Arc`**——也就是说**架构上已经要求**驱动侧用
  `std::thread` + `Arc`。
- 所以"工具链内部可以用 `std::thread`"**不是本文件发明的**，本文件只是把 E3B 会用到的那部分
  **显式冻结成可依据的规则**。

**⚠️ 反面要求**：**不得**因为内部并发用了 `std::thread`，就宣称语言级并发"已经定了"。
两者互不推论（§二.4）。

### 1.2 并发原语：`std::thread::scope`，零新依赖

**冻结**：

- 用 **`std::thread::scope`**（Rust 1.63+；本仓 `core/rust/Cargo.toml:31` 的
  `rust-version = "1.85"`，满足）；
- **不引入** `rayon`、`crossbeam`、`tokio`、`async-std` 或任何任务池 crate；
- **不在工具链内部引入 `async`/`await`**。

**理由**：

1. `scope` 允许工作线程**借用栈数据**，不需要 `'static` 或 `Arc` 包装——
   而 `Arc` 会引出共享可变状态的同步问题，那正是要避免的复杂度；
2. **有界是天然的**：并发度由"开几个线程"直接决定，不需要任务池的调度器；
3. **零依赖**与本仓核心 crate 的现状一致（`xiao-package` 目前只有
   `serde`/`serde_json`/`sha2` 三个外部依赖）；
4. **不把 `async` 带进代码库风格**——一旦引入，调用链上所有函数都要改签名，
   而本仓的其余部分是同步的。

**⚠️ 与 `xiao-driver` 既有做法的关系**：那里的 `Arc` 用法**不受本文件鼓励也不受禁止**——
它已经存在且有架构测试锁定。本文件只约束**新增**的并行代码。

### 1.3 有界并行：界是多少

**冻结**：

- **并发上限是一个具名常量，不是"源的个数"**；
- 建议值 **8**，并**在实现里写明它为什么是这个数**（本文件不给绝对理由，
  给的是"必须是常量且必须写下依据"这条要求）；
- 源的数量若超过上限，**分批**执行，而不是每源一线程。

**为什么不能是"源的个数"**：E3A 已支持**导入源列表**（`list = { list = ..., digest = ... }`），
导入展开后源的数量**由上游清单决定**，不受本项目控制。几十个源各开一线程会同时打开几十个
文件描述符/连接——**这是可被上游触发的资源耗尽**。

**⚠️ 上限同时约束"在途请求数"**：分批的边界要保证**任一时刻在途的读取不超过上限**，
而不是"起了 8 个线程就不管了"。

### 1.4 结果确定性（**本批最容易翻车的地方**）

`00-decisions:291` 已冻结：「**不能依赖网络返回顺序或遍历偶然顺序**」。

**⚠️ 并行读取的直接后果就是"完成顺序 ≠ 配置顺序"。** 冻结规则：

> **并行读取的结果在合并前必须按 `config_order` 重新排序；
> 禁止以完成顺序、`Vec` 追加顺序或任何"先到先得"的顺序作为合并输入。**

这与 E3A 已冻结的 `select_source`（按 `config_order` 排序后逐源尝试）是**同一条要求的延伸**。

**必须有的区分度测试**：构造一个**"快源排在配置末尾、慢源排在最前"**的场景，
断言最终结果**仍按 `config_order`**——而不是按完成顺序。
**去掉排序这一步，这条测试必须失败。**

### 1.5 失败与取消语义

E3B 要记录每个源的 `fresh`/`cached`/`unavailable` 状态（`11a` 的 E3B 任务 5），
所以**单个源失败不能导致整体中止**。冻结：

| 失败类别 | 行为 |
| --- | --- |
| **单源不可达 / 摘要不匹配 / 协议版本不认识** | 记为该源的**状态**，**不影响其他源**，继续合并 |
| **缓存根不可写、锁无法获取、磁盘满** | **中止**——这是本地基础设施失败，不是"某个源的问题" |

**⚠️ 判据**：问一句「这个失败是**某个源**的属性，还是**本机环境**的属性？」
前者降级为状态，后者中止。把基础设施失败记成"某源不可用"会**掩盖真正的问题**。

**取消**：`scope` 会在块结束时 join 所有线程，本身不提供"提前取消"。
**不要**为了实现取消去引入通道 + 标志位的复杂协议——**本阶段不需要取消**
（源数量有上限、单次读取有超时）。若要中止，**等所有线程 join 完再返回错误**。

### 1.6 进程协调：跨进程锁缓存

E3B 任务 4 要求「用临时文件、**进程协调**和原子提交处理并发下载」。

**这里的"并发"有两个层次**，**不要混淆**：

- **线程级**（同一进程内的并行读源）——§1.2/§1.4 已覆盖；
- **进程级**（两个 `xiao sync` 同时跑，写同一份缓存）——**这一节**。

**冻结**：

- 跨进程互斥复用 **E1 已建立的 `create_new`（`O_EXCL`）模式**
  （`cache.rs:233` 已在用 `ErrorKind::AlreadyExists`），**不引入文件锁 crate**；
- **锁的粒度是缓存条目，不是整个缓存根**——否则两个 sync 不同依赖的项目会互相阻塞；
- **必须有陈旧锁的判定与回收**：持锁进程崩溃会留下锁文件。判定依据要**写下具体规则**
  （如锁文件内含 PID + 时间戳，且判活失败即回收），**不能只写"超时"**；
- **⚠️ Windows 与 Unix 的差异**：`create_new` 在两平台上都原子，但**删除一个被其他进程
  打开的文件**在 Windows 上会失败。锁文件的设计要避免依赖"可以随时删掉它"。

**⚠️ 与 `atomic_write_file` 的关系**：E1/E2A 已有「同目录暂存 + `rename`」的原子提交
（`lockfile.rs` 的 `atomic_write_file`）。**E3B 复用它，不另造原子写入**。

### 1.7 复用既有设施（不要重造）

| 需要 | 已有 | 位置 |
| --- | --- | --- |
| 原子写文件 | `atomic_write_file` | E2A 的 `lockfile.rs` |
| 内容摘要 | SHA-256（`sha2`） | E1 的 `cache.rs` |
| JSON 规范化 | JCS | E3A 的 `jcs.rs` |
| 目录树规范化 | 排序 + 路径规则 | E1 的 `cache.rs` |
| 崩溃条目隔离 | `.corrupt` 隔离 | E1 的 `cache.rs` |
| `O_EXCL` 互斥 | `create_new` + `AlreadyExists` | E1 的 `cache.rs:233` |

**本文件不新增任何数据结构**——它只冻结**用法**。

## 二、语言级并发边界（**仅登记，不冻结**）

### 2.1 本文件**不**冻结语言级并发

**明确声明**：`async`、`await`、Actor、发送/冻结/共享 API、线程亲和协议
**在本文件之后仍然不是正式语言契约**。

### 2.2 既有的约束（照抄，供接手者一次看全）

- **`07:39`**：「并发实现**必须晚于单线程字节码和原生执行闭环**，并在执行机制确定后建立
  **新的独立阶段**。`async`、`await`、Actor 等关键字在此之前不进入正式语法，
  也不属于第 07 阶段退出条件。」
- **`00-decisions:401`**：06-B 的 `StrongHandle`/`WeakHandle` 是**单线程、非原子**句柄；
  `Rc` 标记只让宿主 Rust 类型不自动实现 `Send`/`Sync`，**不代表已有语言级线程亲和协议**。
- **`00-decisions:402`**：`xiao-lifetime` 的 `CrossThread` 是**挂在具体 `ValueId` 上的
  生命周期事实，不是类型能力**；并发表面冻结前**不得通过名称启发式产生**。
- **`00-decisions:403`**：当前 `RefCountStrategy` **只有 checked 算术**，不能直接承载
  原子计数存储、弱升级竞态、载荷同步或对象头回收。未来共享句柄必须经过**独立的对象头/句柄
  设计**，**不得仅增加策略枚举值或改造所有普通句柄**。
- **`00-decisions:404`**：`Arena` 不豁免 RC 强环。

### 2.3 07-D 的研究计划与阻塞条件

`07:252-262` 的「后置并发研究」四条：共享可变值的所有权/访问记录、编译期拒绝明显竞争的
最小规则集、动态值的运行时检测钩子、**用线程/任务池/Actor 原型分别评估成本**。

**⚠️ `07:39` 的阻塞条件要核实**：它说"晚于单线程字节码和**原生执行闭环**"。
**B0 字节码已交付**；**N0 原生闭环的状态需要在接手时确认**——
若 N0 尚未闭环，07-D 仍被阻塞。**本文件不代替这个判断，只是把它标出来。**

### 2.4 ⚠️ 最重要的风险：不要把内部选型读成语言承诺

本文件冻结了「工具链内部用 `std::thread::scope`」。**这不是**：

- 不是"Xiao 的并发模型是线程"；
- 不是"`async`/`await` 已被否决"；
- 不是"语言级并发可以开始做了"。

**判据仍然是 §1.1 的那句**：改它会不会让某个 Xiao 程序的语义变化？
内部并发的选型**可以随时改**（换成任务池、换成顺序），**不影响任何 Xiao 程序**——
这正是它与语言级并发的区别。

**接手者若在别处看到"并发模型已冻结"的说法，以本文件的 §1.1 与本节为准。**

## 四、最可能翻车的地方

1. **把内部并发读成语言级并发**（§1.1、§2.4）——两个方向的误读都会出事：
   往上读会以为可以开始做语言级并发；往下读会认为 E3B 被 B0/N0 阻塞而停摆。
2. **不按 `config_order` 重排结果**（§1.4）——并行下"完成顺序 ≠ 配置顺序"，
   而这直接违反 `00-decisions:291`。
3. **并发度取"源的个数"**（§1.3）——导入列表由上游控制，等于把资源耗尽的口子交给别人。
4. **把基础设施失败记成"某源不可用"**（§1.5）——掩盖真问题。
5. **在 Windows 上依赖"可以删除被打开的文件"**（§1.6）。
6. **为取消引入通道 + 标志位协议**（§1.5）——本阶段不需要。
7. **另造原子写入或锁**（§1.7）——E1/E2A 已有。
8. **新增依赖**（§1.2）——`rayon`/`tokio` 都不是必需。

## 五、验收（设计冻结与后续 E3B 分开）

1. **§一 已写进 `00-decisions`**，且**包含 §1.1 的判据**（不只是结论）；
2. **并行结果按 `config_order`**：快源排在末尾的区分度用例，去掉排序必须失败（§1.4）；
3. **并发上限是常量且有依据**，源数超上限时分批（§1.3）；
4. **单源失败不影响其他源**，基础设施失败中止——**两类各有正反例**（§1.5）；
5. **跨进程锁**：两个进程并发写同一缓存条目的用例；陈旧锁能被回收（§1.6）；
6. **零新增依赖**（`Cargo.toml` 不新增并发相关 crate）；
7. **§二 未被越界**：`async`/`await`/Actor 未进入任何语法或公共 API。

## 六、不负责与不要重复做的事

- **不做语言级并发**（§二）——归 `07-D`。
- **不改 06-B 的句柄模型**——`StrongHandle`/`WeakHandle` 保持单线程非原子。
- **不引入 `async`/`await`**，包括工具链内部。
- **不产出实现代码**——本文件是冻结件。
- **不在本文件里决定 E3B 的缓存布局**——那属于 E3B 交接文档
  （E3A 已冻结 `snapshot.json` 与 `index/<package>.json` 的分片形状）。
