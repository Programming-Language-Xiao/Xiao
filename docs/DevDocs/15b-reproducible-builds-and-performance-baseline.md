# 15B. 可复现构建与性能基线

> **15 阶段的第二批，也是收尾批。** [15A](15a-native-pass-mapping-and-runtime-trimming.md)
> 把 LLVM Pass 映射与可证明的 Runtime 裁剪交付了；本批做**剩下那一半**
> （`15.5`–`15.11`）：调试与可复现构建、性能基线。
>
> **一句话概括本批**：让**同一份输入真的产出同一份产物**——
> 不是"我这台机器上两次一样"，而是**换机器、换时间、换路径也一样**；
> 并让性能数字**能区分噪声与真实回归**。
>
> **⚠️ 本批要先清 15A 留下的一笔断言债**（§二）。

## 二、上一批（15A）的一笔断言债 —— **先清**

### 2.1 可观察操作断言：**从"计数相等"提升到"逐项相等"**

15A 交付的 `optimization_pipeline_preserves_observable_operation_families`
（`xiao-bytecode/src/optimize.rs`）做法是：

```rust
let count_observable = |items: &[TacInstr]| { /* 匹配八种 opcode 后 count() */ };
assert_eq!(before, after);
```

**它的优点已经确认**：**真的经过完整优化管线**（`optimize_bytecode` + `O1`），
不是只调某个内部函数——这是 §2.1 当初点名要求的形式。

**但它比的是「个数」，不是「序列」。**

**后果**：若某个 Pass 把一条 `Release` **换成了另一条别的可观察指令**，
**总数不变、断言仍然通过**。而 §2.1 的原话要的是
「优化前后 **`drops` 序列逐项相同**」。

**冻结**：

- **改成逐项比对**（至少**按类别分别计数再逐类比对**）；
- **在注释里写明每个 opcode 对应 14B §3.1 七类中的哪一类**——
  现在八种 opcode 对七类，**映射关系没写出来，读的人要自己猜**；
- **`Copy` 是否真的对应「引用计数」要给出结论**：引用计数的增减可能由别的指令承载，
  若 `Copy` 只是值复制，那**"引用计数"这一类实际上没有用例**。
  **要么补上真正的指令，要么明确记录"该类由 X 承载"**。

**⚠️ 这属于 14B §八 第 1 条的同一族陷阱**：用例看起来有、覆盖其实没到。
只不过 15A 已经迈过了"有没有用例"，本批要迈过"用例够不够严"。

## 三、必须先冻结的 7 条

### 3.1 **可复现构建的确定性 —— 同一条原则的第三次出现**

`15.6` 要求「**规范化构建时间、路径和符号排序**，支持重复构建结果比较」。

**⚠️ 这与 13A `§3.7`（指纹）、14A `§3.3`（`.xiaoc` 格式）是同一原则的三次落地**：
**时间戳、临时路径、机器标识不得进入可寻址产物；未定义排序必须消除。**

**冻结**：

- **三处共用一条规则**，**不是三套**——本批若发现前两处有漏，一并记下而不是各自打补丁；
- **「符号排序」是本次的新面**：符号表来自链接器，其顺序取决于输入顺序与链接器实现——
  **要显式排序并验证**，不能假定"同一个链接器就稳定"（10K 已经证明**不同平台差别很大**）；
- **重复构建比较要有用例**：同一输入构建两次、**产物逐字节相同**（或差异在白名单内）。

### 3.2 **差异白名单必须逐条列出**（15 验收）

规范验收原文：「……**或差异具有明确白名单**」。

**冻结**：

- **白名单是"逐条 + 理由"**，不是"有些差异是正常的"这种留白；
- **每一条都要说明为什么不可避免**（工具链版本、平台 ABI、链接器行为）；
- **与 13B `§3.3` 的"仍不可避免的目标差异清单"是同一形式**——
  那份清单当时为空，**本批很可能第一次不为空**（构建层面的差异比字节码层多）；
- **⚠️ 白名单不能用来掩盖真问题**：加入白名单前要先证明它**确实不可消除**。

### 3.3 **不得为性能指标破坏语义**（`15.11`）

规范 `15.11`：「优化收益不足或 Pass 不适用时**保留可运行结果**，
**不得为追求指标破坏语义**」。

**冻结**：

- **与 15A `§3.2` 同源**（禁止快速数学、未定义溢出回绕、跳过 Runtime 检查）；
- **性能章节的每一个数字都不能成为放松语义约束的理由**——
  若某个基线达不到，**记录差距，而不是调整语义**；
- **`15.11` 的"保留可运行结果"与 13A 的 `SkipReason` 是同一件事**：收益不足时跳过，不硬做。

### 3.4 **性能基线要区分噪声与真实回归**（`15.10`）

规范 `15.10`：「使用**固定硬件/容器条件**记录可比较基线，**区分噪声和真实回归**」。

**冻结**：

- **固定条件**是前提——不同机器/负载下的数字**不可比较**，不能混在一张表里；
- **噪声阈值要显式给出**（重复测量的离散度），否则"回归"可能只是抖动；
- **⚠️ 不要把性能数字写进产物或指纹**——那会破坏 §3.1 的可复现构建；
- **本机（开发机）的测量只作方向参考**，正式基线必须在**受控环境**下取得。

### 3.5 **strip / 调试符号 / 可诊断模式各自独立验收**（`15.7`）

**冻结**：

- **三者是三件事**，不能用一个验收覆盖：
  `strip`（剥离）、**调试符号**（保留）、**可诊断模式**（保留诊断组件启动能力）；
- **与 10H 的 `-debug` 三一脉相承**：调试版产物要能开诊断窗口，普通产物不能；
  本批要验的是**优化之后**这条边界仍然成立；
- **⚠️ 调试信息的发布保留策略属待定决策 3**——**本批建验收，不冻结策略**。

### 3.6 **三平台顺序仍适用**（`15.8`）

15A `§3.6` 冻结的「**Windows → Linux → macOS**」**本批继续有效**。

**冻结**：

- `15.8` 要的「三平台链接器差异、Runtime ABI 和失败原因的**稳定诊断**」
  要**按顺序在三平台上验**；
- **10K 的教训**：三平台一起红、根因各异——**别同时推**。

### 3.7 **本批不做 16–19 阶段的事**

**冻结**：

- **不做 Protobuf 索引与内容寻址缓存**（16）——**包括待定决策 4**（原生二进制是否进同一套缓存）；
- **不做 `.xar` 归档**（17）、**TS CLI 参数解析**（18）、**Java 对照与发布验收**（19）；
- **不做**待定决策 2（LTO/PGO/向量化/目标 CPU 特化的纳入时机）——
  15A 已建开关，**本批不启用**。

## 六、硬约束

5. **性能基线要固定条件 + 噪声阈值**（§3.4）——**数字不进产物或指纹**。

8. **不擅自冻结待定决策**，尤其第 3 条（调试信息的发布保留策略）（§3.7）。

## 八、最可能翻车的地方

1. **构建时间/路径进了产物**（§3.1）——一处在就全盘皆输；且**它可能藏在很偏的字段里**。
2. **符号顺序靠"同一个链接器应该稳定"**（§3.1）——10K 已证明**不同平台差别很大**。
3. **差异白名单留白**（§3.2）——"有些差异是正常的"，但没人知道是哪些。
4. **用白名单掩盖真问题**（§3.2）——加入前没有证明"确实不可消除"。
5. **为达到性能数字放松语义**（§3.3）——和 15A 禁止快速数学是同一件事的不同形式。
6. **把性能数字写进产物或指纹**（§3.4）——直接破坏可复现构建。
7. **把抖动当回归**（§3.4）——没有噪声阈值，报告会天天报警然后没人看。
8. **三平台同时推**（§3.6）——10K 的教训。
9. **顺手冻结了调试信息的发布保留策略**（§3.7）——待定决策 3。
10. **断言债只改 `count` 不改映射**（§二）——`Copy` 是不是"引用计数"这个问题会被绕过。
11. **忘了两个 lock 文件**（§六 第 9 条）。

## 九、验收

按 15 规范 4 条（其中两条属本批），加上执行面：

1. **15A 的断言债已清**（§二）：可观察操作为**逐项**比对；opcode ↔ 七类**映射写明**；
   **`Copy` 与"引用计数"的关系有结论**；
2. **可复现构建**（`15.6`）：**同一输入重复构建产物逐字节相同**，
   或差异**逐条列在白名单里并有理由**；**不受机器绝对路径、时间戳或未定义排序影响**（15 验收）；
3. **调试映射**（`15.5`）：优化后的指令能回溯到源码位置，**内联栈可还原**；
4. **strip / 调试符号 / 可诊断模式**（`15.7`）：**三者各自独立验收**；
   **优化之后** `-debug` 边界仍成立（调试版可开窗、普通版不自开窗）；
5. **三平台诊断**（`15.8`）：链接器差异、Runtime ABI 失败有**稳定诊断**（沿用 10K 的机器字段口径）；
   **按 Windows → Linux → macOS 顺序验证**；
6. **五维基线**（`15.9`）：各 `-O` 级别的编译/启动/运行时间、内存、体积**可比较**；
7. **噪声与回归可区分**（`15.10`）：**固定条件 + 显式噪声阈值**；**数字不进产物**；
8. **语义未被指标侵蚀**（`15.11`）：收益不足时**保留可运行结果**，无任何为指标放松语义的改动；
9. **不回归**：15A/14A/14B/13A/13B/10 已交付内容保持绿；`cargo test --workspace` 全绿；
10. **门禁全绿**：`bun run check`（含 `check:lock`）、clippy、TS 类型检查、`cli/ts` 测试。
