## 二、F-6 的四个对象

| 对象 | 建议目标 | 必须冻结的行为 |
| --- | --- | --- |
| B2-A 中间快照 | ABI 1.18 / 生成器 20 | 仅内部验证，不发布为最终 B2 产物；不假定旧 Runtime 具备新高精度语义 |
| B1 旧原件 | 旧 `.xiaoc`/`.xar`/原生元数据 | 在 B2-B 1.19/21 执行前按现有头/索引/指令流/元数据版本拒绝，原件不改写 |
| B2 最终新原件 | ABI 1.19 / 生成器 21 | `.xiaoc` 头、`.xar` 索引、指令流、原生元数据记录精确 1.19；旧 Runtime 执行前拒绝 |
| 原生对象缓存 | 生成器 20 → 21 | 缓存身份不匹配，重新生成并链接；不把旧缓存伪装成新产物 |

现有源码事实：

- `.xiaoc` 头把 ABI min/max 写成当前精确版本；
- `.xar` 索引写入精确 `runtime_abi_min/max`，启动前检查范围；
- 指令流校验精确 `runtime_abi_version`；
- 原生元数据校验 ABI 与标准库身份；
- 缓存指纹包含生成器、ABI、优化计划和 Runtime 静态库内容。

因此“旧原件直接兼容重放”不能静默成立；建议拒绝旧原件并从 B1 源码在 1.19/21 重新生成回归。
这项选择仍需星崽按 §三确认，文档不得提前写成已裁定。

## 三、需要确认的规则

### F-6a：旧 `.xiaoc`/`.xar`/原生元数据

建议：

1. B1 原始 1.18 `.xiaoc`/`.xar` 在 B2-B 1.19/21 下执行前拒绝，不改写原件；
2. B2 新 1.19 原件在旧 1.18 Runtime 下执行前拒绝，不依赖“执行到未知原语”才失败；
3. 原始 1.18 原生元数据在 B2-B 验证器前拒绝；新 1.19 元数据在旧验证器前拒绝；
4. 不通过手改旧头、放宽 max 版本或忽略指令流版本宣称兼容；
5. 不改变现有容器格式/索引 schema 版本。

备选：仅对旧原件做显式迁移工具（需另立迁移契约），或保留范围兼容（与现有精确版本事实冲突，不建议）。

### F-6b：B2-A 中间快照

建议：

- A 保持 1.18/20，仅内部验证；不发布、不承诺旧 Runtime 具备新的高精度语义；
- A 的版本号不变不等于可以混用旧 Runtime；内部取证仍绑定源码、Runtime 内容和输出路径；
- A 产物不进入 B2 最终兼容矩阵。

### F-6c：B2-B 最终产物与 C 符号

建议：

- B2-B 集中升 ABI 1.19、生成器 21；标准库接口版本保持 1；
- 保留既有 1.18 C 符号和布局；新增 C 符号按加法兼容处理，不改变旧符号语义；
- `.xiaoc`/`.xar`/原生元数据/缓存按 §二 的精确矩阵执行；
- B1 源码在 1.19/21 重新生成后，重跑 B1 20 入口和完整 721 条 F10；旧成绩只作历史；
- 不修改现有容器格式/索引 schema 版本。
