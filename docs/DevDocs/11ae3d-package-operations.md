## 三、必须先冻结的 6 条

### 3.1 约束语法（**完整 semver，本批冻结**）

要冻结的完整集合：

| 形式 | 含义 |
| --- | --- |
| `"1.2.3"` | 精确版本 |
| `"^1.2.3"` | `>=1.2.3, <2.0.0`（首位非零为界） |
| `"~1.2.3"` | `>=1.2.3, <1.3.0` |
| `">=1.2, <2"` | 比较运算符 + 逗号合取 |
| `"1.*"` / `"1.2.*"` | 通配符 |
| `"1"` / `"1.2"` | 分别等于 `"1.*"` / `"1.2.*"`（用户已确认，不按 `^` 展开） |
| 预发布 `-alpha.1` | **默认不匹配预发布**，除非约束自身含预发布 |
| 构建元数据 `+build` | **不参与比较**（semver 规范） |

**⚠️ 两处最容易各写一套的地方**：**部分版本的展开**（`1.2` 的含义）与
**预发布的匹配规则**。这两条必须写死在 `00-decisions`，且**求解器与写回器共用同一个解释函数**。

### 3.2 求解的确定性与失败语义

`12-tests:775`：「常规运行**不会隐式升级**依赖」；`12-tests:776`：「版本求解、离线模式、
冻结模式和损坏缓存诊断可用」。

**要冻结**：

- **候选集来自联邦索引**（E3A/E3B 已有），**多源选择先于版本比较**——
  `00-decisions:291` 已冻结「不得跨源比较版本号择高」，**求解器必须遵守**；
- **同源内的版本选择**：满足约束的**最高版本**，还是别的？**要写死**；
- **不唯一时报错**（沿用 `:291` 的歧义口径）；
- **求解必须确定性**：同一输入两次求解结果相同（`12-tests:776` 的"可复现"）。

**⚠️ 回溯**：`00-decisions:292` 提到"为支持版本约束回溯，索引保留源提供的全部可用版本元数据"
——**说明设计预期有回溯**。本批要么实现，要么**显式说明首版不回溯及其后果**
（不回溯会在复杂约束下求解失败，而那是**正确的失败**，不是 bug）。

### 3.3 包操作命令的名称与边界

`11a:376-380` 列的候选：`xiao add <package>` / `xiao remove <package>` / `xiao lock` / `xiao update`。
**本批冻结其名称、参数与错误边界**（`12-tests:774` 要求"分别具有稳定命令与错误边界"）。

**要冻结的语义差异**（这四个命令最容易做成四个别名）：

| 命令 | 是否写锁文件 | 是否改 `config.xiao` | 是否动环境 |
| --- | --- | --- | --- |
| `lock` | **只写锁文件** | 否 | 否 |
| `update` | 更新锁文件中的版本 | 否 | 否（明确是否顺带同步） |
| `add` | 是 | **是**（新增依赖条目） | 否（明确是否顺带安装/激活） |
| `remove` | 是 | **是**（删除条目） | 否 |

**⚠️ `11a:417` 已冻结**「`install`/`i` **不重新求解**」——**`add`/`remove`/`update` 则必须重新求解**，
因为它们改的就是求解输入。**这条区分要写进文档**。

### 3.4 `config.xiao` 的写回（**E3A 遗留，本批唯一消费者在此**）

E3A 的 §十 把「**保留用户注释的结构化写回**」留给本批。**这是本批的技术难点**：
`config.xiao` 是**自定义语法**，格式保留的编辑需要**带 trivia 的语法树**或**等价的区间编辑**。

**要冻结**：

- **保留什么**：注释、空行、键序、原有引号风格；
- **不保留什么**：**必须显式列出**（否则"尽量保留"是没法验收的模糊承诺）；
- **冲突处理**：写回时目标条目已存在（`add` 一个已有的包）→ 报错还是覆盖？
- **原子性**：写回失败不能留下半个文件——**复用 E2A 的 `atomic_write_file`**；
- **不重新扫描**：`05d:103` 明令消费 `ConfigDocument`。**若现有 `ConfigDocument` 不带 trivia**，
  本批要**扩它**（并在文档里说明扩了什么），而不是**另写一个配置解析器**。

**⚠️ 最后一条是本批最大的单一来源风险**——`05d:103` 的约束在这里第一次真正吃紧。

### 3.5 锁文件可能需要的升版

E2A 冻结了 `lock_version: 1`。本批要往里加什么？

- **求解出的版本**（E3A 已记录 `version`）；
- **预编译变体与目标条件**——`00-decisions:287` 冻结「字段保留但首版为空」，
  **本批仍不移除该口径**（依赖 14 阶段）；
- **签名字段**——`任务 3 明说"签名方案单独冻结"`，**本批不留字段**。

**冻结**：**若需升版则升到 2 并说明**；**若不需要，明确写"本批不改 `lock_version`"**。
（E2A 的先例：升版必须保留读旧版的能力。）

### 3.6 完整性校验与来源审计（**签名不在本批**）

`12-tests:775`：「远程内容必须通过完整性校验」；任务 3：「源元数据和包正文的完整性校验、
来源审计、权限/凭据边界及**明确的信任失败诊断**；**签名方案单独冻结**」。

**冻结范围**：

- **做**：摘要校验（E1/E3C 已有）、**来源审计**（锁文件记录的源身份+commit+摘要链）、
  **权限/凭据边界**（凭据从哪读、能不能进日志、能不能进锁文件）、**信任失败诊断**；
- **不做**：**签名**——`00-decisions:626` 的"远程信任/签名格式"**本批不冻结**，

**⚠️ 凭据的硬约束**：**凭据绝不能进锁文件、日志或诊断**。要有测试断言

## 九、验收

1. **约束语法**：§3.1 表格每一行都有正例；部分版本与预发布各有**边界反例**；
   约束解释函数**只有一份**（写回器调用它，不另写）。

5. **写回往返**：读→改→写→再读，**注释与键序保留**；失败不留下半个文件。
6. **凭据**：不出现在锁文件、日志、诊断里（断言式）。
7. **`00-decisions:626`** 的"版本约束算法"待定项已清；**签名仍待定且未预留字段**。
