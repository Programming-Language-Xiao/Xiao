## 缺陷 1（严重，已关闭）：选择器核心语义零验证

### 症状

「选出了哪些元素」——R2b 唯一要交付的语义——在交接时**没有任何测试断言过**。

### 证据（三层都表达不了结果值，全部已核实）

| 层 | 事实 |
| --- | --- |
| 公开 API | `RunResult::Success` 是**无载荷变体**（`run.rs:19`）。`exec.rs:139` 写的是 `Ok(_) => RunResult::Success`——**`execute()` 返回的 `Option<RuntimeValue>` 被丢掉了**，没有任何路径能拿到计算出的值 |
| 向量 schema | `r2_vectors.rs:44` 的 `Expectation` 只有 `outcome` / `error_code` / `releases` / `max_call_depth`，**没有结果值字段** |
| 新增测试 | 交接时 `r2_stack.rs` 新增用例的断言**逐条统计过**：只有 `is_success()`、`error_code()`、`unsupported.is_empty()`，**零处取值比较** |

### 后果（用一条真实存在的测试说明）

`r2_stack.rs` 的 `executes_selector_ranges_steps_and_random` 里有：

```rust
let source = "values = [1, 2, 3, 4]\na = values[1~3]\nb = values[<2]\nc = values{2}[=]\nd = values{ -1 }[=]\ne = values[?2]\n";
...
assert!(run(&program, VmOptions::new()).result.is_success());
```

它只断言「跑成功」。所以：

- **`values{2}[=]` 里的步长被完全忽略、当成 `values[=]` 全选，这条测试照样通过。**
- 多选 `values[0, 2]` 只返回第一个元素，通过。
- 四种单边范围的包含关系搞反，通过。
- 结果**形状**（标量 vs 数组 vs 元组）错、字典列重复键没有转成有序元组，通过。

### 一个反直觉但必须知道的点：**三机型对拍不是这里的安全网**

载体只承载值、**不解释指令**——选择语义在**共享的** `exec.rs` / `ops.rs` 里。
所以选择算错是**三台一起错**，`assert_all_machines` 依然全绿。

**不要**把「三种载体都跑过了」当成语义正确性的证据。它验证的是载体正确性，不是选择语义正确性。

### 修法（已核实可行，不是泛泛的「加测试」）

**第一步：让入口返回值可观察。**

给 `RunOutcome`（`run.rs:96`）加一个 `value: Option<RuntimeValue>` 字段，在 `run()` 里把
`Ok(_)` 改成捕获 `Ok(value)`。

**影响面已实测很小**：`RunResult::Success` 全仓只有 **4 处匹配、3 个文件**
（`run.rs` / `semantics/exec.rs` / `tests/r2_vectors.rs`）。

这是研究模块（不是生产 VM），暴露一个调试用返回值是合适的；但要在 Rustdoc 里写清它
**只是研究可观察性**，不承诺成为生产接口。

**第二步：用手工 TAC 夹具断言选择结果。**

范式**已经存在**：`r2_stack.rs:1197` 的 `manual_check_program` 就是手搓 `TacProgram`。
照它构造以 `Return` 结尾的选择器程序，就能直接断言产出的 `RuntimeValue`
（注意 `Flow::Return(register)` 会 `read` 该寄存器，所以选择结果放进被 `Return` 的寄存器即可）。

**第三步（可选）：给 `Expectation` 加结果值字段。**
注意脚本入口本身没有返回值，所以只有能被改成返回值的用例才吃得到。
**不要为了它去改语言语义**——这一条是可选，前两步才是必需的。

### 必须补的区分度用例

逐条覆盖 `09-bytecode-runtime.md:164-172` 的九条运行验收（交接时 R2b 声称满足，实际一条没断言）：

1. **非单位步长**，且要能区分「逐项应用」与「全局应用一次」——构造**两个选择项 + 非单位步长**，
   两种实现的结果不同。**撤掉步长实现必须让该用例失败。**
2. 多选的选择**顺序**与**去重语义**（重复项与重叠范围不自动去重）。
3. 四种单边范围（`<x` / `<=x` / `>x` / `>=x`）的包含关系，以及 `~` 双端包含。
4. 全选 `[=]`。
5. **结果形状保持来源根类型**：多选/范围/随机返回数组、元组、`str` 或字典列，
   单项精确索引返回元素。**撤掉形状判定必须失败。**
6. **字典列重复直接键 → 按选择顺序排列的元组**。**撤掉该判定必须失败。**
7. 嵌套路径的形状保留（不扁平化）。
8. 空结果返回同根类型的空容器。

### 修复结果（已完成）

- `RunOutcome.value` 保存脚本入口的 `Option<RuntimeValue>`；错误和 Fatal 结果不暴露伪造值。
- `r2_selector_values.rs` 的 7 条夹具覆盖精确/多选顺序与重复、逐项步长、四种单边范围、
  双端闭区间、全选、负步长、数组/元组/字符串/字典列形状、字典列重复键元组、嵌套路径、
  随机顺序与无放回约束、放回超量和零数量空结果；每条在三种载体上断言实际值。
- 临时禁用步长应用时，`selector_step_is_applied_per_item` 按错误序列失败；临时禁用字典列
  重复元组投影时，`dictionary_repetition_returns_ordered_tuple` 按根形状失败；恢复后均通过。

### 验收（已完成）

- ✅ 上列每一条都有**值断言**，不是 `is_success()`。
- ✅ 步长和结果形状各做过区分度验证：撤掉对应实现 → 用例失败 → 还原 → 通过。

## 缺陷 3（一致性回退，已关闭）：新测试用错误码字面量

`r2_stack.rs` 的 `:108` / `:203` / `:219` 直接写字符串：

```rust
assert_eq!(outcome.result.error_code(), Some("X06-RUNTIME-018"));
```

而该文件只导入了 `FATAL_STACK_OVERFLOW_CODE` / `NUMERIC_OVERFLOW_CODE` / `TYPE_MISMATCH_CODE`
三个旧常量，**R2b 新增的四个码一个都没导入**。

本仓此前专门清理过这个问题：`e900f3b test: reference diagnostic code constants instead of literals`
把 18 个测试文件从字面量改成常量引用。**码值一旦变更，字面量测试会静默继续通过**——
这正是那次清理要消除的漂移。

**交接时全仓只剩这 3 处；现已全部清零。**

### 修法

导入并引用 `xiao_diagnostics` 的常量：`SELECTOR_BOUNDS_CODE`（`X06-RUNTIME-017`，
`xiao-diagnostics/src/lib.rs:45`）、`SELECTOR_STEP_CODE`（`:47`）、`RANDOM_COUNT_CODE`（`:49`）、
`RANDOM_SEED_CODE`（`:51`）。

### 验收（已完成）

`grep -rn 'Some("X0[0-9]-' core/rust/crates/ --include=*.rs` 结果为 **0**；
现有错误码测试直接引用 `SELECTOR_STEP_CODE`、`RANDOM_COUNT_CODE` 和
`RANDOM_SEED_CODE`，边界码仍由 `SELECTOR_BOUNDS_CODE` 统一提供。

## 验收（完成记录）

命令见 09R2D 文档 2.4 节。**关键验收不是「测试通过」**：

1. **每一类选择语义都有值断言**，且**撤掉对应实现必须让用例失败**——这是本批存在的唯一理由。
2. **步长的「逐项应用」有区分度**：两个选择项 + 非单位步长的用例，与「全局应用一次」结果不同。

4. **字面量清零**：`grep` 结果为 0。

6. **不算假通过**：不用 `#[allow]` 掩盖；`unsupported` 非空的产物仍被验证器拒绝。
