## 审核结论（已处置）

审核判定：**总体方向保留，但当时不能直接作为 E3A 的可实施冻结**。七条决策与既有冻结项
没有一处「直接互斥」的硬冲突，真正阻塞的是**源引用语义、导入顺序、摘要的信任边界**三处。
下面保留原文，处置结果记在这里——**不改写原文**，因为原文正是这三处问题的证据。

| 审出的问题 | 处置 |
| --- | --- |
| **`name` 语义自相矛盾**：决策说它只作显示，而 11A 示例与命名冲突规则都拿它当引用 | 已拆成三个概念并冻结：`source_id` / `alias` / 显示名；**依赖只能引用 alias 或 source_id**；`alias` 冲突默认报错。11A 示例同步改为 `alias` + `display` |
| **导入列表没有确定顺序**：「不得压过显式源」与「按书写顺序」在导入项写在前面时会给出不同结果 | 已冻结为**确定算法**：先全部直接声明的源（书写顺序），再各导入列表的源（列表按配置顺序、内部按清单顺序）。展开结果写入**可提交、可 diff 的源清单** |
| **派生层摘要是自证的**，不能证明来源可信 | 已明确：锁文件或源清单必须保存**客户端期望的摘要**；首次接受要记录「来源身份未验证」；**摘要校验状态与发布者认证状态分开** |
| **"摘要相同即同一份内容" 措辞过强** | 已改为**内容对象同一性**：字节相同不代表相同的包名、版本或依赖语义；只支持缓存去重，**不替代锁文件的逻辑包身份** |
| **RFC 8785 建议成立但必须正式冻结** | 已写入 `00-decisions`，并补：UTF-8、拒绝重复键与非 I-JSON 数值、超安全整数范围以字符串表达、**Rust 与 TypeScript 共用同一组规范化测试向量**。RFC 是**规范依赖**，不要求运行时依赖外部服务或库 |
| **源列表内容是否进配置指纹** | 已冻结：**进**，且不能只存 `source_id` 集合——要同时保存**整份列表的摘要**与**按最终优先级排列的规范化源序列**（集合会丢顺序、重复项与导入来源） |

**审核者对五个问题的答复也一并落地**：① RFC 8785 正式记录并做跨语言一致性测试；
② 选「保留间接引用 + 保存展开结果」，展开清单必须可见、可提交，**并参与冻结模式校验**；
③ 进配置指纹（见上）；④ 无硬冲突，但 `name`/`source` 与导入优先级属潜在冲突；
⑤ 最容易被"看起来生效、实际没有"的是**第 2 条**（派生层摘要）——见下方区分度要求。

### 由此追加的区分度要求（尚未实现，登记为本协议的第一批验收）

1. **同时替换 Protobuf 内容与它内部的摘要**，而客户端仍持有已钉住的 JSON 摘要
   → 客户端**必须拒绝派生层并回退权威 JSON**。只替换其中一个测不出这条。
2. **低优先级源提供更高版本**时，解析器仍须选择**高优先级源**——这条防的正是
   「把不同源的候选放在一起比版本号」（已冻结的禁止项）。

### 由审核补入 `sync` 的冻结项

`--frozen` 只使用已钉住的源清单与展开结果，缺失或摘要不符**直接失败**；
`--locked` 可读远端验证摘要，但**发现变化必须失败，不得自动采用新列表**；
源列表更新走**显式命令**，不得由普通 `sync` 静默完成。

### 仍未决断（审核未推翻，保持空白）

包名命名空间、依赖约束表达、分片切法与字段名、`alias` 冲突的**具体机制**（只定了"必须显式"）、
首次导入的信任呈现形式、变体维度（暂缓至第 14 阶段）、E3D 的签名与凭据。

## 二、本轮已决断

1. **`source_id` 规范化**：`kind + ":" + location`；协议与 host 小写、去默认端口、
   去路径尾斜杠与 `.git` 后缀。**用户书写的 `name` 只作显示，不参与身份**——否则改显示名
   会让整份联邦索引缓存失效（失效规则以它为依据）。

2. **索引格式：规范化静态 JSON 为唯一权威，Protobuf 只是派生加速层。** 派生层必须携带
   所依据的 JSON 摘要；不匹配、缺失、过期一律**回退 JSON**；加速层由**源侧**重生成，
   客户端不参与。

3. **协议版本处置照搬仓内 AST 适配器协议**：不认识就拒绝该源并明确诊断，
   **不得尽力而为地解析或静默降级**。

4. **解析键与同一性分开**：求解期用「规范化包名 + 版本 + 源身份」（摘要下载前不知道）；
   下载后由**内容摘要**判定同一性。

5. **JSON 采用规范形式**（本轮新增）：键序固定、无多余空白、数字与转义规则固定，
   摘要对**规范形式的字节**计算，规范化在**源侧生成时**完成。

6. **包源列表是第三类产物**（本轮新增）：描述「有哪些源」，与描述「有哪些包」的包源索引
   **不共用 schema、不互相嵌套**。

7. **导入他人源列表的三条规则**（本轮新增）：导入的源不得压过用户显式书写的源；
   清单内命名冲突必须显式解决、不得静默覆盖；**清单本身必须可被摘要钉住**。

**已明确拒绝**：引入 MD5。碰撞可构造、且会形成第二套摘要口径（单一来源被打破）。

## 三、未决断（已知的空白）

- **包名有没有命名空间**。已冻结的多源规则意味着包身份是**裸名**、源是另一个维度——
  那么生态里两个不相关的同名包，用户除了"换源名"没有别的表达方式。首版保守可以接受，
  但**协议里包名字段要不要预留限定形式**是个现在定比事后加便宜得多的决定。
- **依赖约束的表达**：`config.xiao` 里的 `^1.4` 对应到协议里是什么形状，完全未定。
- **分片的具体切法、准确文件名与字段名、缓存目录布局、压缩方式**——按 `11A` 留给 E3A/E3B。
- **源列表的命名冲突用什么机制解决**（加来源前缀 / 撞名即错 / 用户显式改名）——只定了
  "必须显式"，没定"怎么做"。
- **首次导入的信任姿态**（见第四节第 2 条）。
- **锁文件的预编译变体与目标条件维度**——已登记暂缓到第 14 阶段。
- **E3D 的签名、可信根、私有源认证、凭据存储**。

## 四、风险与张力（**请重点审这六条**）

### 1. 规范形式可能**根本无法落地**——除非钉一个既成标准

「JSON 必须是规范形式」这个要求，落到实现上意味着：**每一个客户端都要能验证规范化**，
而**每一个源侧发布工具都要能生成规范化**。N 个实现同一套规范化算法，
就是 N 份互相漂移的规则——**正是本仓登记在案的头号病史**。

而我们刚才**没有指定算法**，只说了"键序固定、无多余空白"——这不够。不同实现对
键序（Unicode 码点序？UTF-16 码元序？）、数字（`1.0` 还是 `1`？）、转义（`/` 要不要转？）
的选择都不同，**各自自洽但对不上**。

**建议**：直接钉 **RFC 8785（JSON Canonicalization Scheme, JCS）**，不要自造。
它是既成标准、有现成实现、且规则细到不留解释空间。**请审核者判断这个建议是否成立**，
以及"钉 RFC 是否引入我们不该有的外部依赖"。

### 2. 派生层的摘要是**自证的**，首次导入时它不构成信任边界

攻击者可以**同时替换 Protobuf 和它内部携带的摘要**。所以它能挡传输损坏，挡不住替换——
除非期望摘要来自客户端**已经信任的地方**。

于是能力是有条件的：

| 场景 | 能否只拉 Protobuf |
| --- | --- |
| 首次导入（无期望摘要） | ❌ 要么拉权威 JSON，要么**明确告诉用户"未验证"** |
| 后续更新（摘要已钉住） | ✅ |

**风险**：实现者很容易把"有摘要校验"说成"已验签"，从而造出一个**看起来验证过、其实没有**
的形态。`11A:294` 已经禁止这种表述，但规范与实现之间存在滑坡。

### 3. 导入列表把**源优先级**变成了一个间接层

已冻结的选择规则完全依赖 `config.xiao` 里源的**书写顺序**。导入一份策展列表之后，
那个顺序来自**远端**——用户 review 自己的 `config.xiao` 时**看不出实际优先级**。

**风险**：供应链攻击面从"包内容"上移到了"源顺序"。导入一个 50 条的列表，
等于把"哪个源优先"交给了别人。

**未定**：导入后要不要把**展开结果**落到用户可见处（config 的生成区 / 锁文件 / 一个可 diff 的清单）。

### 4. 「钉住摘要」与「拿到上游更新」直接冲突

钉住 → 上游加了好的源你不知道；不钉 → 上游可以悄悄加源，而你毫无察觉。

**未定**：更新的触发与可见性（显式命令 + 展示 diff？只提示不自动应用？）。

### 5. 源列表变化算不算「配置变化」

已冻结的失效规则是：**改源地址、源身份、源顺序 → 旧联邦索引失效**。
导入列表的内容在上游变化时，等价于源集合变了——**应当算配置变化**，
但这需要把"列表内容"也纳入配置指纹。`00-decisions:286` 目前只提了地址/身份/顺序三类。

**风险**：如果列表内容不进指纹，上游增删源会**静默复用旧联邦索引**，正好绕过失效规则。

### 6. 与已冻结的"不能悄悄升级版本"的边界仍未完全划清

本轮已冻结：`sync` 自动写锁文件是**受控例外**（显式、可 diff、有 `--locked`/`--frozen`）。
但**源列表的自动更新**属于哪一类？它不写在锁文件里，也不受 `--locked` 约束——
如果它能在 `sync` 时静默刷新，就等价于"每次同步都可能换一批源"。

**未定**：源列表的刷新是否也受 `--locked`/`--frozen` 约束。
