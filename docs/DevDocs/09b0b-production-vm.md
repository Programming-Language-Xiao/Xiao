## 一、先还 B0-A 的两笔债

### 1.1 `verify_production` 目前**没有生产调用方**

B0-A 交付了 1326 行的 `verify.rs`，但 grep 确认：调用 `verify_production` /
`verify_for_execution` 的**只有 `tests/b0_a_api.rs`**。这符合批次划分（消费方就是本批），
**但本批的第一件事就是让它进门**——否则一个写了六类校验的验证器会长期"备而不用"，
而它守的正是"编码器或执行器之前的唯一结构关卡"。

**落点**：本批的生产运行入口必须**无条件**先走 `verify_for_execution`，且要有一条
区分度用例（注入一个结构错误的 `TacProgram`，断言运行入口拒绝且**不是** VM 内部崩溃）。

### 1.2 `RuntimeCheckKind` 的名单有**两份**，靠人工同步

实测：

```text
core/rust/crates/xiao-ir/src/lower.rs         supported 数组（14 项，#[cfg(test)]）
core/rust/crates/xiao-bytecode/src/lower/mod.rs  matches! 白名单（14 项，生产）
```

B0-A 把两边**都**同步了，但**没有任何机制保证一致**；而且 `xiao-ir` 那份只断言**名字
清单**，不断言**实际接线**——真正决定行为的是 `xiao-bytecode` 那份。这是 09R2D `:174`
登记的 A 类病形态（同一条规则在两层各写一份）。

**本批至少要做到**：在新接通任何检查时，**两条名单同批改**，并写进提交正文。
**更好**：把 `xiao-ir` 那份测试改成消费 `xiao-bytecode` 的公开名单常量（若依赖方向允许），
或给 `xiao-bytecode` 的白名单加一条**它自己的**穷尽性守卫。选哪条要在本批交接记录里写明依据。

## 二、生产入口 ABI（本批最大新增）

### 2.1 先用掉一个事实：**降低器完全忽略 `entry_mode`**

实测：`grep -rn "entry_mode" core/rust/crates/xiao-bytecode/src core/rust/crates/xiao-vm/src`
**只命中 `verify.rs` 的测试**。而 `lower/mod.rs:137` 写死：

> 脚本入口固定占用索引 0，命名函数从 1 开始

也就是说：**脚本模式与 `[main]` 工程模式降低后是同一个入口函数 0**，
`IrEntryMode::Project { span }` 携带的表头位置目前**无人消费**。

**这改变了本批的形状**：B0-B 不是"实现两条运行路径"，而是：

1. **确认并断言这个同一性**——两种模式共用入口函数 0，是**已成立的设计**还是**尚未
   被发现的缺口**？必须给出结论。若确认成立，加一条测试钉住它（两种 `entry_mode`
   的同一份源码降低出同一个入口）。
2. **补上 `Project` 模式独有的责任**：`IrEntryMode::Project` 时，`[main]` 表头的存在性
   与结构由前端保证（`X04-PARSE-006`）；运行入口**不得重新解析源码**去验证它
   （09 文档 `:15`）。需要确认的是：**入口函数 0 的体在两种模式下分别是什么**，
   并在本批文档里写明判据。
3. **`span` 的用途**：`Project { span }` 现在无人读。它应当用于**诊断定位**（例如
   未捕获错误报告里的入口位置）。若本批不消费它，要写明"为什么不"。

> **不要**为"看起来对称"而新增第二条入口路径。09R 的冻结与 B0-A 的迁移都建立在
> "唯一入口函数 0"之上；凭空造第二条会同时违反单一来源与冻结。

### 2.2 研究期入口的三个「不承诺」必须逐条替换

`xiao-vm/src/run.rs` 自己写明了三处临时契约，本批要**逐条给出生产答案**：

| 位置 | 研究期措辞 | 本批要做的 |
| --- | --- | --- |
| `RunOutcome.value` | 「为了让 09R 研究测试观察语义结果而暴露的调试字段，**不是生产执行接口的稳定承诺**」 | 决定：进入生产契约，或移出 `RunOutcome`。**若保留，必须写明它对脚本模式与工程模式各自意味着什么** |
| `run_with_values` | 「只供研究 VM 注入入口形参；**不承诺生产 VM 的脚本调用 ABI**」 | 生产是否需要"注入入口形参"？`[main]` 无参数（§2.3），脚本模式呢？给出结论 |
| `VmOptions` | 只有 `max_call_depth` | 见第三节 |

### 2.3 `[main]` **没有参数契约**，这是已定事实

查证链：04 阶段 `:159-161` 只记录入口模式元数据；UseDocs `language/entry/README.md` 的
工程模式示例是 `[main]` + 语句块，**没有参数列表**；`IrEntryMode::Project` 只携带 `span`。

**所以命令行参数不是本批的事。** 用户程序如何取得外部输入（`argv` 之类）属于 20（内置
函数）与 11（CLI）的交界，且 09 文档 `:94` 明说本阶段「不解析配置文件，也不依赖最终
表名或键名」。**不要在 B0-B 发明一个参数注入机制**——那会在 11/20 冻结前先占位，
正是 `04:212` 警告过的「不得复制一份参数匹配规则」。

## 三、规范化运行参数对象

09 文档 `:94` 原文：

> 本阶段**定义并消费与配置文件无关的规范化运行参数对象**；没有外部参数时使用运行时
> 默认值，调用栈等限制超限必须产生可诊断错误。第 11 阶段负责把 `config.xiao` 和命令行值
> 校验、归一化后映射到该对象，因此本阶段不解析配置文件，也不依赖最终表名或键名。

现状 `VmOptions { max_call_depth }` 已经被部分满足（默认值 + 超限可诊断）。本批要**定稿**
这个对象，要求：

1. **每个字段都有默认值**，且默认值来源唯一（不要在 VM 里散落 `unwrap_or(1024)`）。
2. **每个字段都有超限/非法值的稳定诊断**，不是 `panic`、不是静默截断。
3. **字段语义与 `config.xiao` 的键名解耦**——第 11 阶段负责映射，本批不猜键名。
4. **`ModuleLoaded` 事件的模块标签**现在用 `abi.target` 占位（`sink.rs:14` 的注释自陈）。
   本批要么给它一个真实来源（模块身份），要么写明为什么继续用目标平台描述。

> **不要**把用户程序参数、locale、日志级别塞进这个对象。locale 归 11C，且 09 文档
> `:175` 要求它「只改变显示文本，不改变错误身份、堆栈、退出码或用户输出」——
> 混进运行参数对象会让这条约束难以守住。

## 四、结构化退出结果

**实测：全仓没有退出码概念**（`exit_code` / `ExitCode` / `退出码` 零命中）。
09 文档 `:120` 要求「为每个可观察执行结果保留稳定的结构化表示，避免 TypeScript 通过
解析人类可读文本来判断成功或失败」，`:175` 要求 locale 不改变退出码。

`RunResult { Success, Error(XiaoError), Fatal(FatalError) }` 的**三分支划分是好的**——
`Fatal` 不是"更严重的错误"，它不可被普通 `catch` 恢复、也不执行释放计划。本批要做的是：

1. **把三分支提升为生产契约**（研究期它是研究契约），并在文档注释里写明它与
   「未捕获错误由入口报告器输出」（`:108`）的关系。
2. **决定退出码的归属**：建议**本批只冻结结构化结果的语义边界**，**具体整数值留给
   11/X0**（它是 CLI 暴露面，且 X0 退出条件第 6 条要求「接口版本失配、核心崩溃和取消
   都转换为稳定的机器可读诊断」）。
   **若本批就定数值**，必须在文档里写明与 11 阶段的接口约定，不能只写一个数字。
3. **`panic` 走独立终止路径**（`:128`），不得被普通处理器伪装为成功。

> **修正批注（2026-09-21，B0-D）**：本条“具体整数值留给 11/X0”是依据不足的旧建议，
> 原文保留用于追溯。`00a:135` 已把退出码列入第 09 阶段边界字段，`00a:127` 留给 CLI
> 的是终端映射；因此 B0-D 冻结 `0`–`4` 的 `ExitCode` 语义，11/X0 不得重新定义它们。

## 六、`VmEventSink` 生产化

09R `:611` 要求事件接收器「至少记录模块、函数、作用域、释放、错误、堆栈和运行指标」。
`sink.rs` 的 `VmEvent` 枚举**已经覆盖**这些类别，本批要解决的是**实现性质**问题：

- `RecordingSink` 把所有事件存进 `Vec`——那是研究期为了断言事件序列的设施。
  **生产不能默认无限累积**。本批要定义生产的事件消费接口与背压/丢弃策略，
  并**保留** `RecordingSink` 供测试与基准使用（它现在是 `r2_*.rs` 的断言依据）。
- **事件不得改变执行顺序或释放语义**（09 文档 `:108` 末句）。这条要有断言。

1. **`RunOutcome.value` 被当成生产契约直接暴露**，而它带着「不是稳定承诺」的自陈。

## 八点一、本批落地记录

本批已经把生产执行契约接到 `xiao-vm`：

1. `RunRequest` 同时携带 `IrProgram`、`TacProgram`、规范化参数、模块/源码身份和事件容量；
   `run_request` 先调用 `verify_for_execution`，验证失败以 `FatalError::corrupt_artifact`
   返回，并把验证编号、路径和原因放入结构化报告。
2. 脚本模式与 `IrEntryMode::Project` 都执行降低器已经固定的函数 0；工程入口的表头跨度
   用作入口诊断回退位置，没有重新解析源码，也没有新增参数或第二入口。
3. `RunOutcome.value` 现在是稳定的入口显式返回值观察面；两种入口没有显式返回值时均为
   `None`。旧 `run_with_values` 仅保留给研究向量的形参注入。
4. `VmOptions::validate` 集中提供默认调用深度、零值和上限诊断；生产请求的事件容量和身份
   也在进入 VM 前校验。整数退出码仍留给 11/X0，本批只冻结 `Success/Error/Fatal` 三分支。
5. `PcMap::span_at_pc` 的结果通过 `StackFrame::with_source` 接入 `ReportRecord`；
   研究兼容入口继续使用默认身份，生产请求必须提供真实模块/源码身份（构造器提供稳定内存默认名）。

## 九、验收

沿用 09R2D 的「撤掉实现 → 用例必须失败 → 还原 → 通过」。**关键验收不是「测试通过」**：

1. **两种入口模式各有断言**：`IrEntryMode::Script` 与 `IrEntryMode::Project` 的程序都能跑，
   且 §2.1 的"同一入口函数"结论有测试钉住（或缺口有明确定论）。
2. **§1.1 已还**：运行入口无条件调用 `verify_for_execution`，区分度用例证明注入结构
   错误会被拒绝，且**不是** VM 内部崩溃。
3. **运行参数对象定稿**：每个字段有默认值、有非法值诊断；默认值来源唯一。
4. **退出结果结构化**：三分支语义边界冻结；若定了数值，与 11 的接口已写明。
5. **栈回溯带源码位置**：未捕获错误能回溯到 `IrSpan`。
6. **事件不改变语义**：有断言证明开启/关闭事件接收不改变结果与释放序列。
7. **三载体仍一致**：本批改动必须在**三种载体**上语义一致（09R2D/09R2G 的既有范式），
   尽管生产只暴露栈式。
8. **门禁全绿**：`cargo test --workspace`、`cargo clippy --workspace --all-targets -- -D warnings`、
   `cargo fmt --all -- --check`、`cargo doc --workspace --no-deps`、`bun test`、
   `bun run check`、`bun run check:coverage`。
