# 11C-1. 文案搬运与渲染器贯通

> **11C-0 的续批。** 上一批交付的是**骨架**：消息模型、语言上下文、
> 参数校验、回退渲染器、协议 `locale`/`text` 透传都已接通，
> **但内置目录只有 3 条示范条目**，全仓文案基本还在原地。
>
> **本批的主体是搬运**——把 Rust 侧各 crate 的硬编码文案逐批收进目录，
> 并把 `XiaoError`、日志、`-debug` 窗口接到**同一渲染器**上。
>
> **技术难度不高，面极广**。验收核心不是"新功能能跑"，而是
> **「搬运没有悄悄改变任何一句默认语言的文本」**（§3.1）——
> 功能全绿但某句错误信息被顺手改掉，是最坏的结果，因为没人会看第二遍。

## 三、必须先冻结的 4 条

### 3.1 **搬运不得改变默认语言的文本**（**本批最硬的一条**）

上一批已经确立了这条，本批是它的**主战场**——要搬的是几十上百处。

**冻结**：

- **默认语言下，搬运前后的人类可读文本必须逐字一致**；
- **⚠️ 允许的例外只有界面标签本地化**（`11c0` `:305-306` 已用过的口径）：
  原先为占位的英文示例标题（`Press Enter to confirm and run` 等）
  在 `zh-CN` 下显示中文。**这类例外要在提交信息里逐条列出**；
- **不接受"顺手修文案"**——想改措辞**另开提交**并说明理由；
- **每批搬运都要有对照**：不是"跑通测试"，而是**同一输入下渲染结果不变**
  （默认语言下逐字比对）。

### 3.2 **不是所有中文字面量都该进目录**

实测剩约 61 处，但**它们不都面向用户**。抽样显示 `xiao-bytecode/src/verify.rs` 的
`push_error(..., "函数表不能为空")` 之类是**字节码验证器的内部诊断**——
那是**开发者可见的断言**，不是用户可见的错误信息。

**冻结判定标准**：

| 该进目录 | 不该进目录 |
| --- | --- |
| 出现在**标准错误流**、**诊断报告**、**日志**、**`-debug` 窗口**里的 | `#[cfg(test)]` 里的、`assert!`/`panic!` 的开发者消息 |
| 用户会照着做下一步的（"路径不存在"、"版本不兼容"） | 内部不变式违反（"函数表不能为空"），用户无从修复 |
| 包管理器、编译器、Runtime 面向用户的提示 | 交给 `debug_assert` 或内部错误码更合适的东西 |

**⚠️ 判定要逐条做，不能按 crate 一刀切**——同一个 crate 里两类都有。
**不确定时按"用户看到这句话能做什么"判断**：不能做什么的，就不是用户消息。

**⚠️ 若判定为"不该进目录"，要在文档里登记一句为什么**，
而不是默默跳过——否则下一批会重新发现它们，再来一遍。

### 3.3 目录条目与消息身份

- **消息身份用 `xiao.<域>.<名>` 形式**，域按组件划分（`error` / `cli` / `package` / …），
  **与 11C-0 已建立的命名空间一致**（`11c0` §3.1）；
- **`params` 签名要显式**——参数类型与顺序是目录契约的一部分，
  **不是"随手插值"**；
- **两套内置目录（`zh-CN` / `en-US`）必须同步补齐**，不留"只有中文"的条目；
- **`en-US` 是回退链的第三级**（`11c:76`），**它的完整性直接影响回退质量**。

### 3.4 渲染器贯通的范围

`11c:110`（L2 第 1 条）要求 `XiaoError`、堆栈报告、标准错误流、结构化日志、
`-debug` 窗口**使用同一消息渲染器**。

**冻结**：

- **"同一"指的是同一份实现**，不是"各写一个但行为一致"——
  后者正是本仓头号病史；
- **`-debug` 窗口的标题也要本地化**（`11c:66` 明列），
  而它是**独立进程**（`xiao-diagnostics`）——**语言上下文要能传过去**，
  方法与协议侧带 `locale` 同理；
- **机器输出不受影响**：`code`/`message_id`/参数/位置/退出码**跨语言一致**（`11c:112`）。

### 3.5 逐条分类台账（本批冻结）

以下台账按**实际用户可见出口**登记，而不是按 crate 一刀切。相同
`message_id` 的多个调用点仍逐个检查；表中的“进入目录”表示调用点保留原有
`zh-CN` 预览文本，并在 `en-US` 目录提供同签名模板。“排除”表示该字面量只
服务内部校验、测试或开发者断言，不会沿标准错误流、诊断报告、日志或调试窗口
到达用户。

| 范围 | 进入目录的逐条判定 | 排除的逐条判定与理由 |
| --- | --- | --- |
| `xiao-package` | `resolver.rs` 的根包/依赖配置读取失败、包身份冲突、缺失本地依赖、依赖环（`x05.package.*`）；其余包源、锁文件、缓存和同步操作中返回给 CLI 的失败原因（路径、源、版本、锁文件和权限相关文本） | `cache.rs`/`lockfile.rs` 中仅用于 `FileOperation` 的 `operation` 标签，以及原子提交编号耗尽、父目录缺失等只能由开发者修复的内部文件系统不变量 |
| `xiao-types` | `checker/diagnostic.rs`、`control_checker.rs`、`function_checker.rs`、`checker/*`、`container_checker.rs`、`set_checker.rs`、`selector_checker.rs`、`table_checker.rs` 产生的用户源码诊断；保留现有 `x02.*`/`x03.*`/`x04.*`/`x05.*`/`x07.*` 身份及参数 | `environment.rs`、`conversion.rs` 等测试和内部环境不变量的 `expect`/`unreachable` 文本；它们不随源码诊断传播 |
| `xiao-driver` | 协议字段校验、核心崩溃、诊断窗口启动失败、包视图失败、运行/测试/构建/取消及环境状态错误（`x11.*`）；标准错误流和响应 `text` 统一使用目录渲染 | `protocol_tests.rs`、集成测试和仅供协议线程内部关联请求编号的 `expect`/`unreachable` 文本 |
| `xiao-runtime` | `XiaoError`/`FatalError` 的构造器消息、数值/容器/句柄/表状态错误；消息身份和参数进入统一目录，调用方传入的用户错误文本保持原文 | 引用计数实现中的溢出/下溢 `expect`、测试名称和仅说明 Runtime 不变量的断言；这些不是用户可操作的失败提示 |
| `xiao-vm` | VM 运行请求边界、模块/函数/表执行失败、取消和堆栈故障；通过 `XiaoError`/`FatalError` 的同一报告渲染器输出 | 损坏 TAC 的测试注入、`unreachable!` 清理分支和仅说明解释器内部状态的断言 |
| `xiao-syntax` | 词法、解析、导入、声明、选择器和控制流诊断；已有 `x01.*`～`x07.*` 的 `Diagnostic` 记录全部进入目录 | `ast.rs` 中“未初始化声明/try 语句”等 API 误用 `panic!`，以及 `lexer.rs` 中缩进栈不变量的 `expect`；都属于调用者或实现违反内部前置条件，不进入用户目录 |
| `xiao-ir` | 无——IR 验证失败面向的是**编译器内部调用者**，不沿标准错误流、诊断报告、日志或调试窗口到达用户 | `validate.rs` 的源码区间、名称与标量类型名称、集合空/未知标记、表类型身份、基本块编号、入口块、值编号和作用域编号一致性检查；与 `xiao-bytecode/verify.rs` 同类，属开发者可见不变式，用户无从修复（**本行由审核补齐**，见 §十一） |
| `xiao-codegen-llvm` | 工具链不可用/失败、目标不支持、动态代码生成输入拒绝和用户可修复的构建失败；标准构建错误保留稳定身份 | 动态降低器的槽位映射、释放计划、ABI 结构和测试架构断言；它们是后端内部一致性错误，不是用户可执行的修复提示 |
| `xiao-bytecode` | 仅生产入口向用户报告的 TAC/产物拒绝原因；保持 `code`、路径和输入版本等机器字段不变 | `verify.rs` 的函数表、签名表、释放计划和结构一致性 `push_error`，以及 `encode.rs` 研究编码器的内部格式错误；这些属于开发者可见断言，按本节标准不进目录 |

**对照规则**：迁移提交必须同时给出“原调用点 → 目录键/参数 → `zh-CN` 原文”
对照；若一个调用点没有可安全拆出的参数，就保留原文作为 `message`，不得为了
套模板而改变中文标点、空格、路径或错误原因。未进入目录的条目不能悄悄删除，
必须能在本表按文件和类别找到排除理由。

## 八、最可能翻车的地方

1. **搬运时改了默认语言文本**（§3.1）——功能全绿但用户看到的信息变了，最难发现。
2. **把内部诊断也搬进目录**（§3.2）——目录里塞进一堆用户永远看不到的东西，
   翻译成本白付且稀释了真正要翻译的部分。
3. **按 crate 一刀切**（§3.2）——同一 crate 里两类混着，切不干净。
4. **只补中文不补英文**（§3.3）——回退链第三级失效，`en-US` 用户看到 `message_id`。
5. **渲染器写成两份**（§3.4）——本仓头号病史。
6. **`-debug` 窗口沿用默认语言**（§3.4）——它是独立进程，容易漏传上下文。
7. **顺手"改进"了某句错误信息**（§3.1）——另开提交也不行，本批只搬不改。
8. **做 `.xar`**（§2.3）——没有可接的实现，硬做会造出临时设计。
9. **只跑部分 crate 就说门禁全绿**（§六 第 8 条）。

## 九、验收

**以 [11C 规范](11c-localization.md) `:131-158` 为准**（跳过 `:145` 插件验收），本批补充：

1. **默认语言逐字对照**：`zh-CN` 下搬运前后文本一致；**例外逐条列出**（§3.1）。
2. **判定有据**：约 61 处逐条判过，**不进目录的也登记了理由**（§3.2）。
3. **目录全覆盖**：`zh-CN` 与 `en-US` **同步**覆盖所有核心消息（`:139-144`、§3.3）。
4. **回退链**：四级可测，**末端显示 `message_id` + 参数**（`11c:74-77`）。
5. **渲染器同一份**：`XiaoError`、堆栈、标准错误流、结构化日志、`-debug` 窗口共用
   （`:110`、§3.4）。
