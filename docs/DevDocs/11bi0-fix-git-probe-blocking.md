## 二、实测证据（2026-09-27，Windows 11 / Bun 1.4.0 / git 2.53.0）

### 2.1 门禁实测为红

```text
bun test（cli/ts 全目录）
  100 pass / 1 fail / 5 skip    106 项，18 个文件，34.23s
```

**`e3b03ed` 的提交信息写的是「CLI 全目录 101 项通过、5 项条件跳过」——与实际不符。**
失败的那个用例我连跑三次，**三次都失败**，不是偶发。

### 2.2 冷进程首次探测要 ~5 秒

在**独立进程**里测 `probeGitSummary`（探测前只做过同步建仓）：

```text
首次（默认 250ms）：10067ms -> {"summary":null,"diagnostic":{"reason":"timeout"}}
```

同一进程内后续调用：

```text
第 2 次：90ms  -> {"branch":"main","ahead":0,"behind":0}
第 3 次：91ms  -> 正常
第 4 次：91ms  -> 正常
```

**首次 ~10 秒、之后 ~90 毫秒。** `git.ts:38` 的 `options.timeoutMs ?? 250` 和 `git.ts:49`
的 `Promise.race` 超时**在首次调用时形同虚设**。

### 2.3 生产表现：第一条提示符没有摘要

把 `main.test.ts` 的超时拉长后看到它的真实输出：

```text
Xiao (c) XiaoCZX
V0.1.0
…\project [X>              ← 首次探测超时降级了，没有摘要
1
…\project main-1↑-0↓ [X>   ← 第二次才正常
```

用例期望 `main-0↑-0↓ [X>`（`main.test.ts:196`），实得 `main-1↑-0↓`。
**不是计数算错，是首次探测整个失败了。**

### 2.4 预热救不了，原生 timeout 也拦不住

| 尝试 | 结果 |
| --- | --- |
| 先 `await execFileAsync("git", ["--version"])` 预热，再探测 | 预热本身 **10105ms**，预热后探测仍 **10056ms** 超时 |
| 直接用 `execFile` 的**原生 `timeout: 250`** 选项 | **10104ms 才返回**，超时同样不生效 |

### 2.5 根因：Bun 的 `execFile` 首次调用

同一台机器，**冷进程**里首次调用的耗时：

| 运行时 | 调用方式 | 首次耗时 |
| --- | --- | --- |
| **Bun** | `promisify(execFile)` | **5113ms** ← |
| Bun | `spawn` | 93ms |
| Bun | `execFileSync` | 108ms |
| Node | `promisify(execFile)` | 105ms |
| Node | `spawn` | 96ms |

**`promisify(execFile)` 在 Bun 上的首次调用有约 5 秒的固定开销，Node 上没有。**
CLI 的生产路径就是 Bun（`bun build` 产物 + bun 运行时），所以**必须按 Bun 的现实处理**。

这个开销**同时解释了三件事**：

1. **超时失效**——开销发生在 `execFile` 内部，且**阻塞事件循环**，所以 `setTimeout` 的回调
   和原生 `timeout` 选项**都排不上队**；
2. **提示符卡顿**——首次探测实耗 5 秒，用户看到的就是 5 秒空屏；
3. **测试互相拖垮**——见 2.6。

### 2.6 测试是 flaky 的

同一个提交，跑三次三种结果：

| 跑法 | 结果 |
| --- | --- |
| 三个文件一起跑 | `git.test.ts:32` 挂 + `main.test.ts:196` 挂 |
| `bun test` 全量 | 只有 `main.test.ts:196` 挂（超时 6316ms） |
| 单独跑 `git.test.ts` | **4 pass，656ms，全绿** |

`git.test.ts` 单跑全绿、同跑必挂——因为 `main.test.ts` 的首次 `execFile` 调用
**阻塞事件循环约 5 秒**，把并发运行的其他文件的 `setTimeout` 一起冻住了。
`bun test` 每次报的 `killed 1 dangling process` 也是同一来源。

**这不是"环境慢"，是初始化阻塞。**

## 四、修复要求

### 4.1 核心：把 `execFile` 换成 `spawn`（**已验证有效**）

`ui/git.ts:74-79` 的 `readGitStatus` 改用 `spawn`，手工收集 stdout：

- **首次耗时从 5113ms 降到 93ms**（§2.5 实测）；
- **超时由我们自己控制**：`setTimeout` → `child.kill()` → 降级。
  因为 `spawn` 快、不阻塞事件循环，`setTimeout` 能正常排队；
- **不要**退回 `execFileSync`——它是 108ms 没错，但**同步阻塞事件循环**，
  在交互式 REPL 里不可接受。

⚠️ **要保留的约束**：

- 仍然**只调一条命令** `git status --porcelain=v2 --branch`（`11b:225` 的冻结）；
- 仍然**不启动 Shell**（`shell: false`）、`windowsHide: true`、**有界输出缓冲**；
- 仍然走**同一个降级语义**：不可用/非仓库/超时/失败**一律不显示摘要**，
  且**失败原因保留结构化诊断**、非 debug 不打扰用户（`11b` 已冻结）。

### 4.2 `session.ts` 传明确的超时

`repl/session.ts:108` 目前不传 `timeoutMs`，走的是 `git.ts:38` 的默认值。
**要么把默认值调到有依据的值，要么在调用处显式传**——但**不要用调大超时来掩盖阻塞**：
真正的修复是 §4.1，超时值只是兜底。

### 4.3 测试改造（**这是不再复发的前提**）

**⚠️ 现在的测试抓不住这个 bug。** 因为它在**同一个进程里连续探测多次**，
第二次就已经是热态（90ms）。**必须加一个冷进程测试**：

- 用 `Bun.spawn` / `spawnSync` 起一个**子进程**，在子进程里做**第一次**探测；
- 断言**子进程的总耗时**低于一个明确阈值（建议 2 秒，实测修复后应在 1 秒内）；
- **这是唯一能守住"首次不阻塞"的测试**，必须有。

**另外按缺陷 4 消除 flaky**：

- `main.test.ts` 的 Git 摘要用例**改用注入的 `runStatus`**（`GitProbeOptions` 已经支持，
  `git.test.ts:13-22` 就是范例），**不依赖真实 git**；
- **真实仓库的端到端验证只保留一处**（`git.test.ts:32` 那个门控用例，它单跑是好的），
  且**不要**在同一测试文件里做多轮真实 `execFileSync` 建仓——那会把并发跑的其他文件冻住。

⚠️ **本批最容易踩的坑**：把「测试改成注入」当成"降低覆盖"。
**不是**——注入测的是**逻辑**，门控的真实仓库用例测的是**与真实 git 的契约**，
两者都要有，只是**不该让真实 git 出现在会阻塞事件循环的路径上**。

### 4.4 文档更正

- `11bi0-terminal-skeleton.md` §十一 的「250 毫秒到期就取消探测」**是错的**，
  要改成实测情况，并**记录 Bun `execFile` 的这个坑**（这是**跨批次有用**的环境知识，
  其他要起子进程的地方会再撞上）；
- `docs/DevDocs/README.md` 里 I0 的「未通过验收」状态要等本批通过后再改为「已完成」。

## 六、验收

1. **冷进程首次探测 < 2 秒**，且有**子进程测试**守住（§4.3）。
2. **首次提示符就带 Git 摘要**——在真实仓库里跑 `xiao`，第一条提示符即显示分支与计数。
3. **超时真能生效**——构造一个挂住的探测，断言在超时值附近就降级，**不是 5 秒后**。
4. **门禁全绿**，且**连跑三次结果一致**（消除 flaky，§2.6）。
5. **`bun test` 不再报 `dangling process`**。
6. **缺陷 6 收尾**：`--inLF` 的那个文件参数要么真正使用、要么明确拒绝，不再"接受后丢弃"。
7. **缺陷 7 登记**：「每行新进程导致跨行状态不保持」写入 11B 债项，交给 I4。
8. **文档更正**（§4.4）。

## 八、实现与验证记录（2026-09-27）

- `ui/git.ts` 改用无 Shell 的异步 `spawn` 调用同一条 `git status --porcelain=v2 --branch`；
  stdout/stderr 各限制 64 KiB，取消或超过限期时杀掉子进程。会话调用处明确使用
  250 毫秒限期，诊断与静默降级规则不变。
- `main.test.ts` 使用注入的 `runStatus` 验证配置优先级和每次提示符的计数刷新；
  唯一真实仓库测试保留在 `git.test.ts`，并在全新 Bun 子进程中测第一次探测的
  总耗时与无上游语义。挂起探测的注入用例验证超时可及时返回。
- 当前真实仓库的冷启动首条提示符显示 `main-4↑-0↓`，整次 CLI 启动约 412 毫秒；
  冷子进程测试约 0.5 秒，均低于 2 秒门槛。CLI 全目录连跑三次，每次均为
  **101 通过、5 条条件跳过、0 失败**；仓库根 `bun test` 为 **138 通过、
  5 条条件跳过、0 失败**，无 `dangling process` 报告。
- `--inLF <file.xiao>` 在 I1 前明确拒绝，不再接受后丢弃；每行新建核心进程所致的
  跨行状态债项保留在 I0 文档 §12.5，交给 I4，不在本批扩功能。
