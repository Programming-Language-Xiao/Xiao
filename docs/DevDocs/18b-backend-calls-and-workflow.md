# 18B. 后端调用与可诊断工作流

> **18 阶段的第二批**。18A 把「优化级别」变成了一条从命令行到后端的确定链路
> （参数解析、四层归一化、输入路由）。本批做规范 §「后端调用」的 **`18.5`–`18.8`**，
> 外加 18A 审核转来的两处补强。
>
> **一句话概括本批**：**让 CLI 真的调后端，并把每一步讲清楚**——
> 缓存命中没有、重编译了没有、产物验证过没有，用户和 CI 都要看得见。

## 二、必须先冻结的 9 条

### 2.1 **只新增 `verify` 与 `cache` 两个顶层命令**（已决策）

**已决策**（2026-10-05）：**不新增** `optimize` / `pack` / `inspect`。

**冻结**：

| 规范 `:25-33` 的草案 | 本批处置 | 理由 |
| --- | --- | --- |
| `pack` | **不新增** | 规范 `:57` 已定 `xiao build -xar "<源路径>"` 是**确定入口**，`pack` 与之职责重叠 |
| `optimize` | **不新增** | 优化级别由 18A 的 `-O` 参数表达，已覆盖 |
| `inspect` | **不新增顶层命令** | 作为 `verify` 的详细模式（如 `verify --detail`），避免两个命令共享同一份检查逻辑 |
| **`verify`** | **新增** | 「只验证不构建」是独立工作流，且 `18.7` 要求输出前验证 |
| **`cache`** | **新增** | 16B 的清理/重建是独立工作流；本批只**接 CLI**，库层已就绪 |

**冻结**：命令的具体参数形态（子命令名、`--json` 等）在实施第一步定下并**写入实施记录**；
**不得**与已确定的 `build -xar`、`-xar` 在语义上重叠。

### 2.2 **不在 TypeScript 重写后端逻辑**

规范 `:87`：「调用第 13 至 17 阶段的库/进程接口，**不在 TypeScript 中重写 Pass、哈希或
Protobuf 解码器**」。

**冻结**：

- TS 侧**只做**：参数归一化（18A 已交付）、协议搬运、结果呈现、退出码映射；
- **不得**在 TS 里实现：优化 Pass、SHA-256、Protobuf 编解码、ZIP 容器、`.xiaoc` 校验；
- 需要新的库能力时，**加在 Rust 侧并暴露协议接口**，而不是在 TS 里补一个"够用的版本"。

### 2.3 **缓存展示要说清「为什么」，不只说「命中/未命中」**

`18.6` 要求展示「缓存命中、重编译、**校验和回退原因**」。

**冻结**：

- 四类信息各有**稳定字段**（机器可读），不是一句人读文本：
  **命中**（用了哪个对象）、**重编译**（为什么没用旧的）、**校验**（过了还是没过）、
  **回退**（回退到什么、为什么）；
- **回退原因复用既有机制**——13A 的 `SkipReason`、16B 的保守规则、17A/17B 的拒绝诊断，
  **不新造一套"CLI 专用原因"**；
- 这些字段要能在 `--json` 下被 CI 消费（与 18C 的非交互模式衔接）。

### 2.4 **`.xiaoc` 默认写全局内容寻址缓存，不落源码旁边**

规范 `:69`：「普通源码模块的 `.xiaoc` **默认写入全局内容寻址缓存**，**不落在源码旁边**」。

**冻结**：

- 默认位置走 11A-E1 已冻结的 `~/.xiao/` 与 16A 的分片命名，**不新造目录**；
- **不得**因为"方便调试"就把 `.xiaoc` 写在项目目录里——那会让项目目录出现未声明的产物；
- 需要显式导出时，由用户指定输出路径（若本批支持），**默认行为不因此改变**。

### 2.5 **REPL 片段只进会话缓存，不得提升到全局**

规范 `:69`：「REPL 产生且**依赖当前会话状态**的片段只写入会话缓存；
**完整独立模块**才可提升到全局缓存」。

**冻结**：

- 判据是**是否依赖会话状态**，不是"大小"或"是否成功"；
- 会话缓存与全局缓存**物理分离**（沿用 11B-I4b 的会话生命周期约定）；
- **不得**把会话片段混进全局内容寻址命名空间——那正是 16A §3.4
  「对象类型命名空间必须分离」要防的。

### 2.6 **归档组装不得因缓存命中跳过完整文件校验**

规范 `:69` 末句：「`xiao build -xar` 从经过验证的缓存对象或新生成对象组装 ZIP/ZIP64，
**不允许因缓存命中跳过完整文件 SHA-256 校验**」。

**冻结**：

- 缓存命中**只能**免除"重新生成"，**不能**免除"重新验证"；
- 这与 16A 的 `read_checked`（**每次读取都重算摘要**）、16B 的「**先验证再暴露**」
  是同一条判据，**复用既有实现**；
- **要有测试**：构造一个"索引说命中但对象已损坏"的场景，断言**拒绝**而非静默使用。

### 2.7 **输出前必须确认产物已验证**

`18.7`：「在输出前确认产物已通过格式和完整性验证」。

**冻结**：

- 「输出」包括：写出文件、交给用户路径、交给运行器；
- 验证走**既有**校验器（`.xiaoc` 的 `validate_xiaoc`、归档的 `validate_xar`、
  对象的 `read_checked`），**不新写一套轻度检查**；
- **不得**自动运行未验证文件——规范 `:66` 明写「**不得自动运行未验证文件**」。

### 2.8 **四种入口共用同一运行契约**

`18.8`：「保持 `xiao run`、REPL、`.xiaoc` 和 `.xar` 使用**同一运行契约**」。

**冻结**：

- 四者的**退出码、错误身份、`drop` 记录、诊断字段**必须一致；
- **不得**为某一种入口特化处理——17C 已用 `run_xiaoc_production` 让归档复用统一 VM，
  本批要把 REPL 与直接 `run` 也核到同一处；
- **发现不一致时要报告并统一**，而不是在 CLI 层"抹平"差异。

### 2.9 **承接 18A 的两处缺口**

**① 验收 7 缺副作用探针**：18A 要求「跑完 `-O2` 后项目配置与锁文件**未被修改**」，
但 `optimization.test.ts` 里只有纯函数测试，**没有落盘行为的探针**。

**补法**：构造一个项目（含 `config.xiao` 与锁文件），用 `-O2` 跑一遍，
断言这两个文件的**内容与 mtime 都未变**。

**② 验收 10 的改动未说明**：18A 改了 `parser.test.ts` 的一行
（`["build", "main.xiao", "-O1"]` 从"抛 `X11-CLI-ARG-001`"变成合法），
判据是**必要**的（`-O1` 因本批新增支持而合法），但 18A 文档**没有说明这处改动**。

**补法**：在 [18A 文档](18a-optimization-parameters-and-config.md) 的实施记录里
**写明**这处改动与理由，**不得**让后人看到"改了既有测试却没说"。

**为什么并入本批**：两处都是 18A 的尾巴，且本批要在 18A 的归一化之上继续改同一片代码。

## 五、硬约束

1. **不在 TS 重写后端**（§2.2）——Pass/哈希/Protobuf/ZIP/`.xiaoc` 校验都不许；
2. **缓存展示要有稳定字段**，回退原因**复用既有机制**（§2.3）；
3. **`.xiaoc` 不落源码旁边**（§2.4）；
4. **REPL 片段不进全局缓存**（§2.5）；
5. **归档组装不得跳过完整 SHA-256 校验**（§2.6）；
6. **输出前必须验证**，不得自动运行未验证文件（§2.7）；
7. **四入口同一运行契约**（§2.8）；
8. **不新增** `optimize`/`pack`/`inspect`（§2.1）；
9. **不改** 13A/14A/16A/16B/17 的冻结面（只**消费**）。

## 六、分步提交

1. **`verify` 命令**：走既有校验器，含 `--detail`（吸收原 `inspect` 的定位）（§2.1/§2.7）；
2. **`cache` 命令**：接 16B 的两阶段清理（**plan 先出、apply 才删**），只读查询不落盘（§2.1）；
3. **缓存与验证展示**：四类稳定字段 + `--json`（§2.3）；
4. **`.xiaoc` 物化位置**：默认进全局缓存；REPL 片段的会话缓存分离（§2.4/§2.5）；
5. **归档组装校验**：不得因命中跳过 SHA-256，含"命中但损坏"的拒绝用例（§2.6）；
6. **统一运行契约核对**：`run`/REPL/`.xiaoc`/`.xar` 四项对齐，不一致处报告并统一（§2.8）；
7. **承接项**：18A 的副作用探针与测试改动说明（§2.9）；
8. **文档与登记**：本文件、18A、UseDocs、主表。

## 七、最可能翻车的地方

1. **在 TS 里"顺手实现"一小段哈希或校验**（§2.2）——两套实现的漂移从这里开始。
2. **缓存命中等同于"跳过验证"**（§2.6）——16A/16B 反复立过的判据。
3. **`.xiaoc` 落在源码旁边**（§2.4）——项目目录出现未声明产物。
4. **REPL 片段进了全局缓存**（§2.5）——破坏对象命名空间分离。
5. **回退原因新造一套 CLI 专用文案**（§2.3）——与 13A 的 `SkipReason` 分叉。
6. **四种入口各有一套退出码/诊断**（§2.8）——用户在 CLI 层看到不一致的结果。
7. **输出前没验证，或验证用了"轻度检查"**（§2.7）。
8. **新增了 `pack` 或 `optimize`**（§2.1）——与已确定的入口重叠。
9. **`cache clean` 一步删除**（§2.1）——16B 冻结的两阶段（plan/apply）不得退化。
10. **18A 的两处缺口又没补**（§2.9）。
11. **忘了 `Cargo.lock` 同步**——`check:lock` 会红（16A 栽过一次，17/18 系列已多次）。

## 八、验收

1. **`verify` 可用**：对一个 `.xiaoc` 与一个 `.xar` 分别验证，**只验证不构建**；
2. **`cache` 可用**：`list`/`verify`/`rebuild`/`clean` 中已实现的部分行为正确；
   **`clean` 是两阶段**（先出计划、再执行），有测试；
3. **不重写后端**（§2.2）：TS 侧**不含**哈希、Protobuf、ZIP、`.xiaoc` 校验的实现
   ——用源码检索或架构测试证明；
4. **缓存展示四类字段**（§2.3）：命中、重编译、校验、回退各有**稳定机器字段**，
   且回退原因**取自既有机制**而非自造；
5. **`.xiaoc` 位置**（§2.4）：默认进全局缓存，**源码目录不出现 `.xiaoc`**（副作用断言）；
6. **REPL 片段隔离**（§2.5）：会话片段**不出现在全局缓存**中；
7. **归档不跳过校验**（§2.6）：「索引说命中但对象已损坏」的场景**被拒绝**；
8. **输出前验证**（§2.7）：未通过验证的产物**不会**被写出、交给运行器或自动运行；
9. **四入口一致**（§2.8）：`run`/REPL/`.xiaoc`/`.xar` 的退出码、错误身份、`drop` 记录
   与诊断字段一致，有对照用例；
10. **承接项**（§2.9）：`-O2` 跑完项目配置与锁文件**内容与 mtime 未变**；
    18A 文档写明那处测试改动与理由；
11. **不回归**：18A 的五个入口缺省、优先级四层、输入路由仍通过；
    `cargo test --workspace` 全绿、`cargo clippy --workspace --all-targets -- -D warnings` 绿、
    `cli/ts` 类型检查与 `bun test` 通过；
12. **门禁全绿**：`bun run check` 退出码 0（含 `check:lock`，两个 lock 文件都已提交）。

## 九、不负责与不要重复做的事

- **不做**文件关联的安装/卸载、CI 非交互模式详设、`-debug` 全链路合并
  （`18.9`–`18.13`，归 **18C**）——注意 18C **含 `18.13` 的重活**
  （调试版原生产物脱离启动器 + GUI 子系统开窗）；
- **不新增** `optimize`/`pack`/`inspect`（§2.1）；
- **不重开** 13A 的配置与指纹、14A 的 `.xiaoc` 格式、16A/16B 的寻址与清理规则、
  17 的容器与运行契约；
- **不实施** 19 的发布验收。
