## 三、20C 本体

### 3.1 **第一步是能力探测，不是先写库**

方向稿 §2.1 说得很清楚：**标准库源码同时是语言的长期集成测试**——
「如果官方库只能靠大量特殊编译器分支才能运行，说明语言或 Runtime 契约仍有缺口」。
既然这样，**在写库之前必须先测一次「用现有语言能力写它」**，否则「缺口」会以「库写不出来」的形式
在实现中途才暴露。

**冻结**：

1. 选**两个最小模块**做探测：一个**纯字符串/路径处理**（如 `path.join`／文本拼接），
   一个**带算术与错误路径**（如数字到文本的转换，含溢出/非法输入）；
2. **必须真写、真跑**：VM 与 LLVM 原生**两条路径**都跑，逐个模块记录——
   **成功**，或**在哪一步以什么错误码停下**（写清是解析/类型/IR/原生后端/链接哪一层）；
3. 结果写进实施记录，**用表格呈现**，**不用**一句「大部分能写」；
4. 探测暴露的语言或 Runtime 缺口**不在本批修**，按「原生后端不支持：<拒绝信息>」登记，
   归位到对应阶段（原生后端归 15 一系），并写清它是否阻塞 20C 的某一类模块；
5. **这一步的结论决定 §3.2 的模块清单与工作量**，所以它排在所有库代码之前；
6. 探测中**不得**为了让它通过而：绕开类型系统、加临时 intrinsic、改基准输入。
   探测的意义就是**如实看见缺口**。

### 3.3 **与静态溢出的耦合（已裁定归 20C 之前）**

**事实**：静态路径的 **7 处 `llvm.trap`**（`ir.rs`，[10R-溢出后续](10r-static-overflow-followup.md) 已立项未实现）
在编译器预判的数值失败时**不产生 Xiao 可恢复错误**（Windows 历史观测退出码 `0xC000001D`），
而动态路径返回 `X06-RUNTIME-009`。

**耦合**：官方库的模块（文本、集合、数值格式化）**必然带算术与边界检查**。同一段官方库代码
在两条路径上的**错误身份会不一致**，直接撞上方向稿 §6.1 的「双路径差分：结果、错误身份、
释放顺序一致」这条验收——也就是说，**带着这个已知不一致去写官方库，20C 的验收从第一天就过不了**。

**冻结（星崽 2026-10-11）**：静态溢出**先于 20C 处理**，不把它当无关的 20 系列尾巴挂着。
在 7 处 `llvm.trap` 统一到可恢复错误身份、并完成 VM/LLVM 差分前，20C 不得把静态
溢出相关的官方库验收写成通过；具体实现归 [10R-溢出后续](10r-static-overflow-followup.md)。

### 3.4 **验收（取自方向稿 §6.1 中与 20C 相关的部分）**

1. **双路径差分**：同一模块在 VM 与 LLVM 的结果、错误身份、释放顺序一致；
   **LLVM 尚不可用时不许伪造通过**（写「数据不足」，不写「通过」）；
2. **容器边界**：官方库的值不进集合/字典键/常量池/序列化对象/`.xar`；
   类型名与错误参数**不出现 `dynamic` 等兜底文本**——`20AB-FIX` 修过同类问题，容易复发；
3. **移除验证**：删掉模块、VM 绑定或 ABI 包装里的**任一**环节，专门用例必须失败；
   **只测「能编译」不算**（这是 20AB 的教训，`20AB-FIX` 才补上）；
4. **兼容身份变更要有稳定诊断**，不许静默通过；
5. **元数据同步**：每个模块同步 crate README、UseDocs、阶段索引与兼容元数据；
6. **规模纪律**（方向稿 §6.2）：**不得**为了让官方库跑起来而批量新增 intrinsic；
   普通算法优先 Xiao 实现，必要的性能替换走「优化替换」而不是新 intrinsic。

### 3.5 **不做**

- **不写库代码**，直到 §3.1 探测出结论 **且** §3.2 的 6 条冻结；
- **不做** 20D（`os` 与平台资源）、20E（归档兼容接线）；
- **不修**探测暴露的语言/Runtime 缺口（只登记与归位）；
- **不新增** intrinsic，除方向稿 §一 的四类（宿主能力、Runtime 原语）外；
- **不把**官方库当普通包发布或参与依赖求解。
