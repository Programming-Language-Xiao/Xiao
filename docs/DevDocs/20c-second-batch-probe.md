## 二、并进来的四条修补（先做）

### 2.1 **P-6：「`draft → verified` 的条件」要写下来**

**事实**：`docs/UseDocs/README.md:14` 的口径是「每个**完成**模块必须同时有代码、测试和 `verified` UseDocs 页面」，
而首批两页与 registry 两条目现在都是 `status: draft` —— **状态一致、也诚实**（实施方自己写着原生运行记录待补），
但**判定条件没写下来**，下一批可能无依据翻状态。

**冻结**：

1. 在 [20C-首批](20c-first-modules.md) 写明 **`draft → verified` 的三条前置**：
   **①** 代码/测试/UseDocs 齐全（已具备）；**②** 双路径证据到位（**受控环境或 CI 的运行记录**，本机自跑不算）；
   **③** 页面自身的链接、示例与元数据检查通过；
2. **不许**在运行记录缺失时翻 `verified`——本仓库已在这一类上立过规矩（「不得把本机跑过当 CI 事实」）；
3. 翻状态时**两处同改**（UseDocs 页面与 `docs/module-registry.json` 的同一 id），一处漏改即视为未完成。

### 2.2 **P-7：移除验证缺原生侧那一条**

**事实**：首批覆盖了「模块实现被移除 → 调用者必须失败」与「不经 VM 绑定直接跑 → `X06-RUNTIME-012`」，
但**原生侧的符号表插入**（`dynamic.rs` 新增的那段）**没有移除用例**。

**冻结**：

1. **补一条原生侧移除用例**：去掉 stdlib 符号表插入后，同一调用者的**原生构建必须失败**；
   **按 [20AB-FIX](20ab-fix-lifetime-and-removal-verification.md) 的先例，失败证据可以是编译失败**（不要求运行期失败）；
2. 若因工具链/结构原因确实加不了，**必须在文档里写明**「该环节以编译失败为证据、当前未加用例」——
   **不许**记为已覆盖；
3. 这条与 §4.2 第 2 条同源：**「删掉模块、绑定或包装里的任一环节，专门用例必须失败」**——
   首批覆盖了两处，**第三处（原生绑定）是本批补的**。

### 2.3 **P-8：那条用例的措辞与做法不一致**

**事实**：`standard_library_import_requires_vm_loader_binding` 的注释写「**移除** VM 的真实加载绑定后」，
而代码实际是**不经绑定直接** `run_request`（效果等价：证明绑定是必需的）。

**冻结**：把注释改成实际做法（「不经 VM 加载绑定直接运行时必须失败」），
免得后来人去找一个并不存在的变异点。**只改注释，不改测试语义。**

### 2.4 **一处 N/A 要写明，而不是默认通过**

**事实**：首批 §4.2 第 3 条的「**无 `dynamic` 等兜底文本**」这半条**没有被断言**；
实施方用**源码级**近似覆盖了另一半（`!source.contains('[') && !contains("dict") && !contains("serialize")`）。

**判定**：对这两个**纯 `str`/`bool`** 模块，该子项**基本不适用**（没有会进容器/常量池/序列化的资源或句柄值），
近似断言是合理的。

**冻结**：在 [20C-首批](20c-first-modules.md) §4.2 标注「**该子项对首批不适用**（原因见上）」——
**不许**留成默认通过；**下一批若涉及容器或资源值，则该子项重新适用**，必须真断言。

## 三、能力探测（**先做，成表**）

### 3.1 **候选操作与探测形状**

候选取自首批的「明确不做」清单与集合方向。**每一条都要真写、真跑、双路径**：

| # | 候选操作 | 需要的能力 | 探测要回答 |
| --- | --- | --- | --- |
| 1 | **字符串比较**（`==` / `<` / `>`） | 字符或字符串的序关系 | `str` 之间能否比较；能比较到哪一级（码点序？长度序？） |
| 2 | **取长度** | 长度查询 | 逐个计数（已可用）还是需要新入口 |
| 3 | **逐字符累积** | 循环内拼接字符串 | 循环里 `s = s + c` 是否可用、双路径是否一致 |
| 4 | **子串查找**（`find`/`contains`） | **前瞻**：在位置 i 比较 `s[i]` 与 `s[i+1]` | 非字面量下标被 `X03-TYPE-003` 拒 ⇒ 能否用现有能力等价表达 |
| 5 | **切分**（按分隔符） | 累积 + 边界判断 + 结果容器 | 需要输出容器 ⇒ 与「构造容器」的能力一起判 |
| 6 | **大小写转换** | 字符分类（区间比较） | 依赖 #1（序关系）是否可用 |
| 7 | **集合模块的最小操作** | 集合构造/成员判断 | 现有集合语义能否在**原生双路径**上跑通 |

### 3.2 **冻结：探测的纪律（沿用首批与 10R-D5）**

1. **真写、真跑**：VM 与 LLVM 原生**两条路径**都跑；
2. **逐条记录**：**成功**，或**在哪一步以什么错误码停下**（写清是解析/类型/IR/原生后端/链接哪一层）；
3. **成表呈现**，**不用**「大部分能写」；
4. **不许绕开**：不许用变量下标、不许加临时 intrinsic、不许把逻辑下沉 Rust——
   探测的意义就是**如实看见边界**；**能跑通不等于测到了**（G-5 的教训）；
5. **探测结论先汇报再继续**（[10R-实现](10r-static-overflow-implementation.md) §2.1 的老规矩）：
   它决定第二批的范围；
6. 探测暴露的**语言缺口不在本批修**，按「需要什么 / 当前以什么码被拒 / 阻塞哪条接口」登记。

## 四、第二批接口清单（**探测之后才冻结**）

**冻结**：

1. 清单里的**每一条**都要在 §三 的表里找到对应结论；
2. **被既定边界挡住的**（如子串查找所需的前瞻、依赖非字面量下标）⇒ **移出第二批**并登记为语言缺口，
   **不许**为了让它进来而放宽边界；
3. **需要新增 intrinsic 的** ⇒ **不列**（[20C](20c-official-xiao-library.md) §3.2.1 第 1 条的规模纪律）；
4. 清单逐条含 **模块名 / 函数与完整签名 / 返回与错误身份 / 依赖哪些已探测操作 / 明确不做的部分**；
5. 模块粒度：首批已冻结为**单文件** `stdlib/<模块>.xiao`；第二批**沿用**，除非某模块大到需要目录
   （那就同时更新 `module-registry.json` 的路径登记）。

## 五、实现与验收（沿用首批，四件套不放宽）

**冻结**：

1. **四件套**（[20C-首批](20c-first-modules.md) §4.2）：双路径差分（原生侧实跑）／移除验证（**含本批补的原生那一环**）／
   容器边界与兜底文本（**本批若涉及容器或资源，该子项必须真断言**）／元数据与 UseDocs 同步；
2. **命名空间与加载器**：新模块**必须**经同一套工具链专用加载器与保留命名空间；
   **不许**为某个模块开特例（首批的冲突诊断与「未知模块只报一次」的检查继续适用）；
3. **兼容身份**：只增不改 ⇒ `STDLIB_INTERFACE_VERSION` **保持 1**；若有破坏性改动，提升并给稳定拒绝诊断；
4. **不许为写库扩语言**（首批 §4.4 原样有效）；
5. **执行点**：新增用例走**已改 glob 口径**的两处原生作业，或确认进 `workspace-default-tests`——
   **新加的 ignored 用例不需要再对账枚举**（P-3 的收益），但**必须确认它真的被跑到**。

## 七、验收

1. **四条修补**：`draft → verified` 的三条前置已写进文档；原生侧移除用例已补（或有明确的「未加用例」声明）；
   P-8 注释与做法一致；§4.2 的 N/A 已标注且**下批若适用会重新断言**；
2. **探测表**：7 条候选**每条**都有「成功 / 在哪一层以什么码停下」；双路径都跑过；
   **没有**用变量下标或临时 intrinsic 绕开；结论**先汇报**；
3. **清单**：每条都能在探测表里找到对应；被边界挡住的**已移出并登记为语言缺口**；
   **没有**新增 intrinsic；
4. **四件套**：双路径差分（原生实跑）／移除验证（三处环节都覆盖）／容器边界（本批若涉及则真断言）／同步齐全；
5. **兼容身份**：`STDLIB_INTERFACE_VERSION` 未无谓提升；ABI 主/次仍取自常量；
6. **状态**：首批两模块仍为 `draft`（除非表 B 的运行记录已到手）；**没有**在缺记录时翻 `verified`；
7. **表 B 诚实**：欠项与事实一致；
8. **通用**：`cargo test --workspace`、clippy、fmt、`bun test`、`bun run check`、`bunx tsc --noEmit` 全绿；
   提交标题带类型前缀、正文非空。

## 八、待定决策（给星崽）

1. **第二批的候选范围**：本文 §3.1 的 7 条是否就是全部？要不要加/减（例如把「集合最小操作」单独拆一批）；
2. **探测结论若大面积被边界挡住**：是**只交探测结论 + 语言缺口登记**（不写模块），
   还是**先推动语言能力补齐**（那会变成一条语言侧批次，与本批的库目标不同）——
   审核倾向**前者**：库先按能写的写，边界登记清楚，别把库批次变成语言批次；
3. **子串查找类操作**：若探测确认需要前瞻/下标，是否**永久**排除在标准库之外（由调用方用 `for` 自组合），
   还是登记为「等语言补齐后回来加」；
4. **首批两模块的 `verified`**：等 CI/受控运行号，还是允许用**受控主机的本地记录**（带环境清单）作为依据——
   审核倾向**前者**（CI 运行号可长期复核）。
