# 15A. LLVM Pass 映射与 Runtime 裁剪

> **15 阶段的第一批。** [15. LLVM 原生优化与链接](15-native-optimization.md) 是**权威规范**；

## 二、上一批（14B）的两笔债 —— **先清**

**核 `drop` 时发现：当前实现是对的，但保护是间接的。**
这两笔债与 §3.3 是同一条原则在字节码侧的未落部分，**本批一并清掉**。

### 2.1 补一条**显式**的"释放点不被删"断言

**已核过的事实**（2026-10-02，核 `drop` 专项）：

| 环节 | 现状 |
| --- | --- |
| `compact_registers`（槽压缩） | **只做寄存器重映射，不删指令**；`Release` 被 `map(value)` 重映射 |
| `liveness.rs` 的 `instruction_use_def` | **把 `Release { value }` 的操作数算作 `use`** —— 所以只被释放点引用的寄存器不会漏出集合 |
| `remove_unreachable_blocks` | **只看 CFG 边、不看指令内容**；含释放点的块有前驱即可达；异常边另行显式保留 |
| 三方差分 | **逐方对照 `drops`**（`source == unoptimized == optimized`） |

**四条都对，但都是间接保护**：将来的改动（比如为别的 Pass 扩 `instruction_use_def` 时漏了 `Release`）
**不会立刻有测试报红**，要等差分跑起来才发现。

**冻结**：

- **补一条显式用例**：构造一个「**只有释放点、没有其他可观察操作**」的函数，
  断言优化前后 `drops` 序列**逐项相同**；
- 用例要**真的经过优化管线**（不是只调 `compact_registers`）——
  否则又变成"绕过整条路径的假通过"（13B 踩过一次）；
- **同时钉住 `instruction_use_def` 对 `Release` 的分类**：这条规则本身就是被保护的东西。

### 2.2 §3.1 那七类可观察操作**逐类核查**

14B §3.1 冻结的是「不得删除可观察操作」，规范点名**七类**：
随机、输入输出、模块加载、**引用计数**、**`drop`**、**错误构造**、**数据竞争检查**。

**当前状态**：**只逐类核过 `drop` 一类**（且结论是"缺显式断言"），其余六类**未逐类核查**。

**冻结**：

- **七类逐类**：每类至少一条用例，**断言优化前后该类行为一致**；
- **不许用"看起来没删"代替用例**——那正是 14B §八 第 1 条的头号陷阱；
- **引用计数**与 **`drop`** 分开核：前者是**计数平衡**，后者是**释放顺序**，
  是两个不同的可观察面；
- 核查结论**写进 14B 的实施记录**（哪类有用例、哪类证明不需要）。

### 2.3 顺带更正 14A/14B 的提交 scope

14A（`0673fee`/`f9411a1`）与 14B（`70dbd30`/`c729230`/`47e6d1e`）的提交**缺 `(14a)`/`(14b)` scope**。
不违规（前缀与正文都在），但按 scope 过滤会漏。**本批起按 `feat(15a):` 形式提交**，
不必回改历史。

## 三、必须先冻结的 8 条

### 3.1 **`O0` 不能被解释为跳过安全检查**（15 规范原文）

规范：

> `O0` 是默认未优化路径和差分基线，但**仍执行合法 IR 降低、必要的 ABI 规范化、验证和链接**；
> **它不能被解释为跳过安全检查**。

**冻结**：

- **这与 13A `§3.2` 是同一条**（「`-O0` 是基线，不是直通」）——
  **本批不重开，但要确保 LLVM 侧也遵守**；
- **普通原生构建直接从类型化 IR 进入 LLVM 管线**，
  **不为 LLVM 不消费的模块强制额外生成 `.xiaoc`**（规范明写）。

### 3.2 **不得启用会破坏 Xiao 语义的 LLVM 选项**（15 规范）

规范：

> 任何级别都**不能启用** LLVM 的**快速数学近似**、**未定义溢出回绕**或
> **会跳过 Xiao Runtime 检查**的选项。

**冻结**：

- 这三类**在任何级别下都禁止**——它们是"性能换语义"，而 Xiao 的溢出/错误/所有权
  是**已冻结的语言语义**，不是实现细节；
- **与 14B `§3.1` 同源**：`drop`、错误构造、动态检查都是可观察操作。

### 3.3 **Runtime 裁剪依据可证明的调用图，不依赖链接器偶然删除**（`15.3`）

规范 `15.3`：「让 Runtime 裁剪依据**可证明的调用图和效果摘要**，
**不依赖链接器偶然删除**」。

**⚠️ 这是本批最要紧的一条，因为它正是 10K 那笔债的正面回答。**

10K 的结论是：Windows 的"裁剪通过"来自**自己导出、自己检查**（自证），
而 ELF 上看到的是链接器**实际**拉进来的东西——**当时靠 `--gc-sections`/`-dead_strip` 让链接器真裁**，
但**那是链接器行为，不是证明**。

**冻结**：

- **裁剪的依据是调用图 + 效果摘要**（13A 已交付只读事实），**不是**"链接器删掉了什么"；
- **`15.3` 要的是"可证明"，不是"观测不到"**——
  这与 10K 里那条「**什么都没找到可能只是探测方法失效**」是同一条教训；
- **裁剪报告要能解释保留/删除原因**（验收第 2 条），
  **而不只是给出一个组件清单**。

### 3.4 **不得借"不可达"删除可能产生错误、释放、随机或 I/O 的路径**（15 规范）

规范：

> 后端可以根据优化后的 IR 和链接图裁剪未使用的 Runtime 组件，
> **但不能借"不可达"判断删除可能产生错误、释放、随机或外部 I/O 的路径**。

**冻结**：

- **这与 14B `§3.1`/`§八 第 2 条` 是同一原则**，只是从字节码换到了 LLVM 侧；
- **14B 已经在这里栽过一次**（`47e6d1e`：异常处理器只属于不可达保护区时的 CFG 清理越界）——
  **LLVM 侧会以另一种形式重演**（比如 `unreachable` 块里的 `landingpad`）；
- **排查方向**：任何"删掉看起来到不了的代码"的 Pass，**先问它是否携带有副作用的边**。

### 3.5 **产物比较：允许三类不同，不允许六类不同**（15 规范「产物比较」）

规范原文：

> 允许**指令布局、文件体积和时间**不同，
> 不允许**标准输出、退出码、错误类别、随机序列、容器顺序或 `drop` 记录**不同。

**冻结**：

- **"允许不同"的三类**（布局、体积、时间）**不该被判为差异**——把它们当差异会制造假报警；
- **"不允许不同"的六类逐项对照**——注意这里比 14B `14.10` 的**四样多两样**：
  **多了「容器顺序」**，且用的是**「退出码」**；
- **四个观察对象**（规范「交接检查」）：同一类型化 IR 的
  **未优化原生 / 优化原生 / 未优化字节码 / 优化字节码**——
  **本批是第一次四方都能跑**（13B 建了两方，14B 扩到三方，本批到四方）；
- **沿用 13B 的输入与执行器**，**不另建一套**。

### 3.6 **平台验收顺序固定：Windows → Linux → macOS**（15 规范）

规范：

> 平台验收顺序固定为 **Windows → Linux → macOS**：后一个平台**只有在前一个平台的
> 语义、ABI 和产物回归可复现后**才进入正式门槛。

**冻结**：

- **顺序不可调换**，也不可三平台同时"开始验收"——
  前一个绿了才推进下一个；
- **这与 10K 的教训一致**：当时 Linux/macOS 一起红，根因却是三个平台各自的问题
  （Windows 是自证、Linux 是链接器没裁）——**按顺序推能把平台特有的问题隔离出来**。

### 3.7 **调试/可复现构建与性能基线归 15B**

**冻结**：

- **本批不做** `15.5`–`15.8`（调试映射与内联栈、规范化构建时间/路径/符号排序、
  strip 与调试符号的独立验收、三平台链接器差异诊断）；
- **本批不做** `15.9`–`15.11`（性能基线、固定硬件条件、收益不足时的保底）；
- **⚠️ 但 `15.6` 的"规范化构建时间、路径和符号排序"与 14A `§3.3` 是同一条原则**——
  本批**新增任何进产物的字段时就要遵守**，不能等 15B 再补。

### 3.8 **仍不擅自冻结 4 条待定决策**

15 规范的 4 条：

1. `config.xiao` 与 CLI 的**优化级别优先级**（**未配置时 `-O0` 已确定**，这条可落地）；
2. **LTO、PGO、目标 CPU 特化、向量化和跨模块优化**何时纳入；
3. **调试信息/源码映射的发布保留策略**；
4. 原生二进制是否加入与 `.xiaoc` 相同的**内容寻址缓存和索引**。

**冻结**：`15.2` 要求"分别实现函数内、跨模块、链接时和目标特化 Pass 的开关及验证"——
**"实现开关"不等于"启用"**。待定决策 2 问的是**何时纳入默认级别**，
**开关可以建，默认必须保持不启用**。**接手者要分清这两者。**

## 八、最可能翻车的地方

1. **把 `O0` 当成跳过安全检查**（§3.1）——13A/14A 都点过名，LLVM 侧会以"LLVM 会帮我做"的形式重演。
2. **依赖链接器偶然删除**（§3.3）——**10K 那笔债的成因**：
   `--gc-sections` 让链接器真裁了，就以为"裁剪可证明"了。**那是行为，不是证明。**
3. **借"不可达"删掉副作用路径**（§3.4）——14B 的 `47e6d1e` 是同款，
   LLVM 侧会以 `unreachable` 化的形式重演。
4. **启用快速数学或未定义溢出回绕**（§3.2）——悄悄改掉 Xiao 的溢出语义。
5. **把"体积/时间/布局不同"当差异**（§3.5）——制造假报警，久了就没人看报告。
6. **平台顺序同时推**（§3.6）——10K 时三平台一起红、根因各异，同时推会混在一起。
7. **顺手启用了 LTO/PGO**（§3.8）——`15.2` 允许建开关，**不等于**允许默认启用。
8. **用"看起来没删"代替用例**（§二）——14B §八 第 1 条的头号陷阱，在债的清理里最容易复发。
9. **新增进产物的字段没规范化**（§3.7）——`15.6` 虽归 15B，
   但**一个带路径或时间的字段就够让可复现构建失败**。
10. **忘了两个 lock 文件**（§六 第 9 条）。

## 九、验收

## 本批实现记录

当前落点为 `core/rust/crates/xiao-codegen-llvm/src/optimization.rs`、`ir.rs`、`build.rs`
和 `toolchain.rs`。LLVM 侧复用 13A 的 `OptimizationConfig` 与配置指纹，生成
`LlvmOptimizationPlan`：`O0`–`O3` 映射到安全的 `-O0`–`-O3`，快速数学、未定义溢出回绕、
LTO、PGO、向量化和目标特化保持关闭；跨模块、链接时和目标特化 Pass 只登记为关闭开关。

`LlvmOptimizationReport` 随模块和原生产物携带，包含目标字段、LLVM 版本摘要、计划指纹、
启用的 Pass 类别，以及依据 IR Runtime 效果摘要计算出的组件保留/删除原因。Runtime 裁剪
报告在链接前生成，链接后产物检查仍是独立证据，避免把链接器偶然删除误当作可证明裁剪。

`Toolchain` 现在按构建级别传递安全优化参数，默认构建保持 `O0`；构建指纹同时包含优化级别
和计划指纹。调试/可复现构建与性能基线仍由 15B 负责，平台实测顺序按 Windows → Linux →
macOS 推进。

`xiao-optimizer` 已提供四方差分骨架，固定比较输出、退出码、错误类别、随机序列、容器顺序
和 `drop` 记录；布局、体积和时间不进入差异字段。实际跨平台原生回环和 Windows → Linux →
macOS 的门控运行记录仍需在具备对应 LLVM/Runtime 工具链后推进。
