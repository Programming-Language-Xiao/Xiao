## 一、四条已定决策（2026-09-22）

### 1.1 决策一：**进程协议**，不是库 ABI

`00a:237` 挂了很久的待定决策，现在冻结为**子进程 + 结构化 stdin/stdout**。

**决定性论据来自 X0 自己的退出条件**——第 6 条：

> TypeScript CLI 在三平台均能发现并调用兼容版本的 Rust 核心；
> **接口版本失配、核心崩溃和取消都转换为稳定的机器可读诊断**。

**库 ABI 下，核心 panic 就是 CLI 进程崩溃**——根本没有"转换"的机会。
进程协议天然把核心隔离成一个可被观察、可被重启、退出码可读的子进程，
第 6 条的三个场景（版本失配 / 崩溃 / 取消）才有落点。

它同时契合第 5 条「不要求用户另装 Node.js 的独立可执行程序」和 `00a:135` 划出的
跨语言边界职责。

**反过来说**：一旦选定，**不要中途换**。CLI 的全部错误处理、取消、版本协商都建立在这个
隔离模型上，中途改成库 ABI 等于把它们重写一遍，而且两套边界的诊断形状很难一致。

### 1.2 决策二：**长度前缀 + JSON**

理由按强度排：

1. **机器可读且可调试**——`00a:135` 末句要求「不得以解析人类可读 stdout 代替协议字段」，
   JSON 是字段化表达的直接形态；
2. **Length-prefix 避开分帧的经典坑**：源码片段、错误消息、路径都含换行，
   行分隔（NDJSON）会在这些地方出问题；
3. **不引入 Protobuf**：仓内 Protobuf 的定位是**包索引**（`16:60`、11A.1），
   把它引到核心协议上会把两件事混起来，而且可调试性明显更差。

**帧格式**（具体宽度由本批定死并写进文档）：`长度 + JSON 负载`，长度只计负载字节。
**长度上限必须有**——否则一段损坏输入就能让解码端按伪造的长度去预留内存
（研究编码器在 `MAX_COLLECTION` 上用过同一手法）。

### 1.3 决策三：**内置函数不在本阶段**（记一笔账）

**现状**：`print("hello")` 报 `X06-RUNTIME-012`（`INVALID_VALUE`，运行时找不到该函数）。

**后果**：`xiao run` 做出来之后，用户**能跑程序，但看不到任何输出**。
脚本模式的 `RunOutcome.value` 也恒为 `None`（脚本没有显式返回值）。

**已定（2026-09-22）**：接受这个状态，本阶段继续不做内置函数，归属 **20 阶段**
（`xiao-intrinsics`）。**X0 的验收不含「能观察程序输出」这一条。**

**但有两件必须做的事**：

1. **在 UseDocs 里写明**——否则用户跑完一个程序什么都没看到，会以为程序坏了或 CLI 坏了。
   这是**已知限制**，不是缺陷，但必须写出来；
2. **`xiao run` 仍要能表达结果**——靠**退出码**（B0-D 已冻结的五个值）与**结构化诊断**，
   而不是靠输出。这条与本阶段其余验收一致，不额外增加工作。

### 1.4 决策四：**四批交付**

| 批次 | 范围 | 对应退出条件 |
| --- | --- | --- |
| **X0-A** | **协议契约 + Rust 侧入口** | 第 6 条的前半 |
| **X0-B** | TS CLI 骨架 + `xiao run` / `xiao config` | 第 1、4、7 条 |
| **X0-C** | 独立可执行打包 + 三平台构建矩阵 | 第 2、4、5、6 条 |
| **X0-D** | `-debug` 与诊断窗口 | 第 8 条 |

**诊断窗口单独一批不是保守**：`07:197` 要求它由**独立进程**承载、通过匿名管道或本地
套接字通信、还要在 GUI 子系统下强制打开窗口——它自带进程、IPC 和 GUI 三层，
塞进任何一批都会把那一批变成两个阶段。

## 二、协议契约（本阶段**最核心的产出**）

### 2.1 边界必须包含的字段

`00a:135` 已经列死，**照抄不可删减**：

> 请求版本、语言/Runtime 版本、目标条件、优化配置、源码/模块身份、结构化错误、
> **退出码**、取消和诊断事件。

Rust 侧这些**都已经有了**（B0-C 的 `DriverRequest`/`DriverOutcome`、B0-D 的 `ExitCode`
五值、`CancellationToken`、`ReportRecord`）。**X0-A 是把它们映射到帧里，不是重新发明。**

### 2.2 版本协商

X0 第 6 条要求「发现并调用**兼容版本**的 Rust 核心」。本批要定死：

- **谁先说话**：CLI 启动核心后先问版本，还是核心启动时自报？
- **不匹配怎么办**：拒绝并给出稳定诊断（不是让核心跑一半再失败）；
- **版本字段从哪来**：`DriverRequest` 里已有 `FRONTEND_VERSION`、`DRIVER_VERSION`、
  `TAC_*_ABI_VERSION`、`ABI_VERSION`……**本批要给出一个统一的"核心版本"表达**，
  而不是让 CLI 逐个比对五个版本号。

### 2.3 崩溃与取消

- **崩溃**：核心非正常退出（panic / 被信号杀死）时，CLI 必须产出**稳定诊断**
  （含退出状态），而不是"命令失败了"这种不可编程的文本；
- **取消**：CLI 侧的取消要能触发核心的 `CancellationToken`（B0-C 已交付），
  并反映成一个**退出码**（`ExitCode::ArtifactRejected`，B0-D 已冻结）。

### 2.4 ⚠️ 协议的**单一来源**（本批最需要设计的点）

协议消息会在 **Rust 和 TypeScript 两边各写一份**——这正是本仓登记过 7 次的 A 类病形态
（「同一条规则在两层各写一份，然后漂移」）。

**必须给出对策并写明依据**，三个候选：

- **A. 从 Rust 生成 TS 类型**（例如导出 JSON Schema 或直接用 `ts-rs` 一类工具）；
- **B. JSON Schema 作为单一来源**，两边各自生成；
- **C. 两边手写 + 共享 fixture 契约测试**——沿用 `tests/spec/` 的既有传统，
  同一批请求/响应样本同时喂给两侧解析器。

**选哪个都行，但要写明为什么不选另外两个。** 无论选哪个，**都要有一条测试**：
Rust 侧产生的帧能被 TS 侧解析、TS 侧产生的帧能被 Rust 侧解析，且**用的是同一批样本**。

**X0-A 决定采用 C：两侧保留窄的公共消息类型，共享 `tests/spec/11x0-protocol/` 夹具和
双向回环测试。** 当前仓库还没有 Schema 生成流水线；引入生成器会把协议冻结和工具链建设
耦合到 X0-B/C，并不能减少首批字段审阅。A 方案会让 Rust 构建额外承担 TypeScript
生成物发布与版本追踪，B 方案则需要先建立 `tools/schema` 的生成/校验门禁。C 先用同一批
机器样本锁住字节级边界，后续若字段规模需要增长，再由独立变更把夹具迁移到 B，迁移前不得
同时保留第二套隐式规则。

### X0-A 已落地记录（2026-09-22）

1. **帧格式冻结**：8 字节无符号大端长度字段 + UTF-8 JSON 负载；长度只计算负载字节，
   `MAX_FRAME_BYTES = 16 MiB`。首字节 EOF 是正常结束，部分长度、部分负载、超长负载、
   非 UTF-8 和非法 JSON 都进入 `X11-PROTOCOL-001`，分配前完成上限检查。
2. **版本协商冻结**：首帧必须是 `type = "hello"`。协议用 `protocol_version = 1` 和统一
   `core_version = 1` 做兼容判断；前端、驱动器、字节码布局、Runtime ABI 和 LLVM 版本
   作为 `versions` 诊断字段返回，CLI 不逐个比较这些组件号。失配使用
   `X11-PROTOCOL-004`，不会启动用户代码。
3. **消息集合**：`hello`、`run`、`build`、`cancel`、`shutdown`，结果统一带
   `request_id`、`exit_code`/`exit_name`；运行结果带前端诊断、报告、事件、指标和值摘要，
   构建结果带产物和工具链指纹。目标、语言/Runtime、优化、源码/模块身份均是显式字段。
4. **Rust 入口**：`xiao-driver` 的 `protocol` 模块和 `xiao-core` 二进制读取标准输入、
   写标准输出，分别调用 `FrontendVmDriver` 与 `FrontendNativeDriver`。协议层不解析 AST、
   不做类型/生命周期推断，也不接受手写 TAC；`-O0` 是 X0-A 唯一可执行优化级别。
5. **取消和崩溃**：服务为每个请求登记 `CancellationToken`，`cancel` 按请求 ID 触发，
   驱动器返回的 `ArtifactRejected` 固定映射为进程码 2。请求线程捕获 panic 并返回
   `X11-PROTOCOL-003`/进程码 4，同时在 `details` 写入 `status` 与 `process_exit_code`；
   帧级故障返回 `X11-PROTOCOL-001`/进程码 2。执行前拒绝保留 `report`，错误对象都带
   `next_step`，机器逻辑只读取 `code` 和结构化字段。
6. **跨语言证据**：Rust 测试和 Bun 测试共同读取 `tests/spec/11x0-protocol/`；双方都
   覆盖请求/响应回环、长度字段和截断/超长输入。TypeScript 文件只属于协议适配夹具，
   完整命令路由、打包和平台发现仍归 X0-B/C。

X0-A 的定向验证命令为：

```text
cargo test --manifest-path core/rust/Cargo.toml -p xiao-driver --all-targets
bun test cli/ts/src/protocol/protocol.test.ts
bunx tsc --noEmit -p tsconfig.json
```

## 五、最可能翻车的地方

1. **协议在 Rust 和 TS 各写一份并漂移**（§2.4）。这是本仓的头号病，而协议是它的高发区。
2. **解析人类可读文本判断成败**（`00a:135` 末句、X0 第 6 条）——
   CLI **不得**通过 grep 核心的 stdout 文本来判断结果。
3. **中途换成库 ABI**（§1.1 末段）。
4. **把 `print` 的缺失当成 X0 的缺陷去修**（§1.3：它归 20）。
5. **顺手做诊断窗口**（归 X0-D，见 §1.4 末段）。
6. **在 Rust 侧协议层重新实现语义**——它只能**编排**已有驱动器。
7. **版本协商流于形式**：逐个比对五个版本号而没有统一的"核心版本"表达（§2.2）。
8. **忘了 `tests/benchmarks` 独立 crate 的 lock**——该盲区已经造成**三次**漏提交
   （B0-B / N0-A / X0-A），三次都写在交接文档里提醒过、都没有生效。**2026-09-22 起已固化为
   `check:lock` 门禁并并入 `bun run check`**（见 [00A.1](00a-a0-workspace-and-checkers.md)），
   不再依赖提醒。跑 `cargo check` 之后如果锁文件出现 diff，就是漏提交。

## 七、验收（X0-A）

沿用 09R2D 的「撤掉实现 → 用例必须失败 → 还原 → 通过」。**关键验收不是「测试通过」**：

1. **往返成立**：Rust 侧生成的一批帧能被 TS 侧解析，反之亦然，**用的是同一批 fixture**（§2.4）；
2. **版本协商有断言**：版本不匹配时**拒绝**并给出稳定 `code`，不是跑一半再失败；
3. **崩溃有稳定诊断**：人为让核心 panic，CLI 侧拿到的是机器可读的失败，不是自由文本；
4. **取消可观测**：取消反映成 B0-D 冻结的 `ExitCode::ArtifactRejected`；
5. **不重新实现语义**：协议层只调用现有驱动器，grep 不到重复的类型检查或生命周期推断；
6. **`00a:135` 的字段清单逐项有落点**；
7. **门禁全绿**，含 `tests/benchmarks`，且 `ignored` 数量可见。
