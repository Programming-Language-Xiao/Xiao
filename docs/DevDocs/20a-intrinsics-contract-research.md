## 一、为什么现在必须先把这三件事定下来

### 1.1 20B 的前置列与它的交付内容对不上

方向稿 §七 的表格：

| 子阶段 | 前置 | 交付 |
| --- | --- | --- |
| `20A 契约与盘点` | 现有类型/IR/研究 VM | 独立契约 crate 方案、现有特判清单、id/签名/效果/能力模型 |
| `20B 最小生产入口` | **09-B0、Runtime ABI 基础** | `print`、`input`、错误/转换等最小入口**迁移**和**表驱动分派** |

20B 的两项交付物——「**迁移**」意味着把现有特判搬走，「**表驱动分派**」意味着有一张表——
**都指向 20A 的产出**。但前置列里没有 20A。

**这不是文字疏漏，而是切法本身有歧义**：要么 20A 与 20B 必须同批完成，要么 20B 自己
建一张最小表、20A 再扩展。**两者的工作量与风险差别很大**，必须先裁定。

### 1.2 `print` 卡着 17

[17 规范](17-xar-archive.md) `:21` 的交接检查写的是：

> 接手代理应能用一个只有 `print("hello world!")` 的 `.xiao` 文件生成测试归档。

没有 `print`，`.xar` 的端到端验证**只能看退出码**——归档能打包、能校验、能拒绝坏成员，
但「跑起来对不对」无法观察。**这会显著削弱 17 的验收强度**，也是把 20B 排在 17 之前的原因。

### 1.3 现状比方向稿描述的更需要收拾

方向稿 §三 开头说「生产字节码和 LLVM 不能继续按名称各自维护规则」。
**实测下来问题不止「各自维护」，还包含「不校验签名」**（见 §二）。

## 二、现状盘点（2026-10-03 实测）

### 2.1 类型层的按名称分派：共 5 处

`grep -rn "simple_callee_name" core/rust/crates/xiao-types/src/` 去掉定义本身后：

| 位置 | 名称 | 是否有签名校验 |
| --- | --- | --- |
| `checker/expression.rs:518` | `input` | **无**——只对实参逐个 `check_expression`，不看个数与类型 |
| `checker/expression.rs:524` | `print` | **无**——同上 |
| `checker/expression.rs:540` | `FatalError` 等错误构造 | 有（按错误类型名检查） |
| `checker/conversion.rs:21` | 标量转换（`int`/`str` 等） | **有**——`check_scalar_call` 校验参数个数为 1 |
| `set_checker.rs:184`、`:186` | `set` 构造 | 有 |

**两类要分开看**：

- **有签名校验的**（转换、`set`）：规则至少是明确写下来的，迁移到契约表是**搬家**；
- **无签名校验的**（`print`、`input`）：**当前接受任意参数个数和任意类型**。
  `print()` 与 `print(1, 2, 3)` 在类型层都返回 `Type::None` 而不报错。

**后者是 20B 的真正难点**：迁移不是「把已有规则搬到表里」，而是**规则本身还没定**。
`print` 的可变参数怎么表达、`input` 的返回类型是否受提示参数影响——**这些是语言决策，
不是实现细节**。

### 2.2 执行层是完全空白

`grep -rn '"print"\|"input"'` 在 `xiao-ir`、`xiao-bytecode`、`xiao-vm`、`xiao-codegen-llvm`
中**没有任何命中**。也就是说：

> **类型层认识 `print`，执行层完全不认识它。**

这解释了 UseDocs 与 `11X0-B` 反复出现的「`print` 尚未实现」。

### 2.3 `'intrinsic'` 一词在本仓有歧义

`xiao-codegen-llvm` 里已有 `intrinsic` 标识符，指的是 **LLVM 自己的 intrinsic**
（`llvm.fmuladd`、`llvm.fabs` 之类，见 `ir.rs:1284`、`:1507`）。

方向稿说的「intrinsic」是**Xiao 的内置函数契约**。两者**同名不同物**，
本文与后续文档一律用 **`IntrinsicDecl` / 契约表** 指代后者，避免混淆。

## 三、20A 与 20B 的关系裁定（**已决策：合并为一批**）

**已决策**（2026-10-03）：**20A 与 20B 合并为一批**，一次完成契约表与
`print`/`input`/转换的迁移，验收标准是「**表驱动分派真的跑通**」。

**理由**：**表的唯一价值是被消费**。分开做会产生一段「表已存在但无消费者」的时期，
而方向稿 §三 3.3 明写「**表存在但某个消费者仍按字符串特判，视为未完成**」——
分开做恰好落在这句话的反面。

**代价与对策**：合并后批次较大，且 §二 2.1 显示「有规则的」（转换、`set`）与
「规则本身还没定的」（`print`、`input`）混在一起。对策是把它们**分步提交**：
先迁移有规则的两类（验证表机制本身可用），再接 `print`/`input`（此时才引入新的语言决策），
**不要让语言决策淹没在迁移噪音里**。

<details>
<summary>未被采纳的两个切法（记录以免重复讨论）</summary>

| 切法 | 做法 | 不采纳的原因 |
| --- | --- | --- |
| **先 20A 后 20B** | 20A 只出契约 crate、特判清单与 id/签名模型；20B 再接执行 | 20A 的验收**没有执行面证据**——只能验「表存在且自洽」，无法证明它真能驱动分派；且 `print` 的签名仍悬空 |
| **跳过 20A 直做 20B** | 先给 `print`/`input` 加最小分派，契约后补 | 与方向稿 §三 的单一来源目标冲突；**大概率二次返工**，正是本仓反复栽的「补丁叠补丁」 |

</details>

## 四、开工前必须冻结的决策（**待审**）

### 4.1 `print` 与 `input` 的签名（**已决策：可变参数**）

**已决策**（2026-10-03）：`print` 采用**可变参数**。

**由此产生的硬要求**：`IntrinsicDecl.signature` 的描述能力**必须能表达 variadic**——
这不再是 `print` 一家的需求，而是**契约表的表达能力下限**。往后每个可变参数入口
（`print`、可能的格式化与日志入口）都依赖它，所以**必须做进契约模型本身，
不得用「`print` 特例」的方式绕开**。

**仍待定（`input` 的两个子问题，实施时定，不得默认）**：

- 是否接受提示参数（若接受，同样是 variadic 的一个用例）；
- 读不到输入时返回 `str` 还是可恢复错误——注意 **`print` 家族不再调用它**，
  这条独立成立。

**注意 `print` 的返回值语义**：现状类型层返回 `Type::None`，迁移后**必须保持不变**，
否则会波及所有把 `print(...)` 当语句用的既有代码与规格快照。

### 4.2 契约 crate 的形态（**已决策：新 crate + 声明式数据文件**）

**已决策**（2026-10-03）：新建独立 crate（名称采用方向稿 §三 3.1 的暂定名
`xiao-intrinsics`），声明写成**声明式数据文件**，由构建期或专门步骤生成 Rust 消费者。

**方向稿 §三 3.1 的约束不变**（不可违反）：位于类型/字节码/Runtime/VM/LLVM 与平台实现的
**共同下层**，只存后端无关声明，**不能**保存 Rust 函数指针、`RuntimeValue`、平台句柄或
LLVM 类型；**`xiao-types` 适配契约，而不是契约依赖类型层**。

**由此新产生的待定项（实施文档须冻结，不得默认）**：

| 待定 | 说明 |
| --- | --- |
| **数据文件格式** | JSON（仓库已有 `serde_json` 依赖，**零新依赖**）／ TOML（可读性更好，需新增 `toml` 依赖）。**推荐 JSON**——但注意这是**倾向而非硬约束**：11A-CONC §1.2 的「零新依赖」只约束**并发**，不是全局政策 |
| **生成时机** | 构建期（`build.rs`）／ 提交前手工生成后入库 ／ 测试期校验。**若选「提交前生成入库」，必须同时入库生成器与产物，并加门禁防止两者漂移** |
| **契约表与 `.xiao` 配置的关系** | **不得**复用 `config.xiao` 的解析器——契约表是编译器内部声明，而 `config.xiao` 的解析属于前端，复用会造成契约与前端互相依赖 |

### 4.3 `IntrinsicId` 的编码（**已决策：u32，0 保留为无效**）

**已决策**（2026-10-03）：`IntrinsicId` 宽度 **`u32`**，**`0` 保留为无效/未初始化哨兵**，
永不分配给任何声明。

**冻结**：

- **`0` 不是合法 id**——校验步骤必须拒绝 id 为 `0` 的声明与字节码操作数；
- 数值一经发布**不得复用**（方向稿 §三 3.4）；删除的声明保留 **tombstone**，
  tombstone 的**具体区间划分**在本批内冻结并写入契约 crate 文档；
- **该宽度进入字节码与 LLVM ABI**，本批之后变更需走 ABI 版本提升，**不得静默加宽**。

## 五、盘点范围与方法（本文只给方法，清单是 20A 的交付物）

对每一个候选内置入口，逐层核对它当前**在哪一层按什么规则被识别**：

1. **语法层**——是否有专用关键字/语法（如 `set` 构造）；
2. **类型层**——`simple_callee_name` 之类的名称分派（本文 §2.1 已列 5 处）；
3. **IR/降低**——是否生成专用节点；
4. **字节码**——是否有专用 opcode；
5. **VM**——是否有分派分支；
6. **LLVM**——是否直接声明符号或调用 Runtime ABI。

**判据**：只要上述任一层**按字符串名称**判断，就登记为「待迁移特判」；
六层都查不到，登记为「尚未实现」（`print` 与 `input` 属于这一类）。

## 六、风险

1. **把语言决策当实现细节**（§4.1）——`print` 的可变参数语义一旦由实施者顺手定下，
   就变成既成事实，事后改会波及契约表、类型层、两条后端；
2. **契约 crate 反向依赖 Runtime 层**（§4.2）——会锁死类型层，且与方向稿的
   「后端无关声明」直接冲突；
3. **建表但留特判**——方向稿 §三 3.3 明写视为未完成，验收必须能**证伪**这条
   （建议：删除契约表项或某一消费者后，专门用例必须失败）；
4. **`IntrinsicId` 编码先于 ABI 冻结**（§4.3）——它要进字节码和 LLVM ABI，
   定早了比定晚了代价更大；
5. **批次切得过大**——§二 2.1 显示「转换」「`set`」两类已有规则，而 `print`/`input`
   连规则都没有，两者混在一批容易让语言决策被实现细节淹没。

- **不冻结**方向稿 §八 的 7 条待冻结问题中的任何一条——本文只把它们**拆解成可选的选项**；
