## 二、必须先冻结的 7 条

### 2.1 **CI 是红的，根因是 20AB 的回归，不是原生后端的既有空缺**

**事实**：

- 最近一次定时运行（10-05，`57d4947`）四平台全部在同一步骤失败；最近一次成功是 10-03 的 `48f8ff3`，
  它是 `cd08ca0` 的祖先；
- 两个被读过日志的平台，失败都是 `n0_a_native_driver` 的 `optional_native_catch_does_not_terminate` 与
  `optional_frontend_artifact_differential_round_trip`，报 `动态 intrinsic ArithmeticError`；
- 从 `48f8ff3` 到 `57d4947`，只有 `cd08ca0`（20AB，10-04）改过 `xiao-codegen-llvm`。它让前端把
  `ArithmeticError(...)` 降成 `IntrinsicCall`（`vm_binding = make_error`），而新增的
  `emit_intrinsic` 只接了 `Print` 与 `Input`，其余落到 `_ =>` 分支报 `Unsupported`；此前这类调用走
  `emit_call` → `emit_error_new`。该提交说明里写的是「受控 LLVM 测试按环境门控」，即没有实跑。

**判定方式**：以上是读代码得出的，**没有二分验证过**。`4231138` 修复后，本机 Windows 上这两个用例
转绿；另外新增的不依赖 clang 的测试在撤掉修复时会报出与 CI 相同的 `动态 intrinsic Error`。
这能支持根因判断，但 **CI 上是否转绿还没验证**（见 §2.6）。

**更正 19A**：19A 实施记录把这两个失败写成「原生后端已有缺口，与本批改动无关」，**写错了**。
`d19a_differential.rs` 的 `native_gap` 里 `caught`、`unmatched` 两条登记因此在掩盖一个回归，
修复后必须摘除（缺口消失时该用例本来就会报错提醒）。

**建议处置**：在 `emit_intrinsic` 增加 `MakeError` 分支，复用 `emit_error_new`；归属 20AB/15，
单独一个提交，提交说明写明是 `cd08ca0` 的回归修复。

### 2.3 **兼容矩阵是一张由代码生成、按证据状态逐格核对的表，不是一页散文**

规范要求：旧产物的行为必须明确为「直接运行、重新生成、迁移、拒绝」四选一，**不能因为看起来能解码就跳过版本检查**。

**冻结**：

- 行是被检对象：`.xiaoc` 格式、索引 Schema、`.xar` 版本、Runtime ABI 区间、IR 版本、语言版本、优化配置指纹、目标平台；
- 每一格是「产物版本 × 当前核心版本 → 四种行为之一 + 稳定错误码」，由代码生成；有真实编码器/解码器或运行前校验证据的格子由测试覆盖，暂时没有对应产物字段或入口的格子必须明确标为 `Unverified`，文档里的表来自同一份数据；
- 已有行为先**如实录入**（例如 `.xiaoc` 主版本不同拒绝、次版本更高拒绝、次版本更低放行；`.xar` ABI 区间外拒绝；
  缓存版本不匹配重新生成），**录入阶段不改行为**；
- 录入后发现某一格没有测试、或行为与 16/17 的既有冻结不一致，按 §2.2 的办法回到归属阶段。

旧格式的拒绝、自动重编译和迁移窗口是 19 规范里**尚未决定**的事。决定之前，矩阵里这些格子只能写
「现状」，不能写「策略」。

### 2.4 **跨平台差分复用 19A 的比较与现有复现入口，不另起一套**

- 比较器：合并 D6，让 `d19a_differential.rs` 与 `xiao-optimizer` 的差分模块共用一份；
- 入口：复用 `tools/platform-reproduction/` 与 `platform-reproduction.yml`，不新增第二个工作流；
- **顺序问题**：规范要求「按 Windows、Linux、macOS 顺序，后一平台重跑前一平台回归」。现有工作流是四个平台
  **并行**跑、互不依赖，字面上没满足。建议保持并行（省时间、便于定位），改为**报告层面**按该顺序汇总并逐平台
  列出「前一平台回归是否同样通过」；是否要改成串行 `needs` 留给后续维护决策；
- 平台间的输出必须先**规范化**再比较：退出码在 Unix 上被信号终止时 `status.code()` 为 `None`，
  Windows 则是 `0xC000001D` 这类状态值，19A 的原生差分里暂时用 `unwrap_or(-1)` 顶着，跨平台前要改成明确的
  「正常退出码 / 信号终止」两种。

### 2.5 **`19.7` 先盘点再补，不重复造已有的测试**

五项逐一处理：换行（LF/CRLF 源码与输出）、路径（分隔符、相对与绝对、含空格与中文）、权限（只读对象、
不可写缓存与输出目录）、大小写文件系统（大小写不敏感的卷上同名不同大小写的模块与对象）、进程信号
（`xiao run`、`xiao -xar` 与原生产物收到中断时的退出语义）。

第一步是产出一张「已有测试 / 缺失」清单（§1 现状里标「未核实」的都在这一步落定），**缺的才补**。
补的用例必须能在三平台上得到各自可解释的结果；某平台做不到的（例如 Windows 没有 POSIX 信号）要在用例里
显式写明并断言替代行为，**不允许用 `cfg` 让某平台悄悄少跑**。

### 2.6 **证据来源：本机只有 Windows，Linux 与 macOS 只认 CI 日志**

- 本批所有「Linux 行为」「macOS 行为」的结论，依据只能是某次具体 CI 运行的日志，文档里写明运行号与提交；
- 平台复现工作流**不随 push 触发**。本地现在领先远端一个提交（19A），要让 CI 看到它需要先推送，再手动触发；
  推送与触发都是对共享状态的操作，**需要星崽明确同意**（见 §2.6）；
- 没有 CI 证据的平台，报告里写「未核实」，不写「预期一致」。

### 2.7 **发布报告：由 Rust 核心产出，不新增顶层命令，不在 TypeScript 里算哈希**

规范要求报告包含优化指纹、依赖摘要、对象哈希和归档成员，O6 退出条件 4 还要求「重复构建差异在白名单内」。

**冻结**：

- 报告内容在 Rust 侧计算，CLI 只搬运和呈现（18B §2.2）；
- 不新增顶层命令（18B §2.1）。建议挂在 `verify --detail` 上扩展，前提是先核实它现在返回了什么——
  **这一步没做**，可能需要补字段，也可能需要别的入口，届时回来改本节；
- 字段至少有：源码摘要、依赖锁摘要、优化配置指纹、工具链版本、每个 `.xiaoc` 对象的 SHA-256、
  `.xar` 成员清单与整文件摘要、目标平台、Runtime ABI 区间；
- **白名单**：重复构建允许不同的字段必须显式列出并写明原因（例如时间戳若存在），其余字段逐字节相同；
  列表为空也要写出来。白名单的具体内容本批通过实测两次构建得出，**不预设**；
- 未实现签名时，报告与 CLI 都要明示「SHA-256 只保证完整性，不代表发布者可信」（规范「完整性与信任」一节）。
