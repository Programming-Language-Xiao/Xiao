## 二、⚠️ 本批最容易做错的三件事

### 2.1 把 E3A 做成"联网实现"

E3A 的六条任务全是**定义/设计/冻结**。**真正的 HTTP/Git 传输在 E3B/E3C**。
本批交付的是**接口与数据结构**，以及**本地目录源**（它不需要网络，能让契约立刻可测）。

**判据**：E3A 结束时，**测试里不应出现任何网络调用**。若要验证适配器接口，
用**本地目录源**或**内存中的假适配器**。

### 2.2 只写契约文档，不落数据结构

`11a:241` 明写 D1「只保留 `sources` 表为静态节点，**不解析其字段**」——
**本批必须把"不解析"变成"解析并校验"**，否则 E3A 结束时 `config.xiao` 的多源声明
依然只是一堆没人看的字典值。

### 2.3 JCS 两侧各写一套

`00-decisions:299` 已经把这条路标成红线：

> **Rust 与 TypeScript 两侧必须共用同一组规范化测试向量**——N 个实现各写一套规范化
> 正是本仓登记在案的头号病史。

**已冻结的取舍（见 §三.4）**：E3A 只实现 Rust 侧，**TS 侧暂不实现**（无消费者），
**但共享向量在本批落地**，将来 TS 侧实现时直接跑同一份。

## 三、必须先冻结的 7 条

### 3.1 `[sources]` 表的确切名字与字段形状

**要分清哪一半已冻结、哪一半没有**（`11a:241-259`）：

- **已冻结**：表名是 `[sources]`；数组的书写顺序与依赖 `source` 绑定的优先级；
  三概念（`source_id`/`alias`/显示名）的分工。
- **未冻结**（`11a:259` 原话「**字段名仍待 E3A 冻结**，但三者的分工不再改变」）：
  每个源条目的**字段名与白名单**。
- **示例里的 `source = "community"` 绑定的是 `alias`，不是显示名**——本批的解析必须照此。

`11a:245-246` 的现有写法是：

```xiao
[sources]
sources = [
    { alias = "official", display = "官方源", kind = "registry", location = "..." },
]
```

**⚠️ 这个写法本身有个命名问题**：表名 `sources` 与键名 `sources` 重复，读起来是 `sources.sources`。
本批**要定死一个**，二选一：

- **(a)** 顶层数组式：`[sources]` 下直接是具名条目（`office = { ... }`），
  这与 D1 已冻结的 `[dependencies]` 写法同构，**推荐**；
- **(b)** 保留 `sources = [...]` 数组，但把表名改掉（如 `[packageSources]`）避免重复。

**推荐 (a)**：理由是本仓 `[dependencies]`/`[devdependencies]`/`[toolchain]` 全是
"表下具名条目"的形状，数组式是本仓的孤例。**同一种配置不该有两种书写风格。**

**同时要冻结每个源的字段白名单**（对齐 `11a:211-222` 的"统一包源契约"六项，
但注意那是**协议要表达的逻辑信息**，不是 `config.xiao` 的**用户书写字段**，两者不能照抄）：

- `kind`（源类型）、`location`（地址/路径）、可选 `alias`、可选显示名、可选协议版本约束。

### 3.2 源身份规范化（已冻结 `:295`，本批落地）

`00-decisions:295` 已冻结，**照做即可**：

- `source_id = kind + ":" + 规范化 location`，如 `git-index:github.com/example/xiao-packages`；
- 规范化：协议与 host 小写、去默认端口、去路径尾部斜杠与 `.git` 后缀；
- **三个概念分开**：稳定的 `source_id`、配置内引用的 `alias`、纯展示的显示名；
- **依赖只能引用 `alias` 或明确的 `source_id`；显示名不参与身份、也不能被依赖引用**；
- `alias` 冲突**默认报错**。

**⚠️ 本地路径源已实现**（D1 的 `PackageSource::local_path`，前缀 `path:`）。
本批新增的是**远程 kind**，规范化规则必须与它**共用同一个函数**，不得另写一份。

### 3.3 跨源选择与歧义诊断（已冻结 `:291`，本批落地）

`00-decisions:291` 已冻结：

> 依赖显式指定的源优先；未指定源时按 `config.xiao` 中源的**书写顺序**逐源尝试。
> **不得把不同源的候选放在一起比较版本号后选择"最高版本"**；
> 在既定源优先级、约束和锁定信息仍无法得到唯一结果时，**必须直接报歧义错误**，
> 不能依赖网络返回顺序或遍历偶然顺序。

**⚠️ 还有一条容易漏的**：`:301` 冻结了**导入源列表的最终顺序算法**（不是原则）：

> **先全部直接声明的源（按书写顺序），再各导入列表的源**（列表本身按配置中的书写顺序，
> 列表内部按该清单的顺序）。

`11a1:56` 特别注明这**不重开** 11A 已冻结的逻辑内容。**⚠️ 那处原文引的是当时的
`11A:173-178`，该行号早已漂移**（现在 173 附近是「依赖锁文件」章节的末尾）。
它所指的五类内容现在分布在三节：**六项必列信息**在 `11a:211-222`、
**刷新语义/失效规则/离线规则**在 `11a:261`（联邦源索引）、
**多源选择规则**在 `11a:332`。**接手时按章节名找，不要按那个行号。**
**本批要把它实现成一个纯函数并单测**——它是"确定算法"，正适合做成可穷举验证的东西。

### 3.4 RFC 8785（JCS）的实现范围（**已冻结的取舍**）

`00-decisions:299` 冻结：规范化**采用 RFC 8785（JCS），不自造规则**；
UTF-8、**拒绝重复键与非 I-JSON 数值**、超出安全整数范围的值**以字符串表达**；
摘要一律对**规范化后的字节**计算；规范化在**源侧生成时**完成。

**本批的范围（已定）**：

- **实现 Rust 侧** `xiao-package/src/jcs.rs`；
- **建立共享向量** `tests/spec/11a-jcs/vectors.json`：每条含**输入 JSON + 期望规范字节 + 期望摘要**；
- **TS 侧暂不实现**——索引解析在 Rust，CLI 不做求解、目前无消费者；
- **但向量文件在本批落地**，将来 TS 侧实现时直接跑同一份，**不重新发明**。

**⚠️ 向量要覆盖的边界**（不覆盖就等于没建）：

| 边界 | 为什么必须覆盖 |
| --- | --- |
| 键序（按 UTF-16 码元排序） | JCS 的排序规则不是"字典序"，ASCII 大小写与代理对会分叉 |
| `1.0` vs `1` vs `1e2` | 数值规范化，`:299` 明写"`1.0` 写成 `1` 会让摘要对不上" |
| 超出安全整数范围 | `:299` 要求**以字符串表达** |
| **重复键** | `:299` 要求**拒绝**——不是"后者覆盖前者" |
| **非 I-JSON 数值**（NaN/Infinity） | `:299` 要求**拒绝** |
| 字符串转义（控制字符、`\u` 代理对） | 转义不一致会让字节不同 |
| 空对象/空数组/嵌套 | 基础回归 |

### 3.5 传输适配器接口的形状

`11a:184`：「解析器只能消费适配器返回的**规范化元数据**，不能让某种来源改变依赖、
版本或安装语义。」

**要冻结的是一个 trait**，其形状受三条约束：

- **不泄露传输细节**——调用方拿到的必须是规范化记录，而不是 HTTP 响应或 Git 对象；
- **协议版本必须可校验**——`:297` 冻结：「客户端遇到不认识的协议版本必须**拒绝该源并给出明确诊断**，
  **不得尽力而为地解析或静默降级**」；
- **元数据与正文分离**——`11a:222`：「包源元数据必须能与包正文分开获取，
  使求解器不需要下载完整源码归档才能比较版本」，且要支持**按包名分片或等价的稀疏查询**。

**⚠️ 本批只定义 trait 与一条本地目录适配器**（不需要网络），远程适配器是 E3C。

### 3.6 联邦源索引的合并键与快照记录

`11a:261` 的「联邦源索引」章节已冻结逻辑。要落成数据结构的关键两条：

- **合并键必须含来源维度**——`12-tests:779` 明写「联邦索引**保留同名同版本的不同来源**」，
  所以**包名/版本单键是错的**（`11a:475` 的"不得以包名/版本单键覆盖不同来源"）；
- **每条记录要保留**（`:292`）：源身份、**配置序号**、**快照标识/摘要**、状态、候选来源。

**⚠️ 配置指纹**（`:292` 已冻结，本批落地）：

> 配置指纹必须同时保存**整个列表的摘要**与**按最终优先级排列的规范化源序列**——
> 只存 `source_id` 集合会丢掉顺序、重复项与导入来源。

**⚠️ 这与 E0/E2A 的指纹不是一回事**：E0 的配置指纹用 `stable_hash`（FNV-1a，非加密）、
E2A 的锁文件指纹复用 E0。**本批的源列表指纹是配置指纹的一部分**（进 E0 的输入），
**不是**新的独立指纹。**不要另造第三个指纹体系。**

### 3.7 源粒度的诊断编号

现有编号覆盖包/环境/缓存/锁文件/同步五种粒度（§一现状）。**源是第六种**，
建议新开 **`X05-SOURCE-*`**，并在文档里写明理由。

至少要覆盖：协议版本不认识（`:297`）、`alias` 冲突（`:295`）、
源不可达、快照摘要不匹配、未知源引用。

## 六、硬约束

### 6.1 单一来源

- **不重新扫描 `config.xiao`**（`05d:103`）——消费 `ConfigDocument`；
- **不重写 `source_id` 规范化**——本地源已有实现，新 kind 复用同一函数；
- **不另造指纹体系**（§3.6）；
- **不重写 JSON 规范化**——JCS 只有一份，两侧共用向量。

### 6.2 不联网

§二.1。E3A 的测试**不应出现任何网络调用**。

### 6.3 不执行包代码

`00-decisions:294`：「首个远程包管理闭环禁止包提供或执行任意安装前、安装后脚本。
依赖元数据解析和环境安装均不得执行包代码。」
**本批虽不装包，但解析索引同样不得求值任何东西。**

### 6.4 确定性

联邦合并、候选排序、`alias` 冲突报告**必须顺序确定**：用 `BTreeMap`，
**不用 `HashMap` 的迭代顺序**（D1/E1/E2A 已建立这个习惯）。
`:291` 明写「不能依赖网络返回顺序或遍历偶然顺序」——**这条正是本批要测的**。

### 6.5 门禁

`A0-LAYOUT-002`（§5.1）、`A0-SIZE-001`、`A0-DOCS-001/002`、
`bun run check`（**已含 clippy**，E2A 修复）。

## 十一、上一批（E2B）的欠账与修复（**一并纳入本批**）

E2B 的两条退出条件已满足（审核实测：Rust 测试全绿、激活通道实现**比交接文档建议的更安全**
——它不 `source` 而是提取路径后直接赋值、E2A 三处欠账全部收敛）。以下一并纳入 E3A。

### 11.1 ⚠️ 待修：`bun test` 在真彩色终端下必失败（**真问题**）

**实测**：本机 `COLORTERM=truecolor` 时 `bun test` 得到 1 fail：

```
期望 toContain("[32m")          ← 标准绿色 ANSI（11a 冻结的"绿色 ANSI"）
实收 "[38;2;76;175;80m..."      ← 24 位真彩色
```

**根因**：`activatePromptState` 的测试没传 `colorTerm`，
而 `cli/ts/src/ui/color.ts` 的 `createColorizer` 会回退读 `process.env.COLORTERM`。

**不是 E2B 的回归**——`ui/color.ts` 是 `6d3bb7b`（11X0-B）引入、
`environmentPromptPrefix` 只在 E0（`d9300ce`）出现过。清掉 `COLORTERM` 后 15 pass / 0 fail。

**危害**：**本地红、CI 绿**（GitHub runner 无 `COLORTERM`）。真彩色终端的开发者
要么学会忽略这个失败（信号失效），要么被引去改一个没坏的代码。

**修复**：测试里**显式传 `colorTerm: ""`**（或等价地隔离环境变量），
让测试不再依赖宿主终端。**顺带检查 `ui.test.ts` 是否也有同类依赖**
（它已经显式传了 `colorTerm`，但要确认全部用例）。

### 11.2 ⚠️ 待议：`bun run check` 不含 `bun test`

`check` = `repo-check all && check:clippy && check:lock`，**不含测试**。
CI 通过 `tools/platform-reproduction/reproduce.sh:138` 兜底跑了 `bun test`
（同处 `:136` 跑 `cargo test`、`:141` 跑 `bun run check`），**所以不是漏洞**。

**但本地 `bun run check` 绿 ≠ 测试绿**。E2A 刚把 clippy 并进 `check`，
**本批要决定 test 是否也并入**，并在文档里写明口径——
不能留下"验收条款要求它、门禁不跑它"的落差（这正是 E2A §11.1 修 clippy 的同类问题）。

### 11.3 纪律：交接文档的跨平台/环境假设必须实测

E2A 交接文档有**两处错误断言**被 E2A 执行方更正（Windows 的 `fs::rename` 实际能覆盖；
本地源身份实际是 `path:` 而非 `local:`）。E2B 审核中我又犯了同类错误两次并自我更正：
说"CI 完全没有 `bun test`"（实际在 `reproduce.sh:138`）、
说 E2B 的 spec 夹具"比 D1 薄"（实际字段被真实驱动，只是行数少）。

**本批及以后的交接文档**：
- 凡「某平台/某工具在某条件下会/不会如何」，**标明是实测还是推断**；
- 引用 `file:line` 时，**写完和改完各核一次**——
  E3A 规划时 `11a`/`00-decisions` 的行号已因前几批落地而漂移，本批引用的行号**已全部重核**。

### 11.4 待补：E1 的只读强度差额

`11ae1` §3.6 要求「若三平台无法做到同等强度，要在文档里写明差额」。
E1 代码分了平台（Windows `set_readonly` / Unix `0o555`·`0o444`）但文档没写。
**E2A 与 E2B 均未处理，仍未结清。**
