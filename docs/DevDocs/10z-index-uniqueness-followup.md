## 二、必须先冻结的 5 条

### 2.1 **U1：先把「唯一」的语义定死，二选一，并说明理由**

**这是本批唯一需要星崽拍板的**。两条路都自洽，但代价不同：

**口径 A —— 按目标路径唯一**（把 `targetPath` 真正用起来）

- 优点：与函数注释一致；「同一页面只能登记一次」最彻底；
- 代价：`09R1`/`09R2` **必须合并成一行**，丢掉「一份研究文档承载两个子批次、两个独立状态」的记录能力；
  且若不同时把「每行取全部链接」也改掉，`09R3`/`09-B0` 行里的 `09R` 引用仍看不见——
  **A 口径不配套改这一项，连它自己承诺的「同一页面只登记一次」都做不到**。

**口径 B —— 按链接字符串唯一**（= 现状行为，把规格写明）

- 优点：`09R1`/`09R2` 本来就是**合法登记**（同一文档的两个子批次），无需改动；
  改动最小；最危险的情形——**两行一字不差、状态互相矛盾**（正是 10X/10V 那次的形态）——照样抓得住；
- 代价：理论上可被「故意加不同锚点」绕过。

**建议：口径 B**，并按 §2.2 把两条边界写成规格。理由：A 的唯一优势依赖一个更大的改动（取全部链接），
而那个改动会立刻引出 `09R3`/`09-B0` 的新重复，越滚越大；B 用一行注释 + 两条边界说明就能覆盖真实风险。

**冻结**：

1. **选定后四处必须一致**：`00a` 的规则描述、`docs.ts` 的函数注释、`docs.ts` 的 identity 实现、`repo-check.test.ts` 的用例；
2. **选 B 就不许动 `09R1`/`09R2`**——它们是合规登记，不是待清理的重复行；
3. **选 A 就必须同时处理** `09R1`/`09R2`（合并）与「每行取全部链接」（否则是半个 A 口径，
   比 B 更糟：注释承诺一套、代码做另一套，只是换了个方向）；
4. **无论选哪条，都要把「为什么」写进 `00a` 的规则说明**——一句话即可。

### 2.2 **U2：两条边界必须写成规格，不能只留在代码行为里**

**冻结**：

1. **锚点边界**：写明「identity 含锚点，因此同一目标路径**允许**以不同锚点登记多次；
   锚点必须真实存在（由 `A0-DOCS-001` 的锚点校验兜底）」——**选 B 时**这句话就是 `09R1`/`09R2` 的合规依据；
2. **首链接边界**：写明「**只检查主表每行的第一个链接**」，并给出理由：
   行内括号里的补充引用（如 `09R3`、`09-B0` 的「权威定义见 …」）是**注记**，不构成登记；
3. **不许**顺手把「取第一个链接」改成「取全部链接」——那会立刻把 `09R3`/`09-B0` 行内的 `09R` 引用算进来，
   引出新重复，然后要么放宽规则、要么改 README，与 §2.1 第 3 条绑成一件事。要改就是口径 A，别单改这一处；
4. 两条边界都要有**对应的测试**（§2.3），否则下次重构会静默改变语义。

### 2.3 **U3：测试要覆盖边界，且负例必须承重**

**冻结**：

1. 现有两条用例保留，**新增三条**：
   - 同一目标路径 + **不同锚点** → **不报**（`09R1`/`09R2` 的形态）；
   - 同一目标路径 + **相同锚点** → **报**；
   - 同一行的**第二个链接**与别处重复 → **不报**（首链接边界的显式记录）；
2. **负例必须承重**：审核本轮的做法是把 `checkDevDocsIndexUniqueness` 改成 `return []`，
   确认负例从 26 pass 变成 25 pass / 1 fail。**改动后要重做这一次验证**并把结果写进提交说明；
3. 用例里的 README 夹具要含「## 实际开发顺序」小节，否则检查函数会直接返回空（现有用例已如此，保持）。
