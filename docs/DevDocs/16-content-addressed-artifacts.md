# 16. SHA-256 内容寻址与二进制索引

> 本阶段为 `.xiaoc` 及后续归档建立不可变产物存储。它复用环境与包管理阶段的内容寻址思想，但构建产物、源码包和依赖锁文件必须保持不同的命名空间与生命周期。

## Agent 交接上下文

### 接手前提

- 先阅读 [14. 字节码优化与 `.xiaoc` 产物](14-bytecode-optimization.md)、[11A. 虚拟环境与包管理](11a-environments-and-packages.md) 和 [12. 测试与开发里程碑](12-tests-and-milestones.md) 的 O3 条目。
- `.xiaoc` 已确定为单模块、不可变的优化字节码对象；项目和归档通过索引引用多个对象。
- 摘要算法已确定为 SHA-256，并覆盖最终规范化 `.xiaoc` 的完整文件字节；二进制索引首版已选 Protobuf。每个 `.xar` 只有一个归档索引，本机全局缓存另有一个逻辑缓存索引，不建立项目级 Protobuf 索引。

### 本阶段交付与不负责事项

- 交付：对象类型命名空间、SHA-256 流式校验、不可变写入、Protobuf Schema/编解码、索引事务和扫描重建工具。
- 不负责：字节码指令优化、LLVM Pass、归档入口和 CLI 命令；分别依赖第 14、15、17、18 阶段的稳定接口。
- 索引不能替代依赖锁文件，也不能把未经验证的路径或文件名当作信任依据。

### 交接检查

接手代理必须能在无网络、不同进程和三种目标平台上，用同一规范 `.xiaoc` 产生相同摘要，完成对象写入/读取/损坏隔离，并用 Xiao 内置 Protobuf Schema 查找记录。所有临时文件和锁必须在测试结束后可清理。

## 一级工程目标：建立内容寻址对象库

### 哈希命名

用户要求字节码文件按内容 `SHA-256` 摘要重命名。摘要输入固定为第 14 阶段完成规范序列化后的整个 `.xiaoc` 文件，从第一个魔数字节到最后一个分区字节全部纳入；不是源码文本、解压前的 ZIP 成员、单独的指令流或排除头部的载荷。这样语言/IR/Runtime 版本、优化指纹、调试激活位/诊断组件版本、依赖摘要或调试分区发生变化时都会形成不同对象，避免误复用实际不兼容的字节码。

`.xiaoc` 不在自身内容中保存这个完整文件摘要，避免产生“摘要字段也属于被散列内容”的循环定义。独立对象由文件名提供期望摘要，`.xar` 中的压缩对象由唯一的 Protobuf 索引提供期望摘要；归档校验时对解压后的规范 `.xiaoc` 字节重算 SHA-256。

文件名主体固定使用完整的 64 字符小写十六进制摘要，形式为 `<digest>.xiaoc`，不允许截断或混用大小写。全局缓存采用 `<cache-root>/objects/xiaoc/sha256/<前两位>/<digest>.xiaoc` 的类型、算法和两位分片布局；`.xar` 内使用对应的 `objects/xiaoc/sha256/<前两位>/<digest>.xiaoc`。缓存根目录的跨平台位置仍由第 11A 阶段冻结。

> **注记（2026-09-22，来自 10C）**：**原生产物**的缓存键还要包含代码生成版本。
> `xiao-codegen-llvm` 的 `CODEGEN_VERSION` 在 N0 期间由 1 升到 2——原因是动态 LLVM
> 文本的调用约定修正（COFF x64 的 `XiaoValue` 隐藏 `sret` 返回与 `XiaoAbiBytes` 间接参数）。
> 那次改动说明：**同一份类型化 IR 会因为后端版本不同而生成语义不同的原生产物**，
> 所以 `CODEGEN_VERSION` 必须与语言/IR/Runtime 版本、优化指纹并列进入构建指纹。
>
> **本阶段不做向前兼容**（项目早期阶段的既定态度）：版本不匹配时**直接重新生成**，
> 不保留旧产物、不写迁移层、不为旧版本准备解码分支。这条同时适用于 `FORMAT_VERSION`
> 与 `CODEGEN_VERSION`——它们是**缓存失效的开关**，不是需要向后读的历史格式。

理论哈希碰撞不能静默覆盖：目标摘要已经存在时，写入器必须比较完整字节；摘要相同但内容不同时隔离两个输入、停止提交并报告高严重度完整性错误。名称不匹配、内容损坏或格式验证失败的对象必须进入隔离区，不能参与运行、打包或缓存命中。

### 对象隔离

至少区分以下对象类型：

- 源码/依赖内容缓存。
- 优化后的 `.xiaoc` 字节码对象。
- 可选的原生构建片段或最终二进制。
- `.xar` 归档及其资源。
- 语言包插件的消息目录资源。

不同对象类型不能只凭同一个文件名空间相互解释。对象写入后视为不可变；项目环境、构建缓存和归档索引保存引用关系，而不是原地修改对象。缓存根目录、权限、跨平台位置和淘汰策略沿用第 11A 阶段的待定决策，不能在本阶段偷偷依赖某个操作系统路径。

## 一级工程目标：集中维护二进制索引

### 索引职责

“索引作用域”表示索引服务于哪个存储边界，不表示一个 `.xar` 要携带多个索引。首版固定为以下两种作用域：

1. **归档索引**：每个 `.xar` 固定且仅有一个 `META-INF/xiao/index.pb`。它是该归档的权威清单，描述入口、逻辑模块名、第一方/第三方来源、对象摘要、资源路径和 Runtime 要求。
2. **全局缓存索引**：本机内容缓存拥有一个逻辑索引，用于把“源码摘要 + 模块图 + 依赖锁 + 工具链 + 目标 + 优化配置”形成的构建请求键映射到对象摘要，并反向记录摘要对应的元数据、引用和校验状态。为避免单个巨型文件和并发重写，它的物理实现可以分片或采用快照加日志，但对调用者表现为一个事务性索引。

首版不建立项目级 Protobuf 索引。项目身份、直接依赖和构建声明继续来自 `config.xiao`，完整依赖解析结果继续来自依赖锁文件；它们都不能被缓存索引或归档索引替代。这样一个项目不会同时维护三份容易漂移的依赖事实。

两种索引都需要记录摘要到对象元数据的映射，至少应能回答：对象类型、逻辑模块/路径、语言/IR/虚拟机或 Runtime 版本、目标平台/架构、优化配置、模块图与依赖锁摘要、入口信息、大小、校验状态和创建工具版本。全局缓存索引还必须支持构建请求键到摘要的正向查找，否则编译器只有已经知道摘要时才能定位对象，会被迫扫描并解析整个缓存。

索引首版采用 Protobuf（Protocol Buffers）。归档索引和全局缓存索引使用同一版本体系下的不同消息类型，不能把可变的本机访问时间、缓存路径等字段写进不可变归档索引。Protobuf Schema 和解码器由 Xiao 工具链提供，因此 `.xar` 不重复携带 descriptor；索引自身携带 Schema 标识、主/次版本和记录类型，仅用于让已安装的加载器选择内置解码器，并不构成脱离 Xiao 的“自解释”承诺。通用 ZIP 工具可以列出物理成员，但不需要能够解释入口、依赖或 Xiao 字段；外部工具应通过 `xiao inspect` 获取稳定的 JSON 或文本视图，而不是自行猜测字段号。

索引采用确定性序列化：影响产物的重复字段先按规范键排序，不依赖 Protobuf `map` 的迭代顺序，不写入未知字段或非规范默认值。未知主版本或未知必需功能直接拒绝；同一主版本的未知可选字段按 Protobuf 规则保留或跳过。归档索引是构建完成后不可变的一次性快照，全局缓存索引则必须通过原子快照/日志事务更新。

选择 Protobuf 的理由是：索引字段由 Xiao 工具链控制、读取频率高且需要紧凑编码和稳定的字段编号；它有意依赖随 `xiao` 提供的 Schema/解码器。没有 Xiao 的外部工具可以把归档当作 ZIP 检查物理结构，但不应猜测字段含义；需要语义视图时使用 `xiao inspect` 或由工具链另行提供的 descriptor，descriptor 不属于 `.xar` 的必需成员。

### 原子一致性

全局缓存写入顺序固定为“规范化产物 -> 临时对象 -> 完整哈希校验 -> 原子改名为摘要名 -> 原子更新缓存索引”。缓存索引更新中断时，旧快照仍可读取；孤立对象可以通过扫描回收。读取缓存索引不能只相信文件名，必须重新计算摘要并检查对象类型、长度、版本和格式校验。

归档索引与 `.xar` 作为一个整体通过临时文件和原子改名提交。归档索引保存入口、第三方来源和资源逻辑路径等无法从散列对象可靠恢复的信息，因此索引缺失或损坏的 `.xar` 必须拒绝运行，不能通过扫描成员猜测重建。所谓“索引扫描重建”只适用于本机全局缓存索引。

并发构建需要进程间锁或等价的无竞争提交协议。两个进程写入相同摘要时应共享已验证对象，写入不同摘要时不能互相覆盖。索引损坏、对象缺失、摘要不匹配、权限不足和磁盘空间不足都要有独立诊断及可恢复路径。

## 二级实现任务

### 摘要与对象存储

1. [16.1] 实现完整 `.xiaoc` 字节的 SHA-256、64 字符小写文件名和两位目录分片规则。
2. [16.2] 实现流式 SHA-256、完整内容比较、碰撞保护和摘要校验工具。
3. [16.3] 实现只读对象写入、临时文件、原子改名、权限设置和并发锁。
4. [16.4] 将 `.xiaoc`、源码包、语言目录和可选原生产物分配到独立对象类型。

### 索引编解码

1. [16.5] 分别冻结归档索引与全局缓存索引的 Protobuf 消息、字段编号、版本和确定性序列化规则。
2. [16.6] 实现构建请求键与摘要的双向查找、按元数据筛选、记录追加/替换和原子提交。
3. [16.7] 为全局缓存提供无索引扫描重建能力，重建前重新验证每个对象；明确拒绝猜测重建 `.xar` 归档索引。
4. [16.8] 验证未知版本、未知字段、截断索引和对象缺失的错误边界。

### 缓存维护

1. [16.9] 记录项目、锁文件和 `.xar` 对对象的引用，避免清理仍在使用的对象。
2. [16.10] 实现显式清理、可选 LRU/引用追踪和损坏对象隔离；最终淘汰算法待确认。
3. [16.11] 支持离线读取和跨项目复用，但不能绕过摘要与格式验证。
4. [16.12] 测试多进程同时构建、终止恢复、只读权限和跨平台路径。

## 验收标准

- 同一规范内容在不同机器和进程中得到相同摘要和对象名。
- 修改 `.xiaoc` 文件头、任一必需/可选分区或调试分区都会改变完整文件摘要；ZIP 压缩方式不会改变内部对象摘要。
- 对象写入或索引提交中断不会留下可被误认为有效的半成品。
- 读取前始终验证摘要、长度、格式和版本；损坏对象不会进入运行或打包。
- 全局缓存索引可在损坏或丢失时由已验证对象重建，且不修改依赖锁文件语义；归档索引损坏或缺失时整份 `.xar` 被拒绝。
- 相同 `.xiaoc` 内容可被多个项目复用，不同优化配置/目标/ABI 不会错误命中同一对象。
