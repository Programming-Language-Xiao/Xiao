## 二、必须先冻结的 7 条

### 2.1 **入口条件：10Y 的出口没满足就不开工**

**冻结**：

1. **B 系列实现的前置**是 10Y 的 **Y3 分类已完成并已向星崽汇报、实现范围已确认**；
   分类没做完就动手，等于把 10X 的翻车原样重演一次；
2. **Y1 的原生变异证据**必须在实现开始前落到文档里——否则新写的用例会重复 10X 的错误：
   以为自己有分辨力，实际没有任何证据；
3. **Y4 的 README 唯一性门禁**与 **Y5 的 macOS 标定**属于 10Y，本批不代做；
   若到本批开工时仍未完成，**先在本批补掉**，不要带着两处已知不一致进入收口判定；
4. **Y6 的取数**若在 10Y 内完成，本批直接引用其结果；若未完成，按 §2.4 处理（不阻塞其它条）；
5. **裸机取证轮次**不依赖 Y3，可与分类并行准备——但**报告的产出顺序**仍是先分类、后实现、后收口。

### 2.2 **B 系列实现：两种结局都要有出口，不许为了推进而实现**

**冻结**：

1. **有真缺口**：按 [10P](10p-differential-exemption-and-coverage.md) 的 ABI 顺序实现——
   **B1 纯降低与诊断 → B2 选择计算**，每类一个提交，含差分用例与原生完整比对（值/错误身份/退出码/释放序列）；
2. **无真缺口**：B 系列**直接关闭**，在 10P 与 19D 写明「全部判为一致拒绝或防御性不可达，不实现」，
   **不得**因为「本批需要点产出」而去实现一条判为非缺口的路径——这正是 A3 当初差点走错的方向；
3. 每条新用例必须**能分辨对错**，并有**原生侧**的变异验证（改一处 → 受控原生门控跑红 → 贴输出 → 恢复）；
   10X 的循环断言与 VM 路径测试都不算证据（10Y §2.1、§2.2）；
4. 涉及新 ABI 的按 10T 的版本规则（只加入口走次版本、改既有布局/所有权才升主版本）；
   **纯降低层不升版本**，但要在提交说明里说明为什么不升；
5. **不先删拒绝**；接不通的继续拒绝并登记；判为缺口但工作量明显超出本批的，**单独立项**，不硬塞；
6. 释放证据含**事件数、对象数、销毁位置**与引用持有机制；成对实验只改一处、采数、恢复。

### 2.3 **收尾取证：一次裸机轮次同时补 C 档与性能取数**

**冻结**：

1. **一轮做两件事**（星崽 2026-10-08 定：「一起作」）：**C 档**与 **O6 条件 5 的取数**
   在同一台裸机 Linux 上**同一轮跑完**，不另开轮次。
   **那台裸机 Linux 就是 [10Y](10y-b-series-triage-rework.md) §2.7 所说的受控主机**——
   两个文档指的是同一台机器，不要按两份准备去跑两遍；
2. **目标（C 档）**：`19.14` 的 **Linux 桌面开窗**——**肉眼可见的窗口 + 截图**。
   测试报 `ok` **不算证据**（10T-Linux 那轮就是这么记成未通过的）；
3. **用 10V 的保持让窗口留得住**：**不要**设 `XIAO_DIAGNOSTICS_HOLD_MS=0`，
   默认 5000 ms 即可；如需更多取证时间可临时调大（上限 3600000 ms）。**这是取证用法，不是默认值变更**；
4. **不设 `XIAO_USE_XVFB`**，跑在真实 X 会话上；`xterm` 或候选链上的某个渲染器必须实际存在；
5. 同时采集：`x-terminal-emulator` 指向、候选链各可执行文件是否存在、
   诊断进程与终端进程的 `pgrep` 观察、以及**截图**；
6. **产出格式沿用** [10T-Linux 交接](10t-linux-bare-metal-handoff.md) 的 **results + log 双文件**
   （`10z-…-results-<日期>.md` / `10z-…-log-<日期>.md`），原始输出与判据并列，不要只给结论；
   **同一份 results 同时容纳两组证据**：窗口截图与终端观察（C 档）、三路对照的原始数字与主机环境清单（条件 5）；
7. **取数口径不在这里重定义**，仍按 10Y §2.7：Temurin 21、**跑前落盘环境清单**、三路对照（Java / VM / LLVM）、
   沿用 19D 既定统计口径、原始数字回传、**本机与 CI 数字只作功能证据**；
8. **C 档判定的写法定死**：窗口**确实出现且有截图** → 通过；
   仍无窗口 → **未通过**，并写下当时的观察与下一步假设。
   **不得**把「测试 ok」写成「C 档通过」（10T-Linux 那轮的原文口径）。

### 2.4 **O6 条件 5 的性能取数：本轮做 Linux，其余平台如实登记**

   跑前落盘环境清单、三路对照、原始数字回传、本机与 CI 数字只作功能证据）。**本批不重新定义口径**；
2. **执行位置**：按 §2.3，取数与 C 档在**同一轮裸机 Linux** 上跑完。裸机那一轮是本条的主证据来源；
3. **平台覆盖按 19D 原文口径如实登记**（条件 5 原文要求「按 Windows → Linux → macOS 记录结果」）：
   - **Linux**：本轮裸机实测，是完整证据；
   - **Windows**：本轮按星崽决定直接标缺，不把本机数字写成与裸机 Linux 同口径；待专用受控主机后再补。

### 2.5 **`19.14` 是三平台条目，macOS 那一格要单独写**

**冻结**：

1. `19.14` 原文要求「**在三平台**验证 `-debug` 路径……诊断窗口关闭……」。
   macOS 已由星崽 2026-10-08 定标「**不可验证**」（无 Mac 宿主；CI 显式跳过真实终端），
   所以这一条的判定**必须拆开写**：「Windows 通过 + Linux 通过 + macOS 不可验证（附原因）」；
2. **不得**因为 macOS 不可验证就把整条写成「未通过」（Linux 这轮是要做出来的），
   也**不得**把 macOS 抹掉只写「两平台通过」——**覆盖边界本身是结论的一部分**；
3. 同理适用于 O6 条件 1 与条件 3 里涉及 macOS 的格：**该标不可验证的标不可验证，该标未测的标未测**，
   不要一律写成「部分」含糊过去；
4. `19c-*.md`、`18c-*.md`、`11x0d-*.md` 里涉及该格的措辞一并校准。

### 2.6 **终局判定与收口：判定是什么就写什么**

**冻结**：

1. 对 [19D](19d-performance-comparison.md) 的 O6 五条**逐条**给出「满足 / 部分 / 不满足」+ 证据 + 限制，
   并把表头的「截至 2026-10-07」更新到本批实际日期；
2. **收口的定义已定**（星崽 2026-10-08）：标为「**不可验证**」的格（macOS 真实终端/LaunchServices）
   **算作不阻塞收口**，但**必须在收口声明里写明覆盖边界**——哪些平台/能力被覆盖、哪些被明确排除、
   各自为什么。「写明」是这条决定的组成部分，不是可选补充：**只写「满足」而不写边界，
   等于把「不知道」写成「没问题」**，那正是 10X/10Y 一路在治的毛病；
3. **不得**为了让 19 变绿而：放宽错误身份、删用例、缩小覆盖、
   把「不可验证」写成「已验证/通过」（可以算不阻塞，但不能换个词说成验过了）、
   或用 CI 功能测试数字充当性能证据；
4. 静态溢出（[10R-溢出后续](10r-static-overflow-followup.md)）**不在 O6 五条内**。
   星崽 2026-10-08 定：**归属 20 系列**。本批只在 19D 登记「已立项、归 20 系列、未实现」，
   **不得**把它算成收口阻塞项，也**不得**因为收口而顺手实现；
5. 本条的目的不是让 19 变绿，而是**让 19 的状态与事实一致**——若结论是「不满足」，就写「不满足」。

### 2.7 **O6 条件 1/3/4 的欠格：能补的补，补不了的写明**

三平台白名单复核、条件 4 的「完整三平台白名单复核仍待补」）按这个口径处理：

**冻结**：

1. **先盘点再动手**：把条件 1/3/4 当前的每一个「部分」拆成具体格子，逐格判定
   「本批能补 / 需要特定环境（写清是哪台机器或哪个 CI 作业）/ 无法补（写清为什么）」，
   盘点结果落进 19D，**不要只笼统写「部分」**；
2. **能补的必须真补**：补完要有可复核证据（运行号 / 原始输出 / 复现步骤），
   并按 10Y §2.2 的规则记录——**声称补了就要能 grep 到或复现出**；
3. **需要环境而本轮拿不到的**：明确写「需要什么、谁提供、补了之后能变成什么状态」，
   **不许**用「部分」把「没做」和「做了但不够」混在一起；
4. **无法补的**：按 §2.5 的口径写「不可验证 + 原因」，不写成「未验证」；
5. 本条的产出是**把「部分」这团模糊拆成清楚的格子**——即使最后仍有格子是缺的，
   只要每格的状态与原因都写清了，本条就算做到；
6. **不得**为了减少格子而在盘点阶段放宽判定口径。

## 四、硬约束

1. **入口按 §2.1**：Y3 分类汇报与 Y1 变异证据是硬前置，不到位不开工实现；
2. **B 系列按 §2.2**：只做判为缺口的；判非缺口的**只改文档**；两种结局都要写清；
3. **新用例必须有原生侧变异验证**（改一处 → 受控原生门控跑红 → 贴输出 → 恢复并证明干净）；
4. **不得用互相蕴含的断言冒充验证**（10Y §2.2）；「已验证」必须附可复核输出或运行号；
5. **C 档证据**：肉眼可见 + 截图 + 原始输出；**测试 ok 不算**（§2.3 第 8 条）；
6. **C 档与取数同一轮**（§2.3 第 1 条）；两份证据进同一份 results，不另开轮次；
7. **macOS 拆开写**（§2.5）；覆盖边界必须在结论里显式出现，且**不得**把「不可验证」说成「已验证」；
8. **性能取数只在受控主机（裸机 Linux）上做**（§2.4）；本机与 CI 数字只作功能证据，
   且本机 Windows 数字不得写成与裸机同口径；
9. **收口声明必须写明覆盖边界**（§2.6 第 2 条）——这是「不可验证算不阻塞」生效的前提；
10. **§2.7 的欠格要逐格拆开**，不许只写「部分」；
11. 三平台证据沿用 10T/10U：本机 Windows 受控原生门控 + 推送门控矩阵（Windows + Linux 原生作业）；
12. 不先删拒绝；版本规则按 10T；不新增依赖，`Cargo.lock` 保持同步；
13. 每个提交单独跑 clippy 与 fmt；推送前跑 `cargo test --workspace`、`bun test`、`bun run check`；
14. 本地跑 ignored 用 [10D](10d-environment-gated-test-spec.md) §4.5 的命令（`--skip` 去掉窗口风暴）；
15. **提交说明必须写事实**：声称完成的事，要能 grep 到、或能复现出输出。
