# 11A. 虚拟环境与包管理

> 本阶段在文件模块、双模运行闭环与 CLI 骨架之上建立项目隔离、依赖物化和包管理能力。它是长期工程，不是模块解析器的附带功能，也不进入 Token 或最小 AST 里程碑。

- `config.xiao` 只提供不可执行的声明式依赖配置；项目环境、全局环境、锁文件和全局不可变内容缓存的基础边界已经确定。
- 本阶段采用语言包/项目环境模型，不采用操作系统级 apt 数据库；远程来源允许多个且不要求中央服务器，源码包是规范内容，预编译 `.xiaoc` 只是可选加速产物。

- 包管理器的错误、警告和进度提示使用第 11C 阶段的统一语言上下文；语言包本身是资源型插件，不改变本阶段的依赖求解或源选择语义。

### 本阶段边界

- E0–E2 先完成本地路径依赖、锁定、缓存和环境映射；E3A–E3D 再逐步接入多源、快速解析、静态/GitHub 源和发布安全。

## 一级工程目标：确定环境模型

### D1：外部包契约与依赖图骨架（已完成）

D1 是 11A 的第一批，权威实现边界见 [11A-D1 交接文档](11ad1-package-contract-and-graph.md)。
本批冻结并实现以下最小契约：

- `[dependencies]` 和 `[devdependencies]` 的每个条目必须是字典，字段白名单为
  `path`、可选 `version` 和可选 `source`；`path` 是声明包根目录相对的本地路径，
  `version`/`source` 是静态约束文本，D1 只保存不求解。
- `xiao-package` 读取根包及所有路径依赖的 `config.xiao`，直接消费 `xiao-config` 的
  `ConfigDocument`/依赖声明，不重新扫描配置文本，也不执行任何包代码。
- 包图使用独立的 `PackageGraph`，节点身份为规范化包名、配置版本和来源身份；每个来源
  同时保留独立的 `source_id`、`alias`、`display_name`。D1 的本地路径来源生成 `path:`
  `source_id`，不自动生成 alias。
- 同一图中同名包绑定不同本地路径/版本、依赖名与包元数据名不一致、缺失路径包配置和
  依赖环分别使用稳定的 `X05-PACKAGE-*` 边界；无错误时按依赖优先顺序产生内存解析计划。
- D1 同时读取运行时与开发依赖并保留其分类，但不实现版本求解、缓存、锁文件、环境物化、
  远程源、安装脚本或 CLI 命令；全局环境参与解析等问题留给 E0/E1。

本批不扩展 05 阶段的文件粒度 `ModuleGraph`，也不冻结完整 semver 或多源协议字段。

### 项目环境

每个 Xiao 项目拥有独立的逻辑环境。环境记录当前项目实际启用的依赖图、工具链约束、目标平台和配置指纹，但不为每个项目重复复制全部依赖源码。

项目环境必须可删除、可重建。只要 `config.xiao`、依赖锁文件、工具链版本和目标条件相同，重新同步应得到等价环境。

环境具有彼此独立的逻辑名称和目录规则：

- `xiao venv` 不带名称时，创建逻辑名称为 `venv`、目录名为 `.venv` 的默认环境。
- `xiao venv dev` 带名称时，逻辑名称和目录名都严格使用 `dev`，不会自动添加点号。
- `venv` 与 `.venv` 的不对称只属于无参数默认值，不改变自定义名称。

### 创建与自动激活

`xiao venv [名称]` 创建目标环境后立即激活。`xiao sync` 也在依赖处理完成后激活其目标环境。用户不需要再手工执行 Python 风格的 `activate`。

普通子进程无法修改父终端，因此自动激活通过一次性初始化的 Shell 钩子实现。钩子调用 `xiao` 可执行程序，接收经过校验的环境变更，再应用到当前终端；编译器进程不能直接改写 Shell 配置文件。

11A-E0 冻结的基础协议如下：

- 初始化命令为 `xiao shell-init <shell>`。它只输出一次性、幂等、由用户在当前 Shell 中显式求值的钩子脚本，E0 不自动修改 profile。
- 取消激活命令为 `xiao deactivate`。钩子保存原提示符；重复激活或切换前先移除旧的 `$环境名$ ` 前缀，取消时恢复保存的原提示符。
- E0 的基础支持样本为 Bash 和 PowerShell；PowerShell 实现必须兼容 PowerShell 5.1。`cmd.exe` 是不支持钩子的降级样本：创建环境仍成功，但不修改注册表、不宣称已自动激活，并输出初始化或手工激活提示。
- 非 TTY、`NO_COLOR` 或 `--color=never` 时保留纯文本 `$环境名$ ` 前缀，不输出 ANSI；可着色终端才使用绿色 ANSI。完整 Shell 矩阵、profile 安装和生产级取消激活命令留给 E3D。

11A-E2B 将 E0 的钩子原则落实为私有随机临时目录中的一次性激活文件：Shell 导出
`XIAO_ACTIVATION_FILE` 供 `venv`/`sync` 成功后写入，两行内容仅允许
`XIAO_ACTIVE_ENV='<绝对路径>'` 与 `export XIAO_ACTIVE_ENV`。Bash、PowerShell 均在
**白名单检查后按数据赋值（不求值文件）**，调用成功或失败后删除文件；
`XIAO_ACTIVE_ENV` 由 E0 的不导出环境名称升级为导出的绝对路径。
`cmd.exe` 没有钩子，仍只能手工切换 Shell，不能宣称已自动激活。

`venv` 与 `sync` 的环境目录基准是向上发现到的项目根，即 `config.xiao` 所在目录；找不到配置时回退到当前目录。无参数 `xiao venv` 使用逻辑名 `venv` 和目录 `.venv`，带名称形式使用同一名称作为逻辑名和目录名。

激活后只在原提示符之前增加绿色前缀，环境名和前后两个 `$` 都使用绿色，后接一个空格：

```text
$dev$ D:\project\xiao>
$dev$ /home/project/xiao$
```

上例只表达前缀结构；路径、用户/主机信息、结尾符号和原有配色继续由用户原来的提示符决定。切换或退出环境时必须恢复原提示符，不能反复叠加前缀。

`xiao run`、`xiao build` 和 `xiao test` 仍能自动定位项目环境；“自动激活”不意味着这些命令必须依赖终端已经激活。激活状态主要影响交互提示和 `install`/`i` 的安装目标。

多个环境并存时 `sync` 按激活路径 → `.venv` → 创建 `.venv` 选择目标；锁文件缺失时由本地依赖图生成，冻结模式须已有有效锁文件。11A-E0 已冻结并实现基础
Shell 钩子、取消激活、`cmd.exe` 降级和找不到 `config.xiao` 时回退当前目录的规则。完整 Shell 矩阵、
profile 安装和生产级取消激活命令留给 E3D。

### 全局安装环境

全局安装环境用于接收“当前没有激活虚拟环境”时的 `xiao install`/`xiao i`。它保存一份全局依赖选择和映射，但不重复存放包源码；全局环境与所有项目环境共同引用全局内容寻址缓存。

全局环境的实际路径、版本冲突处理和它是否参与非项目脚本的导入解析仍待定。项目环境不能因为存在全局安装而悄悄读取未声明依赖。

### 交互式解释器的环境视图

交互式解释器在启动时根据终端的激活状态选择唯一的包视图：已经激活虚拟环境时，该环境中的所有包均可引用；没有激活虚拟环境时，全局环境中的所有包均可引用。即使当前目录恰好位于某个项目内，未激活状态的交互式解释器也不能悄悄改用该项目环境。这与 `run`、`build` 和 `test` 自动定位项目环境的规则不同。

“所有包均可引用”不表示启动时逐个导入并执行包代码。环境层只向第 11B 阶段的交互式解释器预注册可解析的包根名称，让交互会话无需逐条 `import` 即可按包名引用；只有源码真正引用某个包中的内容时，运行时才加载所需模块。名称解析或类型检查所需的只读接口元数据必须与模块运行时代码及初始化行为分离，读取接口元数据不算运行时加载。仅启动解释器、渲染提示符、注册包命名空间或读取接口元数据不得触发包初始化副作用；同一具体模块在一个运行实例中仍遵守“至多初始化一次”的模块规则。

### 环境与发布产物

虚拟环境只服务开发、测试和构建。`xiao build` 生成的原生程序不依赖项目虚拟环境存在；需要的 Xiao Runtime 和第三方原生组件按构建规则进入发布产物。

第 17 阶段的 `.xar` 是另一种字节码发布产物：它可以携带项目锁定的外部/第三方 `.xiaoc` 依赖，但不重复携带由已安装 Xiao Runtime 提供的官方依赖（例如标准库）。运行 `.xar` 仍要求用户安装 `xiao`；虚拟环境只用于构建和依赖解析，不会被归档隐式复制。

## 一级工程目标：复用全局内容缓存

### 不可变包存储

依赖源码进入全局内容寻址缓存，以规范化包内容的加密摘要作为缓存身份。来源、包名和版本属于解析与锁定元数据，不参与内容缓存键；来自不同位置但内容完全相同的包只保存一份。

项目环境只保存指向缓存条目的逻辑映射，工具链根据映射直接读取全局缓存，不把缓存内容以符号链接、硬链接或副本暴露到项目环境。缓存条目创建完成后必须设为只读，并在使用前验证内容摘要；校验失败时隔离损坏条目，不能继续构建。

本地路径依赖导入缓存时必须形成经过校验的不可变快照；源目录后续发生变化会产生新的内容摘要，不能原地改写旧缓存条目。

### 构建缓存隔离

源码包缓存与构建产物缓存必须分开。构建缓存键至少考虑：

- Xiao 编译器/运行时版本。
- 目标平台与目标架构。
- 调试或发布模式。
- 功能开关和影响代码生成的配置。
- 源码及完整依赖图指纹。

一个平台或配置生成的目标文件不能被另一平台误用。

第 16 阶段会在此基础上为 `.xiaoc`、可选原生片段和 `.xar` 建立独立的内容寻址对象类型与一个逻辑全局缓存索引；它们不能与源码包对象或依赖锁文件共用同一语义。首版不在每个项目中再保存一份 Protobuf 产物索引；项目继续以 `config.xiao`、锁文件和环境映射描述自身。缓存根目录、权限与跨平台位置由 11A-E1 冻结为 `XIAO_HOME` 或用户主目录下的 `.xiao`；对象类型、对象保留和索引更新规则以 [16. SHA-256 内容寻址与二进制索引](16-content-addressed-artifacts.md) 为准。

### 引用与清理

环境删除只删除项目映射，不立即删除其他项目仍可能使用的全局缓存。缓存清理、占用统计、最近使用时间和并发下载锁属于后续管理能力，不能通过扫描并修改项目源码实现。

## 一级工程目标：定义配置与锁定关系

### 声明式 `config.xiao`

`config.xiao` 复用 Xiao 的词法器和语法基础，但只接受不可执行的声明式子集。配置读取阶段禁止：

- 函数定义与函数调用。
- 条件、循环和其他控制流。
- 模块导入。
- 依赖运行时变量的表达式。
- 任何需要先执行项目代码才能得到结果的构造。

05-D 已将最小数据方向冻结为表头、字符串、数值、布尔值、递归数组和字典表；集合、元组、
常量引用和环境变量仍不属于配置值。11A 只消费已经解析的 `ConfigDocument`，不在包管理器
中重新实现配置语法。

### 依赖分组

所有用户直接选择的依赖都写入 `config.xiao`。D1 首先冻结本地路径依赖的最小写法；完整
版本求解、远程源和额外依赖分组仍由后续批次扩展：

```xiao
[Dependencies]
utils = { path = "../utils", version = "^1.4" }

[DevDependencies]
testkit = { path = "../testkit", version = "^0.3" }

[Toolchain]
xiao = "0.1"
```

普通依赖、开发依赖和工具链约束是否足够，是否增加可选依赖、功能组或构建依赖，仍待定。早期阶段不引入可执行安装钩子。

### 依赖锁文件

依赖锁文件是依赖图的唯一精确输入，记录完整依赖图而不是只有直接依赖。完整环境还同时受项目配置、工具链和目标条件约束；项目环境必须能证明自己对应这些输入，不能悄悄使用其他项目或旧版本的依赖。

锁文件的版本约束算法仍待定；`xiao.lock.json` 的名称、JSON 格式和读写规则已经冻结，用户确认的是“工具生成完整依赖树”，而不是只记录直接依赖。

## 一级工程目标：建立分布式多源包仓库

### 总体模型

Xiao 的包管理器采用“`pip`/`uv` 式语言包与项目环境 + apt 式可配置多包源”的组合模型。它不调用操作系统的 apt，也不维护一份所有项目共享的可变系统包数据库；版本求解、锁定和环境物化仍以 Xiao 项目为单位。与此同时，Xiao 不要求所有第三方包都上传到同一个中央服务器：官方源、社区源、企业私有源、局域网源、本地静态源和符合规范的 GitHub 仓库可以并存。

包源是“能够按 Xiao 统一协议提供包元数据与不可变内容”的逻辑服务，不要求背后运行专用服务器。专用注册表、普通 HTTP 静态目录、本地目录和 Git/GitHub 仓库可以通过不同传输适配器实现同一逻辑契约。解析器只能消费适配器返回的规范化元数据，不能让某种来源改变依赖、版本或安装语义。

推荐的数据流如下：

```text
config.xiao 中的直接依赖与包源
    -> 多源元数据适配器
    -> 统一版本求解器
    -> 完整锁文件（源身份 + 精确版本/提交 + 内容摘要）
    -> 全局不可变内容缓存
    -> 项目/全局环境的只读映射
    -> run / build / test / xar
```

这项能力必须排在 E0–E2 的本地依赖、锁文件和环境映射闭环之后。远程阶段不得为了尽快联网而绕过既有内容校验、锁定或原子更新接口。

### 源码与预编译产物

每个可发布 Xiao 包都必须具有规范源码产物，其中包含 `.xiao` 模块和声明式包元数据。包源可以同时发布一个或多个预编译 `.xiaoc` 模块变体，用于缩短安装、构建或启动时间，但它们只是缓存式加速层：

- 预编译变体必须声明 Xiao 语言/IR/虚拟机或 Runtime ABI、目标平台/架构、优化与调试条件及内容摘要。
- 只有全部条件匹配且格式、摘要验证通过时才能复用。
- 没有兼容变体时必须回到同一锁定版本的规范源码构建，不能因为包源只剩不兼容二进制就悄悄选择另一版本。
- 包可能包含多个 `.xiaoc` 单模块对象；不能把整个包伪装成一个违反第 14 阶段边界的 `.xiaoc`。

首个远程包闭环禁止任意安装前、安装后或卸载脚本。读取包清单、求解依赖、下载、校验和写入环境映射都不得执行包代码。未来若需要构建 FFI 或其他原生扩展，只能通过另行冻结的声明式构建描述、隔离进程、权限边界和可复现输入实现，不能重新引入不受控安装钩子。

### 统一包源契约

每个包源至少需要向客户端表达以下逻辑信息；E3A 已冻结离线目录源的文件名、字段和 JSON 形状（见下文），远程传输与缓存布局留 E3B/E3C：

- 包源协议版本、规范源身份和可选的仓库快照身份。
- 规范化包名、版本列表、撤回状态及版本选择所需的最小元数据。
- 每个版本的直接依赖、功能/目标条件、最低与最高 Xiao/Runtime 兼容范围。
- 规范源码产物的位置、长度和加密摘要。
- 可选 `.xiaoc` 或原生构建变体的位置、目标条件和加密摘要。
- 镜像、过期、完整性和未来签名验证所需的元数据。

包源元数据必须能与包正文分开获取，使求解器不需要下载完整源码归档才能比较版本。源协议应支持按规范化包名分片或等价的稀疏查询，不能要求每次 `sync` 都下载整个生态的完整目录。索引与第 16/17 阶段的本机缓存索引和 `.xar` 唯一索引**职责不同，不能混为同一个文件**。

### 索引格式：JSON 为权威，Protobuf 只是派生加速层（已冻结）

已冻结（记录在 [00. 决策基线](00-decisions.md) 的「虚拟环境与包管理」）：

- **规范化静态 JSON 是唯一权威**，对外展示与人工 review 一律以它为准；
- 可选的 **Protobuf 视图只是派生加速层**，必须在自身携带所依据的 JSON 摘要；
- 客户端读到先校验摘要，**不匹配、缺失或过期时一律回退 JSON**——不得把加速层当作
  第二真相源，也不得在它不可用时视为空索引；
- 加速层由**源侧**在包列表更新后重新生成，客户端不参与生成。

**为什么 JSON 必须在先**：包源本身就是普通 Git 仓库或静态站点，索引要能被人读、
被人 review、能在 PR 里 diff——这是生态能不能长出来的前提，而二进制格式三者都做不到。
Protobuf 的收益是解析速度与传输体积，用一个**带摘要校验、可随时丢弃**的派生层就能拿到，
不必让权威格式变成二进制。

仍留给 E3A/E3B 的是：**准确文件名与字段名**、缓存目录布局、压缩方式、分片的具体切法。

E3A 已把 D1 预留的 `[sources]` 表扩展为具名条目；顺序按条目的源码位置而非配置树
字典序。直接源全部排在导入列表之前；导入项在本批仅有静态契约，不联网：

```xiao
[sources]
official = { display = "官方源", kind = "registry", location = "https://packages.xiao.example" }
community = { display = "社区镜像", kind = "static", location = "https://example.org/xiao-index" }
team = { display = "团队内部", kind = "git-index", location = "https://github.com/example/xiao-packages.git" }
# 如需导入：list_ref = { list = "https://example.org/lists/team.json", digest = "<64 位小写 SHA-256>" }

[Dependencies]
http = { path = "../http", version = "^1.4", source = "community" }
```

源字段白名单：直接源的 `kind`、`location` 必填，`alias`、`display`、`protocol` 可选；
默认 alias 为条目名，`protocol` 默认 1。导入项只有 `list` 和 `digest`（完整 JCS SHA-256）。
源列表 JSON 与包索引严格分离：`{"protocol_version":1,"sources":[{"kind":"static","location":"https://packages.example/lib","alias":"lib"}]}`，
列表条目可附加 `display`、`protocol_version`。首版本地源在根目录放 `snapshot.json`
（`protocol_version`、`source_id`、`snapshot_id`、`shards` 包名到 JCS SHA-256 的映射，
可选 `mirrors`/`expires_at`）；包分片放 `index/<package>.json`（`protocol_version`、
`source_id`、`snapshot_id`、`packages` 全部版本元数据）。正文引用独立包含 `location`、
`length`、`digest`，只在安装时获取，不执行包代码。导入清单由调用方提供已验证字节，
清单修改须重新钉住摘要；E3A 不自动刷新或写回配置。

示例里的 `source = "community"` 绑定的是 **`alias`**，不是显示名。包源有**三个必须分开的概念**
（已冻结于 [00. 决策基线](00-decisions.md)）：稳定的 `source_id`、配置内引用用的 `alias`、
纯展示用的显示名。**依赖只能引用 `alias` 或明确的 `source_id`**；`alias` 冲突默认报错，
只有用户显式改名或建立映射时才接受。E3A 冻结的字段及精确限制见
[包源契约](11ae3a-package-source-contract.md)，三者的分工不再改变。

### 联邦源索引（逻辑已冻结）

#### “所有/最新源列表”的含义

用户在 `config.xiao` 配置的是一个有序源集合，而不是一个需要上传到中央服务器的全局注册表。每次需要重新解析依赖时，客户端必须尝试读取集合中的**每一个已配置源**的最新可用索引快照：

- “所有”指当前配置中的所有源端点，不指网络上 Xiao 生态的所有源。
- “最新”指某个源在本次条件请求、Git 提交解析或本地读取中得到的最新**完整且可验证快照**；“完整”表示快照清单或其一致的索引分片集合内部完整，不要求下载包正文，也不是只保留该源中每个包的最高版本。采用分片时，参与一次求解的分片必须属于同一快照身份。
- 为支持版本约束回溯、锁文件重建和冲突诊断，每个快照保留源公开的全部可用版本元数据。包源码、`.xiaoc` 和其他正文按需下载，不因建立索引而全部下载。
- 若源只发布“当前版本”而不提供历史版本，客户端只能记录源实际提供的候选，不能自行伪造或从其他源补齐历史版本。
- 首次配置源，或修改源地址、源身份、源顺序时，源配置指纹改变，旧联邦索引必须失效并重新尝试全部源；源配置未变且锁文件与快照仍有效时，才允许跳过远程读取。

#### 读取、校验与合并流水线

源读取和合并是依赖求解前的独立阶段，顺序必须稳定且可审计：

```text
config.xiao 的有序源描述
    -> 规范化源身份与配置序号
    -> 并行读取每个源的最新完整索引快照
    -> 校验协议、源身份、快照摘要和元数据结构
    -> 保留每源快照（成功、沿用缓存或不可用状态）
    -> 合并为按源配置指纹隔离的本地联邦源索引
    -> 将索引交给唯一依赖求解器
```

本地联邦索引是客户端的派生缓存，不改变任何源的权威性，也不把包正文集中上传。其逻辑记录至少包含：

| 字段 | 作用 |
| --- | --- |
| `source_id` | 规范化且稳定的源身份；不能只用显示名称 |
| `config_order` | `config.xiao` 中的从零开始的配置序号，用于源优先级 |
| `snapshot_id` / `snapshot_digest` | 本次使用的不可变快照引用与摘要 |
| 包名、版本、目标/ABI 条件 | 版本求解候选的最小元数据 |
| 依赖约束与撤回状态 | 构建完整依赖图所需的信息 |
| 源码、`.xiaoc` 和其他产物引用及摘要 | 延迟下载和完整性校验入口 |
| 快照状态 | `fresh`、`cached` 或 `unavailable`，不能把不可用伪装为空索引 |

合并键必须保留来源维度，至少按“规范化包名 + `source_id` + 版本 + 目标/ABI 变体”区分记录；不能仅以“包名 + 版本”去重。索引序列化时按配置序号、源身份、包名、版本和变体使用稳定顺序，刷新时间等观察信息不得参与依赖选择或可复现指纹。源快照缓存可以跨项目复用，但联邦视图必须纳入有序源配置指纹，避免不同源顺序误用同一结果。

源读取应优先复用未过期的完整快照，并使用 HTTP 条件请求、Git 不可变提交或等价机制增量刷新。多个源可以有界并行读取；合并和索引替换必须在所有已返回快照通过校验后原子提交，不能让求解器看到半个新索引。有效锁文件且正文/元数据缓存齐全时，可以跳过本次远程读取，但锁文件仍须记录其对应的源快照身份。

#### 唯一依赖选择规则

联邦索引交给单一求解器后，按以下顺序处理每一项依赖：

1. 依赖条目显式指定 `source` 时，只在该 `source_id` 的候选中求解；名称未解析、映射到多个活动端点或候选不足以确定唯一结果时，直接报告源绑定/依赖歧义。
2. 未显式指定源时，按 `config.xiao` 的 `config_order` 从前到后检查。找到第一个具有完整可用快照且存在满足名称、版本、目标和其他约束的候选源后，只在该源内继续版本求解；后续源不得用更高版本抢占。
3. 不允许跨源比较版本号后选择“最高版本”。源内的版本约束、锁定和升级算法仍由 E3D 冻结，但其输入已经被源优先级限定。
4. 若源身份、配置顺序、版本约束或锁定信息仍不能产生唯一候选，必须报歧义错误并列出候选源、版本和快照摘要；不得依赖网络返回顺序、线程完成顺序或哈希表遍历顺序。
5. 排在候选源之前的源若没有新快照且没有可验证的旧快照，不能被视为空源并继续向后选择；必须报告“源不可达导致结果不确定”。显式绑定的源不可用时始终直接失败。排在已确定候选之后的不可用源可以不阻断本次结果，但必须在索引状态和日志中保留，不得静默丢弃。

例如，源顺序为 `official -> community -> team` 时，`official` 没有满足约束的 `http` 而 `community` 有 `1.4`、`team` 有 `9.0`，应在 `community` 内按版本规则求解，不能比较后选择 `team` 的 `9.0`；若 `official` 与 `community` 都有满足约束的候选，则无显式绑定时使用 `official`。同名源别名或重复优先级导致无法确定唯一源时，必须在求解前报歧义。

#### 快照失效与离线行为

每个源的最新读取结果、沿用的缓存快照和不可用状态都要进入诊断上下文。源不可达不应触发自动改源、改版本、改配置顺序或删除锁文件：

- 有效锁文件、对应源快照/元数据和完整内容缓存都命中时，允许完全离线地物化环境。
- 需要重新求解且某个可能影响优先级判断的源不可用时，解析失败并明确指出缺少哪个源快照；不能以“未找到包”掩盖网络故障。
- 使用旧快照必须标记为 `cached`，并在锁定或同步报告中显示快照摘要和新鲜度；旧快照过期规则属于 E3B 的实现参数，不能改变优先级语义。
- 联邦索引更新失败时保留上一份已验证索引；不得用空文件覆盖，也不得让并发 `sync` 读取半成品。

### GitHub 与静态仓库源

“GitHub 仓库作为包源”表示该仓库按 Xiao 包源规范维护版本化的源描述、稀疏包索引和内容引用，可以承载一个或多个包；它不是让客户端扫描任意代码仓库并猜测包结构。包实体可以保存在同一仓库、GitHub Releases、GitHub Pages 或索引声明的其他不可变位置，但客户端下载后始终以锁文件中的摘要为准。

解析器不应强依赖 GitHub 私有 API。实现可以使用标准 Git/HTTP、静态文件和条件请求，并应避免为了查询一个包而克隆完整历史。分支可以用于发现新的仓库索引状态，但锁文件必须固定实际解析时的不可变提交、标签解析结果或仓库快照摘要；同一标签或路径内容变化且摘要不符时必须拒绝，不得把可变名称当成完整性证明。

直接把单个 Git 仓库作为某一项依赖，与“该仓库承载一个多包源索引”是两种不同能力。前者属于直接 Git 依赖，后者属于 Git 索引包源；两者最终都要归一化为相同的包身份、依赖元数据和内容摘要，但命令/config 表达及首版是否同时实现仍需分别冻结。

### 多源选择与安全边界

项目可以声明多个包源，依赖解析结果必须保持确定性。锁文件至少记录每个已选包的规范源身份、精确版本、不可变提交或仓库快照引用、源码摘要、实际选择的预编译变体摘要及目标条件。相同内容即使来自不同源也可以在全局内容缓存中去重，但缓存身份相同不能抹掉锁文件中的来源与审计信息。

当多个源提供同名包时，统一采用“显式源优先、否则按配置顺序、仍不唯一则报歧义错误”的规则，具体索引构建和候选扫描见上面的“联邦源索引”章节。解析器不得依赖响应先后、线程完成顺序或遍历偶然顺序，也不得把跨源最高版本当作选择依据。这样即使后来添加的低信任源提供更高版本，也不能悄悄替换已经由优先级确定的包。

SHA-256 只证明收到的内容与锁定内容一致，不能证明发布者身份。仓库元数据签名、可信根、密钥轮换、撤销、过期策略、私有源认证和凭据存储属于 E3D 的独立安全决策；在它们冻结前，客户端不能把 HTTPS、Git 提交哈希或 GitHub 仓库地址描述成完整发布者信任链。

### `uv` 式快速路径

“迅捷体验”主要由客户端架构保证，不依赖所有包集中在一个高性能服务器：

1. 有效锁文件且所需对象已在缓存时，`sync` 不查询远程源，直接校验并物化环境映射。
2. 必须重新求解时，只读取受影响包的轻量元数据；源根描述、分片索引和版本元数据分别缓存，并通过摘要、提交或条件请求增量刷新。
3. 不同包源的元数据查询、包下载、摘要计算和互不依赖的源码构建可以有界并行；结果仍交给单一确定性求解器排序和选择。
4. 包正文按摘要进入全局不可变缓存；跨项目、跨镜像和内容相同的跨源包可以直接复用。
5. 下载采用临时文件、流式摘要和原子提交；中断不会产生可命中的半包，同一对象的并发下载通过进程间协调合并。
6. 有效锁文件和完整缓存必须支持离线同步；网络失败不能迫使解析器改选另一个未经锁定的源或版本。

## 一级工程目标：形成统一管理入口

### 集成到 `xiao`

虚拟环境创建器、同步器和包管理器直接集成到 `xiao` 命令，不额外要求用户安装第二个管理器程序。

已经冻结的环境命令为：

```text
xiao venv [name]
xiao sync
xiao install [project-or-config-path]
xiao i [project-or-config-path]
```

后续依赖编辑与升级命令仍是候选，名称和参数尚未冻结：

```text
xiao add <package>
xiao remove <package>
xiao lock
xiao update
```

### 命令职责

- `venv`：创建指定名称的环境并通过 Shell 钩子激活；省略名称时使用逻辑名 `venv` 和目录 `.venv`。
- `sync`：没有目标环境时先创建默认环境，再根据项目配置安装依赖，最后激活；已有目标环境时**把环境同步到锁文件描述的目标状态**（含移除多余包）。锁文件读写与两个禁止写入模式见下文「`sync` 的冻结语义」。
- `install`：直接安装指定配置声明的依赖，不创建环境，也不自动激活环境。
- `i`：`install` 的短命令，行为必须完全一致；两者都不是 `sync` 的别名。
- `install`/`i` 的路径参数可以指向项目目录或具体的 `config.xiao`。省略参数时只在终端当前目录查找 `config.xiao`。
- `install`/`i` 在已有激活环境时写入该环境的依赖映射；没有激活环境时写入全局环境的依赖映射。依赖内容本身始终进入共享的不可变缓存。
- `run`/`build`/`test`：使用定位到的项目环境，不依赖 Shell 是否已经激活。

### `sync` 的冻结语义（对标 `uv sync`）

`sync` 是否移除多余依赖、如何纠正不符合配置或锁文件的版本、以及何时读写锁文件，
**已按 `uv sync` 的语义冻结**（记录在 [00. 决策基线](00-decisions.md) 的「虚拟环境与包管理」）：

- **默认移除环境中不属于依赖集的多余包**；反向开关保留它们。这正是"把环境同步到目标状态"
  的含义——只补不删会把环境漂移永久留在那里。
- **锁文件在需要重新求解时自动创建或更新**。这是"常规命令不能悄悄升级锁定版本"的
  **受控例外**：写入必须落进锁文件、可 diff、可审计；**只改环境不改锁文件是不允许的**。
- 提供两个**禁止写锁文件**的模式：
  - `--locked`：要求锁文件已是最新；需要变动时**以非零退出码失败并指出原因**；
  - `--frozen`：只使用现有锁文件，缺失或不一致直接失败。

**CI 与可复现构建必须使用 `--locked` 或 `--frozen`**，否则每次同步都可能悄悄改写锁定版本。

**源列表同样受这两个模式约束**：

- `--frozen`：**只使用已钉住的源清单与展开结果**；清单缺失或其摘要与配置不符时**直接失败**；
- `--locked`：可以读取远端以验证摘要，但**发现变化必须失败**，**不得自动采用新列表**；
- 源列表的更新走**显式命令**，不得由普通 `sync` 静默完成——否则"每次同步都可能换一批源"，
  而源顺序决定选择结果（见多源选择规则）。

`install` / `i` **不重新求解**：它按已有锁文件物化，不更新锁文件。需要更新锁文件的路径
只有 `sync`（以及后续冻结的 `add` / `remove` / `lock` / `update`）。

### 暂缓：锁文件的预编译变体维度

锁文件最终要记录"实际选中的预编译变体摘要及目标条件"（见下方"源码与预编译产物"），
但**首版暂缓**：字段保留、内容允许为空，按单目标与源码产物物化。
该维度依赖第 14 阶段的 `.xiaoc` 真正存在，**现在冻结会定错**。届时再定表达方式，
以及切换目标平台时是补装还是重建。

当 `sync` 或 `install`/`i` 需要重新求解依赖时，命令内部必须按“读取已配置源 → 校验并合并联邦源索引 → 应用显式源/配置顺序规则 → 生成或验证锁文件 → 下载并校验正文 → 原子更新环境映射”的顺序执行。源索引刷新失败不得被安装步骤吞掉；错误必须指出受影响的源、快照和是否存在可用缓存。

## 二级实现任务

### D1：外部包契约与依赖图骨架

1. 为 `[dependencies]`/`[devdependencies]` 建立 `path`、`version`、`source` 字段白名单
   和类型/路径校验，并从规范化 `ConfigDocument` 提取结构化声明。
2. 在 `xiao-package` 中读取项目及本地路径包的 `config.xiao`，构建独立于文件模块图的
   确定性包身份图和依赖优先顺序。

4. 明确不实现缓存、锁文件、远程下载、版本求解和 CLI 命令；这些能力由 E0–E3 后续批次
   按边界接入。

### E0：配置与环境指纹

1. 消费第 D0 阶段产出的规范化 `config.xiao` 声明树，不重新执行或解释项目代码。
2. 为项目配置、工具链和目标条件生成稳定指纹，并为后续锁文件摘要预留字段。
3. 实现 `xiao venv [名称]` 的目录规则、环境元数据和重复创建诊断，不接入网络。
4. 建立 Shell 钩子协议，验证创建后激活、绿色提示符前缀和原提示符恢复。

### E1：本地依赖与共享缓存

1. 只支持本地路径包，验证每个包的 `config.xiao`。
2. 把依赖内容导入不可变的全局内容寻址缓存。
3. 让项目环境通过只读逻辑映射引用缓存，并实现 Windows、Linux、macOS 的统一解析接口。
4. 建立全局环境的依赖映射，验证它与多个项目环境复用同一内容且互不污染。

E1 只提供 `xiao-package` 的核心物化 API 和 Rust 集成测试，不新增 `xiao` 命令入口；
用户可见的 `sync`、`install`/`i` 由 E2 接入。

### E2A：锁文件与环境映射

E2A 与 D1/E1 同形：核心逻辑批次，只提供 `xiao-package` 的公共 API 和 Rust 集成测试，
**不新增命令入口**。

1. 生成、校验并复用记录完整本地依赖图的锁文件（名称与格式见交接文档的冻结项）。
2. 原子地更新环境映射，写入中断不会留下损坏的环境元数据。
3. 为配置与锁文件不一致提供独立稳定诊断。

锁文件采用项目根 `xiao.lock.json`（`lock_version: 1` JSON）；本地包的锁定结果同时保存
E0 配置指纹、逻辑身份和 E1 源码摘要。E2A 提供读取、生成、校验及已存在环境元数据的原子
映射更新 API；`sync`/`install` 命令仍留在 E2B。

### E2B：同步与安装命令

1. 实现 `sync` 的“创建或补齐依赖，随后激活”流水线，不自行选择未被规则允许的新版本。
2. 实现 `install`/`i` 对激活环境和全局环境的目标选择，不让它们隐式创建或激活环境。
3. 为缓存损坏和离线缺包提供独立诊断。
4. 向第 11B 阶段提供只读的环境包视图、接口元数据查询和延迟运行时加载接口，验证枚举、注册或类型查询不会执行包代码。

4. [11A.E3B.4] 用临时文件、进程协调和原子提交处理并发下载、索引合并、网络中断、摘要不匹配和损坏缓存；跨进程锁依据 [11A-CONC §1.6](11a-concurrency-model.md)。
5. [11A.E3B.5] 实现 `fresh`/`cached`/`unavailable` 源状态和离线规则：不可用源不能伪装为空源、改变优先级或触发自动改源；必要时报告结果不确定。

5. [11A.E3C.5] 建立分支、标签被改写、仓库索引截断、源不可达和内容摘要变化的稳定诊断及离线回退测试。

## 验收标准

### 隔离验收

- 两个项目可以锁定同一包的不同版本，运行和构建互不污染。
- 两个项目锁定相同内容时可以复用全局缓存，不重复下载或保存源码。
- 删除项目环境后，可以只凭配置、锁文件和缓存重建等价状态。

### 确定性验收

- 未激活 Shell 环境时，`run`、`build`、`test` 与激活后的项目依赖解析结果一致。
- 常规命令不会隐式升级锁定版本。
- 相同锁文件、工具链和目标条件产生相同依赖图。

### 多源与快速路径验收

- 一个项目可以同时配置多个相互独立的包源；解析不要求存在或访问某个唯一中央服务器。
- 官方注册表、HTTP 静态目录、本地目录和符合规范的 GitHub 仓库能够通过源适配器提供同一套包元数据，不因传输方式不同而改变依赖语义。
- GitHub 包源可以通过不可变提交、标签解析结果或仓库快照锁定；分支或标签被改写、源内容摘要变化时会被明确拒绝，不会静默换包。
- 配置源路径后，客户端会尝试读取所有已配置源的最新完整索引快照，并把它们合并为一份按源配置指纹隔离的本地联邦源索引；索引保留每个源的身份、配置序号、快照摘要、状态和全部可用版本元数据。
- 联邦索引按来源维度保留同名同版本候选，不以包名/版本单键覆盖来源；快照元数据可按包名或等价方式稀疏获取，解析单个依赖不要求下载整个仓库或所有包正文。
- 依赖显式指定源时只在该源求解；未指定源时按配置顺序选择第一个满足约束的源；不同源之间不比较版本号择高，仍无法唯一确定时直接报歧义错误。
- 有效锁文件和完整缓存命中时，`sync` 不需要访问网络；必须重新解析时，不同源的索引快照、元数据和包正文可以有界并行获取，最终合并和选择仍由确定性求解器完成。
- 源不可达时会保留 `cached`/`unavailable` 状态，不能伪装为空源、改写源顺序或静默改源；若缺少的快照可能影响选择，必须报告结果不确定。
- 规范源码包始终可用；匹配的预编译 `.xiaoc` 只作为加速路径，验证失败或不兼容时回退到同一版本源码。
- 包源、依赖清单和环境安装流程不执行任意安装脚本；脚本、源码钩子和未声明的构建副作用不会在首个远程闭环中运行。

### 命令与激活验收

- `xiao venv` 创建 `.venv`，提示符显示绿色 `$venv$` 前缀；`xiao venv dev` 创建 `dev`，提示符显示绿色 `$dev$` 前缀。
- `sync` 对不存在和已经存在的目标环境分别完成“创建后安装”和“补齐缺失依赖”，成功后激活同一目标环境。
- `install` 与 `i` 的结果一致；有激活环境时只更新该环境，没有激活环境时只更新全局环境，并且两者都不触发激活。
- 重复激活不会叠加提示符前缀，取消或切换环境后能够恢复原提示符。
- 交互式解释器可读取当前激活环境或全局环境的包视图，但注册、枚举和读取接口元数据都不会执行包代码；真正引用包内容时才进入延迟运行时加载。
- 环境视图为运行时提供稳定模块身份，同一具体模块在一个运行实例中不会因多个引用路径而重复初始化。

### 配置安全验收

- 读取 `config.xiao` 不执行项目函数、导入或控制流。
- 不可执行构造在依赖下载前即被拒绝。
- 包管理器修改依赖时使用结构化语法树或等价结构，不进行脆弱的文本拼接。

## 已冻结补充：E3B 快速解析与缓存

- **布局**：`cache/objects/metadata/sha256/` 存不可变包元数据，`cache/objects/source/sha256/` 复用 E1 正文对象；`cache/snapshots/<source_id 的 SHA-256>/` 保存历次快照及原子替换的 `current.json`，`cache/federation/<配置指纹的 SHA-256>/<有序源序列摘要的 SHA-256>/index.json` 独立保存并原子替换每份联邦视图；旧单文件仅只读兼容。
- **离线命中**：有效且配置指纹一致的锁文件、所有可能影响优先级的可验证源快照/元数据、全部通过摘要验证的正文对象须同时命中；缺更靠前的源不能静默选择后面的源。
- **状态与过期**：配置/锁文件或对象完整性变化才触发重解，不引入时间 TTL；本次读取为 `fresh`、沿用旧快照为 `cached`、源不可达且无旧快照为 `unavailable`，沿用时报告摘要及读取时间，时间不参与选包。
- **中断与断点**：本地源验证中断安全，不把重试成功冒充断点恢复；适配器声明部分读取能力，实际 HTTP Range 留 E3C。
- **诊断**：续用 `X05-SOURCE-*`，区分源故障、缓存基础设施故障和损坏条目；陈旧锁具体回收规则及离线区分度测试由 E3B 实现。细节见 [11A-E3B](11ae3b-fast-resolution-and-cache.md)。
