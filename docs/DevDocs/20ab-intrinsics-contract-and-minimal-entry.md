# 20AB. intrinsic 契约与最小生产入口

> **20 方向稿的首个实施批，由 20A（契约与盘点）与 20B（最小生产入口）合并而成**
> ——切法依据见 [20A 研究](20a-intrinsics-contract-research.md) §三。
>
> **一句话概括本批**：**把「按名称认函数」换成「按表分派」**，并让这张表第一次
> 真的被两条执行路径消费——`print` 是第一个跑通全链路的入口。
>
> **本批之后**：[17. `.xar`](17-xar-archive.md) 的端到端验收才具备观察手段
> （见 [研究文档](20a-intrinsics-contract-research.md) §1.2）。

**⚠️ 两类特判的难度不一样，这是本批最重要的排期依据**：

- **没有规则的**（`print`、`input`）：`print()` 与 `print(1, 2, 3)` 当前都返回
  `Type::None` 且不报错。迁移**不是搬家，而是要在本批把规则定下来**（§2.3 已定签名）。

## 二、必须先冻结的 9 条

### 2.1 **先迁移有规则的，再接 `print`/`input`——顺序不可颠倒**

**冻结**：分步提交时，**先**迁移标量转换、`set`、错误构造这三类**已有明确规则**的特判；
**表机制在那一步就被验证**；**之后**才接 `print`/`input`。

**理由**：§一 的盘点显示两类难度不同。若先接 `print`，则**表机制与新的语言决策同时引入**——
一旦出问题，无法区分是「表设计错了」还是「`print` 的语义没想清」。这是本仓反复栽的
「一次改两件事」的老毛病。

### 2.2 **契约表是唯一来源；留着特判即未完成**

方向稿 §三 3.3 明写：「**表存在但某个消费者仍按字符串特判，视为未完成**」。

**冻结**：

- 迁移完成后，`simple_callee_name` 一类的**名称比较不得再出现在分派路径上**；
- **判定方式必须是可证伪的**：验收含「**移除验证**」——删除契约表项、VM 绑定或
  ABI 包装中的任一环节，**专门用例必须失败**（方向稿 §六 1 最后一条）。

### 2.3 **签名：`print` 采用可变参数**（已决策）

**已决策**（2026-10-03）：`print` 为**可变参数**。

**冻结**：

- **契约模型本身必须能表达 variadic**——不得用「`print` 特例」绕开。
  这是**表达能力下限**，后续每个可变参数入口都依赖它；
- 现状 `print` 返回 `Type::None`，**迁移后必须保持不变**——否则会波及所有把
  `print(...)` 当语句用的既有代码与规格快照；
- `input` 的两个子问题**在本批内定，不得默认**：是否接受提示参数、读不到输入时
  返回 `str` 还是可恢复错误。

### 2.4 **`IntrinsicId`：`u32`，`0` 保留为无效**（已决策）

**已决策**（2026-10-03）：宽度 `u32`，`0` 为无效/未初始化哨兵，**永不分配**。

**冻结**：

- 校验步骤**必须拒绝** id 为 `0` 的声明与字节码操作数；
- id 一经发布**不得复用**；删除的声明保留 **tombstone**，区间划分在本批内冻结并写入文档；
- **该宽度进入字节码与 LLVM ABI**——本批之后变更需走 ABI 版本提升，**不得静默加宽**。

### 2.5 **契约 crate 位于共同下层，依赖方向不可反转**（已决策）

**已决策**（2026-10-03）：新建 crate（暂定名 `xiao-intrinsics`）+ **声明式数据文件**。

**冻结**（方向稿 §三 3.1 的约束，不可违反）：

- 契约 crate **只存后端无关声明**，**不能**保存 Rust 函数指针、`RuntimeValue`、
  平台句柄或 LLVM 类型；
- **`xiao-types` 适配契约，不是契约依赖类型层**——`xiao-types` 目前不依赖任何
  Runtime 层，这个性质必须保住；
- **不得复用 `config.xiao` 的解析器**：契约表是编译器内部声明，`config.xiao` 的解析
  属于前端，复用会造成**契约与前端互相依赖**。

### 2.6 **生成产物与数据文件不得漂移**

数据文件方案引入一道新的漂移面（这正是本仓头号病）。

**冻结**：生成时机（构建期 `build.rs` / 提交前生成入库 / 测试期校验）在实施第一步
**就定死**；若选「提交前生成入库」，则**生成器与产物必须同时入库**，并加门禁防止
两者不一致——**不得只入库产物**。

### 2.7 **复用 13A 的机制，不新造**

**冻结**：跳过原因用 13A 的 `SkipReason`（含 `InsufficientBenefit`、`TargetIncapable` 等）；
快照、回滚与验证阻断沿用 13A 既有接口。**不新造平行机制**——那是「单一来源」病史的复发。

### 2.8 **LLVM 路径不可用时明确报告，不得伪造通过**

方向稿 §六 1 明写：「**LLVM 尚未可用时不能伪造通过**」。

**冻结**：若 `print` 的原生实现因 ABI 或工具链原因在本批内做不完，
**必须产出明确的跳过报告与理由**，**不得**让测试以「未覆盖」的方式变绿。

### 2.9 **不改 09R3 的冻结面**

**冻结**：机型、调用约定、指令编码、源码映射**均不改**。新增的 `IntrinsicId`
操作数**必须能在既有编码内表达**（`u32` 固定宽度）；若做不到，**停下来报告**，
而不是顺手改编码。

## 五、硬约束

1. **契约 crate 不得依赖任何实现层**（`xiao-types`/`xiao-ir`/`xiao-vm`/`xiao-codegen-llvm`/`xiao-runtime*`）；
2. **`0` 不是合法 `IntrinsicId`**——声明与操作数两侧都要拒绝；
3. **生成器的校验必须拒绝**：重复 id、已占用 id 的不同签名、缺少绑定、未声明能力、
   ABI 版本不兼容、类型层与运行时签名不一致（方向稿 §三 3.3）；
4. **机器字段只存 `id`/`code`/`message_id`/结构化参数**——名称、翻译与诊断文本
   **不参与分派**（方向稿 §三 3.4）；
5. **`print` 的 `Type::None` 返回值不变**（§2.3）;
6. **不改 09R3 的编码**（§2.9）。

## 六、分步提交

1. **建契约 crate 与生成机制**：crate 落地、数据文件格式定稿、生成器与校验就位、
   **生成时机定死并加防漂移门禁**（§2.6）。此步**还不接任何入口**。
2. **迁移已有规则的入口**：标量转换、`set`、错误构造改为查表。
   **此时表机制已被验证**，且**无新增语言决策**。
3. **接入 `print`/`input`**：按 §2.3 的可变参数定规则，类型层与 IR 先通。
4. **VM 分派**：`id → 运行时分派表`，`print` 在字节码路径产出可见输出。
5. **LLVM 路径**：`xiao-runtime-abi` 新增输出能力并接线；**做不完就报告，不伪造**（§2.8）。
6. **测试族**：按方向稿 §六 1 的六类落地（表一致性、未知与不兼容、双路径差分、
   资源生命周期、容器边界、归档兼容），外加**移除验证**。
7. **文档与登记**：crate README、UseDocs、主表、契约表自身的说明文档。

## 七、最可能翻车的地方

1. **先接 `print` 再迁移**（§2.1）——表机制与新语言决策同时引入，出问题无法定位。
2. **表建了但留着特判**（§2.2）——方向稿明写视为未完成，**验收必须能证伪**。
3. **契约 crate 反向依赖实现层**（§2.5）——会锁死类型层。
4. **复用 `config.xiao` 解析器**（§2.5）——契约与前端形成环。
5. **`print` 返回值从 `None` 变成别的**（§2.3）——波及既有代码与规格快照。
6. **variadic 用 `print` 特例绕开**（§2.3）——表达能力下限没做进模型，往后每个
   可变参数入口都要再补一次。
7. **分配了 id `0`**（§2.4）。
8. **数据文件与生成产物漂移**（§2.6）——本仓头号病。
9. **新造平行于 13A 的快照/跳过机制**（§2.7）。
10. **LLVM 路径做不完却让测试变绿**（§2.8）。
11. **为塞下 id 顺手改 09R3 的编码**（§2.9）。
12. **忘了 `Cargo.lock` 同步**——`check:lock` 会红（16A 栽过一次）。

## 八、验收

1. **契约表自洽**：id 唯一、`0` 被拒绝、签名/所有权/效果与绑定一致（方向稿 §六 1 第 1 条）；
2. **未知与不兼容在用户代码执行前拒绝**：未知 id、缺失绑定、能力不足、ABI 不兼容；
3. **名称不再参与分派**：`simple_callee_name` 不出现在分派路径上；
4. **移除验证**（**关键**）：删除表项、VM 绑定或 ABI 包装中的**任一**环节，
   专门用例**必须失败**——这是「表真的在被消费」的唯一硬证据；
5. **双路径差分**：同一源码与输入在 VM 与 LLVM 的结果、错误身份、释放顺序、
   诊断字段一致；**LLVM 不可用时按 §2.8 报告，不得伪造**；
6. **`print` 可用**：`print("hello world!")` 在 `xiao run` 下产出可见输出；
   这也是 **17 阶段端到端验收的前置**；
7. **返回值不变**：`print(...)` 仍为 `Type::None`，既有规格快照未改；
8. **依赖方向**：契约 crate 不依赖任何实现层；`xiao-types` 仍不依赖 Runtime 层；
9. **生成一致**：数据文件与生成产物不漂移，门禁能发现人为改动；
10. **不回归**：`cargo test --workspace` 全绿、`cargo clippy --workspace --all-targets -- -D warnings` 绿；
11. **门禁全绿**：`bun run check` 退出码 0（含 `check:lock`，两个 lock 文件都已提交）。

## 九、不负责与不要重复做的事

- **不做 `os` 与平台资源**（`20D`）——文件/目录/进程 API 与能力模型不在本批；
- **不做官方 Xiao 标准库模块**（`20C`）；
- **不做 `.xar` 的兼容检查**（`20E`，且依赖 17）；
- **不实施 17**——本批只解除它的观察能力阻塞；
- **不改** 09R3 的机型/调用约定/编码/源码映射；
- **不重开** 13A 的配置、指纹、Pass 接口与回滚设计；
- **不擅自冻结**方向稿 §八 中不属于本批的条目（第 3–7 条）——
  特别是第 3 条（Runtime ABI 的稳定调用约定）与第 6 条（首批 `os` API），
  它们归 20D 或更后。

## 十、当前实施状态

- `xiao-intrinsics` 已以构建期生成的 `intrinsics.json` 为唯一声明来源；类型层、IR、字节码验证器、VM
  和 LLVM 降低器均按稳定 ID 消费，名称不进入机器分派。
- VM 已实现标量转换、`set`、错误构造、`print` 和 `input`；`print` 通过结构化事件进入协议与 CLI
  标准输出，返回值仍为 `none`。Runtime ABI 已提供 `xiao_runtime_print_values`，并由动态 LLVM
  `print` 调用，调用后按既有所有权规则释放实参。
- LLVM `input` 已通过稳定 `xiao_runtime_input` ABI 接通动态降低器；提示参数、EOF 和读取失败均
  走挂起错误槽，调用方继续按既有值所有权规则释放提示值。真实 stdin 工具链门控仍按 10D
  环境要求执行，未设置工具链时不伪造原生运行通过。
