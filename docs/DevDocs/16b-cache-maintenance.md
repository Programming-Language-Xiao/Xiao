## 二、已登记的输入（前序批次转来）

### 2.1 **索引锁的崩溃残留**（来自 16A 审核，见 16A-FIX §二 2.3）

`IndexLock::acquire`（`xiao-artifacts/src/lib.rs:712` 时点）用 `create_new` 建锁，
只在 `Drop` 里删除。进程被 kill 或崩溃时**锁文件残留 → 后续所有索引操作永久失败**。

**归属依据**：这正是 16.12 的「**终止恢复**」与规范 `:21` 的「**锁必须可清理**」；
验证面是**多进程行为**，与 16A 文档 §十 把「多进程测试」划归 16B 一致。

**推荐方向（未冻结）**：改用 **OS 级文件锁**（Unix `flock` / Windows `LockFileEx`），
由内核在进程死亡时自动释放，**从根上消除 stale 概念**，而不是再写一层 pid/时间戳的启发式判断。
**动手前须先与决策基线对齐**——[11A-CONC](11a-concurrency-model.md) 已冻结工具链内部的并发模型，
本批的锁方案**不得与之冲突**。

### 2.2 **架构测试的精度**（来自 16A-FIX 验收，见 16A-FIX §六 第 3 条）

`xiaoc_contract_constants_have_one_authoritative_source`（`xiao-artifacts/src/lib.rs` 测试模块）
用 `contains("72")` 守住「`.xiaoc` 契约常量单一来源」。方向正确、当前有效，但：

- `contains("72")` 会匹配**任何**含 `72` 的子串（`172`、`7200`、注释），
  将来一处合理写入就会**误报**；而误报的后果是开发者**改断言而非改代码**，约束随之失效；
- `split("#[cfg(test)]").next()` 依赖切片位置——实现部分若新增 `#[cfg(test)]` 项，
  切片会**过早截断**，检查静默变宽松（漏报）。

**推荐方向（未冻结）**：改为**行为断言**——传入一段长度不足的 `.xiaoc`，
断言其错误来自权威校验（带 `XIAOC-001` 之类的错误码），而**不是**旧预检的文案。
它守的是「预检没有回来」这个真实语义，不依赖文本，也不会误报。
字符串测试可作为辅助保留，但至少应把匹配收紧到词边界。

## 三、待定决策（**不得擅自冻结**）

- `16.10` 的**最终淘汰算法**（规范明写「待确认」）——LRU、引用计数还是混合，需先决策。
- `16.9` 的**引用记录载体**——项目侧、锁文件侧还是 `.xar` 侧各自记录，还是统一登记；
  与「索引不能替代依赖锁文件」（16A §三 3.5）的边界需一并厘清。
- §二 2.1 的**锁机制选型**（OS 级锁 vs 其他）——须与 [11A-CONC](11a-concurrency-model.md) 对齐后冻结。
- `16.11` 的**离线读取**是否引入新的信任边界（规范 `:17` 明写「不能把未经验证的路径或文件名当作信任依据」）。
