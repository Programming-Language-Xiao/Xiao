## 一、落地判断

## 二、已确认决策

### 2.1 默认 Runtime 边界

06-B 当前提供单线程、非原子 `StrongHandle`/`WeakHandle`。句柄通过 `PhantomData<Rc<()>>` 避免 Rust 自动实现 `Send`/`Sync`；这是一条当前 Runtime 边界，不等于已经设计了 Runtime ID 或语言级线程亲和协议。

“默认路径保持非原子 RC”可以作为后续设计的基线，但不把“永远不变”写成未来 ABI 承诺。跨 Runtime 能力必须使用显式的新表示或容器，不能把原子语义悄悄扩散到全部普通句柄。

### 2.2 强拥有图是 DAG，不是森林

强边表示会延长目标生命周期的拥有关系；强边必须无环，静态发现自环和多节点环时报告 `X06-LIFETIME-001`。弱边不参加强图拓扑。

正式术语是“有向无环强拥有图（DAG）”。当前图算法允许一个目标有多个强拥有者，因此合法的共享拥有和菱形图不能被误报为错误。除非未来另有明确决策，不增加“每个节点只能有一个父节点”的森林限制。

当前 Runtime 已有 Rust 层 Weak 句柄，但 Xiao 源码尚未开放 Weak 构造和升级语法。后续标准库示例不得假设用户现在就能直接声明 Weak。

### 2.3 `CrossThread` 只记录事实

`CrossThread` 是 `xiao-lifetime` 中记录在以 `ValueId` 索引的 `ValueInfo.escapes` 集合里的 `EscapeReason`。它描述一个具体值已经跨越某种执行边界，不表示某个类型天然可发送或可共享。

在并发表面模型冻结前，不得通过函数名、变量名或容器名称启发式产生它。未来必须由显式的 `send`、任务迁移、消息 lowering 或等价 IR 事实产生。

可发送性和可共享性是另一个层次的类型能力：

- “移动到另一个执行单元”对应类似 `Send` 的能力；
- “多个执行单元同时持有并读取”才需要类似 `Sync` 的能力；
- 同线程协程的挂起/恢复不能自动等同于跨线程传递。

是否拆分 `CrossThread` 与任务边界事实，留给 07-D 研究后的并发阶段。

### 2.4 当前计数策略不是原子实现接口

`RefCountStrategy` 当前只对传入的 `usize` 做 checked 加减；对象头实际使用 `Cell<usize>`，载荷使用 `RefCell`。因此增加一个 `Atomic` 枚举变体，或替换一个策略名称，都不能提供并发安全。

未来共享句柄至少要重新设计：

1. 原子强/弱计数存储和内存顺序；
2. 弱升级的“非零检查并递增”竞争；
3. 最后一个强引用的唯一销毁与对象头回收；
4. 载荷的不可变性、锁或其他访问同步；
5. 与字节码、LLVM 和错误/清理 ABI 的一致性。

可复用的只有溢出、下溢、重复销毁和已释放访问等语义契约。未来实现应优先考虑独立的共享对象头和句柄类型，而不是改造所有普通句柄。

### 2.5 `Arena` 不豁免强环

现有 RC 强图规则继续对所有 RC 对象生效。不得因为对象被称为 `Arena<T>` 就允许 `StrongHandle` 在区域内形成环。

如果未来确实需要区域分配，必须先定义独立的区域语义：区域拥有成员，成员之间使用 ID、区域内句柄或受约束借用；区域外不能保存已失效的成员引用；成员析构和区域释放顺序必须可审计。那是新的存储类别/生命周期模型，不是当前强图算法的一个布尔豁免。

### 2.6 并发实现后置

07-D 只研究线程、任务池、Actor 和其他候选执行机制，不冻结语法或 ABI。完整并发实现必须在单线程字节码和原生执行闭环之后建立新的独立阶段。

因此，单线程事件循环、协程、消息传递、多 Runtime 堆岛和共享对象都只是候选方案。本文不选择其中任何一个作为 Xiao 的正式并发模型。

### 2.7 复制、冻结与共享可变对象尚未冻结

当前类型模型没有只读/可变/可发送能力；`RuntimeValue` 的 `Clone` 对容器是复制强句柄，不是递归深拷贝；数组和表仍提供可变访问路径。

未来消息传递可以选择深拷贝、序列化或冻结共享，但必须分别定义：

- 递归复制的值集合和动态值处理；
- 目标 Runtime 的分配与错误传播；
- 冻结后如何阻止所有别名修改；
- 发布、可见性和失败时的资源清理；
- 共享可变对象是否需要锁、原子操作或完全不同的所有权模型。

在这些契约形成前，不得把“冻结”写成可用操作，也不得把普通 `Clone` 当作跨线程复制。

## 三、后续阶段交接

### 3.1 07-D 研究交付物

07-D 接手时必须产出可比较的研究记录，而不是先写语法：

1. 线程、单线程任务、任务池、Actor/Channel、多 Runtime 等模型的语义和成本矩阵；
2. 每种模型对 RC、Weak、错误传播、取消、清理和调度的影响；
3. `Send`、`Sync`、任务边界和跨 Runtime 值集合的候选定义；
4. 深拷贝、序列化、冻结共享和共享可变对象的差分原型；
5. 竞争可静态证明时的拒绝规则，以及只能运行时检测时的稳定错误边界；
6. 对 B0/N0、IR、Runtime ABI 和标准库接入的依赖清单。

研究结果不能直接改变 `xiao-syntax`、`xiao-types` 或 Runtime 的现有契约。

### 3.2 新并发实现阶段的前置条件

只有以下条件同时满足，才能建立新的并发实现阶段：

- B0 字节码执行闭环和 N0 原生构建闭环可作为稳定消费者；
- 执行机制经过 07-D 比较并由决策基线确认；
- 值传递、可变性、错误传播、取消和清理语义已经有类型/IR 形状；
- 普通单线程句柄与共享句柄的 ABI 边界已经分开；
- 字节码与 LLVM 的竞争检查、释放顺序和诊断字段有共同验收方案。

新阶段应自行登记阶段代号、主文档、12 的里程碑、测试族和必要的 UseDocs；在此之前不要预留不存在的 `H0-C`、`07-D 实现` 或 `std.concurrent` API。

### 3.3 06/Runtime 侧的后置任务

未来实现共享句柄时，接手 Agent 至少要覆盖：

- 普通 `StrongHandle`/`WeakHandle` 继续保持单线程边界；
- 原子共享句柄不与普通句柄混用；
- 弱升级、最后强引用、载荷析构和对象头回收有并发规格测试；
- `ObjectPayload` 的线程安全约束与容器可变性一致；
- 两种执行后端观察到相同的释放顺序、主错误和 suppressed 错误。

## 四、标准库边界

树、双向链表、观察者和图等结构可以在 20C 作为候选官方 Xiao 库模块评估，但当前不冻结 Strong/Weak 布局：

- 纯 Xiao 可表达的封装优先放官方 Xiao 库；
- Weak 构造、升级、冻结和跨 Runtime 发送等 Runtime 原语必须先由内存/并发阶段冻结；
- 图结构不默认使用 Weak，必须先明确节点存活、边失效和 ID/注册表语义；
- 标准库不能用包装层掩盖未解决的所有权或竞争规则。

## 五、验收清单

后续阶段声称消费本文时，至少要证明：

1. 强 DAG 中的共享拥有和菱形图可通过，单节点/多节点强环被拒绝；
2. 当前普通句柄仍不能跨线程发送，且没有借助运行时名称检查替代静态边界；
3. `CrossThread` 只由显式 lowering 事实产生，动态值有明确运行时路径；
4. 原子共享句柄测试覆盖弱升级竞态、恰好一次析构、对象头存活和载荷访问同步；
5. 消息复制不会因浅层句柄克隆而共享可变对象；
6. 冻结共享在类型层或运行时层都能阻止后续不安全写入；
7. 字节码与 LLVM 的错误身份、释放顺序和竞争诊断一致；
8. 相关 UseDocs 只有在功能实现和示例测试通过后才改为 `verified`。

## 六、当前仍待决事项

以下事项明确留给 07-D 或其后的独立阶段，不是本批的隐式决定：

1. Xiao 采用线程、任务池、Actor、单线程事件循环还是组合模型；
2. 任务边界与跨线程边界是否使用不同的生命周期事实；
3. `Send`/`Sync` 或等价能力的名称、推导规则和动态值策略；
4. 深拷贝、序列化、冻结共享和共享可变对象的公开 API；
5. 原子计数的对象头、内存顺序、弱升级和 ABI 形状；
6. 是否真的需要区域分配，以及区域引用的静态表示；
7. 官方标准库中哪些结构值得提供，以及它们的节点/边存活契约。
