# 07. 错误模型与并发安全边界

> 本阶段实现前面各语言能力共同需要的错误基础设施，冻结可捕获错误、致命故障、堆栈、日志和调试诊断边界，并冻结未来并发实现不得突破的安全边界。它不在最小双模式闭环之前实现线程、任务池、`async`/`await` 或 Actor。

第 01 至第 06 阶段必须随各自功能建立最小诊断结构和错误用例，不能等到本阶段才开始报告错误。本阶段接入这些既有诊断，统一跨阶段编号、传播和后端契约。

## 一级工程目标：明确并发术语

### 线程

线程是操作系统调度的执行单位。同一进程可以有多个线程同时运行不同函数。线程共享进程内存，因此共享可变对象时容易产生数据竞争。

### 任务池

任务池预先维护一组可复用的工作线程，把大量小任务分发给它们执行。它能减少频繁创建线程的成本，但不会自动解决共享数据的安全问题。

### `async`/`await`

这是一种“可暂停、可恢复”的函数写法：函数遇到等待网络或文件的操作时主动让出执行权，之后再恢复，不必一直占着线程。它主要解决大量等待任务，不等于自动创建线程。

### Actor

Actor 模型让每个执行单元独占自己的状态，其他执行单元通过消息邮箱通信。它可以减少共享内存，但会引入消息、调度和序列化成本。

## 一级工程目标：冻结数据竞争政策

### 不允许静默竞争

同一可变数据被多个并发执行单元访问时，编译器或运行时必须阻止不安全竞争：

- 编译器能够证明存在竞争时，直接拒绝编译。
- 编译器无法证明但运行时能检测时，运行时报告明确错误。
- 任何未检测的竞争都不能被当成合法且可依赖的行为。

这是一项语义要求，不代表 Xiao 已经选定线程、任务池或 Actor 作为唯一执行模型。

### 阶段范围

并发实现必须晚于单线程字节码和原生执行闭环，并在执行机制确定后建立新的独立阶段。`async`、`await`、Actor 等关键字在此之前不进入正式语法，也不属于第 07 阶段退出条件。

## 一级工程目标：冻结错误模型与分类

### 错误身份与三类边界

Xiao 的错误控制流和观测信息必须分开：错误对象负责传播与捕获，日志负责记录，最终错误报告负责向用户呈现。错误文本不是程序判断错误的接口。

错误分为三类：

1. **编译期诊断**：程序尚未运行时发现的问题。它们只生成诊断，不进入运行时，也不能生成可执行产物。
2. **可恢复运行时错误**：程序可以决定重试、替代或向调用者报告的问题。它们使用统一的 `XiaoError`，可以被 `try`/`catch` 捕获或继续向外传播。
3. **致命故障**：继续执行已经不安全的问题，例如虚拟机不变量损坏、损坏的字节码、无法建立错误对象的内存耗尽、调用栈耗尽或硬件异常。它们进入 `panic`/终止路径，普通 `catch` 不得把进程伪装成正常状态。

语言规定的动态检查失败（溢出、除零、动态类型转换、动态索引和键不存在等）默认属于可恢复运行时错误；内存分配失败只有在 Runtime 能安全建立错误对象时才可捕获，否则转为致命故障。引用计数不变量损坏属于 Runtime 内部故障，不应当作为普通业务错误继续执行。

### 编译期错误

至少包括：

- 未定义名称、重复定义和作用域错误。
- 类型不匹配、非法隐式转换和路径约束冲突。
- 可静态证明的数组越界或数据竞争。
- 字面量零步长、负随机数量、无放回抽取静态超量，以及对字典表或集合使用不受支持的高级选择器。
- 常量无法在编译期求值。

### 运行时错误

至少包括：

- 动态值类型检查失败。
- 数值溢出、除零和非法转换。
- 动态索引越界、键不存在和容器扩容失败。
- 变量在运行时产生零步长、负随机数量、无放回超量或空来源正数抽取。
- 在 Runtime 能安全报告时的内存分配失败，以及运行时检测到的数据竞争。
- 引用计数不变量损坏、损坏字节码和无法安全展开的资源错误属于致命故障，不得伪装成普通运行时错误。

错误消息必须包含错误类别、源位置、相关变量/路径和可行的修复提示。

### 统一错误对象

所有可恢复运行时错误都使用不可变的结构化错误对象。字段职责如下：

| 字段 | 作用 |
| --- | --- |
| `code` | 稳定的机器可读错误码；程序匹配它，不匹配展示文本 |
| `kind` | 错误类别或错误类型，例如算术、模块、输入输出 |
| `message` | 面向人的说明，不作为兼容接口 |
| `location` | 源文件、模块、行、列和可选的字节码/原生位置 |
| `cause` | 原始错误或被包装错误，形成原因链 |
| `context` | 键值形式的操作上下文，不能依赖隐式字符串拼接 |
| `stack` | 产生错误和传播过程的调用栈，按需生成 |
| `error_id` | 本次错误事件的唯一标识，供日志和调试窗口关联 |

包装错误必须保留原始 `code`、`cause` 和源位置；新增上下文不能覆盖原始错误身份。错误对象和已经捕获的堆栈默认不可变，避免处理错误时再次改变错误含义。

### 错误传播语法

首版冻结四个控制流构造：`try`、`catch`、`finally` 和 `raise`。`Result` 风格返回值延后到类型系统和泛型稳定后再实现，不作为首个可运行闭环的前置。

示意语法如下，具体参数类型和错误类型命名在语法阶段补充：

```xiao
def divide(a, b)
    if b == 0
        raise ArithmeticError(code = "XIO-ARITH-DIVZERO", message = "除数不能为零")
    return a / b

try
    value = divide(10, 0)
catch err as ArithmeticError
    print(err.message)
finally
    print("cleanup")
```

`catch` 按错误类型匹配，之后可以增加按稳定 `code` 或显式条件筛选；匹配顺序必须从具体到一般，宽泛的捕获不能静默吞掉错误。没有匹配处理器时，错误继续展开到统一的程序边界。`raise` 重新抛出时保留原始原因链；`panic` 只供 Runtime/系统边界使用，不由普通 `catch` 恢复。

### 作用域展开与资源清理

`raise`、`return`、`break`、`continue`、构造失败和 `panic` 都必须经过同一套作用域展开计划：

1. 每个离开中的作用域执行一次 `finally`（若存在）。
2. 作用域内的资源按反向声明顺序执行 `drop`。
3. 进入匹配的 `catch` 或继续向外传播。
4. `catch`/`finally`/`drop` 产生的新错误不能覆盖已有主错误，只能作为 `suppressed` 错误附加；没有主错误时才成为新的主错误。

`try` 体应视为独立子作用域，处理器不能继续使用已经完成 `drop` 的局部资源。上面的顺序是首选实现方案，最终的 `finally` 与 `drop` 精确顺序必须由生命周期测试冻结；“每次退出恰好一次、主错误不丢失”是不可突破的约束。

### 堆栈与错误报告

错误至少保存产生位置和用户代码调用帧；完整堆栈可以延迟到错误被展示或记录时生成，以降低正常路径开销。每一帧应能表达模块、函数、逻辑源路径、行列号和可选的字节码/原生偏移。`.xiaoc` 的紧凑源码映射与 LLVM 的等价映射必须由同一错误报告器消费。

默认程序报告写入标准错误流，包含错误码、简短消息、首个源位置、用户调用栈和原因链；程序标准输出保持原样。调试模式可显示 Runtime 内部帧、局部上下文和完整原因链，但必须对密码、令牌、环境变量和超大容器内容脱敏或截断。错误报告器不得调用可能再次抛错的用户自定义格式化代码。

### 日志与 `-debug` 诊断会话

日志是观测接口，不替代错误传播。Runtime 提供结构化事件等级：`trace`、`debug`、`info`、`warn`、`error`、`fatal`。错误沿调用链只补充上下文，不在每一层重复写日志；未捕获错误到达程序边界时自动记录一次。

只要运行入口显式收到 `-debug`，Runtime 就必须在执行用户代码前启动独立的诊断进程和诊断终端窗口。窗口滚动显示程序内部事件，包括模块加载、函数进入/退出、作用域与 `drop`、分配/释放、钩子、预断点/断点命中、日志和错误。默认不逐条输出每一条指令；需要指令级追踪时才启用 `trace` 等更细等级。该规则适用于 `xiao run`、源码快捷运行和 `xiao -xar`；`xiao build -debug` 或 `xiao build -xar ... -debug` 生成的调试产物必须保存诊断激活位，之后直接启动产物时同样自动打开窗口，无需再次传参。

每条诊断事件使用统一结构，至少包含单调时间、日志等级、事件类型、模块/源码位置、节点或函数标识、关联的 `error_id`（如有）和结构化负载。终端可以渲染成人类可读文本，文件日志推荐使用一行一条事件的结构化格式，便于筛选、检索和后处理；具体序列化格式在 CLI 阶段冻结。

诊断窗口最后一行固定为状态栏，至少持续显示：

- 程序运行时间。
- 当前内存占用和峰值内存。
- 报错数量：本次运行产生的全部结构化运行时错误事件，不因日志等级、是否捕获或是否展示而过滤；编译期诊断不计入。
- 预断点（或最终确定名称的断点钩子）命中次数。
- 钩子触发次数。

状态栏更新不应把每次刷新写入日志文件；程序结束时写入最终指标快照。诊断窗口关闭、通信中断或日志目标写入失败不能改变程序语义；但在 `-debug` 启动阶段无法创建强制诊断窗口时，不得静默降级为普通无窗口运行，必须报告诊断启动失败。无图形环境下的失败呈现和退出细节由平台阶段冻结。

实现上固定把 Runtime 的事件生产和窗口渲染分开：目标程序只负责生成带长度边界的结构化事件，通过本地匿名管道或本地套接字发送给独立的诊断窗口进程；窗口进程负责滚动区域、固定状态栏、颜色和筛选。这样诊断输出不会抢占程序的标准输入输出，也不会把平台终端 API 渗入语言核心。通信中断时 Runtime 应继续运行并把事件写入已配置的文件目标；窗口进程不得反向执行用户代码。调试版原生程序必须内嵌或随产物携带启动该诊断进程所需的组件，不依赖外部 `xiao` 启动器；普通 GUI 子系统设置也不能抑制调试窗口。

`config.xiao` 的 `[debug]` 表用于配置诊断参数。至少需要支持终端等级、文件等级、日志目录/文件、堆栈详细程度和文件/模块聚焦规则；下面是说明性结构，具体字段白名单由 CLI 阶段冻结：

```xiao
[debug]
terminal_level = "info"
file_level = "debug"
log_dir = "logs"
stacktrace = "full"
focus = [
    { module = "app.net", output = "logs/net.log", level = "trace", mirror = false },
    { source = "src/parser.xiao", output = "logs/parser.log", level = "debug" }
]
```

示例中的 `mirror = false` 表示该聚焦事件只写入指定文件；省略 `mirror` 时默认也是 `false`。只有显式设为 `true` 才同时写入总日志。

聚焦规则按模块名或源码文件匹配，同一事件可以命中多个输出文件。匹配到聚焦规则的事件默认从总日志分流，不写入总日志；需要同时保留在总日志时必须由显式 `mirror` 选项开启。终端等级和文件等级独立过滤，但错误计数仍统计被过滤的结构化运行时错误事件。

`-debug` 是强制的运行时诊断开关：直接运行入口收到它时必须打开独立诊断窗口；`xiao build -debug` 和 `xiao build -xar ... -debug` 必须把诊断激活位、源码映射、诊断元数据和运行时钩子能力写入产物，产物启动时自动打开窗口。普通发布构建不携带该激活位，也不得因 `[debug]` 配置自行打开窗口。调试版原生程序不依赖 `xiao` 启动器；`.xar` 仍按归档运行前提由 `xiao -xar`/Xiao Runtime 启动，但其诊断窗口由独立诊断进程承载，不依赖另一个外部调试窗口启动器。

## 二级实现任务

### 错误基础设施

1. 接入前序阶段的最小诊断结构，统一错误编号、错误类型和源位置结构。
2. 在字节码和 LLVM 后端共享 `XiaoError` 构造、原因链和错误边界。
3. 为溢出、索引、选择器边界、类型和内存错误建立金丝雀测试。
4. 实现错误跨函数、跨模块的传播协议，并为未来跨线程传播预留不改变现有错误身份的扩展点。

### 展开与报告

1. 将 `try`/`catch`/`finally`/`raise` 降低为统一控制流和作用域展开计划。
2. 验证正常返回、提前返回、循环跳转、错误传播和 `panic` 都恰好执行一次 `drop`。
3. 实现主错误、原因链和 `suppressed` 清理错误的合并规则。
4. 实现默认简短堆栈、调试完整堆栈和文本/机器可读错误报告。

### 日志与诊断窗口

1. 实现结构化日志事件、等级过滤、日志去重（不得删除原始错误事件）和标准错误流输出。
2. 实现 `-debug` 诊断会话、独立诊断进程与终端窗口、固定指标状态栏，以及窗口创建失败的明确诊断接口。
3. 实现 `[debug]` 配置、模块/文件聚焦、多文件分流和安全脱敏。
4. 让日志写入失败、窗口关闭和调试开关变化不改变程序的语言语义。

### 后置并发研究

以下工作必须等字节码与原生执行闭环完成后开展，不属于本阶段的顺序任务或退出条件：

1. 为共享可变值建立所有权/访问记录。
2. 设计一个能在编译期拒绝明显竞争的最小规则集。
3. 为动态值设计运行时检测钩子。
4. 用线程、任务池和 Actor 原型分别评估成本，不提前锁死语法。

## 验收标准

### 并发验收

- 文档和编译器都不会把未检测的数据竞争当作合法行为。
- 未选择执行机制前，不出现伪装成已定稿的 `async`/`await` 或 Actor 语法。
- 本阶段完成不代表并发能力已经实现；完整并发阶段必须排在字节码和原生执行闭环之后。

### 错误验收

- 编译期错误不进入运行时。
- 可恢复运行时错误可以被匹配的 `catch` 捕获；未捕获错误到达统一边界时只报告一次并返回稳定的非零结果。
- `panic`、损坏字节码和无法安全展开的故障不会被普通 `catch` 伪装成成功。
- 所有错误退出路径都执行确定性资源清理；清理错误不会覆盖主错误。
- 字节码和原生模式的同一错误具有相同类别、错误码和可比消息。
- 默认错误报告不污染标准输出，堆栈位置能回溯到源码；调试模式能关联错误、日志和指标事件。

### 调试验收

- 任何带 `-debug` 的直接运行都会在用户代码前打开独立诊断窗口；调试版原生构建产物即使脱离 `xiao` 启动器、以 GUI 子系统启动，也会自动打开该窗口。`.xar` 由 `xiao -xar` 按既定 Runtime 前提启动时同样打开窗口。
- 诊断窗口末行持续显示运行时间、内存、全部结构化运行时错误事件计数、预断点/断点钩子和钩子计数，结束时保留最终快照。
- `[debug]` 的终端等级、文件等级和聚焦规则不会漏写未匹配文件；聚焦事件默认不进入总日志，只有 `mirror` 才会双写，也不会因重复路由产生无法解释的无限日志。

## 待定决策

1. `catch` 除错误类型外是否允许按 `code`、条件和模式匹配，以及宽泛捕获的静态限制。
2. `Result` 的具体泛型表示、与 `raise` 的互操作和简化传播语法；它属于后续阶段，不阻塞首版异常式传播。
3. `finally` 与 `drop` 的最终执行顺序、清理错误的 `suppressed` 表示和 `panic` 的诊断格式。
4. Windows、Linux、macOS 创建独立诊断窗口的具体 API、诊断组件以内嵌资源还是随产物附带文件提供，以及无图形环境下无法满足强制窗口要求时的失败呈现和窗口关闭后的行为。
5. `[debug]` 的正式字段名、默认日志目录、日志轮转/保留策略，以及 `mirror` 字段的精确配置形态。
6. 预断点的最终名称、命中计数边界和与未来完整调试器的互操作协议。
