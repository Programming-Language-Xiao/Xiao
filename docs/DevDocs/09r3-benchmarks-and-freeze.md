# 09R3. 跨平台基准与冻结（方向稿）

> **本文是方向稿，不是定稿。** 它定下 09R3 的入场条件、交付物、冻结范围与平台口径；
> 具体的基准程序、参数与报告格式等 09R2G / 09R2H 落地后再回来按实际效果微调。
>
> 09R3 的**权威定义**在执行 [09R. 字节码寄存器机型特别研究](09r-bytecode-machine-research.md)
> `:610-619` 的施工图与 [12. 测试与开发里程碑](12-tests-and-milestones.md) 的退出条件；
> 本文只把它们变成可执行的形状，**不新增要求**。有冲突时以前两者为准。

## 一、为什么现在就要有这份文档

09R2F / 09R2F1 / 09R2G 的交接文档都已经在写「本批必须在 09R3 之前完成」，
而 09R3 本身在仓内**没有对应文档**——接手者看得到约束，看不到约束指向哪里。
本文补上这个缺口，并明确**哪些东西一旦冻结就不能再动**。

---

## 二、入场条件

R3 不是"随时可以开始跑基准"的批次，它有一组硬前置：

| # | 条件 | 现状 |
| --- | --- | --- |
| 1 | 三种机型可运行 | ✅ R2D 已交付 |
| 2 | 指令编码器与 `pc -> IrSpan` 源码映射 | ✅ R2D 已交付 |
| 3 | **迭代指令落地**（09R2G） | ✅ 已交付（opcode 36/37） |
| 4 | `set_membership` 的类型兼容半（09R2F1 记给 09R2G 的债） | ✅ 已通过 `Check.expected` 交付 |
| 5 | 表声明（09R2H） | ⏳ 见下 |
| 6 | **常规路径上 `TacProgram.unsupported` 为空** | ⏳ 取决于 3/4/5 |

### 关于第 3 条：迭代必须在冻结前

`PathStep::Index(i128)` 是字面常量，`for` 需要索引来自寄存器。09R2G 用**新增指令**绕开
（不改 `PathStep` 的编码），但**新增指令本身就是指令集的一部分**。冻结之后再补，
等于在已冻结的指令集上开新口子。

### 关于第 5 条：表声明是可选的，但有一个前提

`09R2H` **若只追加指令与函数条目**（在 `TacProgram.functions` 里加表方法、追加
`LoadTable`/`MemberGet`/`MemberSet` 三条 opcode），那是纯追加，**可以在 R3 之后做**——
追加不破坏已冻结的格式。

**但若它需要新增程序级区段**（例如 `table_definitions`），则**必须提前**：那会改动
`TacProgram` 的编码布局，也就是换 `FORMAT_VERSION` 重新冻结。**这是本阶段唯一的
"可能阻塞"**，`09R2H` 的设计定稿前必须先回答这个问题。

### 关于第 6 条：`unsupported` 会堵死编码体积指标

`encode/validate.rs` 对非空 `TacProgram.unsupported` **直接拒绝编码**。而 R3 的四份报告
之一是**编码体积**——任何残留的未降低 kind 都会让那一项无程序可测。
这解释了为什么 09R2F / 09R2G 反复强调「不要用 `record_unsupported` 记账」。

## 三、交付物

施工图（09R `:612-616`）要求四份报告加一次冻结：

1. **语义差分报告** — 同一源码、同一 IR、同一语义输入下三种机型结果完全一致；
2. **性能报告** — 按 R1-AC 的门槛与 R1-G 的四族分别上报；
3. **内存报告** — 峰值内存，以及 R1-F `:145` 要求的 `stack_map_entries` 与
   `spill_count` 作为**独立指标**（不是性能的子项）；
4. **编码体积报告**；
5. **冻结记录** — 见第四节。

报告与元数据落 `tests/benchmarks/`（R1-AD `:455-457`）。

---

## 四、冻结范围（**本阶段最重要的产出**）

09R `:618-619` 明列七项。冻结的含义是：**这七项在 B0 及其后阶段不得再改**，
改动等于重新冻结、并让本轮全部基准数字作废。逐项确认"冻结的是什么"：

| # | 冻结项 | 说明 |
| --- | --- | --- |
| 1 | **最终字节码机型** | 栈式 / 分类型寄存器式 / 混合式三选一；门槛未过时依据报告选，**不允许实现代理自行拍板**（09R `:607`） |
| 2 | **寄存器类别与分配策略** | R2D 已定的分类与线性扫描规则；`Poly`/释放计划固定引用一律进 `Frame` |
| 3 | **函数调用 ABI** | 参数传递、返回值、保存/恢复边界 |
| 4 | **异常与清理转移 ABI** | handler 路由、`finally` 子程序、释放序列的转移语义 |
| 5 | **指令编码与版本字段** | opcode 表（**只能追加不得重排**）、`FORMAT_VERSION`、操作数宽度策略 |
| 6 | **源码映射格式** | `pc -> IrSpan` 的表示与 `PcMap` 查询语义 |
| 7 | **性能阈值与基准协议** | R1-AC 的门槛与 R1-AD 的协议本身 |

**冻结不等于公开**：R1-AB（09R `:422`）已定，研究编码**不是** `.xiaoc` 文件格式，
不得使用 `.xiaoc` 扩展名落盘、不得借研究编码提前冒充公开格式。正式分段容器仍归 14/16 阶段。

09R2G 为 opcode 25 的 `Check` 追加 `expected` 存在位与类型载荷后，研究编码布局版本已升至
**2**；09R3 应以该版本为冻结起点。单纯追加 opcode 36/37 不要求换布局版本，版本升级针对的
是既有指令的字段布局变化。

## 五、协议与门槛：引用，不复制

| 内容 | 出处 |
| --- | --- |
| 门槛口径（吞吐 ≥ +10%、冷启动/内存/体积恶化 ≤ 10%、语义结果完全一致） | 09R `:429-439`（R1-AC） |
| 基准协议（工具链、构建配置、测量协议、基线来源、统计方式） | 09R `:441-457`（R1-AD） |
| 四族程序（深表达式算术 / 多具名局部循环 / 深调用递归 / 容器密集） | 09R `:172-181`（R1-G） |
| 结构指标（`stack_map_entries` 三机型口径、`spill_count`、`call_save_count`） | 09R `:145-170`（R1-F） |
| 平台顺序 | 09R `:459-464`（R1-AE） |

**只在本文写两件 R1 没写、但落地必须有的东西：**

1. **基准程序用 Xiao 源码写，走真实前端**（`xiao-driver` 的 `FrontendCompiler`），
   不是手搓 TAC。施工图第 1 条要求"同一源码、同一 IR、同一语义输入"——手搓 TAC
   把这一条绕过去了，测出来的差异就未必是语言的差异。
2. **基准规模要够大**：现有 `tests/spec/09-bytecode/*.json` 的 73 条向量是**语义**夹具，
   规模小、帧浅，量不出机型差异。基准程序是**另一类产物**，不复用它们。

## 六、平台口径

按 R1-AE，复现顺序是 Windows → Linux → macOS。**本轮只在 Windows 原生采数**：

- Windows：完成复现；
- Linux 与 macOS：**记入待复现清单**，未跑之前**不得宣称跨平台已验证**。

两条容易踩的补充：

- **WSL 与容器只当开发环境，不进验收**。`Dockerfile.dev` 与 WSL 都可用于在 Linux 上
  开发与跑测试，但 WSL 共享宿主 CPU 与调度、容器多一层文件系统，**其数字不能与
  Windows 原生并列比较**。R1-AD 要求"基线来源：同一次构建产出的栈式原型二进制"——
  同平台内对比才有效。
- 将来要在 CI 上跑多平台时，用 GitHub Actions 的对应 runner 各采一份，
  **按平台分别上报**，不要合并成一个数。

---

## 七、要建的基础设施

`tests/benchmarks/` 与 `tests/differential/` **目前只有 README**，要新建：

1. **零依赖 harness**（R1-AD `:455-457` 明文要求）：`std::time::Instant`，
   **不引入 `criterion`**。固定预热次数、重复次数、输入规模，取**中位数**并记录四分位区间。
2. **基准程序清单**：按 R1-G 四族命名，**代码与期望结果一起进版本控制**。
3. **差分驱动**：同一份程序在三机型上跑，比对结果值（可复用 `RunOutcome::value`
   与 `assert_all_machines` 的既有范式），失败即报告。
4. **报告落盘格式**：稳定、可 diff、可被后续阶段读取。

### 两处现成的冲突要同批清掉

| 文件 | 现写 | 问题 |
| --- | --- | --- |
| `tests/benchmarks/README.md` | "工程期 15、19" | R1-AD 要求 R3 的报告落这里；工程期标注与现状矛盾 |
| `tests/differential/README.md` | "性能比较以 `xiao build` LLVM 原生模式为标准" | 与 R1-AC 的"相对**同机 Rust 栈式基线**"口径冲突；LLVM 原生要到 10/15 才存在 |

## 八、已知风险

1. **门槛可能被计时噪声淹没**（09R `:473` 未决风险 #4）。应对是 R1-AD 的固定协议
   加**按族分别上报**——族间方向相反时必须解释，不允许只报一个总数掩盖失败的那一族。
2. **选题偏差**：R1-G 已明说四族各自放大不同机型的差异，"只覆盖其中一族就宣布 +10%
   不构成通过门槛的证据"。
3. **未降低的 kind 会让编码体积无程序可测**（见第二节第 6 条）。
4. **冻结之后的返工成本极高**：指令集、ABI、编码任何一项事后改动，本轮全部数字作废。
   所以第二节的入场条件是硬前置，不是建议。

---

## 九、退出条件

以 12-tests 的原文为准（六条）。落地时逐条核对，其中三条最容易做假：

- **第 4 条**：四份报告齐全**且按族分别上报**——"有报告"不等于"按族"。
- **第 5 条**：主候选未过门槛时必须**依据报告**选，不允许拍板。
- **第 6 条**：Windows 完成、Linux/macOS 记为待复现，**未复现前不得宣称已验证**。

## 十、不负责

- **不启动 B0**（生产字节码模型与验证器）：那要等冻结结果，且 R1-AB 禁止研究编码冒充公开格式。
- **不实现正式 `.xiaoc` 容器**：归 14/16 阶段。
- **不做 LLVM 原生对照**：R1-AC 的基线是**同机栈式原型**，不是原生构建（见第七节的冲突项）。
- **不把 WSL / 容器数字并入验收**。
