## 三、必须先冻结的 6 条

### 3.1 `import` 的预期运行时语义（**已查明**）

**结论：当前丢弃 `Import` 是未实现，不是静态链接设计。**
`docs/UseDocs/language/modules/imports.md`「位置与加载边界」已经规定：
执行到导入语句时才初始化目标模块，单次运行内只初始化一次；05-B 只承诺静态发现。

已用隔离项目在 `xiao-driver` 的真实 `run` 链路实测：`main.xiao` 只有
`import helper`，`helper.xiao` 顶层写 `raise 1`，结果仍**成功**；
改为 `import helper` 后引用 `helper.answer`，得到 `X02-TYPE-001`（名称未定义），
而不是模块初始化或成员诊断。也就是说，**多模块项目当前不能跑通**。

调用链核对：`FrontendCompiler::compile` 调用 `analyze_project`，仅把结果的
诊断加入前端；`xiao-ir::lower_program` 将项目模块写入 `IrProgram.modules`，
但该路径使用空类型结果降低模块 AST；`xiao-bytecode::lower_program` 不读取
`modules`，`lower/stmt.rs` 丢弃 `Import`；类型检查对 `Statement::Import` 不绑定名称，
VM 没有项目模块运行表。**没有将多个模块拼为可执行编译单元**。

因此项目内导入另有待补的运行时债：执行到 `import` 时初始化模块，
但**环境包根 `pkg.foo` 无需写 `import`**，按 §3.5 走另一套触发和缓存键；
不能通过仅补一条 `Import` 指令代替包命名空间加载。两者的实现与验收分开登记。

以下是查明前的判断框架，保留作为后续审计依据：

现状是 `import` 在 bytecode lowering 里**落进空分支**（`lower/stmt.rs:119`）。
但这**未必是缺陷**，取决于模块系统的设计：

| 若模块是**全量静态链接**（像 C 的静态库） | 若模块是**运行时按需加载** |
| --- | --- |
| `import` 只影响**编译期符号可见性**，**不需要运行时指令** | `import` **必须**产生加载指令 |
| 那么"空分支"是**设计**，不是缺口 | 那么它是**缺口** |

**必须先回答**：

1. **`xiao run` 跑一个**用了 `import` 的多模块项目**，现在是什么行为？**
   —— 能跑通（说明是静态链接）、还是静默丢失符号（说明是缺口）？
2. **05-B 的 `ProjectModuleResult` 是怎么被消费的？**
   —— 它有没有把多模块拼成一个编译单元？
3. **`11b:71` 的"无需书写 `import`"是否意味着包引用走的是另一条路？**
   —— 注意它说的是**包**（来自环境），不是**项目内模块**（`import a.b`）。

**⚠️ 查清后要把结论写进文档**，无论结论是"要修 lowering"还是"丢弃是设计"。
**不要在没有结论的情况下顺手改了 lowering**——那可能破坏一个本来正确的设计。

### 3.2 「至多初始化一次」的作用域：**单次 VM 内**（跨请求归 I4b）

I4a §3.5 已查明：**同一个核心进程内连续两次 `run`，不共享 VM、模块表或已初始化状态**
（`xiao-driver::run` 每次新建 `FrontendVmDriver`，`xiao-vm::run_request` 每次新建 `Vm`）。

**冻结**：

- **本批保证的是「单次 VM 内至多初始化一次」**——同一份源码在一次 `run` 里
  反复引用同一个包模块，模块的顶层初始化**只跑一次**；
- **跨 `run` 的保持归 I4b**（需要长驻 VM，那是会话前置）；
- **⚠️ 不要把这条写成「REPL 会话内至多初始化一次」**——`11b:71` 的措辞是
  「一个 REPL **运行实例**」，而当前每次 `run` 就是一个新实例。
  **如实写「单次运行内」，并在 I4b 交付前不要声称会话级语义。**

### 3.3 加载的触发点：**在 VM 内，不在协议层**

I4a §3.2 已冻结：**"运行时加载"不是新请求，而是 `run` 内部的行为**；
协议层只提供**元数据查询**这一个新读取入口。

**本批沿用**：

- **CLI 不得先调"加载"再调 `run`**——那会把加载时机暴露给 CLI，
  与「首次真正引用时才加载」不符，也让"至多一次"失去落脚点；
- **触发点是「首次真正引用包中内容」**——不是 `run` 开始时把包全加载一遍；
- **⚠️ 这也意味着**：**只读查询（I4a 已交付）永不触发加载**——
  那条边界（`12-tests:863`）不能因为本批而松动。

### 3.4 包模块的编译：**复用现有流水线，不另建**

包模块的源码要变成可执行的东西，**必须走与普通源码同一条路**：
词法 → 语法 → 类型 → IR → 字节码。**不得**为包模块另开一条简化路径。

**理由**（`00-decisions` 已冻结的精神）：**TypeScript 层不实现第二套 Xiao 语义**，
同理 **Rust 侧也不得有两套"怎么编译 Xiao"**。
包模块和用户源码在语言语义上**没有任何区别**——只是来源不同。

**⚠️ 具体含义**：

- 包模块的**诊断**要带**包名与来源环境**（`12-tests:865` 第 4 条的要求），
  但**诊断码本身沿用现有的**，不新编一套；
- 包模块的执行**走同一个 VM**，不是独立解释器。

### 3.5 **区分「项目内模块」与「环境包」**（两种引用，别混）

这是本批最容易混淆的地方：

| | 项目内模块 | 环境包 |
| --- | --- | --- |
| 引用形式 | `import a.b`（05 阶段已冻结的语法） | `pkg.foo`（**无需 `import`**，`11b:71`） |
| 来源 | 项目目录里的 `.xiao` 文件 | `~/.xiao/envs/` 下的已安装包 |
| 发现方式 | 05-B 的文件系统discovery | 11A 的**只读环境包视图** |
| 谁做 | 05（静态已完成） | **本批** |

**⚠️ 冻结**：

- **包引用不经过 `import`**（`11b:71` 明说"无需先逐个书写 `import`"）——
  所以**包加载的触发不是"遇到 import 语句"**，而是**遇到对包命名空间的成员访问**；
- **但包模块内部**可能自己 `import` 同包的其他模块——那时走的是项目内模块那条路
  （取决于 §3.1 的查明结论）；
- **两套的来源不同、触发不同、缓存键不同**，**不要用一个"模块表"糊住两者**。

### 3.6 失败不缓存、诊断载荷（沿用 I4a 已冻结的）

I4a §3.1 已冻结：**首次加载失败不缓存，每次引用都重试**。

**本批要落地它**，并满足 `12-tests:865` 第 4 条：
**失败诊断必须含包名、来源环境、底层原因**，**且失败后会话仍可继续使用**。

**⚠️ "会话仍可继续"的具体含义**：一次加载失败**不得**让整个 `run` 崩溃或让 VM 进入
不可用状态——失败要作为**本次运行内可恢复的错误**上报，后续引用可以再试。

## 八、最可能翻车的地方

1. **没查明 `import` 的设计意图就改 lowering**（§3.1）——可能破坏一个本来正确的静态链接设计。
2. **把「单次运行内」说成「会话内」**（§3.2）——夸大会话级语义，I4b 交付前就是假的。
3. **让只读查询触发了加载**（§3.3）——I4a 的探针会红，且用户只是枚举包就会执行代码。
4. **为包模块另写一条编译路径**（§3.4）——本仓头号病史的 Rust 版。
5. **项目内模块与环境包共用一张模块表**（§3.5）——两套的来源与缓存键都不同。
6. **加载失败让 VM 不可继续**（§3.6）——违反 `12-tests:865`。
7. **顺手做了跨请求状态**（§2.3）——那是 I4b 的会话前置，混进来会让本批无法验收。
8. **把 `import` 的缺失当成包加载的充分解释**——两者相关但不同（§3.5 的表格）。

## 九、验收

1. **查明结论**：§3.1 有明确结论并写进文档；**若结论是"不用改"，要说明为什么**
   （§七 第 1 步）。
2. **静态成立**：`pkg.foo` 形式的引用在**类型检查层**能成立，且**不执行**任何包代码
   （与 I4a 的探针一并保持绿）。
3. **首次引用才加载**：未引用时不加载；引用后才加载（`12-tests:864`）。
4. **至多初始化一次**：**同一份源码在一次 `run` 内**反复引用同一包模块，
   顶层初始化只执行一次——**有可观察的探针**（计数或副作用），不是靠推断。
5. **失败重试**：首次失败不缓存，再次引用会重试；诊断含**包名、来源环境、底层原因**；
   **失败后同一次运行仍可继续**（`12-tests:865`）。
6. **边界不松动**：I4a 的只读查询探针**仍然不执行**任何包模块。
7. **不回归**：11B 前序批次与 05/09 的既有用例保持绿。
8. **门禁全绿**，含 `cargo test` 与协议规格向量。
