### 2.2 **K2 的修法：断言必须能分辨「选了」和「没选」**

一条断言如果两种行为下取值相同，就不是测试，只是装饰。10P 的教训是「豁免会吞掉差异」，
K2 是同一类问题的另一半：**断言本身没有分辨力**。

**冻结**：

1. 范围、开区间、随机三类用例，断言改成**对整段选择结果做聚合**（例如把结果逐元素累加后打印），
   而不是只取一个下标。`for` 循环与算术在现有用例里已经可用（见 `function-dynamic-condition`）；
   具体写法由实现 Agent 验证可行性，**不得**因为「静态类型层会拦」就退回单下标；
2. 修改后必须用**变异验证**：把对应分支改回返回源值，该用例**必须变红**。这是 K2 的验收方式，
   与 10P 对 J1 的要求相同；
3. `selector-all-downstream`（`values[=]`）在**值**这一维上不可能区分——选全等于源数组。
   这条不要硬造断言；应在用例旁写明它只覆盖释放路径，值维度由别的用例负责；
4. 若某类选择器确实找不到有分辨力的可观察量，就**登记为覆盖缺口并说明**，不要留一条假装在测的用例。

### 2.3 **K3 的修法：失败要带证据，且不因豁免存在而沉默**

**冻结**：

- 释放序列不一致时，失败信息必须包含两条序列（或它们的差异摘要），恢复 10P 之前的可诊断性；
- 被豁免的差异仍以「未覆盖」打印并附原因，这条保持不变；
- 失败信息里要能看出**是哪一路与哪一路**不一致，沿用既有的点名格式；
- 这条不写测试，靠实施记录里的实际失败输出为证（变异验证时顺带截取）。

### 2.4 **K4 与 I6：按路径做一次释放账目核对，不要逐条打补丁**

两处差异方向相反：选择器路径**多**一次释放，嵌套 `finally` 路径**少**一次释放。
逐条改容易互相掩盖，也说不清哪一侧是基准。

**冻结**：

1. 先定义**可比较的口径**：同一个程序在同一作用域下的释放事件数、对象数、销毁时机。
   现有 `XIAO_RUNTIME_RELEASE_TRACE_PATH` 的轨迹是可比的基础，但要写明它只记录释放、不记录引用；
2. 对三条路径各取一组最小用例（选择器范围、容器构造与释放、嵌套 `finally`），
   分别给出 VM 与原生的事件数、对象数与销毁位置，做成表；
3. 用**对照实验**定位多余/缺失的那一次：例如对同一源码打开与关闭对应的运行时检查，
   看事件数是否随之变化，以确认它是否由检查路径（`emit_selector` 里的 `selector_dynamic_check`）
   的借用转换产生——这是 J2 记录给出的线索，但**尚缺具体到调用的证据**；
4. 判定每一处差异是**真失衡**（重复释放/漏释放，需要修）还是**追踪口径**（事件数不同但引用平衡、
   无提前销毁，只需登记并说明为什么 VM 那侧是基准）；
5. I6 按 10N 已记录的判据处理：VM 侧 `r2_stack.rs` 断言两个作用域各释放一次，判定 VM 正确、原生少释放，
   因此它属于**真失衡**，要修；
6. 核对结论与数据表写进实施记录，**不得**只写结论不写数据。

## 六、最可能翻车的地方

1. **把聚合断言写成「长度」**——长度同样是弱断言，元素值错、长度对的情况照样漏；
2. **只对 range 做变异验证**，忘了新改的开区间与随机（K2 的两个薄弱点正在其中）；
3. **为 `All` 硬造一个区分的断言**，把用例写成假的；
4. **释放核对只看总事件数**，不看对象数与销毁位置——那分不出「多一次释放」和「提前销毁」；
5. **把两条方向相反的差异一起改**，互相掩盖（10P 已明令分开）；
6. **只写结论不写数据表**；
7. **I6 又被跳过**，或跳过时不写原因；
8. **恢复失败信息时把豁免的打印一起删掉**，让已知缺口变成噪音；
9. **只看 `cargo test` 就宣布门禁全绿**（`bun run check` 不在其中）；
10. **提交没写正文 / 没单独跑 clippy**。

## 九、释放审计原始数据（2026-10-07，修复 I6 前）

受控 Windows x86_64-pc-windows-msvc，基于 0b98371。轨迹格式为 sequence:object_id:action；只记录释放和销毁，不记录 retain，不能仅凭总数证明引用平衡。对象编号仅在一次执行内可比，销毁位置从 0 起算。下表使用 K2 聚合后的范围用例。

| 路径 | VM 事件数 / 对象数 / 销毁位置 | 原生事件数 / 对象数 / 销毁位置 |
| --- | --- | --- |
| held-array [1,2] | 2 / 1 / 1:对象1 | 2 / 1 / 1:对象1 |
| selector-range-downstream 聚合 | 10 / 2 / 7:对象2、9:对象1 | 13 / 2 / 10:对象2、12:对象1 |
| 同一范围源码，仅临时关闭 selector_bounds ABI 检查 | 10 / 2 / 7:对象2、9:对象1 | 12 / 2 / 9:对象2、11:对象1 |
| nested-finally-drops | 6 / 3 / 1:对象3、3:对象2、5:对象1 | 4 / 2 / 1:对象1、3:对象2 |

对照实验只删除 emit_selector 中一次 xiao_runtime_dynamic_check 调用，范围原生源对象 strong_release 从四次变成三次，总事件减少一条；实验后恢复检查。该 ABI 的 value_to_runtime → expect_strong → clone_strong 增加一个拥有引用，函数返回时 RuntimeValue 析构归还同一个引用，因此不是对源槽的重复释放。聚合循环另有两条释放事件差异，不能把 13 对 10 全归因于选择器检查。VM 仍是冻结语义基准；原生 ABI 适配产生的临时引用事件暂按 drops 字段登记。

I6 轨迹更正：原生少的是整个外层 finally 对象的构造和销毁，且先销毁对象1后销毁对象2。代码中函数 return 直接跳 xiao.fn.return，绕过 cleanup_stack；函数生成器也未建立 value_slots，无法消费作用域释放计划。所以这不是单纯追踪口径问题，需要恢复 finally 执行及清理顺序。
