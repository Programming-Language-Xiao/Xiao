# 20. 内置函数与标准库：方向与待决（**讨论稿**）

> **这是讨论稿，不是实现交接。** 请以讨论姿态读：定方向、否掉不成立的判断、
> 补上没看到的风险。文中标「待决」的地方**没有被冻结**，不要当成既有约束引用。
>
> **先说一个事实**：当前路线图（01–19）**没有标准库阶段**。本文编号取 20 是暂定的——
> 标准库该不该单独立项、挂在哪个阶段之后、由谁消费，是本文要讨论的第一个问题。

## 审核结论与待落实清单（**本文正文尚未按此改写**）

一轮对抗式审核已给出结论。**正文保持原样作为问题证据**，下面列出要落实的改动——
落实者按此清单改写正文，不要只删不改。

### 已核实的两处**事实错误**（本文正文写反了，必须改）

1. **`RuntimeValue` 不在 09R3 的冻结清单里。** 清单在 `09r-bytecode-machine-research.md:629-630`
   （审核给的行号 `:618` 已因文件被改而过期），冻结的是**机型、寄存器类别与分配策略、
   函数调用 ABI、异常/清理转移 ABI、指令编码与版本字段、源码映射格式、性能阈值**七项，
   **没有 `RuntimeValue` 枚举**。因此正文第四节与第七节第 3 问里"`os` 必须抢在 R3 前完成"
   的推论**不成立**——正确的问法是：**资源设计是否影响那七项契约中的任何一项**。
2. **`is_hashable` 是排除名单，新变体默认会被允许哈希。**
   `xiao-runtime/src/containers/mod.rs:36` 是
   `!matches!(value, Table | Array | Tuple | DictTable | DictColumn | Set | Error)`——
   新加的 `Resource` 变体**不会自动不可哈希，反而会自动可哈希**。正文第四节写反了。
   首版禁止资源哈希仍然合理，但**必须显式实现并测试**；而且"资源天然不可哈希"不是必然——
   按稳定对象身份哈希在设计上可行，要不要禁是**策略选择**，不是事实推论。

### 要重写的分类（正文第一、二节互相矛盾）

正文第一节说"能纯 Xiao 写的都走普通包"，第二节说"其余标准库用 Xiao 写、随语言分发"——
**两句不能同时成立**。改成两个**独立维度**：

| 决定什么 | 判断依据 |
| --- | --- |
| 用 Xiao 还是 Rust **实现** | 是否需要宿主能力或运行时内部操作；以及**有证据**的性能要求 |
| 属于**标准库**还是普通包 | 是否由工具链直接提供、是否承诺统一基础接口与兼容性 |

**推论（已确认）**：纯 Xiao 实现的库**完全可以是标准库**——路径词法处理、格式化不必因为
"能用 Xiao 写"就退出标准库。同理，`print` 的底层输出需要 Rust，**不代表整个格式化与打印
接口都要成为底层原语**；**共享 Xiao 源码也是共享语义**，不必把所有共享都理解成
"调用同一个 Rust 函数"。

### 已确认的方向（用户裁决）

**纯 Xiao 编写的基础库也随工具链提供，并享有标准库的兼容性承诺。** 理由不是便利，而是
不这样就会把「标准库」的定义与**实现语言**重新绑死；而且 `.xar` 不携带标准库、
需要校验其依赖的标准库接口兼容性（见末条），**这个前提不成立时那条校验没有对象**。

### 要补进设计的内容

1. **存量盘点，不是只管新增**：`input`、`print`、`random.seed` **已经是按名字特判**的——
   `xiao-types/src/checker.rs:1304`、`:1309`（`simple_callee_name(callee) == Some("input"|"print")`）
   与 `xiao-bytecode/src/research/lower/expr.rs:569`（`is_random_seed_call`）。
   审核担心的"表建了但执行仍按名字特判"**在仓内已经发生**。新设计必须逐条裁定
   哪些迁移进表、哪些**保留为语言操作**。
2. **声明表不能只有签名**。还要覆盖：参数是借用/保留/转移所有权、返回值归谁、
   是否产生外部副作用/修改状态/分配对象/抛错、所需能力及版本兼容要求。
   否则签名同源但**优化器可能错误删除调用、后端可能错误释放参数**。
3. **独立契约 crate（暂名 `xiao-intrinsics`）**：只存稳定编号、后端无关签名与绑定标识，
   **不存 Runtime 函数指针**、不依赖 VM/LLVM/平台实现。理由是**依赖方向**——
   Runtime 已依赖类型层，把表放进 Runtime 再让类型层引用会**形成依赖环**。
   LLVM 侧应经**稳定 ABI 包装**调用共享实现，不能直接暴露 Rust 内部枚举与 `Result` 布局。
4. **稳定 id 的理由要换**：审核指出"名字会本地化"**不是依据**（`00-decisions:414` 明确不翻译
   源码标识符）。保留该规则，但理由改为：**id 会出现在编译产物里，其稳定性与 opcode 编号同源**
   ——"只能追加、不得重排"。
5. **`Resource` 变体统一承载，但语言层不抹平资源种类**：文件/目录游标/进程句柄仍须区分，
   不能互相传参。同时规定：复制句柄是共享同一资源还是复制 OS 资源；显式关闭后其他别名
   如何报错；显式关闭与最后一次释放如何避免重复关闭；清理失败如何进入既有错误链；
   **活句柄不得写入字节码常量池或归档**。
6. **性能例外要有证据**：不冻结"能用 Xiao 写就绝不能下沉"。例外必须提供明确语义、
   可复现收益、双后端一致性验证，以及**为什么普通编译优化不足**。
   "几十个以内"是**规模预算不是硬上限**——卡得太死会催生一个接收操作码与动态参数的
   **万能入口**，数量少了契约反而更差。
7. **权限策略与沙箱承诺分开**：首版按普通本机程序运行、权限不超过启动进程，并**明确说明
   `.xar` 是可执行程序、完整性校验不代表可信或安全**。但应从第一批外部能力起就走一个
   **统一、可测试的能力上下文**，将来受限模式才能在**实际操作处**执行检查。
   另：`11A` 禁止安装脚本（`11a-environments-and-packages.md:171`）**推不出**"普通包禁止平台
   适配代码"——安装时执行代码、运行时使用平台能力、未来受控原生扩展是**三个不同问题**。
8. **补一条分发契约**：`.xar` 不携带标准库，因此必须**校验它依赖的标准库接口是否兼容**，
   不能仅凭 Runtime ABI 相容就认定可运行。

### 验收（防"看起来完成"）

最需要防的不是"没有表"，而是**表存在、类型层用了，VM 仍按名字特判、原生侧另写签名、
权限检查也没经过共享入口**。至少包含：

- 改动声明后，**类型检查与执行绑定必须同步响应**，不能继续走旧特判；
- 未知编号、不兼容签名、缺失绑定必须**明确拒绝**；
- 用**可观察输出、状态变化与错误**证明调用确实发生——不能只检查返回类型；
- 资源在正常退出、可恢复异常和显式关闭后释放正确且**不重复**；
- **能力被拒绝时，实际外部操作没有发生**。

**LLVM 尚未实现这些路径时，只能标记字节码侧完成，不能提前宣称双模一致。**

## 一、先把三件事分开

它们的分发与版本化方式完全不同，混在一起谈会把决定做歪：

| | 例子 | 谁实现 | 版本化 |
| --- | --- | --- | --- |
| **intrinsic** | 语言做不到的事：I/O、时间、系统调用、内存原语 | Rust | **随语言版本走** |
| **内置库** | `os` 这类需要平台适配的 | Rust + Xiao 混合 | **随语言版本走** |
| **普通包** | 能纯 Xiao 写的一切 | Xiao | 走 [11A](11a-environments-and-packages.md) 的包管理，独立版本化 |

**划分规则**：**需要语言或运行时新增能力的 → 内置；能纯 Xiao 写出来的 → 包**。
这条比"看重要性"好，因为它是**可判定**的——「这个函数能不能今天就用手上的语言写出来」
是个不需要争论的问题。

## 二、决定性判断：用 Xiao 写还是 Rust 写

**建议：混合，但用一个硬约束锁死。**

- **极小的一组 intrinsic 用 Rust 实现**——连 `print` 都写不出纯 Xiao 版本，底层 I/O 逃不掉；
- **其余标准库用 Xiao 写**，随语言分发；
- **两个后端共享同一份 runtime 与同一张 intrinsic 表**。

第三条是关键，而且它不是我的发明——仓内已有一条冻结项：

> 两条执行路径必须共享同一套类型化语义、诊断和生命周期约束，**而不是在 CLI 或后端
> 各自复制一份语言规则**

**内置函数是这条最容易破的地方。** 同一个 `os.path.join` 在字节码路径和 LLVM 路径各实现
一次，是最自然的写法，也是最糟的。正确形态：VM 调用 Rust 函数，LLVM 后端**调用同一个**
Rust 函数，而不是重写一遍。

用 Xiao 写标准库还有一个附带价值：**它成为语言能力的活体测试**。标准库跑不动，
说明语言本身有洞——这比写测试更早暴露问题。

## 三、必须现在定的：intrinsic 的单一来源表

这一条是全文里**唯一「现在不做、以后贵」**的——事后改要动所有已实现的内置函数。

内置函数必须有**一张单一来源的表**，至少给出：

- 稳定的 **id**（**不是名字**——名字会改、会本地化）；
- 参数与返回类型；
- 它在两侧的绑定。

然后三处从同一份声明派生：

```text
一份声明  →  类型层：签名检查
          →  VM：id → 函数分派
          →  LLVM 后端：生成 extern 声明
```

**仓内有现成范式可照抄**：`ERROR_TYPE_NAMES` 是错误类型名的单一来源，`error_kind_of`
从它派生，类型层与运行时都经它消费。内置函数表照这个来。

**不这么做的后果是注定的**：类型层的签名与运行时的行为分两处写，然后漂移。
这正是本仓登记在案的**头号病史**，而近期已经复发过两次（`Declaration.end_line` 死字段、
`Subset`/`ProperSubset` 标签差点对调）。

## 四、`os` 类库的真问题：外部资源句柄

`os` 不是"多几个函数"，它引入**语言现在没有的一类值**：文件句柄、目录游标、进程句柄。
它们既不是标量也不是容器，而 06 阶段已经冻结了**确定性释放**（引用计数 + 释放计划）。
于是必须回答两件事：

1. **外部句柄要不要是 `RuntimeValue` 的变体？** 如果要，它必须定义
   `PartialEq` / `Hash` / `is_hashable` / `type_name` / 编码 / 两个后端的表示。
   （一处顺带的一致性：仓内刚冻结「集合元素必须可哈希」，而外部句柄显然不可哈希，
   所以它会自动落在拒绝那一侧——这是**对的**，但要说清是刻意的。）

   > **⚠ 这句写反了，见上方「已核实的两处事实错误」第 2 条**：`is_hashable` 是**排除名单**，
   > 新变体默认**会被允许**哈希。"自动落在拒绝那一侧"不成立，必须**显式实现并测试**。

2. **不要每加一个库就加一个变体。** 建议**统一走一个「外部资源句柄」变体**，
   库只提供种类标签与析构行为。否则 `os`、`socket`、`proc` 各来一个，
   `RuntimeValue` 会持续膨胀——而它正是 09R3 要**冻结**的东西。

   > **⚠ 这句也不成立，见上方第 1 条**：09R3 冻结的七项里**没有 `RuntimeValue`**。
   > 正确的约束是"资源设计不得影响那七项契约"，不是"必须抢在 R3 之前"。

`os` 还另有三处特有的：

- **平台差异**：仓内已有平台顺序（Windows → Linux → macOS），`os` 是第一个真正考验它的库；
- **能力边界**：语言是否允许任意文件系统访问？`.xar` 双击启动（17 阶段）分发出去的程序
  是别人给的，`os` 的权限模型必须在那之前想清楚；
- **两个路径一致**：分发的是字节码/原生产物，`os` 的能力在两侧必须完全相同。

## 五、增量流程

不建议一次铺开标准库。每个内置函数走同一条流水线：

1. 往**那张表**里加一条声明（id、签名、绑定）；
2. 三处消费它（类型层 / VM / LLVM 后端）；
3. 补**区分度用例**——撤掉实现必须失败，照 [09R2D](09r2d-machines-and-encoder.md) 的规矩；
4. **纯 Xiao 能写的，就不要写成 intrinsic**。

**规模纪律**：intrinsic 应保持在**几十个以内**。如果某个函数的理由是"用 Xiao 写太慢"，
那应该先去优化语言，而不是把它变成 intrinsic。

## 六、与包管理的关系

- **内置库不独立版本化**：`os` 的错误类型与资源释放语义和语言语义紧耦合，
  独立版本化会造出「语言 1.2 + os 0.9」这种无从测试的组合；
- 能纯 Xiao 写的库走包管理、独立版本化；
- 这也让 [11A](11a-environments-and-packages.md) 那条「**禁止包提供或执行安装前后脚本**」
  有了明确边界：**内置库可以有平台适配代码，普通包不行**。

## 七、请讨论并定下方向的问题

1. **标准库该不该单独立项？** 当前路线图 01–19 里没有它。是插入为独立阶段，
   还是并入 11（CLI 与平台）？它的**前置**是什么（09 跑完？10 的 LLVM 后端？）——
   注意第三条里那张 intrinsic 表**最好在第一个内置函数之前定**，而那可能早于 11。
2. **第三节那张表放在哪个 crate？** 它要被类型层、`xiao-bytecode` 与 LLVM 后端同时消费，
   而仓内对依赖方向有硬约束（`00-decisions` 的架构耦合硬约束）。
   放在最底层还是单独一个 crate，需要给出理由。
3. **外部资源句柄**：统一一个变体是否成立？如果不成立，替代方案是什么，
   以及它如何在 09R3 冻结 `RuntimeValue` 之前落地？
4. **intrinsic 与「语言做不到的事」的边界**：有没有**能纯 Xiao 写、但性能上必须下沉**
   的例子？如果有，它是否构成对"可判定规则"的反例？
5. **`os` 的能力模型**：首版是否默认全开？`.xar` 分发场景下有没有受限模式的需求？
   这一条可能反过来影响 17 阶段的设计。
6. **总体**：本文哪一条判断**最可能在实现时被绕过**（"看起来生效、实际没有"）？
   那一条是否需要一条区分度验证？
