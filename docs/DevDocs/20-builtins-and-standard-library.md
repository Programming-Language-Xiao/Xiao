# 20. 内置函数与标准库：边界、契约与实施路线

> **状态：方向稿。** 本文把审核后的方向写成可交接的工程约束；标为“待冻结”的内容
> 仍需要在对应阶段通过实现和测试冻结。本文不是标准库 API 清单，也不替代 09、10、
> 11A、14 和 17 阶段的具体格式契约。
>
> 本文编号暂为 20。它是一条跨阶段工作线：底层调用契约要在第一个生产内置函数前
> 定好，标准库和平台能力则按各自的前置条件逐步接入。

## 一、先分两个维度

“用什么写”和“由谁分发”不是同一个问题。把它们混成一条规则，会把纯 Xiao 实现的
官方库错误地排除在标准库之外，也会把平台能力误认为必须独立发包。

### 1. 实现方式

| 类别 | 判定 | 典型例子 | 允许的实现 |
| --- | --- | --- | --- |
| **宿主能力 intrinsic** | 需要操作系统、时钟、外部句柄、进程或 Runtime 内部原语 | 文件打开、时间读取、进程启动、输出 | Rust Runtime/平台层 |
| **Runtime 原语** | 语言表面可以调用，但必须由 Runtime 保证对象、错误或所有权语义 | 资源句柄创建、显式关闭、错误构造 | Rust Runtime，并经统一 ABI 暴露 |
| **普通 Xiao 实现** | 只使用已经存在的语言能力和官方接口即可表达 | 路径组合、文本格式化、简单集合工具 | Xiao |
| **优化替换** | 语义可用 Xiao 表达，但后端有证据表明需要专门优化 | 批量搜索、向量化循环 | 仍是 Xiao API；后端可选择优化实现 |

默认规则是“没有宿主/Runtime 必要性，就先用 Xiao 写”。仅仅“现在比较慢”不能直接
制造一个 intrinsic；需要可复现的收益、明确的语义边界和两种执行路径的差分用例。
优化替换是实现策略，不应让公开 API 退化成一批无法检查的宿主入口。

### 2. 分发与版本化

| 类别 | 由谁提供 | 版本化方式 | 是否进入普通依赖求解 |
| --- | --- | --- | --- |
| **官方标准库** | 随 Xiao 工具链/Runtime 提供；可以由 Rust、Xiao 或两者组成 | 随语言/Runtime 兼容契约走 | 否 |
| **普通包** | 项目或包源提供 | 按 [11A](11a-environments-and-packages.md) 独立版本化 | 是 |
| **平台扩展包** | 只有在未来受控原生扩展契约冻结后才允许 | 版本、目标平台和 ABI 一起锁定 | 是，但不允许安装脚本 |

因此，**纯 Xiao 写的库也可以是官方标准库**。它是否为标准库，取决于是否由工具链
直接提供、是否承诺统一的基础接口，而不是取决于是否用了 Rust。标准库不参与普通包的
跨源选择和版本求解，但必须有可验证的标准库接口/ABI 身份，供构建产物和 `.xar` 启动器
检查兼容性。

普通包可以用 Xiao 代码调用官方平台接口，但“运行时能访问平台能力”和“安装时执行
任意脚本”是两件事。11A 继续禁止安装前、安装后和卸载脚本；原生扩展若未来开放，必须
另有声明式构建、隔离进程、权限边界和可复现输入契约。

## 二、总体方向

### 2.1 Rust 只承载不可替代的底层能力

首批 intrinsic 保持很小，主要覆盖：

- 标准输入、标准输出和错误输出；
- 单调时间/墙上时间等需要宿主时钟的操作；
- 文件、目录和进程等外部资源的创建与操作；
- Runtime 自身必须掌握的分配、资源释放和结构化错误边界。

格式化、路径字符串处理、常见集合算法和其他可由 Xiao 表达的功能，优先放在官方
标准库的 Xiao 源码中。标准库源码同时是语言的长期集成测试：如果官方库只能靠大量
特殊编译器分支才能运行，说明语言或 Runtime 契约仍有缺口。

### 2.2 两条执行路径共享语义，不强求共享 Rust 函数指针

字节码 VM 和 LLVM 原生后端必须共享同一套：

- intrinsic 身份与签名；
- 参数所有权、返回值所有权和确定性释放规则；
- 副作用、能力需求和可恢复错误；
- 诊断编号、消息身份和源码位置边界。

VM 可以直接调用 Rust Runtime 的内部实现。LLVM 生成代码则调用稳定的 Runtime ABI 包装
层，由包装层完成宿主布局转换、错误传播和资源生命周期管理。不能要求 LLVM 直接依赖
Rust 私有枚举、函数指针或 `Result` 的内存布局，也不能在 LLVM 后端另写一套同名实现。

“共享实现”的可验证含义是共享语义内核和 ABI 契约；若平台适配必须分支，分支只能位于
平台层，不能改变 Xiao 可观察结果。

### 2.3 现有特殊入口必须纳入迁移清单

仓内已经存在若干内置入口的特判，不能只约束未来新增 API：

- `xiao-types` 对 `print`、`input` 和标量转换有专门检查；
- `random.seed` 在类型检查和字节码降低中有专门路径；
- `set` 构造、错误构造和集合/选择器运行时检查也有各自的识别逻辑。

20A 的第一项工作不是再添加一张平行表，而是盘点这些入口，把能迁移的调用统一降低
为稳定 `IntrinsicId`，把仍属于语言语法或类型构造的入口明确登记为“非 intrinsic”。

## 三、intrinsic 契约的单一来源

这是第一个生产内置函数之前必须完成的基础工作。研究 VM 可以暂时保留已有的实验性
特判，但生产字节码和 LLVM 不能继续按名称各自维护规则。

### 3.1 契约 crate

方向上采用独立的契约 crate，名称暂定为 `xiao-intrinsics`。它必须位于类型、字节码、
Runtime、VM、LLVM 和平台实现的共同下层，只保存后端无关的声明，不依赖这些实现层。
精确 crate 名称和目录登记在 A0/09-B0 接线时冻结。

该 crate **不能**保存 Rust 函数指针、`RuntimeValue`、平台句柄或 LLVM 类型。参数和返回
值使用自己的可版本化类型描述，类型层再把它适配为 `xiao-types::Type`。这样既不会让
类型层反向依赖 Runtime，也不会因为 Runtime 当前的枚举布局而锁死公开契约。

### 3.2 每条声明至少包含

```text
IntrinsicDecl {
    id:            稳定数字身份（废弃后不复用）
    public_name:   源码可见的限定名称（不作为机器身份）
    signature:     参数、关键字规则、返回类型
    ownership:     借用、保留、转移和返回值释放关系
    effects:       读写外部状态、分配、阻塞、随机性等效果
    capability:    所需宿主能力
    errors:        可恢复错误类别与稳定错误身份
    vm_binding:    VM 分派键
    abi_binding:   Runtime ABI 符号/版本键
    target:        平台、架构和 Runtime ABI 约束
}
```

源码名称可以增加别名或调整命名，但稳定 `id` 不因改名、本地化或模块重组而改变。现有
决策明确不翻译源码标识符、包名和路径；“使用数字身份”是为了避免机器格式把名称当成
长期 ABI，不是因为源码名称会随界面语言改变。

### 3.3 从一份声明派生的消费者

```text
一份声明
    ├─ 类型层：注册签名、关键字规则、效果和能力检查
    ├─ IR/降低：生成 IntrinsicId，而不是再次解析名称
    ├─ 字节码：编码 id、参数传递和校验元数据
    ├─ VM：id → 运行时分派表
    └─ LLVM：id → 稳定 Runtime ABI 声明与调用约定
```

生成或校验步骤必须拒绝：重复 id、已占用 id 的不同签名、缺少绑定、未声明能力、ABI
版本不兼容和类型层/运行时签名不一致。表存在但某个消费者仍按字符串特判，视为未完成。

### 3.4 版本规则

- `id` 一旦发布不得复用；删除的函数保留 tombstone 或明确的“不支持”记录。
- 签名、所有权、效果和错误边界发生破坏性变化时，提升语言/Runtime 或 intrinsic ABI
  兼容版本，不能只改函数名。
- 标准库的公开名称和模块布局可以在语言版本内演进，但构建产物必须记录所需的标准库
  接口/ABI 身份。
- 名称解析、翻译和诊断文本不参与机器分派；机器字段始终保存 `id`、`code`、
  `message_id` 和结构化参数。

## 四、统一外部资源句柄

`os` 类库的难点不是函数数量，而是它带来文件、目录游标、进程等语言此前没有的值。
这类值必须服从 06 阶段的引用计数、释放计划和错误展开，而不能成为一套绕过 Runtime
的宿主指针接口。

### 4.1 一个 Runtime 承载变体，多个语言可见种类

方向上采用一个统一的 `ExternalResource` Runtime 承载，内部带稳定的资源种类标签，
例如 `file`、`directory`、`process`。语言类型检查仍然区分种类，不能把文件句柄传给
只接受进程句柄的函数；统一承载只是避免每增加一个库就膨胀 `RuntimeValue` 枚举。

资源句柄的最低契约如下：

- 句柄是单线程 Runtime 对象，不能把宿主裸指针暴露给 Xiao 或跨 ABI 传递；
- 克隆句柄的语义是共享同一逻辑资源，不是隐式复制操作系统资源；
- 显式关闭与最后一个强引用释放必须幂等，重复关闭不能导致二次释放；
- 已关闭或已失效的别名访问必须返回稳定的运行时错误；
- 释放钩子产生的错误沿用主错误与 `suppressed` 规则，不能覆盖原始错误；
- 活句柄不能进入常量池、字节码常量、`.xiaoc` 或 `.xar` 对象索引；产物只保存调用、
  类型和能力要求。

具体的显式关闭 API、关闭后别名的错误身份和每种资源的复制/继承语义，在第一个资源
intrinsic 实现前冻结。

### 4.2 哈希、相等和编码必须显式处理

资源默认**不可作为集合元素或字典键**。这不是“新增变体自然就不可哈希”的推论：当前
`xiao-runtime` 的 `is_hashable` 使用排除式匹配，新变体若漏加分支反而可能被误判为可哈希。
实现时应改为正向允许标量/`none`，或至少为资源加入专门拒绝分支，并覆盖：

- `PartialEq`/`Eq` 的同一资源与不同资源行为；
- `Hash` 与语言层不可哈希规则的一致性；
- `type_name` 返回 `resource<kind>`，不能落入 `dynamic`；
- `scalar_type`、编码器、常量池和两个后端的表示；
- 释放后、失效后和错误路径的回归用例。

资源不可哈希是首版语言契约，不代表 Rust 层不能为内部表查找提供对象身份；内部身份
不得泄漏为用户可观察的集合/字典语义。

### 4.3 与 09R3 的关系

09R3 的冻结清单包括最终机型、寄存器类别、调用 ABI、异常/清理转移 ABI、指令编码、
源码映射和基准协议，**没有把 `RuntimeValue` 枚举本身列为冻结项**。因此，资源承载不必
为了“赶在 09R3 前”伪装完成；但在生产字节码模型、Runtime ABI 或首个资源 intrinsic
冻结前，必须完成影响这些契约的表示、调用和生命周期设计。

任何新增 RuntimeValue 变体都要检查仓内已记录的非穷尽匹配点，尤其是相等、哈希性和
类型名兜底；不能只依赖编译器为 `Hash` 或 `scalar_type` 报错。

## 五、`os` 与能力模型

### 5.1 首版运行边界

首版按普通本机程序的进程权限运行：调用者已经拥有的文件、网络和进程权限不再由 Xiao
另造一套操作系统沙箱。`.xar` 的摘要校验只能证明内容完整性，不能证明发布者可信，也
不能把不可信归档变成安全沙箱。

这不是放弃能力模型。Runtime 请求应携带规范化的能力上下文，至少能表达文件系统、
时钟、进程和网络等能力；首版默认上下文可以全开，但所有外部操作必须通过该上下文
进入。未来受限模式才有可靠的拦截点，且必须失败关闭、覆盖路径穿越/符号链接、进程
启动、网络和原生扩展等边界。

### 5.2 平台顺序和一致性

平台适配沿用 Windows → Linux → macOS。平台层负责路径、句柄、错误码和工具链差异；
语言核心、intrinsic id、错误身份、释放顺序和用户可观察结果不因平台改变。没有某平台
能力时应报告稳定的“能力不可用/目标不支持”错误，不静默改走另一种语义。

字节码、原生程序和 `.xar` 必须使用同一能力契约。当前 LLVM 后端仍处于接口准备阶段，
在它真正能调用 Runtime ABI 之前，只能声称字节码侧完成，不能声称 `os` 已实现双后端
一致性。

### 5.3 与包管理和 `.xar` 的边界

- 普通包不提供安装前后脚本；包代码能否调用某个能力由语言导入、intrinsic 声明和
  Runtime 能力上下文共同决定。
- 官方标准库不作为普通包参与 11A 的源选择和锁定，但 `.xar` 必须记录其所需的标准库
  接口/ABI 身份。启动时先验证已安装 Runtime 提供兼容标准库，再执行任何模块。
- `.xar` 仍不重复携带官方 Runtime/标准库对象；这与 [17](17-xar-archive.md) 的官方依赖
  边界一致。若未来引入标准库兼容层或迁移表，必须在归档索引中版本化记录。
- 完整性、来源信任、签名、撤销和沙箱仍属于 17 阶段的安全决策，不能由本文件提前
  宣称已解决。

## 六、增量实施和验收

不一次铺开整个标准库。每个新增 intrinsic 或官方库模块都走同一条流水线：

1. 在契约表中增加稳定 id、签名、所有权、效果、能力、错误和绑定；
2. 生成/更新类型层、IR、字节码、VM 和 LLVM ABI 的消费者；
3. 为 Xiao 实现的部分提供源码模块，并把它作为官方标准库的一部分发布；
4. 添加撤掉实现就会失败的区分度用例，禁止只测“能编译”；
5. 在 Windows、Linux、macOS 的适配矩阵中分别验证平台差异；
6. 更新对应 crate README、UseDocs、阶段索引和标准库兼容元数据。

### 6.1 必须有的测试族

- **表一致性**：id 唯一、名称别名不影响分派、签名/所有权/效果与绑定完全一致；
- **未知与不兼容**：未知 id、缺失绑定、能力不足、ABI 不兼容均在用户代码执行前拒绝；
- **双路径差分**：同一源码、同一输入和同一能力上下文在 VM 与 LLVM 结果、错误身份、
  释放顺序和诊断字段一致；LLVM 尚未可用时不能伪造通过；
- **资源生命周期**：正常返回、可恢复错误、未捕获错误、显式关闭、别名和重复关闭均
  不发生泄漏或二次释放；
- **容器边界**：资源不能进入集合、字典键、常量池、序列化对象或 `.xar`；类型名和错误
  参数不出现 `dynamic` 等兜底文本；
- **归档兼容**：标准库接口/ABI 不满足时，`.xar` 在执行用户模块前给出稳定诊断；
- **移除验证**：删除表项、VM 绑定或 ABI 包装中的任一环节，专门用例必须失败。

### 6.2 规模纪律

intrinsic 不是性能逃生通道。首版控制在小规模集合，重点是宿主能力、Runtime 原语和
无法由 Xiao 表达的语义；批量算法和格式化功能优先用 Xiao 实现，必要时由后端优化。若
intrinsic 数量持续增长，应先检查语言表达能力、优化器和 Runtime ABI，而不是继续把
普通库函数下沉。

## 七、阶段安排

20 不是替代 09–19 的单独大阶段，而是以下交付顺序：

| 子阶段 | 前置 | 交付 | 不提前承诺 |
| --- | --- | --- | --- |
| **20A 契约与盘点** | 现有类型/IR/研究 VM | 独立契约 crate 方案、现有特判清单、id/签名/效果/能力模型 | 不冻结完整标准库 API |
| **20B 最小生产入口** | 09-B0、Runtime ABI 基础 | `print`、`input`、错误/转换等最小入口迁移和表驱动分派 | 不声称 `os` 或 LLVM 全部完成 |
| **20C 官方 Xiao 库** | 10 原生 Runtime ABI、11A 包/环境边界 | 路径、文本、集合等官方 Xiao 模块及兼容元数据 | 不把官方库当普通可替换依赖 |
| **20D 平台资源** | Windows 平台适配稳定，资源句柄契约冻结 | 文件/目录/进程首批 API、能力上下文、三平台差分 | 不承诺沙箱或跨平台完全同构的系统细节 |
| **20E 归档接线** | 17 索引与启动验证 | `.xar` 的标准库兼容检查、资源能力目标约束和负例 | 不重复携带官方 Runtime/标准库 |

20A 的契约设计可以现在开始，但只有当它改变 09R3 的机型、调用 ABI、编码或源码映射
时，才会阻塞 09R3；否则研究路径可以继续使用已登记的实验性入口，并在进入 B0 前迁移。

## 八、仍待冻结的问题

以下问题不能被本文的方向性结论掩盖：

1. 契约 crate 的最终名称、声明格式和生成器；
2. `IntrinsicId` 的数值宽度、保留区间、tombstone 和 ABI 版本编码；
3. Runtime ABI 的稳定调用约定、错误返回布局和资源句柄跨模块边界；
4. 官方标准库的模块清单、接口兼容策略、源码/预编译对象的发布形式；
5. `ExternalResource` 的具体资源种类、显式关闭语义、继承/复制和跨调用边界规则；
6. 首批 `os` API、平台能力清单及缺失能力的稳定错误码；
7. `.xar` 的标准库兼容字段、签名/信任和未来受限模式的安全策略。

这些问题冻结后，必须同步更新 [12. 测试与开发里程碑](12-tests-and-milestones.md)、
[14. 字节码优化与 `.xiaoc` 产物](14-bytecode-optimization.md) 和 [17. `.xar` 字节码归档与启动](17-xar-archive.md)。
