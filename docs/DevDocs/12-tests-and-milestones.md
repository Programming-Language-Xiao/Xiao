# 12. 测试与开发里程碑

> 本阶段不是最后才做的测试收尾，而是每个前置阶段的退出门槛。没有双模式一致性测试，就不能宣称语言规划已经落地。

退出条件分为两类：当前阶段可以直接执行的单元/规格门槛，以及必须等待后置消费者出现的集成契约。前者未通过时不能进入下一实施阶段；后者必须登记并在对应的字节码、LLVM、CLI 或跨平台里程碑补跑，但不能形成“先完成后端，才能开始建设后端所需前端”的循环依赖。整个工具链宣称完成前，两类条件都必须通过。

## 一级工程目标：建立测试分层

### 单元测试

覆盖词法 Token、缩进、反引号标识符、路径与选择器解析、类型推断、数值运算和引用计数基础操作。单元测试应尽量不依赖操作系统。

### 规格测试

每条已确定语法至少有：

- 一个最小合法例子。
- 一个最小非法例子。
- 一个包含错误位置和错误编号的期望结果。

### 双模式一致性测试

同一源文件分别经过字节码和 LLVM 后端，比较标准输出、退出码、错误类别、容器顺序和 `drop` 记录。允许机器码优化改变性能，不允许改变语义。

### 跨平台测试

在 Windows、Linux、macOS 验证换行、路径、固定宽度数值、环境注入、原生链接、退出码和交互终端行为。涉及按键、粘贴、软换行与颜色的用例必须使用可控的伪终端或等价终端测试层，不能只测试普通标准输入管道。

## 一级工程目标：按真实规模拆分里程碑

这些里程碑表示依赖关系，不表示会话数或固定发布日期。每个里程碑都可能继续拆成很多设计、实现、测试和修复提交。尚未轮到的阶段只维护规范，不提前塞进当前实现。

### F0：工程骨架与源码位置

退出条件：

1. 编译器工程能够读取空文件和 UTF-8 源文件。
2. 源码游标稳定记录字节偏移、行号和列号。
3. `LF`、`CRLF` 和文件末尾行为都有单元测试。

### L0：最小 Token 流

退出条件：

1. 只需识别 ASCII 标识符、十进制整数、`=`、换行和文件结束。
2. `a = 1` 的 Token 种类、顺序和源码区间具有快照测试。
3. 非法字符能产生带位置的诊断，词法器不会死循环或崩溃。
4. 不要求 AST、类型检查、运行代码或集合支持。

### L1：基础词法扩展

退出条件：

1. 字符串、浮点、布尔值、关键字和运算符按独立增量加入。
2. 括号、数组路径和表头符号能稳定分词。
3. `+` 只产生统一 Token，不在词法阶段实现集合并集。
4. `~`、`?`、`!`、逗号和比较符号能组成后续选择器所需的稳定 Token 序列，但词法阶段不判断索引语义。

### L2：UTF-8、注释与缩进

退出条件：

1. 反引号 UTF-8 标识符和未闭合诊断可用。
2. 单行注释、文档注释、空行和缩进交互有规格测试。
3. `INDENT`、`DEDENT`、换行和文件结束序列稳定。

### P0：最小语法树

退出条件：

1. 只解析字面量、名称和简单赋值。
2. AST 节点复用词法阶段的源码区间。
3. 错误恢复不会改变后续合法 Token 的含义。

### P1：表达式、代码块与声明

退出条件：

1. 表达式优先级、控制流和缩进块逐项通过规格测试。
2. `def`、表头和入口声明形成稳定 AST。
3. 此时仍不要求执行程序。

### S0：名称与静态标量类型

退出条件：

1. 名称解析、作用域和基础类型槽可用。
2. 固定宽度数值、转换和溢出规则可检查。
3. 推断声明与 `int a = 1` 等显式声明都能建立锁定的静态类型槽。
4. 普通变量可接受同类型重赋值，不兼容换型在运行前被拒绝。
5. `bool +/- 整数` 对偶数保持、对奇数翻转且结果仍为 `bool`；反向、布尔与布尔、布尔与浮点数运算均有负例。
6. 字符串类型只接受正式关键字 `str`；`string` 不被悄悄当成同义类型关键字。
7. `value as bool` 与 `bool(value)` 共享转换结果和错误类别；已确认的 `str` 字符串有正例，其他字符串和未获支持的源类型都有负例。
8. `bool` 转 `str` 的结果固定为小写 `"true"` 或 `"false"`，转换不会改变源变量的类型槽。

### C0：基础容器

退出条件：

1. 先分别建立数组、元组、字典表和字典列的数据模型。
2. 数组路径和默认填充在规范冻结后单独实现。
3. 本里程碑不以集合完成为退出条件。
4. `list[0]` 命中首个元素，`list[3/2]` 命中外层索引 `3`、内层索引 `2`，并有越界反例。
5. 在实现显式同构容器前，冻结类型前缀在标量槽、容器元素约束、非字面量初始化和无初始化声明中的消歧规则。
6. 路径约束只实现已经确认的类型语义；`const list[path]` 的运行时锁定提案在另行确认前不得进入实现。

### C1：有序容器选择器

退出条件：

1. 数组、元组、`str` 和字典列实现同一对方括号内的多选、闭区间、前后范围与全量选择。
2. 单个精确索引返回值；多选和范围保留来源容器类型与嵌套形状；空结果返回对应类型的空容器。
3. 非零正负步长的方向稳定，零步长报错；字面量和整形变量都通过规格测试。
4. `[?x]` 完成无放回抽取，`[!?x]` 完成放回抽取；零数量、超量和空来源分别具有确定结果或错误。
5. 字典表的精确键路径继续可用，但不接受范围、步长或随机选择；集合仍完全不可索引。
6. 在开放字典列的重复选择前冻结键唯一性与重复条目表示；在扩展选择器前冻结精确项/范围项混用和负索引规则。
7. 在开放 `str` 高级选择前冻结 Unicode 索引单位；范围越界、重复或重叠选择、父子路径合并和多范围步长规则也必须先形成规格测试。
8. 范围路径只允许穿过有序容器；进入无序字典表的范围在两种执行模式中产生同类错误。
9. 在开放异构容器的动态索引、范围和随机选择前，冻结其静态结果类型及运行时检查边界。

### C2：集合与可哈希规则

退出条件：

1. 单一标量集合先完成唯一性、成员判断和不可索引约束。
2. 可哈希类型规则和动态插入检查可用。
3. 再实现异构集合以及 `+`、`&`、`-`、`^` 和集合比较。
4. `frozenset` 不作为本里程碑的强制退出条件。
5. 在实现不同显式元素类型之间的集合运算前，冻结结果元素类型或拒绝规则，并补齐正反例。

### F1：函数与控制流语义

退出条件：

1. `def`、参数推断、返回值和局部作用域具有稳定的类型与控制流表示。
2. `if`、循环、`break`、`continue` 和 `return` 的所有离开边都可供生命周期阶段分析。
3. 脚本顶层入口与显式工程入口不会产生两套函数调用语义。

### D0：本地文件模块与配置骨架

退出条件：

1. `.xiao` 文件能按源码根映射为模块，目录无需 `__init__.py` 即形成纯命名空间。
2. 源码中的模块导入能生成内部依赖图，目录本身不执行初始化代码。
3. 全小写 `config.xiao` 通过不可执行的声明式子集解析，能声明最小项目身份和包外导出。
4. 配置中的函数、控制流、导入及其他可执行构造在读取阶段被拒绝。
5. 相对导入、循环依赖和外部包求解不阻塞最小绝对导入闭环。

### R0：内存与表对象闭环

退出条件：

1. 逃逸分析、引用计数和 `Weak` 分别通过生命周期测试。
2. `[Table]`、`[[Table]]`、`new`、`init`、`drop` 行为明确。
3. 没有追踪式 GC 或隐式全堆扫描。

### H0：错误模型与并发边界

退出条件：

1. 前序阶段的词法、类型、容器、模块和生命周期错误使用统一编号、源码位置与传播结构。
2. 字节码和原生后端能够消费同一错误契约，不各自创造错误语义。
3. 数据竞争政策形成编译器与运行时约束，但线程、任务池、`async`/`await` 和 Actor 不作为本阶段实现内容。

### U0：统一前端集成

退出条件：

1. 已完成的词法器、解析器、名称解析、类型检查和逃逸分析通过明确接口串成单一前端流水线。
2. 类型化 IR 完整携带后端所需的类型、控制流、选择器、模块、生命周期与错误信息。
3. 后端不需要重新解析源码或重新推断任何语言语义。

### B0：字节码最小运行闭环

退出条件：

1. 字节码运行接口能通过内部测试驱动器执行经过检查的最小脚本；用户可见的 `xiao run` 在 X0 接入。
2. 字节码调用栈、错误传播和源码回溯可用。
3. 只纳入已经通过前置里程碑的语义。

### N0：LLVM 原生构建闭环

退出条件：

1. 同一类型化 IR 能通过内部构建驱动器生成 LLVM IR 和原生程序；用户可见的 `xiao build` 在 X0 接入。
2. 原生程序不依赖完整虚拟机。
3. 字节码与原生模式的输出、错误和释放记录一致。

### X0：跨平台工具链

退出条件：

1. CLI 将前序稳定接口接成可用的 `xiao run`、源码快捷运行、`xiao build`、`xiao test` 和 `xiao config`，不复制编译器语义。
2. Windows、Linux、macOS 的最小构建矩阵通过。
3. 从阶段 01 到本阶段已经实现的所有“已确定”规则都有自动化规格测试。
4. CLI 使用 TypeScript 构建并通过静态检查；Windows、Linux、macOS 的命令入口行为一致。
5. 三个平台都提供不要求用户另装 Node.js 的独立 `xiao` 可执行程序，并能正确调用编译器内核。
6. `xiao config CLI.git.summary true` 与 `xiao config --global CLI.git.summary false` 按布尔模式结构化写入目标配置；非法值、未知路径和写入中断具有稳定诊断，且无关配置与注释不被破坏。

### D1：外部包契约与依赖图骨架

退出条件：

1. `config.xiao` 能声明直接外部依赖及版本/来源约束。
2. 依赖解析器能读取本地路径包配置，并在内存中构建完整依赖图。
3. 包身份冲突、缺失依赖和依赖环具有稳定诊断。
4. 本阶段只建立包契约和解析边界，不要求缓存、锁文件或远程下载。

### E0：配置与环境指纹

退出条件：

1. 环境管理器消费第 D0 阶段产出的规范化配置声明树，不执行项目代码。
2. 配置、工具链和目标条件具有稳定指纹，环境元数据为后续锁文件摘要预留字段。
3. `xiao venv` 创建逻辑名 `venv`、目录 `.venv`；`xiao venv dev` 创建逻辑名和目录名都为 `dev`。
4. Shell 钩子能在创建后激活环境，以绿色显示完整 `$环境名$` 前缀，并在切换时恢复原提示符。

### E1：本地依赖与共享缓存

退出条件：

1. 本地路径依赖可以进入经过校验的全局内容寻址缓存。
2. 两个项目环境可以复用相同包内容，同时保持各自的依赖映射。
3. Windows、Linux、macOS 通过只读逻辑映射读取同一缓存内容，不链接或复制依赖源码到项目环境。
4. 项目环境和全局安装环境引用同一缓存；缓存内容使用前经过摘要验证，损坏条目不会进入构建。

### E2：锁定与同步

退出条件：

1. 工具能生成、校验并复用记录完整依赖图的锁文件。
2. `sync` 在目标环境不存在时创建并安装，在已有环境时补齐缺失依赖，成功后通过 Shell 钩子激活该环境。
3. `install` 与 `i` 行为一致：有激活环境时安装到该环境，否则安装到全局环境；二者均不创建或激活环境。
4. 环境映射原子更新；配置与锁文件不一致、缓存损坏和离线缺包具有独立诊断。

### E3：包操作与远程来源

退出条件：

1. 锁定、同步、安装、增加、删除和显式升级分别具有稳定命令与错误边界。
2. 常规运行不会隐式升级依赖，远程内容必须通过完整性校验。
3. 版本求解、离线模式、冻结模式和损坏缓存诊断可用。
4. 支持的 Shell 钩子矩阵、取消激活和无钩子降级规则已经冻结并通过跨平台测试。

### I0：终端骨架与单行会话

退出条件：

1. 无参数 `xiao` 启动交互会话，单行模式能够提交、执行、显示错误并继续下一次输入。
2. 版权行、版本行、当前路径、可选环境前缀与 `[X>` 在三个目标平台稳定显示，不支持真彩色的终端具有可读降级。
3. Git 摘要默认关闭；项目或全局配置启用后，分支及领先/落后数量能够刷新且不会阻断提示符。
4. Git 分支没有跟踪上游时的显示规则已经冻结，不依赖 Git 实现的偶然行为。

### I1：多行编辑与运行确认

退出条件：

1. `xiao --inLF` 和会话内 `!inLF!` 都能进入多行模式，`!outLF!` 与 `Shift + Enter` 都能进入运行确认阶段。
2. 多行粘贴保留换行和缩进，并为每个逻辑行分配五字符宽、右对齐的行号和 `|`。
3. 终端软换行只绘制空白行号区与 `|`，不会修改缓冲区、源码位置或下一逻辑行号。
4. 用户确认后执行完整缓冲区，输出区与编辑区由随终端宽度变化的分隔线隔开，并显示耗时与内存摘要。
5. 运行确认状态按 Esc 能无损返回多行编辑，不调用字节码执行入口，也不改变源码缓冲区、源码行号映射或文件绑定。
6. 空缓冲区、99999 行边界、终端尺寸变化和中断信号都有明确行为。
7. 运行确认标题嵌入上方分隔线，下一行只显示独立的 `>` 输入提示符，并随终端宽度稳定缩放。
8. `!outLF!` 可以在触发瞬间显示为带行号输入，但随后从编辑缓冲区和源码行号映射中剔除，不进入词法器或保存内容。
9. 分隔线和逻辑行栏的 `|` 使用 `#7F7F7F`，运行确认输入栏的独立 `>` 使用 `#DCDCAD`；无真彩色终端仍保持可读。

### I2：文件编辑与保存

退出条件：

1. `xiao --inLF "<file.xiao>"` 能把现有 UTF-8 Xiao 源文件装入多行缓冲区，保留换行和缩进供编辑与运行。
2. 未绑定缓冲区使用 `!save!` 或 Ctrl+Shift+S 时进入保存位置输入，首次成功后绑定实体文件并返回编辑。
3. 已绑定缓冲区通过两个保存入口都直接写回，不显示位置输入；`xiao --inLF <file.xiao>` 成功载入时立即建立绑定。
4. 保存提示输入 `q` 并回车或直接按 Esc 都能无损返回编辑，尚未提交的路径输入被丢弃，且不写入文件、不改变文件绑定；首次覆盖和不存在输入文件的待定规则在本里程碑开始前冻结。
5. `!save!` 触发后从可编辑缓冲区、源码行号映射和保存内容中剔除。
6. 写入使用不会留下半文件的安全流程，路径、权限、编码和换行错误具有独立诊断；失败不会破坏已有绑定或错误建立新绑定。
7. 保存状态的上方分隔线显示 `Enter the save location`，路径输入栏的独立 `>` 使用 `#DCDCAD`；光标不属于实际路径文本。

### I3：空命令面板

退出条件：

1. 单行和多行模式都能通过 Ctrl+Shift+P 或 `!panel!` 打开独立命令面板。
2. 多行模式中的 `!panel!` 触发后从可编辑缓冲区、源码行号映射和保存内容中剔除；单行模式中不作为 Xiao 源码执行。
3. 空面板显示嵌入上方分隔线的 `Command Panel`、独立输入栏 `>` 和下方分隔线；线条字符使用 `#7F7F7F`，输入栏角号使用 `#DCDCAD`。
4. 首版不要求任何实际面板命令；按 Esc 或再次按 Ctrl+Shift+P 都能关闭面板并无损返回原交互状态，源码缓冲区和文件绑定保持不变。

### I4：环境包延迟加载

退出条件：

1. 会话根据激活状态只登记全局环境或当前虚拟环境中的可用包，两个环境视图不会交叉泄漏。
2. 启动、提示符渲染、名称枚举和只读接口查询都不执行包模块，首次真正引用内容时才调用运行时加载接口。
3. 包根名称冲突规则已经冻结，不依赖包扫描顺序选择胜者。
4. 模块加载失败具有包名、来源环境和底层原因，失败后会话仍可继续使用。
5. 同一具体模块成功加载后，在一个 REPL 运行实例中重复引用也只初始化一次；首次失败后的重试与缓存行为在本里程碑开始前冻结。

### I5：交互高亮与编辑增强

退出条件：

1. 多行模式复用正式 Token 与源码位置模型提供语法高亮，不另写一套会改变语言语义的解析器。
2. 高亮关闭、终端不支持颜色或源码暂时不完整时仍可编辑、保存和运行。
3. 本里程碑属于后置增强，不阻塞 I0 至 I4 的基础交互闭环。

### O0：[优化契约与统一管线](13-optimization-contract.md)

退出条件：

1. 优化器、字节码后端和 LLVM 后端共享同一份规范化优化配置与语义约束。
2. 未优化参考路径可稳定生成，且不以任何优化 Pass 作为 B0/N0 的前置条件。
3. IR 验证器能检查类型、控制流、效果、所有权、释放计划和源码映射；验证失败不会继续生成可执行产物。
4. 优化前后差分测试覆盖溢出、`bool +/- 整数`、随机选择、输入输出、动态值、模块加载、容器顺序和 `drop`。
5. 相同输入、工具链、目标和配置产生稳定的优化指纹，临时路径和时间戳不会造成无意义失配。

### O1：[字节码优化与 `.xiaoc`](14-bytecode-optimization.md)

退出条件：

1. `.xiaoc` 的魔数、版本、载荷、源码映射、校验和加载验证规则已经冻结并有编解码测试。
2. 字节码级 Pass 能逐个启用、验证和回归；窥孔、跳转、常量池和槽布局变换不改变语义。
3. 虚拟机在执行前拒绝损坏、截断、未知版本、错误目标、错误 ABI、栈高度错误和释放计划错误的 `.xiaoc`。
4. 源码、未优化字节码和优化字节码的输出、错误、随机序列、退出码和 `drop` 记录一致。
5. 运行时 quickening/JIT（若未来加入）不会原地改写不可变 `.xiaoc`；其范围和缓存策略已明确记录。

### O2：[LLVM 原生优化与链接](15-native-optimization.md)

退出条件：

1. 每个已冻结优化级别都能映射到可记录、可验证的 LLVM Pass 管线，并保留未优化基线。
2. LLVM 不启用破坏 Xiao 溢出、错误、求值顺序、随机、生命周期或 Runtime 检查的变换。
3. 三个平台的原生优化结果与字节码结果通过输出、错误、退出码、容器顺序和释放记录差分。
4. Runtime 裁剪、调试符号、目标 CPU、LTO/PGO 等开关的语义和构建指纹已经冻结，未决定的能力不进入默认级别。
5. 编译时间、启动时间、运行时间、峰值内存和文件体积均有可复现基线与回归阈值。

### O3：[SHA-256 内容寻址与二进制索引](16-content-addressed-artifacts.md)

退出条件：

1. `.xiaoc` 对象的摘要输入边界、文件名表示、目录布局和碰撞处理已经冻结，并能跨平台复现。
2. 对象写入、完整校验、原子改名和索引提交在中断、并发和只读场景下不会产生可误用半成品。
3. 选定的 CBOR、MessagePack 或 Protobuf 索引具有版本、Schema、对象类型和依赖/优化元数据，并与依赖锁文件分离。
4. 索引损坏、对象缺失、摘要不匹配和权限错误可以诊断并由已验证对象重建。
5. 缓存复用不会跨越语言/IR/VM/Runtime 版本、目标平台、依赖锁或优化配置错误命中。

### O4：[`.xar` 字节码归档与启动](17-xar-archive.md)

退出条件：

1. `.xar` 清单、入口、二进制索引、成员布局、版本和完整性验证规则已经冻结。
2. 归档创建、列目录、验证和运行均拒绝路径穿越、重复关键字段、越界长度、缺失对象和版本不兼容。
3. 命令行入口与操作系统双击入口调用同一 `xiao` 字节码运行接口，入口、输出、错误和退出码一致。
4. 瘦包/胖包、依赖、Runtime、资源、源码和调试信息的取舍已经明确，不能把外部环境假设写进未声明的清单。
5. Windows、Linux、macOS 的文件关联、工作目录、参数、权限和无关联退化路径均通过测试。

### O5：[优化与产物 CLI 接入](18-optimization-cli.md)

退出条件：

1. 优化、验证、检查、缓存和打包命令的语法、参数、错误码和帮助文本已经冻结。
2. CLI 能将 `config.xiao`、全局配置和命令行覆盖归一化为同一后端配置，不在 TypeScript 中复制编译或格式语义。
3. `.xiao`、`.xiaoc` 和 `.xar` 的输入路由、缓存命中/失配、版本拒绝和失败回退行为可观察且可脚本化。
4. 三平台独立 CLI 能安装/检查/移除 `.xar` 文件关联，且不要求用户另装 Node.js。

### O6：[优化、兼容性与发布验收](19-optimization-release.md)

退出条件：

1. 已冻结优化级别、字节码格式、索引 Schema、`.xar` 版本和目标平台具有完整兼容矩阵与升级/拒绝策略。
2. 优化前后、不同后端、不同归档入口的差分、模糊、损坏恢复和安全测试全部通过。
3. SHA-256 完整性验证、资源上限、路径安全、权限和离线缓存行为在三平台一致；签名/信任未实现时有明确提示。
4. 发布报告可追溯源码、依赖锁、工具链、优化指纹、对象摘要和归档成员，且重复构建差异在白名单内。

## 一级工程目标：维护文档与决策

### 变更流程

1. 新规则先写入 `00-decisions.md`。
2. 再更新受影响阶段的语法、IR、运行时和测试章节。
3. 实现与文档冲突时，先标记待定并补充回归测试。
4. 每个里程碑完成后在 README 的状态表更新状态。

### 禁止事项

- 不把实验性语法直接写成稳定语法。
- 不让字节码后端和 LLVM 后端各自发明类型或释放规则。
- 不用“测试没覆盖”替代未解决的语言设计决策。

## 二级实现任务

### 测试基础设施

1. 建立源码快照、AST 快照和 IR 快照测试。
2. 建立正例/负例目录和统一期望文件格式。
3. 建立字节码/原生差分执行器。
4. 建立跨平台 CI 和最小发布样例。
5. 建立 IR/字节码/索引/归档的规范化快照、摘要重现和损坏样本库。
6. 建立优化 Pass 单独开关、性能/体积基准和可复现构建比较器。

### 质量门槛

1. 每次语法改动必须更新规格测试。
2. 每次 Runtime 改动必须运行生命周期和内存错误测试。
3. 每次 LLVM 改动必须运行双模式差分测试。
4. 每次配置改动必须验证命令行覆盖和原生固化行为。
5. 每次优化 Pass、字节码格式、索引或归档改动必须运行对应的语义、完整性和兼容性测试。

## 验收标准

### 发布验收

- 文档索引顺序与实际开发依赖一致。
- 每个阶段至少有两个层级的任务和可执行退出条件。
- 所有未决问题在对应阶段开始前有明确结论或被主动延期。
