**三组候选**，其中第一组审核已实测：

### ① 动态成员读写（`expression.rs:735` / `:752`）—— **实测：表形态下不是缺口**

审核用**真实表**接收者跑了**两侧**：

```xiao
[[Item]]
    member = 7
    def init(self) -> none
        self.member = 7
item = new Item()
def read(value) -> int
    return value.member
print(read(item))
```

| 侧 | 命令 | 结果 |
| --- | --- | --- |
| VM | `bun cli/ts/src/main.ts run <file>` | 输出 **`7`**，退出码 0 |
| 原生 | `xiao build -o <out.exe> <file>` → 运行产物 | 构建成功，产物输出 **`7`** |

写入形态同样一致（`value.member = 42` → VM 与原生产物**均输出 `42`**）。
**原因是代码条件**：`expression.rs:735` 的拒绝是

```rust
if !matches!(object.ty, IrType::Table { .. }) { … feature: "动态非表成员访问" … }
```

即**只拒非表接收者**；接收者被推断为表时走 `emit_callback_field_get`，两边都正常。

**真正的分歧在非表接收者**：用字典写同样的形状，VM 报
**`X06-RUNTIME-002`「期望类型 table，实际为 dict_table」、退出码 3**（**运行期**语言错误），
而原生在 **codegen 阶段拒绝编译**（**编译期**）。**这是本组唯一的分歧点，需要星崽定性**（见待定决策 1）：
编译期拒绝 vs 运行期语言错误，算「两边都拒绝」还是算缺口？

### ② 动态扩展赋值（`control.rs:206`）—— **仍差对照**

现有探针是 `write({member = 0})`（字典），VM 报 `X06-RUNTIME-002`、退出码 3，
与①的非表分支同源。**需要补一次表形态对照**，判定口径与①相同。

### ③ 动态选择计划缺失（`expression.rs:270`）—— **仍差对照**

现有记载是「合法动态范围/随机选择 VM 可执行；无计划 IR 被原生拒绝」，可达性写的是
「依赖 IR 选择计划生产契约」——**这句话不是判定**。需要**构造一个前端到底会不会产出无计划 IR 的探针**：
若前端对任何合法源码都产出计划，则该分支是**防御性不可达**；若存在能产出无计划 IR 的源码，
才是缺口。**这一组的性质与①②不同，不要按同一模板走。**

## 二、对照的施工规格

### 2.1 两侧都要实跑，原生侧用 `xiao build`

**原规格只有 VM 侧方法**（`bun cli/ts/src/main.ts --json run …`），**没有原生侧方法**——
这正是「对照」迟迟没做掉的原因：没人说清原生侧怎么观察。补上：

```text
# VM 侧
bun cli/ts/src/main.ts --json run <目录>/main.xiao

# 原生侧（需要 10D §4 的受控环境）
bun cli/ts/src/main.ts build -o <输出>.exe <目录>/main.xiao
<输出>.exe            # 运行产物，观察真实输出与退出码
```

原生环境的准备按 [10D](10d-environment-gated-test-spec.md) §4；`xiao build` 失败（非 0 退出）时
**把它的完整 stderr 记下来**——那就是「编译期拒绝」的证据形态。

### 2.2 判定口径（三选一，与前表和 §2.2 一致）

| 观察 | 判定 |
| --- | --- |
| VM 成功产出结果 **且** 原生产出同值 | **两边一致，不是缺口** |
| VM 与原生**都拒绝**该程序 | **两边都拒绝**（编译期/运行期之别是否算差异，见待定决策 1） |
| VM 成功产出结果 **而** 原生拒绝构建 | **原生缺口**，登记并排实现 |

### 2.3 证据要求

1. **两侧都要有实跑输出**（VM 的 `--json` 摘要、原生的构建结果 + 产物实际输出）；
2. **贴带机器特征的原始文本**——不得只写摘要（[10Z-收尾](10z-closeout-execution.md) §1.3(6) 的教训：
   规格里给过预期输出时，摘要不构成证据）；
3. 探针源码**写进文档或提交说明**，使第三方可原样复现；
4. 若判为「不是缺口」，**同样要记**——把候选降级为一致，是结论的一部分，不是没做事。

### 2.4 落点与顺序

1. ②③ 两组各补一次对照 → 回写 [10P](10p-differential-exemption-and-coverage.md)（**加列不抹旧判定**，
   改判要写明依据）；
2. ① 组按审核实测结论更新（表形态一致；非表形态待定性）；
3. 三组都有结论后，**停下来向星崽汇报**；汇报后才定 Z-1 的范围。

## 四、最可能翻车的地方

1. **只跑 VM 侧**就写「原生缺口」（原规格的口子）；
2. **用字典形态冒充表形态**：①组的探针原本就是 `{member = 1}` 字典，命中 `dict_table` 边界，
   与「动态表成员访问」不是一回事；
3. **只看构建成功就下结论**：还要**运行产物**看实际输出——`xiao build` 成功不等于语义正确；
4. **把编译期拒绝直接当成缺口**（或直接当成一致），不区分「两边都拒绝」的两种形态（待定决策 1）；
5. **③组按①②的模板跑**：它要判的是「前端会不会产出无计划 IR」，不是「接收者是什么类型」；
6. **摘要当证据**（§2.3 第 2 条）；
7. 顺手改后端或开新批（§三）。

   - **算缺口**：可观察行为不同——VM 能产出并运行到报错，原生连产物都没有；
