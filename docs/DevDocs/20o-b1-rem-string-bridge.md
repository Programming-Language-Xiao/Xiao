# REM-C 原生字符串桥接的隐含复制修复

本机受控测量中，最大 URL ASCII 解码的原生 O0 五次中位数为 6.8316662 秒，超过冻结的
2 秒预算，队列返回 1 并保存完整失败样本。没有放宽限额、单次预算或删除最大输入。

原因位于 xiao-runtime/src/abi.rs 的 value_to_runtime：str/lint/lfloat 共用路径先将
整个字符串复制到临时 Rust String，再在 str 分支丢掉副本而只保留句柄。重复的长度、
迭代和下标调用因此仍有整串复制，字符起点索引为 O(1) 并不能消除这个成本。

独立修复只把文本复制放回 lint/lfloat 分支；str 继续验证实际字符串载荷并保留原有强句柄，
失败状态、拥有权和源码行为不变。没有新 ABI 符号/布局、intrinsic、生成文本或生成器版本改变；
与需要额外版本裁定的 [释放前置](20o-b1-rem-release-prerequisite.md) 分开。

新增 b1_string_bridge.rs 通过测试线程的系统分配器观察：对 131,072 字节 ASCII 与
229,376 字节 Unicode 字符串的 ABI 长度、迭代末位和动态负下标，单次申请均不得达到 4 KiB。
这直接拒绝原来的完整来源副本，同时保留真实 ABI 和分配器，不注入生产失败点。
Runtime 全量测试包含此回归均通过，lint/lfloat 的原有转换测试继续保留。

相同 URL 产品源码、最大输入和独立黄金的重测中，原生 O0/O3 中位数分别为
1.0438788 / 1.0116239 秒，均满足 2 秒目标。完整最大输入队列及翻倍比在修复后重测，
本机前后 JSON/日志在 REM 证据中登记；此局部成绩不代替完整 F10 或生命周期验收。
