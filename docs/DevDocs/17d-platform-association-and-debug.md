# 17D. 平台关联与调试窗口

> **17 阶段的收口批。** [规范](17-xar-archive.md) §「平台关联」的 **`17.14`–`17.18`**。
> 17A 钉死容器、17B 装入资源、17C 让归档跑起来；本批把它接到**平台**上，
> 并把 `-debug` 的独立诊断窗口接进归档运行路径。
>
> **一句话概括本批**：**把「能跑」变成「双击也能跑、调试也能跑」**——
> 文件关联、双击时的行为契约、以及 `-debug` 与归档的接线。

## 二、必须先冻结的 9 条

### 2.1 **文件关联只出设计与行为契约，不做真实安装器**（已决策）

**已决策**（2026-10-04）：本批交付**设计 + 可测的行为契约**，**不实现**注册表 / `.desktop` /
`Info.plist` 的实际写入。

**冻结**：

- 规范 `:14` 的动词是「**设计**可安装/可移除的文件关联」——本批据此交付：
  **三平台的关联模型**（关联什么、注册到哪、如何卸载）**+ 17.15/17.16 的行为契约**；
- **不做**写入注册表、生成 `.desktop`、改 `Info.plist` 的实际操作——
  那是**发布工程**，[19. 优化、兼容性与发布验收](19-optimization-release.md) 才做发布验收；
- **但**「设计」**不是**"写一段说明"：行为契约必须是**可执行的测试**（见 §2.2），
  否则本批的验收会退化成文字检查。

### 2.2 **双击的行为契约必须可测**

`17.15` 要求明确「工作目录、参数传递、标准输入输出和退出码」。

**冻结**，逐项定死并**各有测试**：

| 维度 | 冻结口径 |
| --- | --- |
| **工作目录** | **双击时不可依赖**——启动器必须**不得**把双击者的当前目录当作项目根；归档运行只依赖归档自身 |
| **参数传递** | 双击不传参数；`xiao -xar <file> [args...]` 的 `args` 透传到归档程序 |
| **标准输入输出** | `stdin`/`stdout`/`stderr` 直通（`print` 走 stdout、诊断走 stderr，与 17C 一致） |
| **退出码** | 与 `xiao -xar` 命令行形式**完全一致**——双击与命令行走同一条执行路径，**不得**各写一套 |

**「工作目录不可依赖」是本条的重点**：双击的当前目录由桌面环境决定，
若启动器拿它当项目根，同一个人两次双击可能得到不同结果。

### 2.3 **无关联时给同一入口 + 清晰安装提示**

`17.16` 的原文：「在无图形界面或未安装关联时提供**同一命令行入口**和**清晰安装提示**，
**不提供无 Runtime 自包含承诺**」。

**冻结**：

- 命令行入口**始终可用**，与是否注册了关联**无关**；
- 没有任何 `xiao` 安装或没有关联时，**双击不能运行**——命令行要给出**安装提示**；
- **不得**暗示归档能脱离 Xiao Runtime 独立运行（规范 `:27` 写明 `.xar`「不要求自解释，
  也不承诺脱离 `xiao` 和 Xiao Runtime 独立运行」）。

### 2.4 **`-debug` 复用 11X0-D 的机制，不新造**

**冻结**：

- 复用 11X0-D 已冻结的：**新开的终端**（不是 GUI 窗口）、独立诊断进程、
  事件传输方式、**窗口必须在用户代码之前就绪**；
- **不得**为归档另起一套诊断窗口机制——两条路径必然漂移；
- 归档路径与源码路径的 `-debug` 行为**必须一致**（同一套代码）。

### 2.5 **归档不能以自身配置关闭调试窗口**

规范 `:29` 明写：

> 若通过 `xiao -xar ... -debug` 启动，归档运行时必须把结构化事件发送到独立诊断进程并打开窗口；
> **归档不能以自身的普通配置关闭该窗口**。

**冻结**：

- 归档的 `debug_activation` 为真时，**规范化不了**——窗口必须开；
- 这与 14A §3.6 的「`-debug` 激活位只进格式，普通 `.xiaoc` 不自动开窗」是**同一条要求的两面**：
  普通产物不自动开窗，但**声明了调试激活位的归档不许被关掉**；
- 若窗口**启动失败**，按 §2.6 整体拒绝，**不得**静默降级为无窗口执行。

### 2.6 **诊断窗口失败不得部分执行**

规范 `:67` 末句：「校验或**诊断窗口启动失败**时**不得部分执行**已加载模块」。

**冻结**：

- 窗口启动失败 → **整体拒绝**，**不执行任何用户代码**；
- 这与 17C-FIX §2.3 的「不得部分执行」是同一条判据，本批把**窗口启动失败**这一支也纳入；
- 要有**断言"没有执行事件产生"**的用例（不是只断言错误码）。

### 2.7 **启动器要限制权限与临时文件，并留下可审计的记录**

`17.17` 的要求。

**冻结**：

- **临时内容**：只在与归档/本次运行相关的受限目录内创建，**权限最小化**，
  **失败时清理**（规范 `:75` 的「清理失败留下的临时内容」）；
- **不落凭据**：临时文件与审计记录里**不得**出现凭据、令牌、环境变量值
  ——与 17B/17C 的凭据边界、11A-E3D1 的 0600 要求**同一条判据**；
- **可审计的验证结果**：记录**这次运行验证了什么**（归档摘要、索引版本、平台/ABI 判定、
  `debug` 是否激活），且**机器可读**（结构化字段）——**不是**一句"验证通过"；
- 审计记录的**形式与位置**在实施第一步定下并写入实施记录，**不得**只落在代码里。

### 2.8 **安装提示与诊断要双语可渲染**

因 17C-FIX 已接入语言上下文：

**冻结**：

- 本批新增的**所有用户可见文案**（安装提示、窗口状态、审计摘要的人读部分）
  要走 11C 的消息目录，**两套目录都要补**；
- **机器字段不随语言变**（沿用 11C 契约）。

### 2.9 **不重开 17A/17B/17C/11X0-D 的既有冻结面**

**冻结**：

- **不改** 17A 的容器与索引字段、17B 的资源语法、17C 的 CLI 形式与错误码编号；
- **不改** 11X0-D 已裁定的三处（诊断进程位置、平台终端启动方式、管道/套接字选择）；
- **不改** 11X0-C 的独立产物与核心发现顺序（只**复用**）。

### 2.10 **承接 17C-FIX 的两条回归缺口**

17C-FIX §五 第 5、6 条要求补两条**可证伪**的回归，**实测都未落地**——
整个提交只新增了一个语言解析测试，而其实施记录声称做了「归档成功/失败行为测试」
与「损坏归档不会产生执行事件」。

- **成功路径端到端**：断言 `IntrinsicOutput` 携带 `hello world!` 且 `is_success()`；
- **不得部分执行**：断言校验失败的归档**不产生任何执行事件**。

**冻结**：

- 按 [17C-FIX](17c-fix-language-context.md) §3.4 的口径补——断言**具体事件与结果**，
  **不得**只断言 `Ok` 或错误码，**更不得**写成同义反复；
- 删掉对应实现时**必须失败**（与 20AB / 20AB-FIX 的「移除验证」口径一致）；
- 成功路径的用例可直接用审核时的探针形状：
  「源码 → IR → TAC → `.xiaoc` → `.xar` → `run_archive`」——它已被实测证明可行。

**为什么并入本批**：它是两条测试，独立开批成本高于收益；而本批的 §2.6
（「诊断窗口失败不得部分执行」）本来就要写「**没有执行事件**」的断言，
与 §6 这条是**同一个断言手法**，放一起可共用一套事件观察工具。

## 七、最可能翻车的地方

1. **把「设计」做成一段说明**（§2.1）——条款要落成可执行测试，否则验收退化。
2. **依赖双击的当前目录**（§2.2）——同一人两次双击得到不同结果。
3. **双击与命令行各写一套退出码逻辑**（§2.2）——必然分叉。
4. **暗示归档能自包含运行**（§2.3）——规范 `:27` 明文否认。
5. **为归档另造一套窗口机制**（§2.4）——与源码路径漂移。
6. **让归档把它自己声明的调试窗口关掉**（§2.5）——规范 `:29` 明文禁止。
7. **窗口失败后静默降级为无窗口执行**（§2.6）——正是"部分执行"。
8. **审计记录里写了路径或凭据**（§2.7）——审计记录往往比日志留存更久。
9. **忘记了 17C-FIX 的语言上下文**（§2.8）——新文案只补一套目录。
10. **把已完成的 `debug_activation` 当成本批待办**（§一 的提醒）——重复劳动。
11. **忘了 `Cargo.lock` 同步**——`check:lock` 会红（16A 栽过一次）。

## 八、验收

1. **行为契约可测**（§2.2）：工作目录、参数传递、标准输入输出、退出码**各有测试**；
2. **双击不依赖 cwd**：换一个当前目录运行，结果与退出码不变；
3. **双击与命令行一致**：同一归档经两种触发方式，输出与退出码逐字相同；
4. **无关联时可用**：命令行入口始终可用，且给出**安装提示**；
5. **不承诺自包含**：提示文案中**不得**出现可脱离 Runtime 的暗示；
6. **`-debug` 可开窗**（§2.4）：`xiao -xar ... -debug` 打开独立诊断窗口，
   且**窗口先于用户代码就绪**（复用 11X0-D 的既有验证口径）；
7. **窗口不可被归档关闭**（§2.5）：归档 `debug_activation` 为真时，**规范化不了**；
8. **窗口失败即拒绝**（§2.6）：断言**没有执行事件**产生；
9. **临时内容受限且被清理**（§2.7）：权限最小化、失败后不残留；
10. **审计记录机器可读且无凭据**（§2.7）：含归档摘要、索引版本、平台/ABI 判定、`debug` 状态；
    用副作用探针断言**不含**凭据与环境变量值；
11. **文案双语**（§2.8）：新文案在两套目录里都有，且**机器字段不随语言变**；
12. **不回归**：17C 的两种 CLI 形式与端到端仍通过（含 17C-FIX 的用例）；
13. **不重开**：17A/17B/17C/11X0-C/11X0-D 的既有测试未改且全绿；
14. **承接项·成功路径**（§2.10）：端到端用例断言 `IntrinsicOutput` 携带 `hello world!`
    且 `is_success()`——**不是**只断言 `Ok`；
15. **承接项·不得部分执行**（§2.10）：校验失败的归档**不产生任何执行事件**；
16. **两条承接项可证伪**：删掉对应实现时**必须失败**（§2.10 的冻结）；
17. **门禁全绿**：`cargo test --workspace`、`cargo clippy --workspace --all-targets -- -D warnings`、
    `cli/ts` 类型检查与测试、`bun run check`（含 `check:lock`）。

## 十、实施记录

- `cli/ts/src/platform/file-association.ts` 交付 Windows、Linux、macOS 三平台关联模型，
  只生成注册位置、命令模板和卸载动作，不写注册表、`.desktop` 或 `Info.plist`。
  `archiveLaunchContract` 固定 `-xar <path>` 参数、独立于桌面 cwd、继承标准流并原样转发退出码。
- `xiao-xar::ArchiveAuditRecord` 与 `audit_archive` 提供机器可读校验记录：归档摘要、索引版本、
  已验证成员数、Runtime ABI/平台判定、debug 激活位和语言上下文；记录不包含凭据或环境变量值。

  的 `hello world!` 与成功结果，损坏归档通过事件观察器断言没有执行事件；关联契约测试覆盖
  三平台设计、cwd、参数、标准流和退出码。
- `run_archive` 已复用 11X0-D 的 `DiagnosticSession`：归档 debug 激活位或 `-debug` 时先完成
  窗口握手，失败在 VM 前返回；新增安装提示走 CLI 双语目录。
