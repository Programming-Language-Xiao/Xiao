## 一、为什么是这一批

1. **第八批刚把「验证失败」的身份修对，同一批就暴露了另一半**：
   两条路径都通向 `fatal.internal`，但只有一条被处理过；
2. **它是用户可见的**：普通源码（`lint` 取负）触发，报出来的是「**编译器内部故障**」——
   那是在说编译器坏了，而实际是**功能没做**。这与第八批刚立的原则（「不能把用户的东西说成坏了」）
   是同一条原则的**镜像**；
3. **它需要一份实测清单**：`unsupported` 的写入点有 **14 处**（§三 已列），
   要判定每一处属于哪一类，**不能靠读代码归类**；
4. **顺带把 `lint`/`lfloat` 算术债写实**：现在的登记只有一句「算术仍是债项」，
   而实际是「哪些操作、各自当前报什么」——那正是本批补探的产物。

## 二、并入的返工项（**先做**）

### 2.1 H-4（中）：`lint` 一元取负不可用——**既有算术债的更精确表述**

**实测（审核侧临时探针，用完即删）**：

| 形态 | 结果 |
| --- | --- |
| `lint -42` | **成功**，`-42`（小负字面量被**常量折叠**，绕过了 `Neg`） |
| `lint b = -9223372036854775808` | 失败，`X09-BYTECODE-001` |
| **`lint a = 42` → `lint b = -a`**（变量取负） | 失败，`X09-BYTECODE-001` |
| `int -42`（标量对照） | **成功** |

**根因已钉死**（两处，缺一不可）：

1. `xiao-bytecode/src/lower/expr.rs:363-375`：一元负号是「`0 - x`」，
   **零常量必须与操作数同宽**，而那个 `match scalar` 只认 `Sint`/`Int`/`Sfloat`/`Float`，
   `Lint`/`Lfloat` 落进 `_ => lower_unsupported(lowerer, "unary minus", ...)`；
2. **即便补上零常量也不行**：`0 - x` 还要 Runtime 的 `lint` 减法，
   而 `NumericPair::new` 不处理 `Lint`/`Lfloat`——**那是登记在案的算术债**。

⇒ **它不是「新缺陷」，是既有算术债的一个具体面**；本批把它**写实**（哪些操作、报什么），
**不实现算术**（见 §4.2）。

### 2.2 H-5（低）：`lower_literal` 的静默兜底还在

第八批 H-1 的根因正是 `text.parse().unwrap_or_default()`；
`lower_literal` 里 `Sint` 与 `Int` 两臂**仍然是这个写法**。
当前**不可达**（前端范围检查挡着：`sint 2147483648` 与 `int 9223372036854775808`
实测都报 `X02-TYPE-007`），所以**不是活缺陷**——但它只靠前端检查挡着。
**先登记，处置见 §4.2**。

### 3.3 两类的区别是**实质的**

- **已知未实现**：用户能写出合法源码，编译器**有意**没做。报出来应当是
  「**这个能力还没实现**」——一条**编译期**限制。
- **内部不一致**：不该发生；一旦发生说明**降低器与前端/生命周期阶段的契约被破坏**。
  这才是真正的「编译器故障」。

**现在两者共用一个出口**（`X09-BYTECODE-001`，消息 `fatal.internal`）——
第八批刚把诊断身份的原则立起来（「不能把用户的东西说成坏了」），
这一条是它的**镜像**：**不能把没做的功能说成编译器坏了**。

## 四、两道待定裁决

### 4.1 裁决一：分档的形式

| | 做法 | 代价 |
| --- | --- | --- |
| **甲** | **给「已知未实现」自己的档位**，`X09-BYTECODE-001` 只留给意外缺口 | 新增一个稳定码；要动 `verify.rs` 与既有测试的期望 |
| **乙** | **不新增码**，只把 `unsupported` 的**消息**按两类分别措辞（仍是 `fatal.internal`） | 便宜；但档位仍是一个，靠消息区分——**按本仓库的判据，消息不是身份** |
| **丙** | 把「已知未实现」**挪出 Fatal**：它是**编译期**限制，报成编译错误（与 `X02-*` 同族）而不是 Fatal | 最名实相符；但改动面最大，且要处理「降低发生在检查之后」的时序 |

**要一并摆上的**：`unsupported` 是**降低器**发现的，而降低发生在类型检查**之后**——
丙 要求把它接回编译期诊断通道，不是换个码那么简单。

**裁定（星崽，2026-10-16）：甲。** 连带三条：

1. **新码同层**：它是**降低器**发现的，所以留在 `X09-BYTECODE-*` 这一族，
   不当成 `X02-*` 那样的检查期错——**层与发现者一致**；
2. **`X09-BYTECODE-001` 只留给意外缺口**：即「内部不一致」那一类。
   分档的**分界线**由 §五 的实测给出，**不许**按 §3.1 那张读出来的表先定；
3. **要说清它不修什么**：严重级别**仍是 Fatal**（今天就是），
   本裁定只修**身份**——**不许**在文档里写成「已把未实现降级为普通报错」。

**落地**：已知未实现记录使用 `X09-BYTECODE-003`；未标记的 `unsupported` 仍使用
`X09-BYTECODE-001`。两者都经生产验证入口以 Fatal 级别拒绝。

### 4.2 裁决二：`lint`/`lfloat` 算术债的范围

| | 做法 |
| --- | --- |
| **甲** | **只登记与写实**：本批出「哪些算术操作、各自当前报什么」的清单，**不实现** |
| **乙** | **顺带做一元取负所需的最小算术**（`Lint`/`Lfloat` 的 `0 - x`） |

**审核倾向：甲。** 理由：一元取负要的是「大整数减法」，
而算术是**成组**的能力（加、减、乘、除、比较）——只做减法是**半截形状**，
与本仓库反复吃的「半截」是同一类。
**且「为 `lint`/`lfloat` 选统一的高精度表示」在 02 里是一条独立设计任务，本批不顺手定。**

**裁定（星崽，2026-10-16）：乙——顺带做一元取负所需的最小算术。**

### 4.2.1 对上面那段选项文字的更正（**审核侧补记，2026-10-16**）

裁定取乙之后我去核实现形状，发现**我写选项时的前提可能不成立**：

- 我把「一元取负」默认成了「**大整数减法**」。但 `Lint` / `Lfloat` 的表示是
  **十进制文本**（`RuntimeValue::Lint(String)`）。对文本表示而言，
  **取负是文本操作**：`"42"` → `"-42"`、`"0"` → `"0"`、`"-42"` → `"42"`——
  **完整、精确、不需要算术**。
- 真正需要减法的是**另一种实现形状**：lowering 现在把一元负号统一写成
  `0 - x`（`expr.rs:363-375`，零常量必须与操作数同宽）——那是**为定宽类型**定的形状。

⇒ **乙 比我当时说的便宜**，而且**不必然**引入半截算术面。
**但形状必须先钉死**（文本取负 vs 通用减法），所以它是 §五 的第 5 问。
**若取文本取负**，则本批**不动** `NumericPair::new`，算术债维持原样；
**若取通用减法**，那就落回「半截算术」，须把代价写清再动。

**连带（乙 落地必须钉死的语义）**：

1. `-0` 归一化为 `0`（不留 `"-0"`）；
2. 对已有负号的文本取负（`"-42"` → `"42"`）；
3. `lfloat` 的 `-0.0` 与精度表示（**与浮点族既有语义对齐**，不许自成一套）；
4. **`lint` 取负做完之后，其它算术（加、减、乘、除、比较）仍是债**——
   §五 第 3 问的清单照样要出，**不许**因为取负通了就把债写成清了。

**§五 第 5 问结论**：采用**文本取负**。`lint`/`lfloat` 的十进制文本只翻转符号；
`lint` 的 `0` 与 `-0` 统一为 `0`，`lfloat` 的零值也归一化为 `0`，非零值保留原始小数精度。
不修改 `NumericPair::new`，其它高精度算术仍是登记债项。

### 5.1 `lint`/`lfloat` 算术面实测

使用模块导入提供真正的高精度文本值，避免小常量在前端折叠成定宽类型。

| 操作 | `lint` | `lfloat` |
| --- | --- | --- |
| 加、减、乘 | `X06-RUNTIME-012` | `X06-RUNTIME-012` |
| 除 | 前端 `X04-TYPE-003` | `X06-RUNTIME-012` |
| 整除、取模、幂 | `X06-RUNTIME-012` | 不适用（前端数值规则拒绝） |
| 比较 | `X06-RUNTIME-012` | `X06-RUNTIME-012` |
| 一元取负 | 本批已成功 | 本批已成功 |

这张表说明一元取负已经接通，但其它高精度算术债没有收口。

### 10.5 Z-1（中）：`lfloat` 的零在取负前后显示不同（**已完成**）

**实测（审核侧临时探针，用完即删）**：

| 形态 | 输出 |
| --- | --- |
| `float` 正零 `0.0` / 负零 `-0.0` | `0` / `0`（**对称**） |
| `lfloat` 正零 `0.0` | **`0`** |
| `lfloat` 负零 `-0.0` | **`0`** |
| `lfloat` 正零 `0.00` | **`0`** |
| `lfloat` 非零 `-1.50` | `-1.50` ✓ |

⇒ **取负对零是可观测的**：同一个数值，加个负号显示就变了。数值类型不该这样。

**它是本批引入的**：`5abf234` 让 `lfloat` 字面量**保文本**（给 `Lfloat` 单开的那一臂），
`0.0` 因此从 `0` 变成 `0.0`；`c123cd7` 先把取负零归一到 `0`，本次 Z-1 再把正零
也归一到 `0`。实现后正负零显示一致。

**裁定（星崽，2026-10-16）：甲——把 `lfloat` 的零也规范化；已完成。**

1. 正零 `0.0`、`0.00` 一律归一到 `0`；
2. **非零仍保留原文本**——`1.234567890123456789`、`-1.50` 不受影响；
   **零没有精度可保**，所以这不构成对「保留原精度文本」的削弱；
3. 归一后零是**规范值**，取负对零不再可观测，且与 `float 0.0` 印 `0` 对齐。
