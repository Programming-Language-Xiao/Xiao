# 10H. N0-C-3 `-debug` 产物、诊断事件与 N0-C-2 欠账清算

> **10 阶段 N0-C 的第三批，也是收尾批。** N0-C-2（`d95b6ae`）交付了语言上下文、
> 平台异常报告、释放追踪与字节码差分，但留下**五项欠账**并暴露了一个会持续骗人的产物陷阱。
> 本批**先清欠账，再做 10E 八步的第 6 步与第 8 步**。
>
> **一句话概括本批**：让 `-debug` 产物**自己**把诊断窗口打开——**不靠 `xiao` 启动器、
> 不被 GUI 子系统抑制、失败不静默**；并把 N0-C-2 的欠账一并清掉，
> **让四平台门控从人工欠账变成自动跑**。

## 二、欠账清算（5 项，**先做**）

### 2.1 CI 接门控 —— **已定：`schedule` 定时 + 保持手动**

`platform-reproduction.yml` 的 `on:` **只有 `workflow_dispatch`**，四平台矩阵建好了却从不自动跑。
这正是 `10G` 文档里「Linux/macOS 运行期差分矩阵仍待对应 runner 补跑」的根源。

**冻结**：

- **加 `schedule`**（定时触发），**保留 `workflow_dispatch`**（手动）；
- **不加 `push`/`pull_request`**——本阶段节奏是直推 main，PR 触发用处不大且成本高；
- **`reproduce.sh` 已含 `xvfb-run`**（Linux 分支），**本批的窗口验收要复用它**；
- **这是"三平台验证"从人工欠账变成自动的唯一路径**——`10D §五` 说过，
  「每批至少一次齐备环境跑是**唯一能证明那些测试还活着**的动作」。

### 2.2 `stackrestore` 的栈用量**实测**

`10F §七` 与 `10G` 自述：`llvm.stacksave`/`llvm.stackrestore` 只有**生成器覆盖 + `llvm-as` 解析通过**，
**没有实测栈增长**。而 `10G §八` 第 12 条点名禁止把解析验证冒充栈用量结论。

**冻结**：

- **写一个循环内 `try/finally` 迭代多次的原生程序**，**实测栈用量不随迭代增长**；
- **不许**用 `llvm-as` 解析通过代替——那是两回事（解析只看语法，不看运行期栈指针）；
- 反例也要有：**去掉 `stackrestore` 时该程序应当表现出栈增长**（或至少证明确实走到过那条路径）。

### 2.3 `find_renderer` 的陈旧产物陷阱（**用户实际遇到过**）

**现象**：运行 `xiao` 时诊断窗口弹出后立刻报

```
X11-DIAGNOSTIC-START-001: 未知参数：--locale
[已退出进程，代码为 70]
```

**根因（已实测定位）**：

1. `--locale` 的解析与传递**都是 11C 的 `2a3f5fe` 一起加的**——**不是 10G 的回归**；
2. `find_renderer()`（`xiao-driver/src/diagnostics.rs:576-601`）的候选顺序里，
   第三条直接找 `core/rust/target/debug/xiao-diagnostics{suffix}`；
3. **`cargo test` 从不更新这个文件**——它只构建 `deps/` 下的 test harness，
   **只有 `cargo build` 才会**；
4. 于是诊断进程拿到的是一个**不认 `--locale` 的旧版本** → 立即退出。

**⚠️ 这个陷阱会骗人**：审核时门控测试 `real_terminal_session_is_environment_gated`
报的是「**诊断进程未在 10 秒内连接**」，看起来像"环境没有真实终端"；
`cargo build -p xiao-diagnostics` 之后同一测试 **0.57 秒通过**。
**任何"只跑 `cargo test` 不跑 `cargo build`"的流程，诊断进程都在跑旧代码。**

**冻结**：

- **`find_renderer` 已支持 `XIAO_DIAGNOSTICS_PATH`（`:577-581`，最高优先级）**——
  **诊断相关测试应当设它指向 `env!("CARGO_BIN_EXE_xiao-diagnostics")`**，
  cargo 会保证构建正确的 bin，**这是从根上杜绝该类假阴性的方式**；
- **运行期**（不是测试）的同理风险要在 `10D` 或 UseDocs 里写清：
  改了诊断相关代码后必须 `cargo build`，否则产物路径会选到旧的；
- **验收**：**在不执行 `cargo build` 的前提下**，诊断相关门控测试也必须通过。

### 2.4 登记与文档对齐

## 三、必须先冻结的 6 条

### 3.1 `-debug` 产物的**三不**（`:61` + `:72`）

**冻结**：

- **不依赖 `xiao` 启动器**——产物**自带**启动诊断进程的能力，双击/直接运行即可；
- **不受 GUI 子系统抑制**——即使业务程序声明了 GUI 子系统（Windows `/SUBSYSTEM:WINDOWS`）、
  或标准终端不可用，**调试窗口仍要打开**，**不得静默取消**（`:61` 的措辞是"仍不能静默取消"）；
- **⚠️ 难点在"失败时怎么办"**：启动器缺失、套接字连不上、窗口起不来时，
  **要有确定的行为**——**但"静默"不是可选项**。
  **"确定的行为"必须可观测**（非零退出码 / 机器摘要 / 明确的降级路径），
  **不能是"什么也没发生"**。

### 3.2 普通产物：**不带激活位、不自动开窗**（`:73`）

**冻结**：

- 未启用调试的产物**不携带强制诊断激活位**、**不自动打开诊断窗口**；
- **必须有反向测试**：普通产物运行时**不应尝试启动诊断**——
  这一条和 §3.1 是**同一枚硬币的两面**，只验正向会漏掉它。

### 3.3 诊断事件：**真转交，不是空壳**

`xiao_runtime_diagnostic_event`（`xiao-runtime/src/abi.rs:1120`）当前只校验 UTF-8 就 `return Ok`，
**全仓没有调用方**。

**冻结**：

- **让它真转交**到既有诊断会话（`xiao-diagnostics` 的那一套），**不再返回空 Ok**；
- **⚠️ 不查目录、不本地化**——`10:62` 的"原生后端不复制翻译逻辑"同样约束这里；
  机器字段（`event_type`/`code`/`message_id`/位置）**原样透传**；
- **无会话时的行为要确定**（`10E §3.4` 冻结过"无会话时仍保留确定性失败状态"），**不能静默丢弃**。

### 3.4 `-debug` 的语言与 §3.3 的边界

**冻结**：

- **机器字段跨语言一致**（`:74` 已由 N0-C-2 验过，**本批不得回退**）；
- **人类可读文案走 11C-1 的统一渲染器**，**原生侧不复制翻译逻辑**；
- **⚠️ 信号处理器内不能查目录**（非 async-signal-safe，`10G §3.2` 已冻结）——
  所以平台异常报告用**机器摘要或预渲染**；
- **`-debug` 产物的有效语言**：要么随产物保存、要么由启动参数给出
  （`10E §3.3` 留的接口，本批落地）。

### 3.5 CI 验收**分层**（**已定：xvfb + 分层**）

**冻结**：

- **Linux**：`xvfb-run` **真开窗**（`reproduce.sh` 已有该分支，复用）；
- **macOS**：验「**尝试启动 + 不静默失败**」；
- **Windows**：构建**声明 GUI 子系统的产物**，验「**不受 `/SUBSYSTEM:WINDOWS` 抑制**」；
- **三层都断言**：**失败时有确定行为且不静默**（§3.1 第三不）。
  **⚠️ 不要断言"窗口真的出现了"**——那在无桌面 CI 上必然脆弱；
  要断言的是**"产物确实尝试了、且失败路径可观测"**。

### 3.6 与相邻批次的边界

**冻结**：

- **不重开** `10F §七` 的展开契约、`10G` 的错误边界与释放追踪设计；
- **不做 N0-D**（三目标固定宽度、Runtime 裁剪验证、调试构建标志的**产物级验证矩阵**——
  那属于 D）；
- **不做用户可见 `xiao build`**（11 / X0）；
- **不改** 11C 已交付的语言上下文模型、目录与渲染器；
- **本批是 N0-C 的收尾批**——做完它，N0-C 的八步才算走完。

## 六、硬约束

1. **先清欠账、再做新功能**（§二 在 §三 之前）——`10F`/`10G` 的欠账不还，`-debug` 的跨平台验收没有立足点。
2. **`-debug` 三不**：不依赖启动器、不受 GUI 抑制、**失败不静默**（§3.1）。
3. **"失败不静默"必须可观测**——不能是"什么也没发生"。
4. **普通产物要有反向测试**（§3.2）。
5. **诊断事件真转交**，且**不查目录、不本地化**（§3.3）。
6. **栈用量必须实测**，不许用 `llvm-as` 解析冒充（§2.2）。
7. **诊断测试不得依赖已有的 `target/debug` 产物**（§2.3）——用 `XIAO_DIAGNOSTICS_PATH` + `CARGO_BIN_EXE_`。
8. **登记与文档必须对得上**（§2.4）。
9. **门禁**：`cargo test --workspace`、**`bun run check`（含 `check:lock`，两个 lock 文件都要提交）**、
   `cargo clippy --workspace --all-targets -- -D warnings`、TS 类型检查、`cli/ts` 全目录测试；
   **新增门控测试要按 `10D` 写 `#[ignore]` 并同步 §2 清单**。

   Linux/macOS 的平台异常、差分、`-debug` 矩阵**不再依赖人记得**。
2. **`-debug` 产物**（§3.1、`:72`）：
   - **直接启动自动打开独立诊断窗口**；
   - **不依赖 `xiao` 启动器**；
   - **声明 GUI 子系统的产物也不受抑制**（Windows 实测）；
   - **启动失败时有确定且可观测的行为**，**不静默**。
3. **普通产物**（§3.2、`:73`）：不带强制诊断激活位、**不尝试开窗**（反向测试）。
4. **诊断事件**（§3.3）：真的转交给诊断会话；**不查目录、不本地化**；无会话时行为确定。
5. **栈用量实测**（§2.2）：循环内 `try/finally` 迭代多次，**栈不增长**；
   有反例证明确实走到过那条路径。
6. **诊断测试不依赖旧产物**（§2.3）：**不跑 `cargo build` 也能通过**。
7. **`10E`/`10G` 行号已更正**（§2.5）；**登记与文档一致**（§2.4）。
8. **不回归**：N0-A/N0-B、09-B0、11C 系列保持绿；N0-C-2 的差分与平台异常门控保持绿。
9. **门禁全绿**：`bun run check`（含 `check:lock`）、`cargo test --workspace`、clippy、TS 类型检查；

## 十一、实施记录（2026-09-30）

本批代码已按冻结条款落地：

1. `platform-reproduction.yml` 增加定时触发并保留手动触发；Linux/macOS/Windows 复现脚本
   都会实际运行普通与 `-debug` 原生产物，普通产物的诊断反向断言和调试失败摘要断言已接入。
2. `optional_stackrestore_runtime_probe` 使用真实 clang 编译并运行恢复/去恢复两种循环，
   Windows 主机结果为 `1 passed`；它不再把 `llvm-as` 解析结果冒充栈用量实测。
3. Runtime 诊断 ABI 已建立本机端点、令牌握手、事件转交、Final/Close 生命周期和稳定启动
   失败码 `X11-DIAGNOSTIC-START-001`；事件不查目录、不本地化，机器字段和源码位置进入结构化负载。
4. 动态调试原生产物在用户代码前完成准备、启动、握手，普通静态/动态产物不声明或调用诊断
   生命周期；Windows shim 的 locale 占位符、POSIX 终端候选链和失败可观测路径均有回归覆盖。
5. `DiagnosticEvent` 和 `DiagnosticMetrics` 的协议数值字段改为可由 JSON 稳定编码的 `u64`，
   运行时纳秒/毫秒值采用饱和转换，避免首个事件或 Final 帧断链。
6. `10D` 已登记 11 条环境门控测试，`10G` 已记录 `stackrestore` 欠账清算；模块登记暂标为
   `draft`，因为 Linux/macOS 的运行期证据仍需定时工作流实际执行后再升级为 `verified`。
7. 自审核补强了失败收口：握手/启动失败会清理会话并恢复原环境变量，POSIX 超时回收子进程
   有界且可升级为强制终止，macOS 原生 shim 补齐 `osascript` 候选；独立窗口父进程编号拒绝零值。

针对性验证已通过：`xiao-runtime` 诊断会话单测、`xiao-codegen-llvm` 普通/调试 IR 反向测试、
Windows `stackrestore` 真实运行探针，以及受影响 Rust crate 的编译检查。最终门禁中的完整
workspace 测试、Clippy、Bun/TypeScript 检查、文档覆盖和 Windows 原生复现脚本均已通过；
Linux/macOS 的运行期证据仍需定时工作流在对应 runner 上补齐，不能由本机 Windows 结果替代。
