# 17C. 入口与运行器

> **17 阶段的第三批**。17A 钉死了容器与索引，17B 让归档装得进资源与调试对象。
> 本批做[规范](17-xar-archive.md) §「入口与运行器」的 **`17.9`–`17.13`**，
> 外加 17B 审核转来的一项补强。
>
> **一句话概括本批**：**让 `.xar` 真的能跑起来**——把归档从"一堆验证过的字节"
> 变成"一条可执行的启动链路"，并从命令行接上。

## 二、必须先冻结的 9 条

### 2.1 **CLI 两种等价形式**（已决策）

**已决策**（2026-10-04）：**两种命令行形式都要支持**：

```text
xiao -xar <file.xar>
xiao run -xar <file.xar>
```

**冻结**：

- 规范 `:69` 已定 `xiao -xar "<file.xar>"` 为主形式；**第二种是别名**，
  规范同处写「是否保留其他别名由 CLI 阶段决定」，本批即该决定；
- **两者必须完全等价**——同一条执行路径、同样的退出码与诊断，**不得**各写一套；
- 参数顺序：`-xar` 与路径的先后不敏感（与既有 CLI 的选项风格保持一致）。

### 2.2 **协议新增独立的 `run_archive` 操作**

**决策依据**（本批采用独立操作）：

- `run` 的语义是「跑源码」；归档的验证流程与源码**完全不同**——
  要先开中央目录、读唯一索引、校验对象/资源/依赖/平台/Runtime，再解析入口；
- `.xar` 有**源码路径没有的参数**（如归档记录的调试激活位）；
- 复用 `run` 会把「文件类型判断」塞进核心，并让 `run` 的处理路径分支膨胀。

**冻结**：

- 新增协议操作（具体名称在实施第一步定并登记进协议文档，建议 `run_archive`）；
- **`run` 的行为一条都不许改**——既有测试是守门人；
- 协议请求/响应走**既有**的长度前缀 JSON 与 `exit_code`/`diagnostics` 结构，
  **不新造响应形态**。

### 2.3 **启动流程按规范 `:67` 的顺序，且不得部分执行**

规范 `:67` 的九步：中央目录 → 有界读唯一索引 → 验证索引版本与结构 →
校验所有将要加载的 `.xiaoc` 与资源 → 检查虚拟机/Runtime/平台/依赖 →
解析入口 → （若 `-debug`）先起独立诊断进程与窗口 → 调用统一字节码运行接口。

**冻结**：

- **校验或诊断窗口启动失败时不得部分执行已加载模块**（规范 `:67` 末句）——
  这与 17A 的「先验证再暴露」、16A 的「先验证再建 VM」是同一条判据；
- 顺序**不得**调换：尤其**入口解析必须在全部校验之后**，否则会拿未经校验的索引做判断。

### 2.4 **入口解析只读索引，不猜**

`17.9` 要求「定义唯一索引中的入口字段及其与 `[main]`、脚本顶层入口的映射」。

**冻结**：

- 运行时**只**从 `ArchiveIndex.entry` 读入口（17A 已扩展该字段）；
- **不扫描归档成员猜测入口**——与 16A 的「归档索引损坏时**不**靠扫描成员重建」
  是同一条判据（规范 `:80`/`:97`）；
- **入口缺失或指向不存在的成员**要给稳定错误码（见 §2.5），**不得**回落到"第一个模块"之类的猜测。

### 2.5 **错误码续用 `X17-XAR-*` 段，从 `006` 起**

`17.12` 的四类：**缺少对象、版本不兼容、依赖未满足、校验失败**。

**冻结**：

- **续用** 17B 已开的 `X17-XAR-*` 段（`001`–`005` 已占用），**从 `006` 起**，
  **不新起编号段**——新起会与 17B 的登记重复；
- 四类各有稳定 code + `message_id` + 结构化参数 + `SourceSpan`（沿用既有诊断形态）；
- **校验失败**要与 17A/17B 已有的拒绝诊断**打通**（同一错误出口），不另造一套。

### 2.6 **保留 09 的源码映射、错误回溯与 `drop` 记录**

`17.11` 明写：「调用第 09 阶段统一虚拟机接口，**保留源码映射、错误回溯和 `drop` 记录**」。

**冻结**：

- **必须**走 09 的**统一** VM 接口，**不得**为归档另起一条执行路径；
- `.xiaoc` 自带的紧凑源码位置映射要使错误回溯**仍能定位到原始行列**；
- `drop` 记录与释放顺序**不得**因为"从归档加载"而改变
  ——归档是**外层容器**，不改变里层的执行语义。

### 2.7 **不做打包入口，端到端用库层产物**

**已决策**（2026-10-04）：**不做**打包命令。

**冻结**：

- 打包归 **18**（规范 `:47` 说调试包「准确 CLI 参数在第 18 阶段冻结」）；
- 本批的**端到端验证**用**库层 API 生成 `.xar`**，再用 `xiao -xar` 跑——
  这条链路**跨了 CLI 与核心边界**，端到端仍然是真实的；
- **但**库层产物的生成要能**如实反映**打包语义（资源、调试对象、入口），
  不能为了测试造一个"特殊形态"的归档。

### 2.8 **承接 17B 的副作用探针**

17B 的 §八 第 3 条要求「用**副作用探针**断言 `XIAO_HOME` 凭据与环境变量值**不在**归档字节中」，
**实测缺该探针**——防护实现在（`collect_resources` 会 `canonicalize` 根目录、
拒绝符号链接指向根外），但**没有断言锁住它**。

**冻结**：

- 补一条**副作用探针**：构造含凭据的环境，跑一遍打包到归档，**断言归档字节中搜不到该凭据**；
- 这是 [12A](12a-stage-acceptance-audit.md) §2.3「**有实现、缺断言**」形态的第三次出现
  （17A 六类、17B 凭据探针），**不得**再以「实现里有防护」为由跳过。

### 2.9 **不重开 17A/17B/09/11C 的既有冻结面**

**冻结**：

- **不改** 17A 的容器格式、成员布局、索引字段 `1`–`12`；
- **不改** 17B 的资源声明语法、四类诊断语义、`debug`/`source` 的独立性；
- **不改** 09 的调用约定、验证器与指令编码；
- **不改** 11C 的消息目录键与渲染器契约（只**接入**，不改它的规则）。

## 五、硬约束

1. **不得部分执行**（§2.3）——校验或窗口启动失败即整体拒绝；
2. **入口只从索引读**（§2.4）——不扫描成员猜测；
3. **续用 `X17-XAR-*` 段**（§2.5）——不新起；
4. **走 09 的统一 VM**（§2.6）——不为归档另起执行路径；
5. **`run` 行为不变**（§2.2）；
6. **两种 CLI 形式等价**（§2.1）；
7. **不做打包命令**（§2.7）；
8. **不改** 09/11C/17A/17B 的冻结面（§2.9）。

## 六、分步提交

1. **库层运行器**：归档加载 → 校验 → 入口解析 → 调用 09 统一 VM（`17.9`–`17.11`）；
2. **错误码**：四类（`17.12`），续用 `X17-XAR-*`；
3. **语言上下文**：接入 11C，归档记录的语言默认值生效（`17.13`）；
4. **协议**：新增 `run_archive` 操作（§2.2）；
5. **CLI**：`xiao -xar` 与 `xiao run -xar` 两条等价入口（§2.1）；
6. **承接项**：17B 的副作用探针（§2.8）；
7. **端到端**：库层造 `.xar` → `xiao -xar` 跑 → 观察输出与退出码；
8. **文档与登记**：crate README、协议文档、UseDocs、主表。

## 七、最可能翻车的地方

1. **部分执行**（§2.3）——校验没过就跑了半个模块，规范明文禁止。
2. **入口解析早于校验**（§2.3）——拿未校验的索引做判断。
3. **扫描成员猜入口**（§2.4）——16A 已立下「不猜」的判据。
4. **为归档另起执行路径**（§2.6）——两条路径必然漂移，drop 顺序与回溯会不一致。
5. **改了 `run` 的行为**（§2.2）——复用协议时的常见副作用。
6. **两种 CLI 形式各写一套**（§2.1）——退出码与诊断会分叉。
7. **新起错误码段**（§2.5）——与 17B 的登记重复。
8. **顺手把打包命令做了**（§2.7）——与 18 撞车。
9. **忘了 §2.8 的探针**——这是同一形态第三次出现。
10. **忘了 `Cargo.lock` 同步**——`check:lock` 会红（16A 栽过一次）。

## 八、验收

1. **CLI 可用**：`xiao -xar <file.xar>` 与 `xiao run -xar <file.xar>` **两条都跑通**且**输出一致**；
2. **端到端**：库层造出的 `.xar` 能被上述命令**验证并运行**，`print("hello world!")` 有可见输出、退出码 0；
3. **不得部分执行**：故意破坏一个成员的摘要/版本，运行**整体拒绝**且**不产出任何执行副作用**；
4. **入口唯一**：入口从 `ArchiveIndex.entry` 读；缺失或指向不存在的成员有稳定错误码；
5. **错误码四类**（§2.5）：缺少对象、版本不兼容、依赖未满足、校验失败各有 code 与用例；
6. **源码映射保留**（§2.6）：归档内 `.xiaoc` 的错误回溯能定位到原始行列；
7. **`drop` 记录一致**（§2.6）：归档路径与源码路径的释放顺序一致（差分或用例）；
8. **语言上下文**（`17.13`）：归档记录的语言默认值生效；语言资源缺失时**仍输出可读的内置诊断**；
9. **`run` 未受影响**（§2.2）：`xiao run hello.xiao` 仍零诊断、`run` 的既有测试未改且全绿；
10. **承接项**（§2.8）：副作用探针断言凭据不在归档字节中；
11. **不重开**：17A/17B/09/11C 的既有测试**一条未改**且全绿；
12. **不回归**：`cargo test --workspace` 全绿、`cargo clippy --workspace --all-targets -- -D warnings` 绿、
    `cli/ts` 的类型检查与测试通过；
13. **门禁全绿**：`bun run check` 退出码 0（含 `check:lock`，两个 lock 文件都已提交）。

## 九、不负责与不要重复做的事

- **不做**平台文件关联、双击、安装器（`17.14`–`17.17`，归 17D）；
- **不做** `-debug` 的独立诊断窗口与事件传输集成（`17.18`，归 17D）——
  但**要读**索引里的调试激活位（17A 已加字段），**不得**因归档的普通配置而关闭它；
- **不做**打包命令（§2.7，归 18）；
- **不做**数字签名与信任链（规范 `:61` 待定安全决策）；
- **不做**「是否允许平台相关原生组件」（规范 `:47` 末句仍是后续决策）；
- **不重开** 17A 的容器与索引、17B 的资源语法与诊断、09 的调用约定、11C 的消息目录。

## 十、实施记录

- `xiao-xar::run_archive` 先调用 `decode_xar` 完整验证归档，再检查 Runtime ABI、平台和
  索引入口，入口必须指向 `.xiaoc` 对象；未通过任何前置检查都不会进入 VM。运行成功后
  只调用既有 `xiao-vm::run_xiaoc`，不复制执行语义。
- 新增 `X17-XAR-006`（缺少对象）、`007`（版本不兼容）、`008`（依赖/平台不满足）和
  `009`（校验失败），由 `run_archive` 协议响应携带 `message_id`、归档路径和阶段详情。
  语言上下文仍由协议既有 `with_locale` 入口渲染，缺少目录时保留可读原文。
- 协议新增 `run_archive` 能力；CLI 的 `xiao -xar <file.xar>`、`xiao run -xar <file.xar>`
  和选项换序共用同一解析及执行路径。打包命令仍未加入。
- 17B 的副作用探针已补齐：未声明的凭据文件与环境标记不会进入归档字节；资源仍只按
  显式声明读取。归档运行器在调试激活位或 `-debug` 时先启动现有独立诊断会话，失败时
  不执行入口。
- 运行结果沿用 `run` 的 `exit_code`、报告、事件和指标结构，操作字段为 `run_archive`；
  归档运行路径与源码运行路径的 VM 终局映射保持一致。
