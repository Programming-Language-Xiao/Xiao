## 二、本批的范围：把"受控夹具"推到"真实产物"

### 2.1 **这一步的实质**

15D 验的是**判定逻辑**：给一份"不可读的 COFF 表"，判定是否返回 `Unavailable`。
**用构造的字节验这个是准确的做法**——真产物反而不好构造那个场景。

**真实产物能验的是另一类**（夹具验不了的）：

- **链接器实际产出的符号表长什么样**（顺序、内容、在三种格式上的差异）；
- **`strip` 之后实际还能不能诊断**（不是"判定函数怎么说"，而是**产物真的被剥了之后**）；
- **`-debug` 产物在 `-O1`–`-O3` 之后**是否仍能开独立诊断窗口；
- **调试信息里的绝对路径在真实产物里长什么样**。

**所以两层的分工是清楚的**：**夹具验判定，产物验事实**。本批补后者。

### 2.2 **CI 已经具备环境——这是本批最省事的一点**

`reproduce.sh:131` 已经是：

```bash
ignored_command=(cargo test --manifest-path "$cargo_manifest" --workspace -- --ignored)
```

**含义**：**只要把新验证写成 `#[ignore]` 测试，四平台 CI 自动覆盖**。
**不需要改 workflow、不需要加步骤、不需要新的触发方式。**

**冻结**：**本批不修改 `.github/workflows/platform-reproduction.yml`**。
若确实需要改（例如某平台缺工具链），**先说明为什么 `--ignored` 覆盖不到**。

### 2.3 本批要写的门控验证

| # | 验证 | 依赖 |
| --- | --- | --- |
| 1 | **真实产物的 strip 三态**：`Release` / `Debug` / `Stripped` 各跑一次，**在真实链接产物上** | clang + Runtime staticlib |
| 2 | **`-debug` 在各 `-O` 级别仍能开窗**（`-O0`–`-O3`） | 同上 + 诊断组件 |
| 3 | **真实产物的链接器符号表顺序**（三种格式） | 各平台工具链 |
| 4 | **真实产物的调试路径**（`-debug` 产物里的绝对路径被归一化或记录） | 同上 |
| 5 | **重复构建逐字节比较**（15B `§3.1` 要求，此前只在文本层做过） | 同上 |
| 6 | **正式性能基线取数**（15B 模型 + 受控条件） | **CI runner 即为受控条件** ✓ |

**⚠️ 第 6 条要特别说明**：15B/15C/15D 三次都说"没有受控环境就记待补"。
**CI runner 正好是受控条件**——但**跨平台 runner 的硬件不同**，所以
**基线要按平台分别记录**，**不能把三个平台的数字混成一张表**（15B `§3.4` 已冻结）。

## 三、必须先冻结的 6 条

### 3.1 **门控测试按 10D 写，且同步 §2 清单**

**这是硬要求**，10D 已经写得够细：

- **`#[ignore = "需要 …；准备方式见 10D §4"]`**，理由字符串要能定位到准备方式；
- **缺变量用 `expect` 失败，不是静默 `return`**——
  **这是 10C 那次缺陷活下来的原因**（10D 原文：「那条测试从写出来那天起就没真跑过，
  **第一次真跑就失败了**」）；
- **每加一条就同步 10D §2 清单**——清单是**唯一能证明那些测试还活着**的地方。

### 3.2 **真实产物上的 strip 三态，不是判定函数的复测**

15D 已经测过判定逻辑。**本批要测的是产物**。

**冻结**：

- **要真的跑工具链生成产物、真的 strip**，然后**验行为**；
- **"能不能诊断"要落在可观测量上**（诊断进程是否连接、窗口是否尝试打开、退出码），
  **不是"报告里写了什么"**；
- **`Stripped` 模式下不可读是预期的**（15D 已实现 `accepted = true` + 诊断）——
  但**"预期"不等于"不验"**：要断言**诊断确实给出了**，而不是静默。

### 3.3 **基线按平台分别记录，不混表**

15B `§3.4` 已冻结「固定硬件/容器条件」。**CI 的四个 runner 硬件不同。**

**冻结**：

- **每个平台一张表**，**不跨平台比较绝对数字**；
- **噪声阈值按平台各自测量**；
- **同一平台多次运行**才谈得上"回归"。

### 3.4 **平台顺序继续适用**

15A `§3.6` 的 **Windows → Linux → macOS** 继续有效。

**冻结**：**CI 是并行跑的**，但**验收顺序不能因为并行就变成同时**——
**看结果时按顺序读**：Windows 绿了再看 Linux，Linux 绿了再看 macOS。
**某平台红了先修它，不要三平台一起改**（10K 的教训：三平台一起红、根因各异）。

### 3.5 **不改 CI 配置**（§2.2）

**冻结**：本批**不动 workflow**。`--ignored` 已经覆盖。

若必须改，**先说明 `--ignored` 为什么不够**——否则改配置会掩盖"测试没写对"。

### 3.6 **本批不做 16–19 阶段的事**

- **不做** Protobuf 索引与内容寻址缓存（16）——含待定决策 4；
- **不做** `.xar`（17）、TS CLI 参数解析（18）、Java 对照与发布验收（19）；
- **不启用** LTO / PGO / 向量化 / 目标 CPU 特化（待定决策 2）；
- **不冻结**调试信息的发布保留策略（待定决策 3）。

## 本批实现记录

新增 `core/rust/crates/xiao-codegen-llvm/tests/15e_ci_gated.rs`，共 5 条 `#[ignore]`
门控，均要求显式配置工具链环境，不缺变量静默跳过：

- 真实 clang + Runtime staticlib 链接产物在 O0-O3 上分别验收 Release、Debug、Stripped；strip 后产物必须
  仍可运行，且 `Stripped` 报告明确给出不可再验证诊断；
- Debug 激活位在 O0-O3 的真实产物中保留，运行结果为成功或稳定诊断失败；
- 真实符号表顺序、调试路径归一化字段和重复 Release 产物字节比较；
- 按当前 CI runner 的目标与工具链独立采集 15B 五维基线，样本只输出到日志，不进入产物指纹。
  首轮报告携带 20% 的显式初始噪声阈值和实际离散度；首轮只建立平台样本，不把未校准
  的先验阈值当作失败条件，后续按平台实际重复测量校准。

`toolchain.rs` 现在为 Debug 产物传递 `-g`，使路径门控实际覆盖 DWARF/PDB/CodeView；
`artifact.rs` 只有 ELF `.symtab`、Mach-O `LC_SYMTAB` 或实际 COFF 符号表可读时才报告
`Readable`。`reproduce.sh`/`reproduce.ps1` 仅增加 `XIAO_STRIP` 工具准备，workflow 未改，
现有 `--ignored` 会自动覆盖新增测试。产物比较同时归一化 PE 调试目录中的链接器时间戳，
避免真实 Runtime 链接重复构建因 POGO/CodeView 时间字段产生未解释差异；ELF 链接关闭
机器路径相关的 GNU build-id，比较层仍能识别并记录已有 build-id 元数据；Linux ELF
链接器仍可能因临时输入路径改变节布局，门控沿用 15B 的 `BinaryLayout` 白名单并写明原因，
不把该差异伪装成字节完全一致。

本机 Windows 原生工具链已跑通 5 条新增门控：strip/Debug O0-O3、真实符号与路径、
Release 重复字节比较、平台独立基线均通过。其他平台须由四平台 CI 按 Windows → Linux →
macOS 顺序读取结果；本机结果不代替其他平台证据。
