## 二、必须先冻结的 6 条

### 2.1 **入口：先清尾巴，再动 Z-4**

**冻结**：

1. **Z-4 的判定依赖尾巴**——尤其 **T1（阈值冻结）**：阈值没冻结，条件 5 就无从判定；
   **T2（`baseline.json` 回填）**没做，报告与清单就对不上；
2. 顺序：**T1/T2/T3/T4 + B1 判定 → 再写 Z-4**。**不许**先写收口声明再倒推补证据；
3 **B1 的判定若不落在本批**（例如需要更多实验），**不算阻塞 Z-4**——但条件 2 的缺口清单要**如实保留它**，
   不许因为「还没判完」就把那条豁免写成「已解释」；
4. 若某笔尾巴因故做不了，**如实记为未完成并写明原因**，不许用「部分」含糊过去（[10Z-收尾](10z-closeout-execution.md) §2.7 的口径）。

### 2.2 **T1：阈值冻结要有依据，不是拍一个数**

**冻结**：

1. 填 `tests/benchmarks/baseline.json` 的 `threshold`：`status`、`allowed_error`、`regression_limit`；
2. **必须写出冻结依据**：这一轮的**比值、置信区间、误差来源**，以及为什么取这个门槛——
   「拍一个数」不算冻结；
3. **同步 `baseline_id` 与 sha256**（冻结属基线变更），并在提交说明里写清；
4. **冻结后按阈值给出判定**（通过 / 回归 / 数据不足）——**这是本批第一次可以真正判条件 5 的地方**；
5. **不得调优**：冻结只看已有的那一轮数据，**不许先改实现让数字好看再冻结**。

### 2.3 **T2/T3：回填是「据实」，不是「补齐」**

**冻结**：

1. 回填 `baseline.json` 的槽位时，**每一格都对应实测**：`runtime.resolved_version` 与
   `version_text_sha256` 来自那一轮的 `java -version` 文本；各 workload 的 `performance_status`
   与报告一致；**`platforms.linux` 由 `not-measured` 改为实测**；
2. **`container-dense` 的理由必须改**——它现在的 `data-insufficient` 理由来自 **Windows** 观察，
   而 Linux 上它是 `measured`。要**写明平台差异**：Linux 通过、Windows 那条观察仍成立（若仍成立）；
3. **`platforms.windows-native` 保持标缺**、`platforms.macos` 保持**不可验证**——
   **不得**顺手用本机或 CI 数字填上（[10Z](10z-19-closeout-and-b-series-implementation.md) §2.4）；
4. 回填后**清单与报告要能对上**：拿那一轮的 JSON 逐格核，不一致就是回填错了。

### 2.4 **T4：修 `host_cpu_model()` 并给出反例**

**冻结**：

1. 修匹配逻辑（容忍 `/proc/cpuinfo` 的分隔符），或改用 `lscpu`；
2. **必须有一次反例验证**：修之前在同一台机器上跑，`cpu_model` 是 `unavailable`；
   修之后是真实型号——**两个输出都留**。只有「修好了」不算证据（本批一路的教训）；
3. 该字段进的是 `HostSnapshot`，属**受控环境记录**的一部分；它缺失会让「固定硬件」的证据变弱，
   所以这不是纯装饰性的修复。

### 2.5 **B1 的释放性质判定：成对实验，且如实登记**

**冻结**：

1. 已收窄的范围写死在 [10Z-Z1](10z-z1-scope-and-gap-verdict.md) §三 末尾：
   **Runtime 入口本身能归零**（有夹具），**嫌疑在原生调用点的实参/临时槽组合**；
2. **成对实验**：只改一处 → 采数 → 恢复；给出 `destroy` 是否出现、轨迹是否与 VM 逐项一致；
3. **判定为泄漏 → 应当修**；判定为口径 → 按四要素（事件数 / 对象数 / 销毁位置 / 持有机制）
   把依据登记全；
4. **不许**因为「夹具已经证明了入口没问题」就顺手撤销豁免——[10Z-Z1](10z-z1-scope-and-gap-verdict.md) 末尾
   已写明那条夹具**不覆盖调用点组合**；
5. 判定结论回写 [10P](10p-differential-exemption-and-coverage.md)（**加列不抹旧判定**）与 [10Z-Z1](10z-z1-scope-and-gap-verdict.md)。

### 2.6 **Z-4：判定是什么就写什么，且必须写明覆盖边界**

**冻结**：

1. 对 [19D](19d-performance-comparison.md) 的 O6 五条**逐条**给出「满足 / 部分 / 不满足」+ 证据 + 限制；
   **现状是四条「部分」+ 一条「不满足」，没有一条是「满足」**——**本批要做的是判成它实际的样子**；
2. **收口声明必须写明覆盖边界**（星崽 2026-10-08 定）：哪些平台/能力被覆盖、哪些被明确排除、各自为什么。
   `19.14` 的 macOS 一格是**不可验证**（不是「未验证」），Windows 性能格是**标缺**——
   这些都**算不阻塞收口，但必须写明**；**不得**把它们换个词说成「已验证/满足」；
3. **不得**为了让 10 系列关掉而：放宽错误身份、删用例、缩小覆盖、用 CI 数字充当性能证据、

4. **若结论是「不能收口」，就写不能收口**，并列出还差什么、归谁、卡在哪；
5. 收口声明落点见 §三；**产物是一份可独立阅读的声明**，不是散落在各文档里的几句话。

## 待定决策

1. **条件 5 在阈值冻结后能不能判「满足」**：它要求「按 Windows → Linux → macOS 记录结果」，
   而 Windows 是**标缺**（不是结果）、macOS **不可验证**。是按「标缺/不可验证算已记录、不阻塞」
   （与 macOS 那格同一口径）判，还是按「Windows 那格没有结果 ⇒ 条件不满足」判？
   审核**倾向仍判「部分」**——因为 Windows 那格**不是「不可验证」（有宿主就能做），而是「暂无专用主机」**，
   性质与 macOS 不同，写成满足会把「还没做」写成「不用做」。
2. **B1 若判为泄漏**：修它属于 10 系列还是 20 系列？审核**倾向 10 系列内修**——
   它是 B1 自己引入的（[10Z-Z1](10z-z1-scope-and-gap-verdict.md) §三 末尾），
   不修就会带着一笔已知泄漏进入 20。
3. **10 系列关闭后是否立即转 20 系列**，还是先把 §2.7 第 3 条列出的未完成项带走/留下列清后再转。
