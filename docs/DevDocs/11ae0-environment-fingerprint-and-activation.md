## 四、Shell 钩子的跨平台现实

### 4.1 设计已冻结的部分

`11a:59`：普通子进程改不了父终端 → **一次性初始化的 Shell 钩子**；钩子调 `xiao`
可执行程序、接收**经过校验的环境变更**、再应用到当前终端；
**「编译器进程不能直接改写 Shell 配置文件」**。

`11a:61-68`：激活后**只在原提示符之前**加绿色前缀，环境名与前后两个 `$` 都绿、后接空格：

```text
$dev$ D:\project\xiao>
$dev$ /home/project/xiao$
```

且明说「上例**只表达前缀结构**」；路径、用户/主机、结尾符号、原有配色**由用户原提示符决定**；
**切换或退出必须恢复原提示符，不能反复叠加**。

`11a:70`（**降低难度的一条**）：`run`/`build`/`test` **仍能自动定位项目环境**，
「自动激活」不等于这些命令依赖终端已激活。**激活状态主要影响交互提示和 `install`/`i` 的目标。**

### 4.2 ⚠️ 文档的 Windows 示例给的是 **cmd** 风格，而 cmd 没有钩子机制

示例 `$dev$ D:\project\xiao>` 是 **cmd** 的提示符（PowerShell 是 `PS D:\...>`）。
而 **cmd 无法在会话内让子进程改父进程的 `PROMPT`**，要自动只能改注册表
`HKCU\Software\Microsoft\Command Processor\AutoRun`——**那比「改写 Shell 配置文件」
更进一步，直接违反 `11a:59` 的禁令**。

**所以 cmd 必然落在第 3 条待冻结项（不支持钩子的降级）**。E0 要么：
- **(a)** 把 cmd 明确定义为「不支持钩子」的样本，走降级路径；
- **(b)** 改掉 `11a:63` 的示例，改用 PowerShell 形态。

**两种都要写进文档**，不能让示例悬着。

### 4.3 三个 Shell 各自的实现要点（文档全没写，属待冻结内容）

| Shell | 改什么 | 已知坑 |
| --- | --- | --- |
| **bash/zsh** | `PS1`（zsh 还有 `PROMPT`/`RPROMPT`/`precmd`） | 须保存原值以便还原；`PS1` 里已有的 `\e` 转义要处理 |
| **PowerShell** | `prompt` 函数（保存原 `Function:prompt` 脚本块） | ⚠️ **PS 5.1 不支持 `` `e `` 转义**，这是真实兼容坑（`11x0p1` 刚在 `reproduce.ps1` 上踩过 PowerShell 5.1 的坑） |
| **cmd.exe** | `PROMPT` 环境变量（`$E[32m`，需 VT） | **无法保存/还原任意原提示符**，也无法跨进程改父会话 → **必然降级** |

**颜色降级**：`cli/ts/src/commands/parser.ts:6` 已有 `color: "auto" | "always" | "never"`，
`cli/ts/src/ui/` 是既有降级落点——但**两者与钩子的接线文档里没写**。
非 TTY / `NO_COLOR` 时前缀如何呈现（纯文本？不加前缀？）**要先定**。

## 五、⚠️ 最大隐性工作量：**测试设施要从零新建**

### 5.1 条件 4 的验收要求断言**父终端状态**

`11a:499` 的验收：「重复激活不会叠加提示符前缀，**取消或切换环境后能够恢复原提示符**」。

**这是父 shell 会话状态**——**普通 stdin 管道根本无法表达**（子进程改不了父进程的 `PS1`）。

### 5.2 而 `12-tests:33` 的伪终端要求**适用**

> 涉及**按键、粘贴、软换行与颜色的用例必须使用可控的伪终端或等价终端测试层，
> 不能只测试普通标准输入管道。

条件 4 的「**绿色**前缀」正落在「颜色」与「交互终端行为」两个词上。**所以这是硬约束。**

### 5.3 仓库**没有任何**伪终端设施

- `pty` / `conpty` / `expectrl` 在所有 `Cargo.toml` 里**零命中**；
- 最接近的「真实终端」设施是 `xiao-driver/src/diagnostics.rs:844` 的
  `real_terminal_session_is_environment_gated`——**但它是开一个独立 GUI 终端窗口**
  再做 TCP 回环握手，验证「诊断窗口能打开」，**不能用来测 `PS1`**。

**所以 E0 需要新建跨进程终端测试层**，形态必然是：
启动真实 `bash`/`pwsh` → 注入钩子 → 执行 `xiao venv dev` →
**断言父 shell 的提示符字符串被改绿** → 断言取消后还原、重复激活不叠加。

⚠️ **这与仓内既有的两套测试设施都不同**：`tests/spec/*.json` 是静态夹具、
`xiao-package/tests/d1_package.rs` 是写临时项目跑 Rust API——**两者都无法断言父 shell 状态**。

**两条路**：引入伪终端依赖（`portable-pty` 等），或**按 `10D` 用 `#[ignore]` 环境门控**
+ 显式准备方式，把「需要真实 shell」的用例隔离出去。
**要在文档里拍板选哪条**，并说明另一半的代价。

## 六、指纹（条件 2）：复用与新建

### 6.1 可复用的（**但会牵出依赖方向问题，见 §七.2**）

| 维度 | 现成物 | 位置 |
| --- | --- | --- |
| 工具链 | `Toolchain::fingerprint(target, codegen_version) -> ToolchainFingerprint` | `xiao-codegen-llvm/src/toolchain.rs:167` |
| 目标条件 | `TargetDescription::fingerprint_fields()` | `xiao-codegen-llvm/src/target.rs:178` |

⚠️ 工具链指纹有一条**必须继承的设计原则**（`toolchain.rs:163-166`）：
「指纹输入**不含绝对路径**，避免同一工具链安装到不同目录后产生无意义失配」。
E0 的配置指纹**同理不能含项目绝对路径**。

### 6.2 ⚠️ 顺手修：`toolchain.rs` 里有一份**漏网的重复实现**

`toolchain.rs:886` 的 `fnv1a64` 与 `text.rs` 的 `stable_hash` 是**同一算法**：

```rust
// toolchain.rs:886
fn fnv1a64(bytes: &[u8]) -> u64 { /* FNV-1a 逐字节 */ }
// 调用处 toolchain.rs:898：format!("{:016x}", fnv1a64(&bytes))  ← 与 stable_hash 逐字节等价
// 另一处 toolchain.rs:186："xiao-fnv1a64-{:016x}", fnv1a64(...)  ← 加个前缀即可
```

而 `text.rs` 的文件注释就写着「LLVM 文本**和构建指纹**共用的纯文本辅助」——
**它本来就是为此准备的**。

**这是 `11X0-H` 合并时的漏网之鱼**：那批把 `ir.rs`/`dynamic.rs` 的两份合到了 `text.rs`，
架构测试也断言了「两边不许自己定义」——**但只断言了 `ir.rs` 和门面，没扫 `toolchain.rs`**。

**E0 正好要做指纹，正是修它的时机**。⚠️ 但**不能只删 `fnv1a64`**——
还要把 `dynamic_architecture_tests.rs:67-70` 的断言**扩到整个 crate**，
否则同样的漏网会再发生一次。

### 6.3 配置指纹是**全新的**

`ConfigDocument` 是 `BTreeMap` 树，**没有任何规范化序列化**（`NormalizedConfig` 只是类型别名）。

⚠️ **一个必须先声明的选择**：`00-decisions:293` 已冻结「包源索引的 JSON 规范化采用
**RFC 8785（JCS）**」且「**Rust 与 TS 必须共用同一组规范化测试向量**」。
**E0 的配置指纹要不要纳入 JCS**——不声明就会造出**第二套规范化**，
而那正是 `00-decisions:293` 点名的「本仓登记在案的头号病史」。

**另外**：`PackageGraph`（D1 的成果）是**内存图、无 serde、无摘要**。
若环境元数据要含依赖图，**必须消费它的 `resolution_order`（依赖优先序）而不是重算拓扑序**——
`model.rs:157-165`。

## 七、落点与依赖方向

### 7.1 落点

- **Rust**：`xiao-package`。它的 README 明写职责含「**环境物化**」，
  建议新建 `src/environment.rs` 一类的子模块。
  ⚠️ 新增 `.rs` 要同步 `module-registry.json:36` 的 `code` 数组，**测试文件同步 `tests` 数组**。
- **TS**：`cli/ts/src/environments/`（README 已声明职责：「虚拟环境命令、Shell 激活/取消激活钩子、
  `$环境名$` 前缀」，且明写**不实现依赖求解**）。

### 7.2 ⚠️ 复用指纹会引入**图里没有的依赖边**

若 E0 复用 `Toolchain::fingerprint` 与 `TargetDescription::fingerprint_fields`，
就引入 **`xiao-package → xiao-codegen-llvm`**——而 `00a-project-layout.md:62-73` 的图里
**只有** `xiao-config`/`xiao-modules → `xiao-package`。

按 D1 的惯例（那次也是「先补图再落代码」，见 `11ad1:144-159`），**必须先补这张图**。

**替代方案**：把指纹的**输入**（字符串字段）而非**实现**传进 `xiao-package`，
由调用方（`xiao-driver`）拼装——那样不新增依赖边，但会造出第二处拼装点，
违反单一来源。**两条路要在文档里拍板并写明理由。**

### 7.3 ⚠️ `environments/` 未登记，放第一个 `.ts` 就报错

`module-registry.json` 的 `ts.xiao-cli.code` **不含** `cli/ts/src/environments`。
门禁 `A0-LAYOUT-002`（`tools/repo-check/src/layout.ts:83-102`）只把**含源码扩展名的目录**
当源目录——所以现在只有 README 不报错，**放入第一个 `.ts` 立刻报「未登记」**。

**登记方式**：并入 `ts.xiao-cli.code` 加 `"cli/ts/src/environments"`，
并把新增测试文件加进该条目的 `tests` 数组（注意：现有惯例是 **`code` 用目录级、
`tests` 用文件级**，别写错）。

### 7.4 CLI 命令接入

加 `venv` 分支要动四处（`parser.ts` 的联合类型 `:14-21`、分发链 `:55-66`、
新解析函数、`helpText()` `:70-83`）+ 执行入口 `commands/index.ts:51-60`。

**未实现命令的先例是 `X11-CLI-REPL-001`**（`index.ts:55`）：
解析成功、执行层返回稳定诊断。但 `11a:417` 要求 E0 **真实现** `venv`，
所以**要新增 `X11-CLI-VENV-*` 编号**（现有只有 `X11-CLI-ARG-001` 与 `-REPL-001`）。

## 十、最可能翻车的地方

1. **跳过 §二 直接写码**——尤其**第 4 条（`venv` 目录基准）**，D1 的清单都漏了它。
2. **把 E0 当成"要做完整钩子矩阵"**（§2.1）——那会让本批爆炸；矩阵归 E3D。
3. **低估测试设施**（§五）——以为"加个脚本"就行，结果发现要新建跨进程终端测试层。
4. **为 cmd 硬做自动激活**（§四.2）——改注册表违反 `11a:59` 的禁令。**该降级就降级。**
5. **PowerShell 5.1 的颜色转义**（§四.3）——`` `e `` 在 5.1 里不工作。
6. **造出第二套 JSON 规范化**（§六.3）——不声明是否纳入 RFC 8785 就会犯头号病史。
7. **重算拓扑序**（§六.3）——D1 的 `resolution_order` 就是为此存在的。
8. **只删 `fnv1a64` 不扩断言**（§六.2）——漏网会再发生。
9. **在未登记的目录里放第一个 `.ts`**（§七.3）——`A0-LAYOUT-002` 会拦。

## 十一、验收

1. **§二 的 5 条已冻结**，且写进了 `11a`/`00-decisions`，不是只写在本文档；
2. **`00a` 的依赖方向图含 E0 引入的边**（或写明为何不引入）；
3. **`fnv1a64` 已合并到 `stable_hash`**，且**架构断言扩到整个 crate**
   （撤掉合并该断言必须失败）；
4. **条件 1**：消费 `ConfigDocument`，不重新扫描、不执行代码；
5. **条件 2**：配置/工具链/目标三者指纹稳定；**同输入同输出**、**不含绝对路径**；
   **已声明是否纳入 RFC 8785**；
6. **条件 3**：`xiao venv` → 逻辑名 `venv`/目录 `.venv`；`xiao venv dev` → 都是 `dev`；
   **目录基准符合冻结的规则**；重复创建有稳定诊断（**新编号已定**）；
7. **条件 4**：至少一种 Shell 走通完整闭环（激活 → 绿前缀 → 取消 → 还原 → 重复激活不叠加），
   **至少一种不支持钩子的降级路径**，且**降级行为符合冻结规则**；
8. **终端测试用可控的伪终端或等价层**（`12-tests:33`），或按 `10D` 显式门控并写明准备方式；
9. **未接入网络、未执行包代码**；
10. **门禁全绿**，含 `check:lock`、`bunx tsc`。
