# 11B-I4b. 会话生命周期与 TS 接入

> **11B 的最后一批。** I4a2 已把**单次 `run` 内**的包加载打通
> （导入指令、命名空间、导出值载体、去重、失败重试）。
> 本批把它推到**会话级**，并把 TS 侧接上。
>

> 变成「**有状态的会话**」。协议**一个字段都不改**，但**同一个核心进程内多次 `run`
> 会共享已初始化模块与表状态**——这是 `11b:71` 要的，也是本批最大的风险面（§3.3）。
>
> 本批交付后 **11B 全线完成**（I4a 的搁置项由 I4a2 + 本批共同收口）。

## 三、冻结条款与实施结果

### 3.1 长驻形态：**CLI 持有长驻进程，核心侧会话状态跨请求复用**（已实施）

- **TS 侧**：`session.ts` 与 `multiline.ts` **不再每次 `new ProtocolClient`**，
  而是持有**一个**实例跨行复用；会话结束时才 `shutdown`；
- **Rust 侧**：核心进程持有 `FrontendVmDriver` 与 `VmSession`；每次 `run`
  新建主程序 VM，但复用同一会话的已初始化模块与表状态；
- **协议一个字都不改**——这是选它的理由：改动集中在两边的会话生命周期，
  不扩协议、不动向量、旧客户端无需降级分支。

**⚠️ 代价必须一并接受**：**核心进程从无状态变成有状态**。
下面 §3.2–§3.5 全是这条的推论，**不能只做长驻而不管它们**。

### 3.2 状态失效：**每次 `run` 校验环境指纹，不一致就重置会话**（已实施）

用户在会话期间可能 `xiao add` 了新包、切了虚拟环境。**会话状态必须跟着变。**

**冻结**：

- **每次 `run` 时由核心读取当前活跃环境与包视图的指纹**，与上次比对；协议不增字段；
- **不一致 → 丢弃会话状态重开**（VM、模块表、已初始化集合全部重建）；
- **⚠️ 指纹要覆盖**：活跃环境路径（`XIAO_ACTIVE_ENV`）、包视图的内容
  （至少是包名与版本集合）——**只有路径不够**，`xiao add` 不改变环境路径；
- **⚠️ 指纹的来源要单一**：复用 E0 既有的环境指纹做法，
  **不要为会话另造一套指纹**——那是本仓头号病史。

**⚠️ 重置的粒度是"整个会话"**，不是"受影响的模块"——
增量失效需要依赖图，代价远超收益，且容易做错（漏失效比全失效更糟）。

### 3.3 **这是一条语义变更**：核心进程内多次 `run` 会共享状态

**⚠️ 本批最需要显式记录的一点。**

改动前：`run` 是无状态的，**任何一次 `run` 互不影响**。
改动后：**同一个核心进程内的多次 `run` 共享已初始化模块与表状态**，主程序 VM 每次重建。

**冻结**：

- **这是 `11b:71` 要的**（「一个 REPL 运行实例」），**但要写进协议 UseDoc**——
  因为它改的是「`run` 的语义」而**不是字段**，最容易在读协议时被漏掉；
- **⚠️ 同一进程内多次 `run` 之间，模块初始化只发生一次**；
  **用户可见的后果**：有副作用的模块（计数器、表状态）**不再每次归零**；
- **⚠️ 每次 `run` 的普通变量仍然不跨行保持**（`Session` 的顶层绑定）。
  主程序声明的单例表也须逐次重新初始化；**模块级状态保持、语句级状态不保持**——
  这个区分要写清楚，否则会被误读成「REPL 有变量记忆了」；
- **旧客户端不受影响**：它们每次新起进程，自然拿到全新状态。

### 3.4 并发：**会话是有状态的，请求必须串行**（已实施）

`11A-CONC` §一 冻结的是**工具链内部**并发（`std::thread::scope`、有界、
结果按 `config_order` 重排）——那是**包管理**的场景，**与本批不同**。

**冻结**：

- **一个会话内的 `run` 必须串行**——有状态的 VM 不能并发执行；
- **⚠️ 但核心进程仍然接收并发请求**（`serve` 把请求派给独立工作线程）。
  **要冻结的是**：**同一个会话的请求排队**，
  不同核心进程之间可以并行；
- **⚠️ 要与 `11A-CONC` 的冻结显式区分**——本批**不重开**工具链内部并发的结论，
  只是它不适用于会话状态。**这条区分要写进文档**，否则后来者会以为冲突。

### 3.5 异常后的状态：**失败不得污染会话**（已实施）

长驻之后，**一次失败的 `run` 可能留下半初始化的 VM 状态**，
而它会被下一次 `run` 继承——这是长驻最危险的失败模式。

**冻结**：

- **一次 `run` 失败后，会话必须仍然可用**（`12-tests:865` 的要求在会话级同样成立）；
- **⚠️ 模块初始化的失败不缓存**（I4a2 已实现），**下一次引用会重试**——
  在长驻下这要求**失败的模块不留在 `initialized_modules` 里**（已满足，要保住）；
- **⚠️ 要冻结"状态损坏"的判定与恢复**：
  若 VM 处于无法继续的状态（例如栈未清空、有未完成的初始化），
  **宁可丢弃整个会话重开**，不要带着可疑状态继续跑。
  **判定条件要明确，不能靠"看起来还行"**。

### 3.6 TS 侧的接入：注册、呈现、以及**不重写语义**（已实施）

- **首次真实执行前**：TS 用 I4a 的 `repl_packages` 请求只读查询包视图，
  核心侧在 `run` 时只登记根名称，**不加载任何模块**（`11b:71` 的红线，I4a 的探针已在守）；
- **首次引用时**：**由 VM 侧触发加载**（I4a §3.2 已冻结）——
  **TS 侧不得先调加载请求再 `run`**；
- **失败呈现**：I4a2 的诊断带**包名、来源环境、底层原因**，
  **TS 侧要原样呈现这三项**，不得只显示一个笼统的「加载失败」；
- **⚠️ 命名空间注册不得触发加载**——这条 I4a 的探针已覆盖，
  本批接入后**探针必须仍然绿**（§九 第 5 条）。

## 八、最可能翻车的地方

1. **只做长驻，不接失效与恢复**（§3.2、§3.5）——长驻是三步里最容易的那步，
   另外两步不做就会留下"会话越跑越脏"的 bug。
2. **指纹只比环境路径**（§3.2）——`xiao add` 不改变路径，用户装了新包却引不到。
3. **把语义变更当字段变更**（§3.3）——协议没改字段就以为没改语义，UseDoc 漏写。
4. **让模块级状态保持被误读成变量保持**（§3.3）——要写清"模块保持、语句不保持"。
5. **会话内并发跑 `run`**（§3.4）——有状态 VM 会崩。
6. **以为与 `11A-CONC` 冲突而重开它的冻结**（§3.4）——两者语境不同。
7. **失败的 `run` 留下半初始化状态被下次继承**（§3.5）。
8. **TS 侧先调加载再 `run`**（§3.6）——违反 I4a 的冻结，且让"至多一次"失去意义。
9. **接入包视图时触发了加载**（§3.6）——I4a 的探针会红。
10. **只跑部分 crate 就说门禁全绿**（§2.2）——这次的存量债就是这么躲了四天。
