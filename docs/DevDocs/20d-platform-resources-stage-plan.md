# 20D. 平台资源：阶段规划与 20C 出口对账

> **背景**：20C 已走完九批。路线稿 [20. 内置函数与标准库](20-builtins-and-standard-library.md) §七
> 把下一阶段定为 **20D 平台资源**，交付物「**文件/目录/进程首批 API、能力上下文、三平台差分**」，
> **前置**是「**Windows 平台适配稳定，资源句柄契约冻结**」。
>
> **但**：规划前核了两件事，都不乐观——
> **(a) 20C 没有成文的阶段出口条件**（只有模块级验收与批次链）；
> **(b) 20D 的前置未满足**：方向稿 §八 把与资源句柄直接相关的三条明列为「**仍待冻结**」，
> 而「**能力上下文**」在仓内**不存在**（§三，逐条给实测）。
>
> **一句话概括**：**先给 20C 写出口条件并对账，再把 20D 的前置冻结做成它的第一批**——
> 而不是直接去写文件/目录/进程的 API 计划。

状态：**规划完成（2026-10-17）**：§六 三条**全部裁定**（均取甲）。
**结论**：20C 按 §4.1 四条关闭、并把「集合」立项带走；
**20D 的前置目前不满足**（§三 资源句柄契约未冻 + §6.2 判据的 (b) 半不满足），
所以第一步只能是 **20D-冻结**，不是实现。**未改任何代码。**

## 一、为什么在这个节点规划

1. **20C 已经九批**，且**它的路线稿交付物有一项没交**（§2.1 的「集合」那一行）——
   继续往里加批次之前，得先把「20C 要交什么」写下来，否则批次链没有终点；
2. **20D 的前置未满足**，而这是**实测**出来的（§三），不是推测；
3. **能力上下文是 20D 的地基**：方向稿 §5.1 要求「**所有外部操作必须通过该上下文进入**」，
   而它现在**不存在**——不先建它，文件/目录/进程的 API 一写就是绕过能力模型；
4. 既定纪律：**先清欠账再开新阶段**。

## 二、20C 出口对账（**先做**）

### 2.1 交付物逐条（对方向稿 §七 里 20C 那一行）

路线稿原文的交付是「**路径、文本、集合等官方 Xiao 模块及兼容元数据**」。
逐条核现状（`ls stdlib/` 与第五批复探表）：

| 交付物 | 现状 | 判定 |
| --- | --- | --- |
| **路径**模块 | `stdlib/path.xiao`（`join`）已交付、`verified` | **已交** |
| **文本**模块 | `stdlib/text.xiao`（`contains_char`/`length`/`is_ascii_upper`/`lower_ascii`）已交付、`verified` | **已交** |
| **集合**模块 | **不存在**。第五批复探：「集合最小操作 | 成功，`ok` | 成功 | **只保留探测结论**；**公共函数参数类型尚未冻结**」 | **未交** |
| 兼容元数据 | `docs/module-registry.json` 的 `stdlib.` 条目 + `StandardLibraryIdentity` | **已交** |

⇒ **20C 现在不能按路线稿关闭**：它自己的交付物里有一项（集合）**连前置都没解封**。
而那个前置是**语言侧**的——「**公共函数参数类型**」未冻结，属容器/泛型参数能力的登记缺口，
**不是** 20C 这一阶段内部能补的。

### 2.2 未清候选（**带走清单**，不是「已被否决」）

这些是 20C 期间**探测过、被既定边界挡住、已登记**的候选。**20C 关不关都不改变它们的状态**，
但**必须逐条写清归属**，否则下一阶段会重新发现它们（[11C](11c1-message-migration.md):123 的教训）：

| 候选 | 最近的挡点 | 归属 |
| --- | --- | --- |
| 字面量常量折叠（字符串字面量比较 `X02-TYPE-005`） | 编译期求值路径未开放 | **语言批次**（未立项） |
| 子串查找 / 切分 | `X01-PARSE-007` / `X02-TYPE-005` | **语言批次**（依赖非字面量下标与容器参数类型） |
| **集合公共接口** | **公共函数参数类型未冻结** | **语言批次**（**它同时是 20C 交付物的前置**，见 §2.1） |
| 非字面量下标 `s[i]`（`X03-TYPE-003`） | 迭代器式语言的既定边界 | 见下方**坏引用**更正 |
| `lint`/`lfloat` 高精度算术 | 清单见 [第九批](20c-ninth-batch-unsupported-diagnostic-split.md)，[02. 类型系统](02-type-system.md):144 | **语言批次**（02 的二级实现任务） |
| 浮点族与 `lfloat` 的转换方向 | 第八批裁定「本批不做」 | **语言批次** |

**一条坏引用的更正（审核侧，2026-10-17）**：
[20C](20c-official-xiao-library.md):395 把非字面量下标写成「与 [00. 决策基线](00-decisions.md) **第 669 行**待定项相连」。
实测：**第 669 行现在是 `X05-PARSE-*` 的错误编号**，与下标无关；
而 00 的 `## 待定决策`（第 707 行起）**通篇没有**非字面量下标这一项
（最接近的是「从异构容器按运行时索引……读取值时，静态结果类型用什么表示」——
那是**结果类型**的问题，不是**下标能否非字面量**）。
⇒ **这条交叉引用既是漂移的行号、也对不上内容**。本文**不沿用**它；
非字面量下标的归属按「类型层既定边界」记，**要不要立项由星崽定**。

### 2.3 20C 缺一份成文的出口条件——本文件补上

**事实**：20C 文档有**模块级**验收（[20C](20c-official-xiao-library.md) §3.4 六条）与**批次链**，
但**没有**「满足什么才算 20C 结束」的一句话。10 系列当初有（[10Z-收尾](10z-closeout-execution.md) §2.5 七项），
20C 没有——**所以「20C 能不能关」现在无从判定**。

**本文件给出提案（§四 第 1 组）**，由星崽裁定后写回 20C 文档。

## 三、20D 的前置：实测缺口

方向稿 §七 给 20D 写的前置是「**Windows 平台适配稳定，资源句柄契约冻结**」。逐条核：

### 3.1 资源句柄契约：**未冻结**，而且方向稿自己列了三条待冻结

[20. 内置函数与标准库](20-builtins-and-standard-library.md) §四 给了**最低契约**（六条：
单线程 Runtime 对象、不暴露宿主裸指针、克隆即共享、关闭幂等、失效别名报稳定错误、
释放钩子错误走 `suppressed`），**但** §4.1 末句写着：

> 具体的**显式关闭 API**、**关闭后别名的错误身份**和**每种资源的复制/继承语义**，
> 在**第一个资源 intrinsic 实现前冻结**。

而 §八「仍待冻结的问题」里，与 20D 直接相关的有**三条**：

| §八 条目 | 内容 | 对 20D 的影响 |
| --- | --- | --- |
| 第 3 条 | Runtime ABI 的稳定调用约定、错误返回布局和**资源句柄跨模块边界** | 句柄能不能过模块边界、以什么 ABI 形式 |
| 第 5 条 | **`ExternalResource` 的具体资源种类、显式关闭语义、继承/复制和跨调用边界规则** | 就是 §4.1 末句要冻的那批 |
| 第 6 条 | **首批 `os` API、平台能力清单及缺失能力的稳定错误码** | 没有它就没有验收对象 |

⇒ **前置「资源句柄契约冻结」不成立**。

### 3.2 能力上下文：**不存在**（这条最要紧）

方向稿 §5.1 要求：

> Runtime 请求**应携带规范化的能力上下文**，至少能表达文件系统、时钟、进程和网络等能力；
> 首版默认上下文可以**全开**，但**所有外部操作必须通过该上下文进入**。

**实测现状**：

- 契约层**有**能力声明 ✓：`xiao-intrinsics/src/lib.rs:97` 的 `Capability` 枚举目前只有
  `None` / `Stdout` / `Stdin` 三个变体；`intrinsics.json` 里 `capability` 的实际取值分布是
  **20 条 `none` + 1 条 `stdout`（`print`）+ 1 条 `stdin`（`input`）**；
- 消费点**只有两处**，且都是**形状校验**：`xiao-vm/src/semantics/exec.rs:1956` 与 `:1980`
  检查「这条 intrinsic 的 `capability` 必须恰好是 `Stdout`/`Stdin`」；
- **`xiao-runtime` 与 `xiao-driver` 里没有任何能力上下文的运行时表示**（按 `capability`
  全仓检索，除契约表生成与上面两处校验外**零命中**）。

⇒ **能力现在是一个「声明字段 + 两处校验」，不是一条执行路径**；
方向稿要的「**所有外部操作通过上下文进入**」**尚无载体**。
**这是 20D 的地基，不是它的一个子任务。**

### 3.3 「Windows 平台适配稳定」：没有成文判据

维护回归的两个原生作业（Windows/Linux）在 push 上是**绿的**，
每周的 `platform-reproduction.yml` 也覆盖四个平台——**但「稳定」不是一个判据**。
**本文件不替它下结论**：§四 第 2 组要求把「稳定」写成**可判定的条件**，再判定。

## 四、本文件要产出的两组结论（**已裁定，见 §六**）

### 4.1 第 1 组：20C 的出口条件（提案）

建议由**四条**构成（每条都要可判定）：

1. **交付物**：路线稿 §七 那一行的每一项，**要么已交、要么有书面裁定说明为何不带**——
   当前「集合」既未交也未被裁定排除；
2. **状态名实相符**：`docs/module-registry.json` 里 20C 相关条目的 `status` 与其证据一致
   （骨架条目仍为 `draft`，**这是对的**——不许为了关闭而翻状态）；
3. **欠账登记齐全**：§2.2 那张表**逐条落在某份文档里**，且写明归属；
4. **移除验证与双路径**：按 20C §3.4 第 1/3 条，首批模块的两项**始终**可执行（已具备）。

### 4.2 第 2 组：20D 的批次切分（提案）

**第一批必须是「冻结批」，不是实现批**：

| 批次 | 内容 | 依据 |
| --- | --- | --- |
| **20D-冻结** | 冻 §八 第 3/5/6 条：资源种类清单、显式关闭语义、复制/继承与跨调用边界、句柄跨模块 ABI、首批 `os` API 与平台能力清单、缺失能力的稳定错误码 | §3.1 |
| **20D-能力上下文** | 建能力上下文：Runtime 请求携带它、外部操作经它进入、首版默认全开但**路径存在**、缺失能力报稳定错误 | §3.2、§5.1 |
| **20D-资源承载** | `ExternalResource` 的 Runtime 变体 + §4.2 的哈希/相等/编码/类型名五条（含 `is_hashable` 的**正向允许**改造） | §4.2 |
| **20D-首批 API** | 文件/目录/进程首批 intrinsic + 纯 Xiao 模块 + **三平台差分** | §七 |

**顺序不可颠倒**：冻结 → 上下文 → 承载 → API。
理由：API 的签名与错误身份**由冻结决定**；而承载必须**先于**第一个资源 intrinsic
（§4.1 末句、§4.3）。

## 五、不许（写下来免得做漏）

1. **不许**在冻结之前写任何资源 intrinsic 的签名——§4.1 末句明写「在**第一个**资源
   intrinsic 实现前冻结」，冻结是**前置**不是产出；
2. **不许**把能力上下文做成「一条 if 判断」——方向稿要的是**载体**，
   不是多一个字段；
3. **不许**新建 `RuntimeValue` 变体而**只**依赖编译器报错：§4.2 明写
   `is_hashable` 是**排除式匹配**，新变体漏加分支**会被误判为可哈希**，
   必须**覆盖相等、哈希性、`type_name`、`scalar_type`、编码器、常量池与两条后端**；
4. **不许**因为要开新阶段就把 20C 的骨架条目翻成 `verified`（§4.1 第 2 条）；
5. **不许**在本阶段顺带做 §2.2 的语言批次候选——它们是**带走清单**，不是 20D 的范围。

但按 [20C](20c-official-xiao-library.md) §2.4 **G-2**，一致**不等于**推定，本文以**直接裁定**记。

### 6.1 第 1 条的连带：**关闭不等于丢弃**——「集合」要立项

按 [20C](20c-official-xiao-library.md) §3.1 第 4 条的登记口径，写清三要素：

- **需要什么**：**公共函数的容器参数类型**（能让一个函数接受任意元素类型的容器，
  而当前函数形参必须是具体类型）；
- **当前以什么被拒**：第五批复探表第 6 行的「集合最小操作」**探测成功**（VM 与原生都输出 `ok`），
  但只能**保留探测结论**——挡点是**函数参数类型**，不是运行时能力；
- **阻塞哪条接口**：官方 `set`/`collections` 模块的**全部公共接口**，
  以及 [20C](20c-official-xiao-library.md) 路线稿交付物里「集合」那一项。

**归属**：**下一个语言批次**（与 §2.2 的「非字面量下标」同族，**由星崽定要不要同批**）。
**本阶段（20D）不做它**——它是**带走项**。

### 6.2 第 3 条的连带：判据的两半，以及**其中一半现在就不满足**

判据写成两半，**每一半都要能回答「满足了吗」**：

- **(a) 近端稳定**：维护回归的 **Windows 原生作业**在**最近 5 次由 push 触发**的运行上全部成功
  （取 5 是**本文件定的参数**，星崽可改；判据的**形式**才是本裁定要的东西）；
- **(b) 无未结的 Windows 专属项**：Windows/PE 专属的**未结项清单为空**——
  **清单必须先做出来**，本文**不假装它已经是空的**。

**而它现在不是空的**：`00-decisions.md:697` 登记着
「PE 内部节裁剪证据债（`unverified-coff-exports`）」，标注为**工具链条件**
（**证据债，不是缺陷**）。所以 **(b) 当前不满足**；
(a) 需要一次真实取数才能判定，**本文不下结论**。

⇒ **结论：20D 的前置（§三 的资源句柄契约 + 第 3 条的两半）目前不满足**，
**20D 的第一步只能是 §4.2 的「20D-冻结」**，不是实现。

**这里必须写清一件事**：(b) 那一半要不要把**证据债**算进去，取决于裁定想要的是
「没有未修缺陷」还是「没有未结项」。**两者不同**——前者现在可能是满足的，
后者不满足。**本文件按字面（未结项）判为不满足，并把区别摆出来**，由星崽改口径。

## 八、验收

1. **对账成表**：20C 交付物逐条有判定（§2.1），未清候选逐条有归属（§2.2）；
2. **前置有实测**：§三 的每一条都带执行点（不是「看起来没做」）；
3. **两份提案可判定**：20C 出口四条与 20D 四批，**每条都能回答「满足了吗」**；
4. **诚实**：「Windows 平台适配稳定」**不许**在没定判据前写成「已满足」；
   `draft` 条目**不许**为关闭而翻状态；
5. **通用**：`bun run check`、`bun test` 全绿；提交标题带类型前缀、正文非空；
