### 2.1.1 F1 的方向（星崽已定边界与参数形态）

- `cache clean` 接收**调用方显式给出**的引用来源，沿用 16B §2.5「引用来源由调用方给出、现算、不持久化」：
  项目目录或 `xiao.lock.json`、`.xar` 归档、显式的对象引用列表；
- **没有任何来源时保持现在的全量保护**，这是 16B §2.6 的保守规则，不能退回「没扫到就当没引用」；
- **任何一个来源读取失败，整体失败**，不得按「它没有引用」处理；
- 执行阶段（`--apply`）必须**重新收集**引用，不复用计划阶段的结果；
- `collect_references` 吃的是原始索引字节，而 `.xar` 是 ZIP。由驱动层先解出索引再交给它，**不新增归档字段，不改 16B 冻结面**；
- 测试必须在协议层断言**真实删除**：未被引用的对象消失，被引用的对象留下，来源损坏时一个都不删。

本批冻结的参数形态如下：协议字段为 `project_path`、`archive_paths`、`references`；CLI
对应 `--project <path>`、可重复的 `--archive <file.xar>` 和可重复的
`--reference <sha256>`。`project_path` 既接受项目目录也接受 `xiao.lock.json`，归档由驱动层
先完整调用 `.xar` 解码器再把 `ArchiveIndex` 交给对象存储；`references` 按跨命名空间摘要保护。
没有三类来源时保持全量保护，任一声明来源读取失败则在计划或执行前返回错误。

### 2.2 **Java 基线按星崽裁定冻结，取数仍需受控环境**

19 规范要求：Java 发行版与版本、代表性工作负载、允许误差和发布优化配置冻结之后，才能写「达到 Java 以上」。
星崽已在 2026-10-06 会话中冻结发行版族为当前 LTS 的 Temurin/OpenJDK 21，并要求 JVM
参数固定；本批据此建立基线清单，但没有受控 Java 主机运行记录时仍不能下性能结论。

**冻结**：

- 本机 `java -version` 的结果（1.8）不作基线；基线清单固定记录 Temurin/OpenJDK 21 的完整
  版本文本和 JVM 参数，不能只写一个大版本号；
- 当前固定参数写入 `tests/benchmarks/baseline.json`：`-Xms256m`、`-Xmx256m`、
  `-XX:+UseSerialGC`、`-Dfile.encoding=UTF-8`；受控主机的实际 `java -version` 文本和摘要仍待补；
- 原生发布参数按 `-O2` 记录为 clang 优化，明确 `xiao_passes_registered=false`，不把 Xiao
  LLVM Pass 尚未注册误报为已启用；
- Java 参考实现与 Xiao 程序**必须算同一件事**，用 `manifest.json` 里的期望值互相校验输出；
  校验不通过的程序不进入对照，也不改输入去凑；
- 溢出用例（`scalar-overflow-and-bool-parity`）保留在套件中，但 Xiao 报错而 Java 的
  `int`/`long` 默认静默回绕，**两边语义不同，结果只记为数据不足，不参与通过或回归判定**；
- 基线一旦冻结，取值写进一份机器可读的清单，报告里引用它的摘要，之后的改动都算基线变更。

### 2.3 **第一步是「原生能不能构建这四个基准程序」的探测**

19A 实跑时，原生后端拒绝过带 `try/finally` 的函数样本，而只有一个 `def` 的样本能构建。
基准程序用到函数、递归、容器、`try/finally`、表与 `drop`，**原生能构建多少，没有人核实过**。

**冻结**：

1. 实现 Agent 先对 `manifest.json` 里每个程序走一遍 `xiao build`，逐个记录：成功，或在哪一步以什么错误码停下；
2. 结果写进实施记录，用表格呈现，不用一句「大部分能构建」；
3. **原生构建失败的程序不进入性能对照，也不在本批修**。它们按「数据不足」判定，
   原因写「原生后端不支持：<拒绝信息>」，缺口归 15，登记为后续输入；
4. 如果四个程序族一个都构建不了，19.16 的原生一半就没有可测的东西。此时本批**照实报告**，
   不得退回去只测 VM 再把结论写成「达到 Java」（规范明确 VM 不是硬门槛）；
5. 这一步的结论决定 19D 后半段的工作量，所以它排在所有测量工作之前，并且先向星崽汇报再继续。

### 2.4 **测量与判定：诚实地出「数据不足」**

现有协议是中位数加四分位区间，19.17 要的是置信区间。两者不是一回事。

**冻结**：

- 统计方法固定为不新增依赖的**百分位自助法区间**：对每个工作负载的逐次比值做有固定种子的
  10,000 次重采样，取 2.5%/97.5% 分位数作为 95% 区间；样本量和种子写进基线清单与报告。
  在没有受控样本时不计算区间，也不把已有四分位区间冒充置信区间；
- 判定只有三种：**通过、回归、数据不足**。阈值未冻结、受控 Java/Xiao 基线未取、样本量不够、原生构建失败，
  一律是「数据不足」，**不是通过，也不是回归**；
- 启动、吞吐或延迟、峰值内存、产物体积、编译时间**各自判定**，不出综合分数；
- 冷启动对 JVM 包含类加载和预热，对原生是进程启动，二者的计时边界必须写清楚；
  整进程型的原生程序怎么量「稳态吞吐」，由实现 Agent 提出方案并说明局限，
  **不得**为了凑出稳态而改基准输入；
- Windows 上的峰值内存口径沿用 09R3 的「峰值工作集」，Linux、macOS 用什么口径要单独写明，
  不同口径的数字不互相比较；
- 本机只有 Windows。Linux 与 macOS 的数字只有在拿到 CI 或别的机器的运行记录后才写，
  否则一律写「未测」。
- §2.4 的固定硬件受控环境取数目前没有运行记录；本批只完成原生可构建性探测，性能基线明确记为
  「待补」，不能用探测提交或 CI 托管机数字代替。

### 2.5 **证据按平台分档，没有运行记录的平台写「未测」**

规范要求按 Windows → Linux → macOS 顺序记录结果。本机只有 Windows。

**冻结**：

- 报告里每个平台一栏，内容只有三种：有运行记录的数字、「未测」、「数据不足」；
- CI 托管机的硬件不固定，星崽已裁定 CI 数字仅作「诊断性」记录，不进通过或回归判定；
- Docker 和 WSL 的数字不计入验收，沿用 09R3 的口径；
- 轻量工作流的触发范围已接受；真正推送、触发和读取运行记录仍要星崽授权（F8）。

`19.14` 的 macOS 真实终端一格采用独立的「不可验证」口径，不写成「未验证」：当前没有 Mac 宿主，CI 对真实终端测试显式跳过，因此该格没有可补的同口径路径；这不影响其它平台的结论。

### 2.6 **报告可追溯，且不靠改输入达标**

**冻结**：

- 每份报告记录：Xiao 与 Runtime 版本、优化级别和后端（clang，非 Xiao Pass）、编译器工具链、
  Java 基线清单摘要、硬件、系统、预热与重复次数、统计方法、环境噪声处理；
- 未达标的工作负载给出可追溯结论：慢在解释器、Runtime、优化 Pass、代码生成还是外部依赖。
  **本批只定位，不修**，修复归对应阶段；
- 任何「让结果变好」的改动（缩小输入、换程序、调预热）都要在报告里以基线变更的形式单独列出，
  不得悄悄合并；
- 报告格式沿用 09R3 的 JSON 风格，新增字段不改旧字段含义，旧报告保持冻结。

#### 条件 3 —— 五子项 × 平台：**测试存在，但只在 Linux 上跑过**

**执行点（实测）与结论**：

| 触发 | 跑什么 | 覆盖哪些 crate 的**默认**测试 |

#### 条件 4 —— 发布报告与白名单：**机制齐、执行点只有周定时、白名单只覆盖 ELF**

| 组成 | 实测 |
| --- | --- |
| 白名单机制 | `xiao-codegen-llvm/src/reproducible.rs`：`ReproducibleDifference` 逐条带 `reason`；未被解释的差异进 `unexpected_differences` |

- 判定：**能补（需逐条复核 + 留档）**——「完整三平台白名单复核」缺的不是机制，是
  **把四个平台各自的 `15e` 输出按平台留档**，并明确「白名单为空」在 COFF/Mach-O 上是**结论**（逐字节相同）
  还是**尚未遇到差异**。两者写法不同，不能混。
- **`XarFormat` 与 `LanguageVersion` 那两类「无法补」不属本条**——它们是条件 1 的结构性欠格。

#### 盘点结论

| 条件 | 欠格性质 | 处置建议 |
| --- | --- | --- |
| **1** | 13/18 格未验证；其中**结构性无法补 4 格**（`XarFormat` ×2、`LanguageVersion` ×2）、**目标表 2 格无执行环境**（`macos_x86_64`、`windows_aarch64`）、其余 **能补** | 能补的排进后续批次；无法补的**在收口声明里显式写明「无法补 + 原因」**，不计入缺口 |
| **3** | **两个平台的默认测试从未运行**，「三平台一致」无证据 | 需星崽定：把哪些 crate 的默认测试接进 Windows/macOS 执行点（涉 CI 时长） |
| **4** | 机制齐；缺**按平台留档的逐条复核** | 能补，纯记录工作 |

**因此条件 1/3/4 在 Z-4 里仍不能写「满足」**——但本盘点把它们从「部分」拆成了
**可执行的格子 + 明确的无法补项**，Z-4 只需按上表填状态并写明覆盖边界。
