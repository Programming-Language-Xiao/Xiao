## 一、三条已定决策（2026-09-22）

### 1.1 CLI 独立可执行 + `xiao-core` 作为**同目录资源**

用 `bun build --compile` 产出单个 `xiao` 可执行（内嵌 bun 运行时，**不要求用户装
Node.js**）；`xiao-core` 作为**相邻文件**随包分发。

**为什么不是单文件**：X0 第 5 条的原文只要求「不要求用户另装 Node.js 的独立 `xiao`
可执行程序，**并能正确调用编译器内核**」——**没有要求把内核也塞进同一个文件**。而单文件
内嵌要在运行时解包到临时目录，引入毒理与权限问题，而且调试时看不出实际用的是哪个核心。

**分发形态**（具体目录布局由本批定死并写进 UseDocs）：

```text
<安装目录>/
  xiao            ← bun 编译产物
  xiao-core       ← Rust 核心（Windows 上带 .exe）
```

### 1.2 验证**环境矩阵**

**已定（2026-09-22）**：本批的验证覆盖以下环境。**注意 §3 对"验证"与"验收"的区分**——
这张表列的是**验证环境**，不等于全部可作为跨平台验收。

| 环境 | 实际平台 | 用途 |
| --- | --- | --- |
| Windows 原生 | Windows | **主验收环境** |
| Docker（Ubuntu） | Linux | 构建与功能验证（主要 Linux 证据） |
| Docker（**Arch**） | Linux | **发行版差异**验证（glibc、文件系统布局） |
| WSL（Ubuntu） | Linux | 第二个 Linux 实现，交叉验证容器结论 |
| **Git Bash** | **Windows** | PATH 与 shell 差异（**不是 Linux 环境**） |

**Arch 的价值要说清楚**：Ubuntu 与 Arch 的 glibc 版本、默认路径、`lib` 布局不同。
一个只在 Ubuntu 上跑通的产物，可能依赖了 Ubuntu 特有的东西——**Arch 是廉价而有效的
反例探测**。

**Git Bash 的归类要说清楚**：它跑的是 **Windows 二进制**，只是提供了 POSIX 风格的 shell
与 PATH 转换。它**不是 Linux 环境**，因此不能为 X0 第 2 条提供任何 Linux 证据。
它的用途是验证 CLI 在 **MSYS2 的 PATH 语义下**能找到核心——而我们的 clang 恰好也在
MSYS2 里，所以这条不无价值，但归属是**平台适配层**，不是 Linux 矩阵。

### 1.3 `xiao build` 归 **X0-E**，不在本批

协议里 `build` 消息已经有了（X0-A 定义），但接它需要先做**主机工具链发现**
（clang / llvm-as / rustc 在哪、版本是否匹配）。那是 `10:21` 留给本阶段的一块独立工作，
和"打包 + 平台矩阵"不是同一个主题。

**单开 X0-E**（`xiao build` 与主机工具链发现）。**本批不要顺手接 `build` 消息**——
协议支持它不等于 CLI 要暴露它。

## 二、打包与分发（本批核心）

### 2.1 `bun build --compile`

bun 1.4.0 支持 `bun build --compile`。本批要定死：

- **入口与产物名**：`cli/ts/src/main.ts` → `xiao`（Windows 上 `xiao.exe`）；
- **目标三元组的表达**：`--target=bun-<platform>-<arch>`，**与 Rust 侧的目标描述对齐**
  （`TargetDescription`，`10A` §2.1 已定它进构建指纹）；
- **交叉编译的边界**：bun 能交叉产出，但**Rust 核心不能**（Windows 上的 macOS 交叉需要
  额外工具链）。所以**打包能与不能，跟随核心能构建的平台**（见 §3）；
- **构建脚本落点**：`cli/ts/package.json` 的 `scripts`——补上 `build`，
  并说明它与 `typecheck`、`test` 的关系。

### 2.2 `xiao-core` 的**生产发现契约**

现状是**开发回环**的发现逻辑（仓库根相对路径那一串），生产环境**没有仓库根**。
本批要把它改成生产形态，并保留开发回环：

**候选顺序**（本批定死并写进 UseDocs）：

1. **显式覆盖**：`XIAO_CORE_PATH` 环境变量；
2. **同目录**：与 `xiao` 可执行**相邻**的 `xiao-core`（§1.1 的分发形态）；
3. **PATH**：`where.exe`（Windows）/ `which`（其他）——**保留现有的**；
4. **开发回环**：仓库根相对路径——**只在检测到仓库根时启用**，且要在诊断里标明
   这是开发布局。

**失败时的行为**：沿用现有的"列出全部候选"形状——那是**稳定诊断**，
不要退化成一句"找不到核心"。

**关键约束**：**不要靠解析 `--help` 文本或试运行来探测核心**。
发现之后要走 X0-A 的 `hello` 握手做**版本协商**（§2.3）。

### 2.3 版本协商与崩溃诊断（第 6 条）

X0-A 已经冻结了协议：首帧 `hello`、`protocol_version` + 统一 `core_version`、
失配用 `X11-PROTOCOL-004`、崩溃用 `X11-PROTOCOL-003`。

**本批要补的是"三平台一致"**：

- 三平台上**同一份 CLI 二进制**（各自平台构建的）对同一份源码产生**相同的机器字段**
  （`code`、`exit_code`、结构化诊断），**只有路径分隔符等平台事实可以不同**；
- **核心崩溃**在三个平台都要产出 `X11-PROTOCOL-003` + 进程码 4，且都带 `status` 与
  `process_exit_code`（X0-A 已实现，本批验证它跨平台成立）；
- **取消**在三个平台都要映射到 `ExitCode::ArtifactRejected`。

## 三、环境矩阵：**验证 ≠ 验收**

**这一节是本批最容易出错的地方**，因为它要处理两个既有约束的张力：

- X0 第 2 条要求「Windows、Linux、macOS 的最小**构建矩阵通过**」；
- 而 [09R3 `:135`](09r3-benchmarks-and-freeze.md) 写死了「**WSL 与容器只当开发环境，
  不进验收**」。

### 3.1 那条约束说的是**性能数字**，不是**功能验证**

09R3 的原文限制的是**基准数字**：

> WSL 共享宿主 CPU 与调度、容器多一层文件系统，**其数字不能与 Windows 原生并列比较**。

**"构建能否成功""CLI 能否跑通""退出码是否正确"不是性能数字**——它们不会因为容器共享
宿主调度而不同。所以容器里的**功能结果**是有效证据。

**但**：容器也不能自动等同于"真机 Linux 通过"。内核版本、cgroup、文件系统仍然与裸机
有差异，**而且容器里没有真实的安装路径与用户环境**。

### 3.2 本批的口径

- **Windows 原生**：完整验收；
- **Linux（Docker + WSL）**：取得**可复现的构建与功能证据**，并在交接记录里**逐项说明
  每个环境跑了什么、结果如何**；
- **macOS**：**没有环境**，如实记为**待复现**，**不得**宣称已验证；
- **X0 第 2 条的完整达成**：需要**真实 Linux 主机**复现一次，或说明为什么容器证据
  足以替代。**这个判断要写出来**，不能含糊。

### 3.3 每个环境要说清"跑了什么"

不是"在 Linux 上验证通过"就完事。至少要逐项列出：

| 项 | 说明 |
| --- | --- |
| 构建 | `bun build --compile` 与 Rust 核心构建是否都成功；产物的目标三元组 |
| 运行 | `xiao run` 能否跑通真实源码；退出码是否符合 B0-D 的五个值 |
| 发现 | 同目录 / PATH / 开发回环三条路径各在一个环境里验证 |
| 版本协商 | 失配时是否拒绝；崩溃是否产出 `X11-PROTOCOL-003` |
| **差异** | 与 Windows 原生的**逐项差异**——没有差异也要写"无差异" |

## 四、最可能翻车的地方

1. **把容器的功能结果当成"跨平台验收"**（§3.1）。要分清"有效证据"与"验收"。
2. **把 Git Bash 当成 Linux 环境**（§1.2）——它跑的是 Windows 二进制。
3. **顺手接了 `build` 消息**（§1.3）。
4. **发现逻辑只改生产、砍掉开发回环**——开发时会更难用；要保留并**标注布局类型**。
5. **靠解析文本或试运行探测核心**（§2.2 末段）。
6. **忘记 macOS 只能记待复现**——不得宣称三平台已验证。
7. **打包产物依赖 MSYS2 或开发机的 PATH**——那是开发环境，不是分发形态。
8. **锁文件**：本批若给 Rust crate 增删依赖，`check:lock` 会拦住（已固化，见 `00A.1`）。

## 六、验收

沿用 09R2D 的「撤掉实现 → 用例必须失败 → 还原 → 通过」。**关键验收不是「测试通过」**：

1. **独立可执行**：产出的 `xiao` **不依赖已安装的 bun/Node.js**（在干净环境里验证）；
2. **同目录发现**：把 `xiao` 与 `xiao-core` 放进一个**不含仓库根**的目录，
   `xiao run` 仍能找到核心；
3. **开发回环仍可用**：仓库内的开发路径不被 §2.2 的改动破坏，且诊断里**标明**这是开发布局；
4. **三平台一致性**：相同源码在各环境产出**相同的机器字段**（§2.3）；
5. **环境矩阵有逐项记录**（§3.3 的表），含**与 Windows 的差异说明**；
6. **macOS 明确记为待复现**，没有宣称已验证；
7. **门禁全绿**，含 `check:lock`、`bunx tsc`，且跳过数可见。

## 八、X0-C 已落地记录（2026-09-22）

1. `cli/ts/src/platform/packaging.ts` 接入 `bun build --compile`，默认按当前宿主生成
   `dist/<bun-target>/xiao[.exe]`，并写入 `xiao-package.json`；构建机需要 Bun，生成物运行时
   不依赖 Bun 或 Node.js。
2. `xiao-core` 按显式覆盖、独立可执行同目录、`PATH`、仓库开发回环的顺序发现；候选带有
   `override`、`adjacent`、`path`、`development` 来源，生产失败诊断不会把无仓库目录误当
   开发布局。
3. `hostPackageTarget` 与 `parsePackageTarget` 同时产出 Bun 目标和 Rust `HostTarget`，
   保持 `bun-windows-x64` 等命名与协议目标三元组一致；没有接入 `xiao build` 或工具链发现。
4. Windows 原生已完成独立产物、同目录核心和开发回环的真实源码回环；Linux Docker/WSL
   与 macOS 原生仍为待复现清单，当前不宣称三平台验收完成。
