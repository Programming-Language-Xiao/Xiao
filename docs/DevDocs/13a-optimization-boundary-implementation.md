# 13A. 优化契约与统一管线的实施

> **13 阶段的第一批**。[13. 优化契约与统一管线](13-optimization-contract.md) 是**权威规范**，
> 本档是它的实施交接：把「可以怎样变换程序」的边界立起来，
> **不做任何具体优化**（那些归 14/15/16）。
>
> **一句话概括本批**：把 `-O0` 也变成**走完整管线**的一等公民——
> 生成、规范化、验证一个不少，只是不跑可选的语义 Pass；
> 并让**每个 Pass 的假设可声明、结果可回滚、失败不外泄**。
>
> **⚠️ 最容易被误解的一点**：`13.3` 说的是「`O0` 是**不做语义变换的基线**」，
> **不是「跳过管线」**。把 `-O0` 做成直通是**本批头号翻车点**（§八 第 1 条）。

## 三、必须先冻结的 7 条

### 3.1 **优化器不重新解析源码**（13 规范「优化输入与输出」）

优化器**只接收**第 08 阶段的**类型化 IR**，或**已经通过验证的字节码级 IR**。
它**不能**重新解析源码、重新推断类型、自行决定生命周期语义。

**冻结**：管线的入口是 IR/字节码，**不是源码**。任何"顺便修一下语法"的念头都越界。

### 3.2 **`-O0` 是基线，不是直通**

`13` 原文：`-O0`「**仍执行生成、规范化和验证，但不运行可选语义优化 Pass**」。

**冻结**：

- **`-O0` 必须走完整管线**（生成 → 规范化 → 验证），只是不跑可选 Pass；
- **缓存命中、规范化序列化、格式验证和安全检查不属于可关闭的优化**（`13` 原文）——
  把 `-O0` 做成"什么都不做"会**同时丢掉验证**，那是错的；
- **优化开启不得成为 B0/N0 最小闭环的前置条件**（验收）。

### 3.3 **语义保持是硬约束**（13 规范「语义保持约束」）

优化**只能**改变执行成本、产物体积、启动时间、编译时间。
**必须保持**（`13` 原文七类，**逐条都要有测试**）：

1. 固定宽度数值的**溢出错误**——不得变成目标平台的静默回绕；
2. `bool +/- 整数` 的**奇偶翻转**规则及结果类型；
3. **有副作用表达式的求值顺序**、输入输出、模块初始化和延迟加载行为；
4. **资源所有权、逃逸提升、引用计数、`Weak` 和 `drop` 的确定性释放顺序**；
5. **随机选择的抽取顺序**、放回/无放回模式、注入测试随机源后的结果；
6. **动态值检查、数据竞争诊断、错误类别、退出码**和必要的源码位置；
7. **字典表无序、字典列有序、集合不可索引**等容器约束。

**冻结**：

- **编译器必须为每个变换声明其效果、所有权和控制流假设**——
  **不能因为某个平台的 LLVM 或 VM「通常如此」就省略证明**；
- **常量折叠遇到语言规定的溢出或错误，必须遵守统一错误契约**，
  不得自行决定提前报错还是留到运行时（那属待定决策，见 §3.6）。

### 3.4 **未实现的 Pass 不得伪装为已启用**（`13.3`）

**冻结**：

- `O1`/`O2`/`O3` 本批只建**配置占位**；
- **未实现的 Pass 不得伪装为已启用**——`-O2` 跑出来若其实只做了 `-O1` 的事，
  报告里必须如实说；
- **`13.8` 的跳过策略**：优化收益不足、目标不支持、证明失败，都要**有明确的跳过路径与原因**。

### 3.5 **验证失败不得外泄**（验收第 3 条）

「**任一 Pass 验证失败都不会把未验证结果交给虚拟机或链接器。**」

**冻结**：

- `13.4` 要求每个 Pass 可**独立快照、回滚到上一个有效 IR、输出稳定诊断**；
- **失败路径必须真的阻断**——不是打个日志然后继续；
- **与 10K 的产物验证衔接**：`10K` 那套"剥离符号表不能静默通过"的精神，
  在这里对应「**验证失败不能静默降级**」。

### 3.6 **不擅自决定 4 条待定决策**

`13` 规范的「待定决策」四条，**本批一律不得冻结**：

1. 命令行与 `config.xiao` 的**优先级、配置表名称**，以及 `-Os`/`-Oz` 等扩展级别是否加入；
   （**无配置时统一 `-O0` 是已定的**，这条可以落地）
2. 是否在后续版本支持 **JIT、PGO、跨模块优化、LTO、向量化和目标 CPU 特化**；
3. **常量错误的发生时机、优化后栈位置和变量可见性**的精确规则；
4. **Pass 失败时回退上一份产物还是终止命令**，以及优化报告的稳定格式。

**冻结**：遇到这些，**回写到「待定决策」**，不要就地决定——
`13` 规范原文明写「接手代理**不得**把某个临时 `-O` 级别、文件头字段或缓存目录
直接写成语言规范」。

### 3.7 **指纹确定性**（验收第 4 条）

`13` 原文：

- 指纹至少覆盖：优化级别与 Pass 集合、调试/诊断保留策略、**构建产物是否嵌入系统文案时的 `locale` 与语言目录摘要**、目标平台/架构/Runtime ABI/工具链版本、项目模块图与依赖锁定图、是否允许目标 CPU 特化/LTO/实验性 Pass；
- **「时间戳、临时路径和机器随机标识不能未经规范化写入可寻址产物」**；
- **⚠️ `locale` 的边界**：只有在**产物实际嵌入语言目录**时，语言标签/目录摘要才进指纹；
  **若文案由运行时外部目录提供，不得把用户当前显示语言混入代码语义指纹**。

## 六、硬约束

1. **优化器只接 IR/字节码，不重新解析源码**（§3.1）。
2. **`-O0` 走完整管线**，不是直通（§3.2）。
3. **语义保持七类逐条有测试**（§3.3）——不许拿"通常如此"代替证明。
4. **未实现的 Pass 不得伪装启用**（§3.4）。
5. **验证失败必须阻断**，不得静默降级（§3.5）。
6. **4 条待定决策不得擅自冻结**，遇到就回写（§3.6）。
7. **指纹确定性**：时间戳/临时路径/机器标识不入可寻址产物（§3.7）。
8. **两条后端共享一套接口**（验收第 1 条）——**不许各写一套 Pass 管理**。
9. **门禁**：`cargo test --workspace`、**`bun run check`（含 `check:lock`，两个 lock 都要提交）**、
   `cargo clippy --workspace --all-targets -- -D warnings`、TS 类型检查、`cli/ts` 全目录测试。
   新增环境门控测试按 `10D` 写 `#[ignore]` 并同步 §2 清单。

## 八、最可能翻车的地方

1. **把 `-O0` 做成直通**（§3.2）——那会**同时丢掉验证**，而验证正是 `13.4` 的立足点。
   本批头号陷阱。
2. **`-O1`/`-O2`/`-O3` 伪装启用**（§3.4）——报告说做了、其实没做，比不做更坏。
3. **优化改变语义**（§3.3 七类）——尤其**释放顺序**与**求值顺序**，
   它们不像溢出那样容易写出反例。
4. **验证失败还继续**（§3.5）——"打个日志接着跑"是最常见的静默降级形态。
5. **指纹混入时间戳/临时路径/机器标识**（§3.7）——导致缓存永远不命中，或更糟：**错误命中**。
6. **把 `locale` 无条件写进指纹**（§3.7）——文案由运行时提供时，**用户换显示语言不该让代码产物失配**。
7. **擅自冻结待定决策**（§3.6）——命令行优先级、`-Os`/`-Oz`、Pass 失败回退方式，
   这些**写进实现就成了事实规范**。
8. **两条后端各写一套 Pass 管理**（§六 第 8 条）——本仓头号病史的又一变体。
9. **优化器伪造所有权**（`13.6`）——只读接口是硬要求。
10. **不接 10G 的差分口径另立一套**（§四）——两套口径必然漂移。
11. **忘了两个 lock 文件**（§六 第 9 条）——`31fb944` 的翻车方式。

## 九、验收

按 `13` 规范的 8 条，加上本批的执行面：

1. **管线**：字节码与 LLVM 后端**共享同一套已验证的 IR 优化接口**（不是两套）；
2. **`-O0` 基线**：关闭优化时得到**稳定的未优化参考产物**；
   **优化开启不是 B0/N0 最小闭环的前置条件**；
3. **验证阻断**：任一 Pass 验证失败，**不会**把未验证结果交给 VM 或链接器；
4. **指纹**：同一输入与配置的指纹**稳定**；改变源码、依赖图、目标或工具链
   会**明确失配**；**时间戳/临时路径/机器标识不出现在可寻址产物中**；
5. **语义**：优化前后**所有已冻结语言规则一致**——尤其溢出、布尔加减、随机选择、
   容器顺序、动态检查和**释放顺序**；
6. **可追溯**：错误类别与必要的源码位置仍可追溯；**优化不会通过删除诊断来伪造成功**；
7. **`locale` 边界**：切换 `[language].locale` **不改变优化后的代码语义**；
   只有产物实际嵌入语言目录时，语言标签/目录摘要才进指纹；
8. **报告**：能说明**启用的 Pass、跳过原因和验证状态**；
9. **差分**（`13.10`）：同一源码分别执行**未优化与优化**的字节码、LLVM 原生结果，
   比较**输出、错误、退出码和 `drop` 记录**——**沿用 10G 的口径**；
10. **不回归**：10 阶段与 11 阶段已交付的内容保持绿；`cargo test --workspace` 全绿。

### 当前实施记录（2026-10-01）

- `xiao-optimizer` 已建立规范化配置对象、`O0`–`O3` 级别、稳定配置指纹和嵌入式语言目录边界；
  指纹只消费规范化文本、目标、工具链摘要、模块图和依赖锁定图，不消费时间戳、临时路径或机器标识。
- 共享 Pass 接口已要求每个 Pass 提供版本、效果/控制流/所有权假设；IR 的控制流、源码映射、
  所有权和生命周期事实通过只读摘要提供，优化器不能修改或伪造这些事实。
- O0 已执行 JSON 规范化、快照和 IR 验证；O1–O3 只生成明确的 `not-implemented` 跳过报告，
  不伪装成已启用优化。Pass 候选输出验证失败时保留上一份有效快照并阻断结果提交。
- LLVM 与字节码降低入口都消费同一条 O0 规范化/验证管线；LLVM 模块保留优化报告，字节码失败
  则生成带内部拒绝信息的 TAC，由既有 TAC 验证器阻断执行。
- 优化报告已包含快照大小、控制流、源码映射、所有权值槽和运行时检查等可比较成本指标；
  `xiao-optimizer` 也提供统一比较输出、错误、退出码和 `drop` 顺序的差分函数，供 13.10–13.12
  的后端夹具复用。

本批尚未接入具体语义 Pass、CLI 优先级、`-Os`/`-Oz`、LTO、PGO、目标 CPU 特化或未优化/优化
差分套件；这些边界仍按 §3.6 和后续 14/15/18 阶段交接。
