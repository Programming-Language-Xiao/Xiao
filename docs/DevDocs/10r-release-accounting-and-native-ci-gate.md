### 2.2 **原生 CI 门控：新增作业，Windows 先行**

星崽已批「跑」。这是 20AB、10L、10N 三次回归都能溜过去的同一个原因。

**冻结**：

1. 落在 `maintenance-regression.yml` 里新增一个作业，**不另建工作流**；路径过滤沿用该文件现有的
   Rust 路径集合，并补上 `tests/benchmarks/**`（原生探测读 `manifest.json`）；
2. 首版只在 **Windows**（`windows-2025`）跑，与现有体积作业同宿主；内容至少包含
   `n0_a_native_driver`、`d19a_differential`、`native_benchmark_probe` 的 `--ignored`；
3. 环境按 [10D](10d-environment-gated-test-spec.md) §4 与 `platform-reproduction.yml` 的准备方式：
   MSYS2 提供 clang/llvm-as/llc、`XIAO_TARGET_TRIPLE` 取宿主、`cargo build --release -p xiao-runtime`
   后把 `XIAO_RUNTIME_LIBRARY` 指向 `xiao_runtime.lib`、`XIAO_DIAGNOSTICS_PATH` 指向 debug 的
   `xiao-diagnostics.exe`。**特别注意 10D §4.3 的三个坑**（vcvars 与 PATH 的先后、Git 自带 `link.exe`
   的遮蔽、`.bat` 里不写中文）；
4. 作业必须**真的会因为原生回归而红**。上线后要做一次验证：在分支上故意把选择器改回返回源值
   或还原一处已修缺陷，确认作业失败，然后撤回。这一步的截图或运行号写进实施记录；
5. Linux、macOS 是否也进这个随 push 的作业，**由星崽定**（待定决策 1）；在决定之前，
   跨平台仍靠 `platform-reproduction` 的定时与手动运行，且要在记录里写明它的最近状态；
6. 作业超时与缓存沿用该文件现有风格（20 分钟量级 + `Swatinem/rust-cache`）。

### 2.3 **I6：按后续文档重构函数清理链**

`nested-finally-drops` 是 19 O6 条件 2 的直接缺口之一。10Q 已给出最小复现与判据（VM 销毁顺序 3→2→1，
原生 1→2，外层 `finally` 根本没执行），并记录了试过但撤回的方案。

**冻结**：

1. 按 [10q-i6-cleanup-followup.md](10q-i6-cleanup-followup.md) 的清单做：统一
   `dynamic/control.rs` 的函数返回与嵌套 `finally` 调度，处理 pending return、`finally` 覆盖返回或抛错、
   作用域释放计划，以及 `llvm.stackrestore` 的有效期；函数出口**不得**再靠按名称扫描槽位替代计划顺序；
2. **不得改 VM 语义**，**不得新增豁免字段**；所有权值到槽位的映射按函数作用域隔离（同名值不能共用一个槽）；
3. 改完必须摘掉 `nested-finally-drops` 的 `native_gap`——过期豁免守卫会强制这一步；
4. 先用 10Q 的数据表作为「改前」，改完补一张「改后」的对照（事件数、对象数、销毁位置），
   证明三者的销毁顺序与 VM 一致；
5. 这条是引用计数的结构性改动，提交说明要写清**为什么**这么改，不能只写「修好了」。若中途判断
   需要更大的重构，按 10Q §2.5 的口径写明去向，**不得静默放弃**。

### 2.4 **释放核对扩到容器与 `try`/`catch`**

星崽已批「可以」。10Q 只覆盖了选择器、容器（`held-array` 一条）、嵌套 `finally`。

**冻结**：

1. 按同一口径（事件数 / 对象数 / 销毁位置，轨迹只记释放、不记 retain）扩展到：
   元组、字典表、字典列、集合、表实例与 `drop`，以及 `catch` 命中、`catch` 未命中、`finally` 正常退出三条路径；
2. 每条路径用**最小源码**做差分用例进 `d19a_differential.rs`（不是一次性脚本），
   并声明基线输出/错误/drop，防止「两边都为空也算一致」；
3. 新用例先跑一遍记录基线，**不一致的先登记带具体原因的 `Drops` 豁免**，不当场改代码——
   本批的目标是**把账目摸清**，不是顺手改一批释放逻辑；判定为真失衡的按 §2.3 的做法单独立项；
4. 数据表并入 10Q 第九节或本批实施记录，注明测量提交、平台与工具配置；
5. 若某条路径两边一致，不要为了「有产出」而叠加用例——一致本身就是结论，写进表里即可。

### 2.5 **静态路径溢出：本批只建立项记录**

星崽已定「单独立项」。`ir.rs` 的 7 处 `llvm.trap` 仍未接 `X06-RUNTIME-009` 统一错误路径，
而动态路径已经接通——两条路径行为不同这件事必须在文档里说清楚。

**冻结**：

- 产出立项记录：现状（7 个发射点、原生退出码表现）、要接的统一错误路径是什么、
  与 10E 把「非法指令」归为平台级异常这一条如何协调、影响面、验收方式；
- **本批不实现**，也不改 `ir.rs`；
- 记录要与 10L §11.4 的量化结果一致（那里的 7 处是对的），不要重新发明数字。

### 2.6 **剩余拒绝面：按 ABI 排序，只定顺序**

星崽已定「按 ABI」。10P 已枚举：动态表方法、表构造参数、表字段复合/扩展赋值、动态函数调用、
动态非成员访问、动态错误构造非字符串参数、多项与字典键选择器。

**冻结**：

- 本批把这批缺口按**是否依赖 Runtime ABI 扩展**分类：需要新 ABI 的（表方法函数表、表构造、
  函数表调用）放前，纯降低层可做的（成员访问诊断、选择器形状）放后；
- 给出批次切分建议与每批的验收范围，**本批不实现**；
- 切分建议写进本文件，并同步 10P 的枚举表（加一列「顺序」），避免两处说法不一致。

## 六、最可能翻车的地方

1. **CI 作业只是「加上去了」**，没有做「故意让它红」的验证——那和没加一样；
2. **作业里用的是干净的 runner，`.bat` 或 vcvars 顺序踩了 10D §4.3 的坑**，导致作业常年红灯或常年跳过；
3. **I6 顺手改了 VM 语义**来让顺序对上；
4. **I6 中途判断需要大改就悄悄放弃**，没写去向（10Q 已立过这条规矩）；
5. **核对扩展时当场改释放逻辑**，把「先摸清账目」变成「边测边改」，失去基线；
6. **新用例只断言总事件数**，不看对象数与销毁位置；
7. **一致就以为无事**：一致本身要写进表，否则后人不知道测过；
8. **把 10P 枚举表和本文件的顺序写成两套**；
9. **只看 `cargo test` 就宣布门禁全绿**（`bun run check` 不在其中）；
10. **提交没写正文 / 没单独跑 clippy**。

## 十、I6 清理链修复

函数 return 改为挂起结果后展开 cleanup_stack；在运行外层 finally 前暂存内层作用域释放，最后按内到外消费计划，避免提前销毁。结果槽位于调用方栈上，finally 的 stackrestore 不会回收它。覆盖返回归还旧结果，finally return 清除可恢复挂起错误；错误出口归还未返回的结果，Fatal 跳过普通清理。函数值映射只收集当前函数作用域及其子作用域，入口排除函数内部值；正式函数出口按作用域计划处理，不再按名字枚举槽位代替计划。返回临时值在最终返回点复制后归还帧内引用，返回命名绑定则归还计划标记 transferred 的原引用，匹配 VM 的返回寄存器读取与帧结束行为。
