## 一级工程目标：统一三地址语义模型

### R1-A：指令形状与操作数空间

统一三地址模型（下称 TAC）**不绑定任何一种物理字节码**。它在语义层描述"算什么"，
把"放在哪里、怎么编码"完全留给机型。

指令形状固定为：

```text
TacInstr { op: TacOp, dst: Option<VReg>, span: IrSpan }
```

`span` 不可省略。它是回填 `StackFrame.backend.bytecode_offset` 的唯一来源，该字段已经
存在于 `xiao-diagnostics` 的 `BackendLocation` 中，属于 09 阶段必须填充的既有契约。

操作数空间固定为四类，不引入第五类：

| 操作数 | 含义 |
| --- | --- |
| `VReg(u32)` | 虚拟寄存器编号；TAC 层不区分类别 |
| `Const(ConstId)` | 常量池引用 |
| `Func(FuncId)` | 函数引用 |
| `Block(BlockId)` | 基本块引用 |

释放类指令额外携带 `IrValue.id`。`IrOwnership.release_plans` 的 `actions[].value` 是值
编号，如果 TAC 只剩虚拟寄存器，`drop` 序列就无法与已冻结的释放计划对账。因此 TAC 维护
`IrValue.id <-> VReg` 的双向表，`Release` 指令同时携带值编号与虚拟寄存器，验证器逐条比对。

### R1-B：类别不写在指令里

TAC 指令本身**不记录寄存器类别**。类别由一张独立的 `CategoryMap: VReg -> CategorySet`
携带，取值 `{Int, Float, Bool, ObjHandle, Dynamic, None, Poly}`，从 `IrExpression.ty`
单向推导；控制流合流点取并集，无法收敛时退化为 `Poly`。

理由：类别的最终归属是机型决策。混合式可能把某个值放在局部窗口而不是寄存器里，如果
TAC 锁死类别，栈式机型就被迫携带自己完全不需要的类别状态，三机型也就不再是"同一输入的
可比实现"。

`TacOp` 按语义分为以下组，编号留给 09R3 冻结，本阶段只冻结语义分组：

| 组 | 指令 |
| --- | --- |
| 常量与立即数 | `Const`、`LoadNone`、`LoadFunc`、`LoadTable` |
| 传送 | `Copy` |
| 表示转换 | `Box`（类别 → 动态值）、`Unbox`（动态值 → 类别）、`Cast`（静态目标类型） |
| 算术 | `ArithI`、`ArithF`、`ArithBool`、`ArithL`（`lint`/`lfloat`） |
| 比较 | `Cmp`（结果恒为布尔） |
| 分支 | `Jump`、`BranchIfTrue`、`BranchIfFalse` |
| 容器构造与索引 | `NewArray`、`NewTuple`、`NewDictTable`、`NewSet`、`NewDictColumn`、`AppendElem`、`SetElem`、`IndexExact`、`SelectorApply`、`MemberGet`、`MemberSet` |
| 调用 | `Call`、`CallDynamic`、`NewCall` |
| 错误 | `Raise`、`Check`（携带失败目标块） |
| 释放与转移 | `Retain`、`Release`、`Transfer`、`RunReleasePlan` |
| 作用域 | `ScopeEnter`、`ScopeExit` |

`ArithBool` 单列，因为布尔与整数的加减在 Xiao 中是奇偶翻转而不是算术；`ArithL` 单列，
因为它必然降低为运行时库调用而不是内联指令。

`IrExpressionKind::Group`（括号分组）在 TAC 层**必须穿透消失**，不得产生任何指令。

### R1-C：装箱分层的唯一分界

这是必须钉死的一条，否则三机型的对比会失去可比性：

- **TAC 层决定"哪里需要装箱/拆箱"**，并显式发出 `Box`/`Unbox`。插入位置对所有机型完全一致。
- **机型层决定"怎么做"**，即用哪个寄存器或帧槽、这个箱是真实堆分配还是联合槽。

这样三机型的 `Box` 序列可以逐条对照，差异只出现在编码和载体选择上。

### R1-D：从 IrProgram 降低到 TAC 的边界

TAC 降低器逐语句、逐表达式消费 `IrStatement`/`IrExpression`，只做 1:1 语义展开。它：

- 不推断类型（只把 `IrExpression.ty` 映射为类别）；
- 不重算生命周期（只消费 `IrOwnership` 的既有结论）；
- 不重排释放顺序（逐条重放 `IrReleasePlan.actions` 的 `order`）。

## 一级工程目标：三种候选机型

### R1-E：机型定义

**栈式**：没有虚拟寄存器到物理载体的映射，所有 TAC 操作数来自单一求值栈。局部变量用帧内
索引槽寻址，`dst` 是压栈、源操作数是弹栈，栈深由表达式树决定，参数经操作数栈传递。

**分类型寄存器**：没有求值栈。五类寄存器文件各自独立，所有值（含匿名临时值）经线性扫描
分配到寄存器，参数经参数寄存器传递，跨调用存活的值由被调用者保存规则保证。

**混合式**必须定义成架构差异，而不是某个机型的溢出参数——否则 09R3 比出来的只是一次参数
扫描，不是三种架构。本阶段冻结的定义是：

> **具名值走每帧固定局部窗口**（按下标寻址，按 `IrValue.declaration_order` 排列，窗口满则
> 溢出到帧槽）；**匿名临时值走求值栈**；**参数在求值栈顶的连续区间内传递**（与栈式同路径）；
> **返回值走返回寄存器**。

### R1-F：三机型结构对比表

| 维度 | 栈式 | 分类型寄存器 | 混合式 |
| --- | --- | --- | --- |
| 具名局部值存放 | 帧内索引槽 | 寄存器（线性扫描分配） | 每帧固定局部窗口，满则溢出帧槽 |
| 匿名临时值存放 | 求值栈 | 寄存器 | 求值栈 |
| 参数传递路径 | 操作数栈 | 参数寄存器 | 操作数栈顶连续区间 |
| 返回值路径 | 操作数栈顶 | 返回寄存器 | 返回寄存器 |
| 指令操作数形式 | 隐式（栈顶） | 显式寄存器号 | 具名值用窗口下标，临时值用栈 |
| 需要的栈映射位置 | 每个跳转目标 | 无 | 仅调用点与帧尾 |
| 表达式求值顺序可观察性 | 由栈序强制 | 由指令序强制 | 由指令序强制 |
| 主要成本来源 | 压栈/弹栈与栈深验证 | 寄存器分配与溢出重载 | 窗口下标解析与调用点栈编排 |

**"需要的栈映射位置"是三者真正可量化的分界**：栈式必须在每个跳转目标都能验证栈深，
混合式只需要在调用点和帧尾，寄存器式完全不需要。因此 `栈映射条目数` 和 `spill_count`
必须作为独立的基准上报指标，不能只报一个总耗时。

> **口径收敛（R2D 实现后补记）**：本节原先在措辞上留了一处含糊——行标题写「**位置**」，
> 末句却写「栈映射**条目数**」。R2D 的实现初期因此出现三种量纲（栈式累加占用槽数、
> 混合式每次调用 `+1`、寄存器式记帧槽数与保存数），而**这个数恰恰是本表要量出的分界**，
> 不同量纲等于没有分界。
>
> 现按上表语义统一为「**需要建立栈映射的程序点数量**」：栈式数跳转目标、混合式数调用点
> 与帧尾、分类型寄存器式恒为 0；落帧槽与跨调用保存分别记在 `spill_count` 与
> `call_save_count`，**不混入本指标**。实现与区分度用例见
> [09R2D 文档的任务 1](09r2d-machines-and-encoder.md)。

### R1-G：机型差异必须可被基准区分

09R3 的基准程序集至少覆盖四族，每族都能把上表的差异放大成可测信号：

1. 深表达式算术（栈式与寄存器式差异最大）；
2. 多具名局部、少临时值的循环（寄存器式与混合式占优）；
3. 深调用、多参数的递归（栈传参吃亏）；
4. 容器密集操作（三者趋于接近，用于确认没有机型在容器路径上作弊）。

只覆盖其中一族就宣布 +10%，不构成通过门槛的证据。

## 一级工程目标：分类型寄存器模型

### R1-H：寄存器类别与编号空间

采用**单一扁平 `Reg(u16)` 空间 + 类别区间**，而不是五个互相独立的命名空间——独立命名空间
会让溢出和保存恢复需要写五套并行逻辑。

| 区间 | 类别 | 载体宽度 | 默认槽位数 |
| --- | --- | --- | --- |
| `R0..R15` | 整数 | 64 位 | 16 |
| `F0..F15` | 浮点 | 64 位（`sint`/`sfloat` 占低 32 位，不另开文件） | 16 |
| `B0..B7` | 布尔 | 字节 | 8 |
| `O0..O15` | 对象句柄 | 句柄宽度（引用计数指针） | 16 |
| `D0..D15` | 动态值 | 带标签的联合 | 16 |

`none` **不分配寄存器文件**。它是零宽值，用 `LoadNone` 的立即数形式表达，无值返回时置帧
状态位。保留一个恒为空的类别只会污染溢出逻辑。

### R1-I：类别指派表

| 静态类型 | 寄存器类别 | 说明 |
| --- | --- | --- |
| `int`、`sint` | 整数 | 固定宽度整数 |
| `float`、`sfloat` | 浮点 | 固定宽度浮点 |
| `bool` | 布尔 | 独立类别，不与整数共用 |
| `str`、数组、元组、字典表、字典列、集合、表实例 | 对象句柄 | 全部经 `xiao-runtime` 的强句柄 |
| `lint`、`lfloat` | 对象句柄 | 归运行时数值对象类，其算术经 `ArithL` 降低为库调用 |
| `dynamic` | 动态值 | 需要运行时类型标签 |
| `none` | 无 | 零宽，不占槽位 |

`lint`/`lfloat` 归**对象句柄类而不是动态值类**：它们的静态类型是确定的，放进动态值类会破坏
"动态值只用在需要它们的路径"这条已冻结的性能约束。代价是 `O` 类上的 `ArithL` 是慢路径，
必须走运行时库调用，不指望内联。

### R1-J：逃生路径

从寄存器逃到帧槽只有三条合法路径，且都必须被计数：

1. **窗口溢出**：局部窗口满，或寄存器压力超过类别槽位数。
2. **合流点退化**：`CategoryMap` 在控制流合流点无法收敛为单一类别，取 `Poly` 后强制落帧槽。
3. **闭包捕获**：被闭包捕获的值强制堆提升（对应 `IrValue.storage` 为堆类）。

局部窗口默认 16 槽。溢出次数以 `spill_count` 上报，它是判断寄存器机型是否真的赢了的
关键指标——如果溢出率高到把收益吃掉，09R3 报告的结论必须是"未通过门槛"。

### R1-K：寄存器模型的边界

寄存器模型**只做载体指派**。它不得：

- 复制类型推断（类别只能来自 `IrExpression.ty`，不能自己推导新类型）；
- 重算生命周期（`IrValue.storage` 是输入，不是输出）；
- 重排或合并 Runtime 释放动作（`IrReleasePlan` 的 `order` 是唯一合法顺序）。

## 一级工程目标：冻结函数调用约定

### R1-L：调用签名表是前提补全

**当前不存在可用的调用 ABI 描述。** `IrStatementKind::Function` 只给出被调方的
`parameters: Vec<IrParameter{name, kind, ty, default, span}>`；调用点的 `IrExpression.ty`
即使解析成 `IrType::Function`，也只保留参数类型和返回类型，**丢掉了 `IrParameter.kind`
（位置专用、`*args`、关键字专用、`**kwargs`）和 `default`**。

因此 TAC 构建期必须合成一张调用签名表：

```text
CallSig {
    param_kinds:  Vec<ParamKind>,
    param_types:  Vec<IrType>,
    defaults:     Vec<Option<ConstId | FuncId>>,
    has_varargs:  bool,
    has_kwargs:   bool,
    ret_ty:       IrType,
}
```

调用点只携带 `SigId`，不再内联裸参数语义。被调用对象类型不是 `IrType::Function` 时退化为
`DynamicSig`，走全动态派发路径——慢但语义完整，且必须与静态路径产生完全一致的语义结果。

### R1-M：帧布局

固定顺序，`fp` 指向帧指针：

| 区域 | 内容 |
| --- | --- |
| 帧头 | 保存的 `fp`、返回地址、上一层 handler 表指针、清理状态字 |
| 参数区 | 定长实参按声明序 → `varargs` 数组句柄（无则空哨兵）→ `kwargs` 字典句柄（无则空哨兵） |
| 局部槽 | 承载 `IrValue` 的固定槽位 |
| 临时区 | 仅栈式与混合式使用 |
| handler 表 | 帧内指针 + 本帧条目 |

### R1-N：参数传递的职责划分

**默认值由被调用方的前导代码填充，不由调用方填。** 调用方只写实际提供的参数槽；
关键字参数由被调用方在前导代码里按名字重排到形参位置。

这条必须写死。`*args`/`**kwargs` 与默认值的组合只要在两端各实现一次，三机型之间就一定会
出现行为分叉，而这种分叉在标量基准里根本看不出来。

### R1-O：保存责任划分

| 类别 | 内容 |
| --- | --- |
| 调用者保存 | 全部参数寄存器、全部临时寄存器、求值栈 |
| 被调用者保存 | `fp`、handler 表指针、清理状态字、**所有承载 `IrValue` 的帧槽与寄存器** |

`IrValue` 必须被调用者保存，因为作用域退出时的释放计划要读它们。

由此得到一条硬约束：

> **凡出现在任何 `IrReleasePlan.actions` 里的值必须钉在帧槽，不得只活在易失寄存器中。**

判定条件直接使用冻结数据：`IrValue.storage != "stack"`（等价于生命周期阶段的
`needs_release()`）。这条约束同时决定了分类型寄存器机型能拿多少分——它必须为整个作用域的
堆类值预留槽位，而这部分收益会被"具名值本来就少"的基准族稀释。

### R1-P：递归与调用深度

递归使用同一帧模板重入。运行参数 `max_call_depth` 默认 1024，超限抛已存在的
`FATAL_STACK_OVERFLOW_CODE`（`X07-FATAL-004`）。它是致命故障，**普通 `catch` 不可恢复**。

### R1-Q：闭包边界

04-B 至今只把嵌套函数记录为静态事实，不生成闭包对象。本阶段冻结的边界是：

- 本轮只支持**无捕获闭包**；跨函数边界传值只能走参数和返回值。
- 帧布局预留一个 `closure_env` 隐式槽位，供后续阶段填充被捕获环境，**本轮不写入**。
- 捕获语义本身不在 09R 范围内。若 09R2 发现基准程序族需要真实捕获，必须作为显式债项
  登记，而不是在原型里悄悄加一套捕获规则。

## 一级工程目标：控制流、异常与清理转移

### R1-S：基本块与跳转

跳转指令形态对齐 `IrControlFlow` 的边类别，但**TAC 不拿 `IrBasicBlock` 作为块划分依据**，
原因见"未决风险"第 1 条。TAC 按结构化、语法导向的降低自行重建块结构，把 `IrControlFlow`
降级为校验预言机：用它的 `scope` 与 `exits` 反查某个程序点上活跃着哪些
`(ScopeId, ExitKind)`。

### R1-T：handler 表

每个函数帧携带一张 handler 表，条目固定为：

```text
HandlerEntry {
    protected_pc: Range<Pc>,       // 受保护区间
    handler_pc:   Pc,              // 处理器入口
    scope:        ScopeId,         // 所属作用域
    exit_kind:    ExitKind,        // 该条目的退出语义
    kind:         Catch | Finally,
    binding_slot: Option<FrameSlot>,  // catch 绑定的错误对象
    catch_type:   Option<TypeId>,
    next:         Option<HandlerIdx>,
}
```

条目按嵌套深度降序存放。查表 = 本帧条目线性扫描 + pc 区间命中。跨帧传播时沿调用链上溯。

### R1-U：11 种 ExitKind 的转移映射

`xiao-lifetime` 已冻结 11 种退出类别，逐一给出转移语义：

| ExitKind | 转移语义 |
| --- | --- |
| `Normal` | 顺序落到 `ScopeExit` |
| `Return` | 执行 `(scope, Return)` 计划 → 返回值入返回寄存器 → 拆帧 |
| `Break` | 执行循环作用域计划 → 跳到循环出口标号 |
| `Continue` | 执行循环作用域计划 → 跳到循环回边标号 |
| `Error` | 任意运行时错误 → 执行 `(scope, Error)` → 查 handler 表 |
| `Raise` | 显式 `Raise` → 同上，但使用 `(scope, Raise)` |
| `Catch` | 命中处理器 → 执行 `(scope, Catch)` → 跳 catch 体并填 `binding_slot` |
| `UnmatchedError` | 本帧无匹配处理器 → 对本帧每个外层作用域依次执行 `(scope, UnmatchedError)` → 拆帧 → 调用方继续 |
| `ConstructFailure` | 构造失败 → 执行 `(scope, ConstructFailure)`；半构造对象自身的计划与外层作用域计划是两份，不得合并 |
| `DynamicCheckFailure` | `Check` 失败 → 执行 `(scope, DynamicCheckFailure)` → 再构造 `XiaoError` |
| `Fatal` | **完全绕过所有释放计划**，只记录"未清理"标志，走 `FatalError` 通道，不进 catch、不合并 `suppressed` |

`Fatal` 那一行是刻意的不对称：致命故障下继续执行释放钩子已经不安全，因此不允许普通
`catch` 把进程伪装成成功状态。

> **实现冲突登记（09R2C）**：`xiao-lifetime/src/escape.rs:887-901` 仍把
> `ExitKind::Fatal` 列入可被 catch 消费的摘要集合，这与 07-B 的冻结规则冲突。VM 按本表与
> `CATCH_FATAL_CODE` 实现 Fatal 隔离，handler 表不依赖该摘要；本批不改生命周期阶段，后续
> 生命周期重构时再统一两处模型。

### R1-V：`finally` 使用子程序，不内联复制

11 种 `ExitKind` 乘以嵌套作用域，内联复制会让编码体积按层数爆炸，直接违反"编码体积不得
恶化超过 10%"这条门槛。

因此：**每个退出作用域只有一份释放序列**，编译为子程序；子程序末尾的 `RetFromSub` 按挂起的
`ExitKind` 分派到正确目标。内联是 14 阶段优化器的可选优化，**不在 TAC 层做**。

### R1-W：`drop` 序列不可重排

按 `IrReleasePlan.actions` 的 `order` **逐条原样**发出 `Release{value, kind}`。TAC 层禁止：

- 重排、去重、下沉、提升释放动作；
- 把相邻动作合并成批量释放；
- 把释放动作移出所属作用域的退出边。

`plan.transferred` 的成员发出 `Transfer` 以抑制其释放，同样不参与排序。已冻结的
`finally -> drop -> 匹配 catch / 继续传播` 顺序不得反转。

### R1-X：未捕获错误边界

错误在 `xiao-vm` 的拆帧边界构造为 `XiaoError`，逐帧填充
`StackFrame.backend.bytecode_offset`（取抛出点 pc，由 TAC 指令的 `span` 映射而来）。
清理过程中产生的新错误追加到 `suppressed`；清理过程中产生 `Fatal` 时由 `Fatal` 胜出。

## 一级工程目标：指令编码草案与 ABI 版本

### R1-Y：指令编码草案

采用变长指令：`opcode: u8` + 变长操作数。需要在这一期比较的不是"哪个编码更好看"，而是：

- 寄存器号与常量池索引用 LEB128 还是定宽 u16；
- 窗口下标访问是否需要独立操作数形式（混合式专属）；
- 调用指令携带 `SigId` 后，参数是否还需要逐条编码。

以上比较口径在 09R2 落地为可往返的编码器，在 09R3 以**编码体积**作为量化指标。

### R1-Z：源码位置映射

源码映射是独立于指令流的 `pc -> IrSpan` 表，采用增量编码。它必须支持：

- 错误回溯到源码区间（填 `BackendLocation.bytecode_offset` 后由报告器消费）；
- 三机型共用同一张映射表语义，机型差异不得改变映射结果。

### R1-AA：ABI 版本字段

```text
bytecode_abi_version   研究用编码的版本
runtime_abi_version    xiao-runtime 句柄与值表示版本
ir_version             当前为 1（IrProgram::version）
language_version       语言版本字符串
target                 目标平台描述
```

版本不匹配时必须拒绝执行，不得静默降级。

### R1-AB：与 `.xiaoc` 的边界

09R 冻结的是**研究用编码**。正式 `.xiaoc` 的分段格式、分区编号、内容寻址和 Protobuf 索引

## 一级工程目标：性能门槛与基准协议

### R1-AC：门槛口径

| 指标 | 门槛 |
| --- | --- |
| 稳态吞吐 | 相对**同机 Rust 栈式基线** ≥ +10% |
| 冷启动 | 恶化不超过 10% |
| 峰值内存 | 恶化不超过 10% |
| 编码体积 | 恶化不超过 10% |
| 语义结果 | 必须完全一致 |

栈式原型同时充当"对照方案"和"基线"，因此它必须先于另外两种机型达到可运行状态。

### R1-AD：基准协议

门槛本身不足以构成证据：三类机型可以靠选题赢。因此同批冻结以下协议：

- **基准程序清单**：按 R1-G 的四族命名固定程序，代码与期望结果一起进版本控制；
- **工具链**：仓内 `rust-toolchain.toml` 已固定 `1.96.0`，基准不得使用其他工具链；
- **构建配置**：`--release`，固定 `opt-level` 与 `codegen-units`，关闭 LTO；
- **测量协议**：固定预热次数、重复次数、输入规模，取中位数而非均值；
- **基线来源**：同一次构建产出的栈式原型二进制，不允许跨构建比较；
- **统计方式**：记录中位数与四分位区间，不隐藏离散度。

**按族分别上报结果，但门槛仍按全局 +10% 判定。** 若族间方向相反，09R3 报告必须给出解释，
不允许只报一个总数掩盖掉失败的那一族。

基准设施使用零依赖自建 harness（`std::time::Instant`），不引入 `criterion`：仓库当前依赖面
只有 serde/serde_json/syn，引入基准框架会打破这一现状且需要联网拉包。报告与元数据落
`tests/benchmarks/`。

### R1-AE：平台顺序

复现顺序为 Windows → Linux → macOS，后续平台不得跳过前一平台的回归。**本轮及 09R3 初期只
在 Windows 本机产出报告**；Linux 与 macOS 写成明确的待复现清单与复现脚本，**不宣称已复现**。
`00-decisions.md` 已把"Rust VM 在三平台的构建、接口版本和性能基准复现"列为需要实现验证的
条目，该条目在本阶段不会被关闭。

三处必须记下的结论：

- **临时值泄漏已修**。容器字面量与 `str` 字面量产生的值 `temporary=true`，被释放
  计划排除；降低器现在在消费点之后显式发出 `Release`，解释器的 `Release` 也改为
  容忍空寄存器。撤掉该登记会让 `releases_temporary_heap_values` 立即失败。
- **全栈元组按堆对象物化**。`(1,2)` 在静态存储类别里是栈值、没有 `IrValue`，解释器
  却只能把它建成堆上的元组对象。这是已知差异而非缺陷，R3 的峰值内存指标会体现它；
  解释器基线本来就不对应 LLVM 原生。
- **`RuntimeValue::Hash` 目前没有消费者**。字典键是 `String`（有序表足够），集合去重
  用有序 `Vec` 加线性扫描——这是刻意的，哈希序会污染语义向量的释放序列。实现 `Hash`
  是为了让公共契约成型；若确认长期不用，可以只保留 `Eq`。

#### 实施中新发现的边界（带入后续批次）

- **调用参数的引用计数与跨机型所有权**仍需在 R2b/R3 的寄存器与混合载体中做差分基准；当前
  栈式原型已经在临时值消费点发出显式 `Release`，并由向量锁定释放序列。
- **`dynamic_conversion` 目前是窄语义**：它只验证动态值是否为 `RuntimeValue::Error`，服务
  `raise` 的错误边界；动态标量转换没有目标类型字段，暂不伪装成完整实现。
- **`string_boolean` 与选择器/集合/迭代器检查**继续进入 `TacProgram.unsupported`，待对应
  R2b 语义落地后再执行。
- **形参按名查找必须按作用域消歧**：两个函数各有一个同名形参时，全局取首个会串到别的函数
  的绑定上，读到本帧从未写入的寄存器。降低器已按作用域栈取最内层候选。
- **运行时可恢复错误不能用字面量构造**：`value = 7 % 0` 会在类型阶段被常量折叠拒绝
  （`X02-TYPE-007`），那是正确行为。语义向量一律用编译期不可知的形参参与运算。
  容器侧同理：常量越界与缺失键都被静态检查器提前拒绝，运行时容器错误在字面量程序里
  不可达，改由 `xiao-vm` 的 `ops.rs` 单元测试覆盖。
- **已修复：字典字面量的键与选择器路径段归一化不一致**。形如 `mapping = {"a" = 1}`
  后取 `mapping[a]` 曾得到运行时 `X06-RUNTIME-015`。根因是两侧各写了一份键规范化：
  `xiao-types` 的 `dictionary_key` 对字符串键调用解码函数（去引号、处理转义），而
  `xiao-ir` 的 `dict_entry` 直接存含引号的源码切片，于是静态认为键是 `a`、IR 存的是
  `"a"`。修法是把解码提为 `xiao_types::decode_string_literal` 并让 IR 消费同一个
  函数，两侧不再各写一份；`xiao-ir/tests/u0_ir.rs` 增加两条跨层回归用例钉住它。

两者都必须：

- 只消费已验证 `IrProgram` 或统一三地址结果，不重新解析源码；
- 三种机型共用同一组语义向量，**禁止为某种机型修改期望结果**；
- 增加 `VmEventSink` 事件接收器，至少记录模块、函数、作用域、释放、错误、堆栈和运行指标。

**对账断言（09R2 实施时修正过两处）**。第一版设计写的是「TAC 产生的
`(ScopeId, ExitKind)` 集合是 `IrOwnership.release_plans` 键集的超集」，实现时发现
**这条断言恒真、区分不了任何东西**：`release_plans` 是「每个作用域 × 全部 11 种退出边」
的无条件笛卡尔积，上游对每个作用域都插入一条，哪怕 `actions` 为空。真正可验证的内容是
每个计划自身的完整性（`order` 从零连续、`value` 唯一、`transferred` 不与 `actions` 重叠），
以及后端实际发出的释放序列与对应计划逐条相等。

第二处修正是落点：原设计写「加在 `xiao-ir` 验证器上」，但 `IrValidator::validate(&IrProgram)`
是零字段单元结构体、没有携带外部观测的通道，而 TAC 在 `xiao-bytecode` 里，`xiao-ir` 不能
反向依赖它。实际做法是在 `xiao-ir/src/validate.rs` 加**并列入口**
`reconcile_release_plans(program, observed)`，`observed` 是 `xiao-ir` 自己定义的纯数据
`ObservedRelease`，既不做依赖倒置，也不修改已冻结的 IR 模型；新增稳定编号 `X08-IR-003`。

比较必须**按 `order` 排序后进行**，不能比 `Vec` 下标：IR 里释放计划的排序键是 `exit`
**字符串**，与上游枚举序不同。

### 09R3：跨平台基准与冻结

1. 同一源码、同一 IR、同一语义输入，分别运行三种机型；
2. 按 R1-AD 的协议固定工具链、优化级别、输入规模、预热与重复次数和统计方式；
3. 以栈式原型作为同机基线，应用 R1-AC 的相对门槛；
4. 输出语义差分报告、性能报告、内存报告和编码体积报告；
5. 主候选未通过门槛时**必须依据报告选择栈式或混合式**。

09R3 结束后冻结：最终字节码机型、寄存器类别与分配策略、函数调用 ABI、异常/清理转移 ABI、
指令编码和版本字段、源码映射格式、性能阈值与基准协议。

## 09-B0 接入边界

09R 完成后才进入 09-B0，并拆为：

1. **B0-A：生产字节码模型与验证器**——把 09R 冻结结果从研究模块迁入生产 `xiao-bytecode`；
   建立指令边界、寄存器类别、跳转目标、调用帧和释放计划验证。

   错误、退出码、堆栈和事件结果；`xiao run` 与 TypeScript CLI 接线继续留到 11/X0。
